Obsidian / Confirmación de diseño de copia de seguridad y recuperación

Determine el rango a permanecer y el estado que se puede devolver

Obsidian diseño de copia de seguridad
Git, recuperación de archivos, rol de almacenamiento separado

Antes de perder una nota, decida qué texto y configuración dejar y desde dónde volver. Con un pequeño ejemplo creado por el autor, confirmamos la restauración de una versión anterior de Git, el cuerpo antiguo de File Recovery y una copia fuera de la bóveda. Divida el papel desempeñado por los tres métodos y el alcance que no se confirma en este ejercicio.

Escrito: SimpleMemo Developer · Operación real: 2026 año 9 mes 30 UTC (hora de Japón 10 mes 1) · Linux / Obsidian 1.13.7

Diseñar "volver a la versión anterior" y "otra ubicación de almacenamiento" por separado

Al planificar una copia de seguridad, decide qué conservar, a qué momento volver, dónde guardarlo y cómo comprobar el contenido restaurado. Tener sincronización configurada o ver los archivos ahora no demuestra que se conserven las versiones anteriores y el alcance que necesitas.

  1. Versión anterior de GitExtrieve un texto incluido en la confirmación en un archivo de alias
  2. Recuperación de archivosSeleccione el texto antiguo del historial local de la aplicación, restaúrelo y vuelva a mostrarlo
  3. Copiar fuera de la bóvedaAbre los tres Markdown seleccionados en una ubicación nueva y diferente

Los tres son ejemplos locales que en realidad han sido confirmados. Las copias fuera de la bóveda no son el resultado del uso de dispositivos físicos independientes o nubes en el mismo sistema de archivos. La existencia de tres métodos no se trata como evidencia de que se almacenaron en tres medios independientes.

Primero, decide el rango a dejar y dónde guardar

Haga una lista de lo que necesita en su repositorio y conéctela a los elementos que se comprobarán en el destino de restauración. El siguiente es un elemento para el plan, no una tabla que dice que este ejercicio ha guardado y restaurado todo.

"Hasta qué punto se debe dejar el cambio" y "el tiempo requerido para regresar" también se deciden por su propio propósito. Esta vez, no hemos medido el objetivo de RPO/RTO y el tiempo de recuperación. Determinar la frecuencia de copia y poder dejar versiones pasadas durante un cierto período de tiempo son elementos de confirmación separados.

1. Git: Lleva la versión anterior del texto comprometido a un alias

Un ejemplo de Git es para una práctica Git履歴メモ.md. Después de confirmar el primer texto y cambiar y guardar los elementos de confirmación en el editor Obsidian real, hice una segunda confirmación. Además de eso, Saqué el blob real de la confirmación anterior al nuevo Git復元メモ.md y lo abrí con la aplicación real. El archivo original después de que se mantenga el cambio.

Los dos commits tienen una relación padre-hijo, y el blob del texto también es diferente. Solo este Markdown ha sido rastreado en Git, y la nueva nota que se restaurará, la nota para la recuperación de archivos y la configuración no se ha rastreado. No es el resultado que toda la bóveda está en la historia.

Este es el texto completo del Markdown real devuelto. El blob anterior de la demostración, el archivo restaurado y la distribución original eran el mismo byte 98 UTF-8.

# Git履歴メモ

著者作成の練習です。

- 確認項目: 保存前の本文を読む。

Para comprobar en cuestión, primero lea el estado y el historial del objetivo, y seleccione la confirmación y la ruta que desea devolver. El siguiente es un ejemplo de la forma de lectura. Reemplace <commit> con el valor de su historial.

git status --short -- "Git履歴メモ.md"
git log --oneline -- "Git履歴メモ.md"
git show "<commit>:Git履歴メモ.md"

Seleccione el nuevo nombre no utilizado que se pueda distinguir de la nota original, lea el texto antiguo y decida qué adoptar. La operación Git de esta demostración es un shell local, y el complemento Obsidian Git, el control remoto, el push/pull, la confirmación automática y la reflexión a otro terminal no se han probado. No se trata como poder devolver archivos que no estaban incluidos en la confirmación.

2. Recuperación de archivos: Seleccione y devuelva el texto antiguo del historial local

La pantalla de configuración de la demostración complementaria es una interfaz de usuario en inglés. De hecho, activé el interruptor Settings → Core plugins → File recovery y abrí la configuración de recuperación de archivos. El valor inicial de Snapshot interval 5 minutos se ha cambiado a 0.05 minutos para verificación, y luego 0.5 minutos. History length mostró 7 días, pero no se ha verificado la retención de siete días.

El ajuste de 0.5 minutos es el intervalo mínimo entre entradas del historial; no significa que se guarde necesariamente una instantánea cada 30 segundos. El núcleo de esta versión tiene un temporizador de 60 segundos para reintentar los guardados pendientes. Confirmamos que las versiones A y B, guardadas en el editor real, pasaron al estado pendiente y se añadieron al historial mediante ese temporizador normal. El evaluador no escribió en la base de datos del historial ni llamó a una API de creación de historial.

  1. Guarda A en el editor real. Introduzca A incluyendo "Compruebe el texto que queda antes". Revisé los archivos guardados y confirmé que estaban en espera y que aún no había historial de A.
  2. Confirmar la conservación natural. Aproximadamente 60 segundos después, A entró en el historial. A continuación, lo edité a B y lo guardé, y B se incluyó en otra preservación natural después de aproximadamente 58 segundos. Dos observaciones no garantizan un tiempo universal requerido.
  3. Seleccione el texto antiguo en la pantalla. Presione View para buscar notas de recuperación, seleccione la última B y la A anterior respectivamente, y lea el texto.
  4. Restaurar y mostrar de nuevo. Presioné el Restore real mientras seleccionaba A. El archivo guardado coincidía con A, y después de pasar a otra nota, volví a abrir la nota de recuperación en el explorador de archivos real, y el texto era el mismo.

UI muestra "44 B" como A y "47 B" como B. El UTF-8 real utilizado para hacer coincidir el archivo de distribución es A es 110 bytes y B es 119 bytes. El valor de visualización de la interfaz de usuario no se utiliza como el número de bytes de UTF-8. Después de la restauración, la A restaurada también se agregó a la nueva línea de historial. Esta línea adicional es el resultado de la operación de restauración y la distingue de la evidencia de preservación natural de los anteriores A y B.

3. Copiar fuera de la bóveda: Comprueba el texto, la jerarquía y el enlace en otro lugar

En la demostración de copia original, tres Markdown creados por el autor se almacenaron fuera de la bóveda y se devolvieron a un nuevo destino de restauración diferente del original. Es una configuración que enlaza de 索引.md a ノート/観察メモ.md y ノート/確認メモ.md. El nombre del archivo y la ruta relativa se han conservado.

La restauración no se sobrescribió al estado original y se hizo en otra ubicación nueva. El objetivo es solo tres Markdown, y la configuración y los archivos adjuntos no se han copiado. La copia está en el mismo sistema de archivos ejecutable fuera de la bóveda. La confirmación de que se puede restaurar desde dispositivos de almacenamiento independientes, nubes, fallas y desastres es un elemento separado que queda en el plan de respaldo.

El orden de practicar la restauración en su propio trastero

  1. Exporta el objeto guardado. Decida si incluir solo Markdown o configuraciones, archivos adjuntos e historial necesario, y reserve el nombre y la ruta relativa.
  2. Compruebe el destino de almacenamiento y la versión anterior. Compruebe dónde dejarlo, si es independiente del dispositivo original y si la versión en el punto que desea devolver permanece.
  3. Guarda el original y pruébalo en otro lugar. Lea si el texto, la configuración y los archivos adjuntos seleccionados son necesarios para volver al nuevo destino de restauración.
  4. Comprueba el enlace y vuelve a mostrarlo. Abra la referencia del cuerpo, vuelva a abrir el archivo y compare el contenido guardado.
  5. Deja los resultados y los elementos no confirmados. Registre la versión utilizada, el rango de almacenamiento, el destino de almacenamiento, la hora de regreso, el tiempo requerido y determine el horario que se revisará regularmente.

Este es un procedimiento para que el lector planifique por sí mismo. Este ejercicio no verifica las bóvedas de los lectores, las copias de seguridad regulares, los servicios de sincronización y los medios independientes. La entrada para comprobar la combinación con la sincronización es la guía del método de sincronización de Obsidian.

Preguntas frecuentes

Si la sincronización funciona, ¿puedo omitir la comprobación de la copia de seguridad?
No sé si puedo volver al texto anterior o si hay un destino de almacenamiento independiente basado en el hecho de que configuré la sincronización. Compruebe el historial del método utilizado, el rango que se puede devolver y la ubicación de almacenamiento. Este ejercicio no utiliza la sincronización y no ha intentado restaurar Obsidian Sync o iCloud.
¿Realmente usaste Git y File Recovery para confirmarlo?
En Git, hice dos confirmaciones para una práctica Markdown, devolví el blob anterior a un nuevo archivo de alias y lo leí con el Obsidian real. En Recuperación de archivos, A y B guardados en el editor real ingresan el historial con un temporizador natural, seleccionan la antigua A en la pantalla para restaurar y confirman el guardado y la revisualización. No se ha verificado la copia de seguridad automática de Git, el control remoto y la retención a largo plazo.
¿Ha revisado toda la sala de almacenamiento y la recuperación en caso de una avería?
El ejemplo de copia es solo tres Markdown, y no incluye configuraciones ni archivos adjuntos. El destino de almacenamiento también está en el mismo sistema de archivos ejecutable. No hemos intentado restaurar dispositivos físicos independientes, nubes, fallas, desastres, período de retención de historial y almacenamiento completo. Compruebe los resultados de restauración local de Git y File Recovery y la recuperación de toda la bóveda por separado.
¿Qué nombre y ubicación desea guardar la distribución Markdown?
Coloque 索引.md para el ejemplo de copia, y coloque 観察メモ.md y 確認メモ.md en carpeta ノート. El navegador no crea carpetas automáticamente. El archivo de comparación modificado, los ejemplos de Git y File Recovery, se guardan con alias distinguibles y no se sobrescriben al conjunto de restauración. Si desea utilizar un nombre de distribución en inglés, compruebe también el enlace en el texto.

Método de verificación y rango de resultados

  • Aplicación real:Versión Linux Obsidian 1.13.7. Revise la aplicación/instalador en la pantalla General de la configuración y use las notas japonesas creadas por el autor. No uso complementos de la comunidad.
  • Ejemplo de copia:Preparar, copiar, cambiar y eliminar el texto para practicar, y copiar a otro destino de restauración del Markdown seleccionado son operaciones de shell. Revisé el texto, los enlaces y la revisualización con la interfaz gráfica de usuario real.
  • Git:La extracción de commit/past blob de semilla y Git local es shell. Guardé los cambios en el editor real y abrí el destino de restauración desde el explorador de archivos real para leerlo. Los plug-ins y el control remoto de Git no se utilizan.
  • Recuperación de archivos: La activación y la configuración son la interfaz de usuario real. A/B se introdujo y guardó en el editor real, y el historial del temporizador del núcleo natural se seleccionó en la pantalla real para restaurar, guardar y volver a mostrar.
  • Auxiliar y original: La configuración inicial del perfil se establece directamente, y el estado de la aplicación, el estado pendiente y el contenido histórico son leídos por API. No hay creación de historial API o escritura de DB por parte del verificador. El PNG publicado es una pantalla real sin procesar, y Markdown tiene los mismos bytes que el original.
  • Rango remanente: Todo el almacenamiento, configuraciones y archivos adjuntos, dispositivos independientes, nube, retención a largo plazo, fallas, sincronización, múltiples terminales, iOS/Android/macOS, SimpleMemo entrega, velocidad, productividad y efectos de entrada no se han verificado.
