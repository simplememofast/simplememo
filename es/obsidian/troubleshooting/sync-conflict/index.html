Obsidian / Ejemplo de recuperación de conflictos de Git

Conserva los originales y elige el contenido

Resuelve los conflictos de Git en Obsidian
Conserva, compara y guarda los originales

Si aparecen marcadores de conflicto en una nota, conserva por separado las dos versiones originales y decide qué contenido mantener. En este pequeño ejercicio elegimos dos elementos, los guardamos en Obsidian y comprobamos que la fusión local de Git terminara y que la nota volviera a mostrarse correctamente.

Escrito: SimpleMemo Developer · Confirmación de operación real: 2026 año 9 mes 30 día · Linux / Obsidian 1.13.7

El orden de confirmación es el texto original, el contenido seleccionado y los resultados de guardado

El objetivo esta vez es cuando se incluye un marcador de la competencia en el mismo texto Markdown en la fusión de Git. Edité una de las notas creadas por el autor con dos ramas del Git local, y confirmé el fallo de fusión real, la comparación del texto original y la corrección manual. No es el resultado de la sincronización con múltiples terminales.

  1. Deje manualmente ambos textos originalesPrepare una copia que pueda distinguir cuál es el contenido
  2. Compare la diferenciaCompruebe la línea inusual y las partes comunes
  3. Decida el contenido a adoptarEste ejemplo coloca dos elementos compatibles en líneas separadas
  4. Editar y guardarCompruebe la finalización de la fusión en el texto y el lado de Git
  5. Volver a mostrar y confirmarEncolar el contenido seleccionado y guardar Markdown

Este orden es un diagrama que organiza este ejercicio. No es un diagrama que muestre la garantía de restauración automática y prevención de pérdidas, y el procedimiento de operación para cada servicio de sincronización.

Primero, compruebe la forma de su competencia

En este ejemplo, Git merge se detuvo con el código de salida 1 y 作業メモ.md quedó marcado como UU. El índice de Git conservó la base común y ambas versiones editadas. En el texto aparecieron los marcadores <<<<<<< HEAD, ======= y >>>>>>> draft-b.

Si hay una pantalla de archivos de conflicto de alias o historial en su entorno, verifique de acuerdo con el método de sincronización. La entrada para comprobar el método es la guía de métodos de sincronización de Obsidian. Los resultados de Git en este artículo no se pueden leer en el comportamiento de Obsidian Sync o iCloud.

El texto guardado en este estado competitivo es el siguiente. Se publica el texto completo del archivo real, incluido el marcador.

# 作業メモ

ローカルの競合を確かめるために著者が作った練習用ノートです。

## 次の確認
<<<<<<< HEAD
- 確認する項目: 見出しの順番を確認する。
=======
- 確認する項目: 内部リンクの保存先を確認する。
>>>>>>> draft-b

1. Deje los dos textos originales a mano por separado

Antes de comenzar a editar, guarde cada versión a mano por separado con un nombre que muestre la versión original. Si solo tiene uno de ellos a mano, no trate al otro como si pudiera guardarlo, y compruebe el estado de Git y el historial del método que está utilizando. Esta vez no he intentado recuperar el historial de cada servicio.

Si desea comprobar la preparación para volver al texto anterior antes de solucionar el conflicto, consulte también Git, recuperación de archivos y recuperación de copias fuera de la tienda.

En este ejercicio, el autor conservó manualmente copias de las versiones A y B antes de la fusión. Para compararlas, también colocó y abrió 原文の控え/案A.md y 原文の控え/案B.md dentro de la bóveda. No son copias en conflicto generadas automáticamente por una herramienta de sincronización.

En lugar de juzgar solo por el tiempo de actualización, lea el texto y verifique la información necesaria. Dado que los dos son compatibles como elementos de confirmación separados esta vez, el autor decidió adoptar ambas líneas en el orden de A y B. Si la oración real es contradictoria o duplicada, debe elegir según el contenido.

2. Edita el contenido acordado en Obsidian y comprueba que se haya guardado

Abrimos 作業メモ.md en el editor real de Obsidian e introdujimos el texto elegido. En este ejemplo mantuvimos la explicación común, colocamos los dos elementos en líneas separadas y eliminamos los marcadores de conflicto. Esperamos al guardado automático y verificamos que el archivo real contuviera todo el texto siguiente.

# 作業メモ

ローカルの競合を確かめるために著者が作った練習用ノートです。

## 次の確認
- 確認する項目: 見出しの順番を確認する。
- 確認する項目: 内部リンクの保存先を確認する。

Además de la desaparición del marcador, releeré el contenido seleccionado, el orden de las líneas y las partes comunes que decidí dejar en mi cuaderno. La decisión de resumir el texto y la operación para completar la fusión en el lado de Git se confirmará por separado.

3. Compruebe el estado no resuelto de Git y complete la fusión

En este ejercicio, incluso después de guardar el texto con Obsidian, el estado de Git era UU. Después de eso, hice explícitamente git add con solo la nota de destino e hice una confirmación de fusión localmente. Las dos confirmaciones originales permanecen como padres, el git ls-files -u está vacío y el estado de Git está limpio.

El siguiente es un ejemplo del comando para comprobar el archivo de destino en el Git local. Compruebe el nombre real de la nota y el repositorio antes de usarlo. Antes de git add, compruebe el texto a adoptar y el otro estado de trabajo.

git status --short -- "作業メモ.md"
git ls-files -u -- "作業メモ.md"
# 採用する本文を確認した後、対象ノートをstageする
git add -- "作業メモ.md"
git commit
# merge完了後の未解決indexと状態を確認する
git ls-files -u
git status --short

La operación Git se realizó con un comando local. El plug-in Obsidian Git no se utiliza, y el control remoto, el empuje/pull y la reflexión en otros terminales no han sido confirmados. El hecho de que la condición esté limpia no prueba la durabilidad de la copia de seguridad o la entrega a todas las terminales.

4. Vuelve a abrir el cuaderno y lee el contenido seleccionado

Tras crear el commit de merge, volvimos a abrir 作業メモ.md desde el explorador real de archivos. La vista de lectura mostró ambos elementos sin marcadores de conflicto. El archivo Markdown conservó el mismo SHA256 antes y después de abrirlo, y se mantuvieron las copias originales A y B y el contenido de cada commit.

Este resultado fue confirmado con la nota de este autor y una restauración local. No es un resultado que muestre que la información no se perderá en todos los conflictos y en todos los métodos de sincronización.

Preguntas frecuentes

¿Los marcadores de conflicto en el texto y la copia conflictiva son los mismos?
En este ejemplo comprobamos los marcadores de conflicto que Git insertó en el texto Markdown de la nota de trabajo. El autor creó manualmente las copias de los originales. Este ejemplo de recuperación no comprueba si un método de sincronización genera automáticamente otro archivo. Consulta las instrucciones del método que utilizas.
¿Puedo resolverlo si dejo ambas oraciones?
Los dos elementos de este ejemplo son compatibles, por lo que el autor decidió conservarlos en líneas separadas. Si el contenido es contradictorio o repite la misma explicación, revisa el significado y la información necesaria antes de elegir. El procedimiento no consiste en añadir siempre ambas versiones.
Si borro y guardo el marcador de conflicto, ¿se completará la fusión de Git?
En este ejercicio, el estado de Git era UU incluso después de guardarlo con Obsidian. Después de comprobar el contenido, agregar la nota de destino y crear una confirmación de fusión, confirmé que el índice no resuelto estaba vacío y que el estado de Git estaba limpio. Por favor, separe la edición del texto y la finalización del lado de Git.
¿Se ha verificado este procedimiento en Obsidian Sync y iCloud?
Se verificaron la versión Linux de Obsidian 1.13.7 y un repositorio Git local fuera de línea. Obsidian Sync, iCloud, otros servicios de sincronización, dos terminales, iPhone, los enlaces SimpleMemo no se han probado. Por favor, compruebe el historial y el mecanismo de conflicto de acuerdo con el método real.
