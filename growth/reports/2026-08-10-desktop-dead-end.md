## 2. それでも塞ぐ理由

効果量ではなく、**判断に統計的検出力が要らない**ことが理由である。

これまでの施策（スニペット、CTA配置）はすべて「変えたら良くなるか？」という問いで、
1,600セッション/28日では倍近く動かないと判定できなかった。

今回は違う。**この21人は現に壁に当たっている。** 検証を待つ性質の問題ではない。

実装コストも低い。`/ai-tags/` に既に正しいパターンがあった:

```css
.ai-release__qr{display:none}
@media (min-width:900px){ .ai-release__qr{display:block} }
```

**パターンは存在していて、横展開されていなかっただけである。**

## 5. 検証（当初「未検証」としたが、機械的に確認できた）

当初この節は「デコーダが無いので、Readyにする前に1枚スマホで読み取ってほしい」と書いていた。
その後、**出荷したSVGからモジュール行列を復元し、独立したデコーダ（jsQR）で
読み直す検証を実装した**（`scripts/generate-qr-codes.mjs --check`）。

エンコードに渡した文字列を突き合わせるだけでは「入力が正しかったこと」しか言えない。
実際に出荷されたファイルを読み直せば、エンコーダの不具合も書き出しの失敗も引っかかる。

```
15 verified, 0 failed.
```

### この検証が欠陥を1つ見つけた

```
ok  quiet=1   ← 初版
ok  quiet=4   ← 修正後
```

初版は静音領域を**1モジュール**にしていた。同じ枠内でコードを大きく見せる意図だったが、
**QR規格は4モジュールを要求する。** 読み取り成功率は下がるが、エラーとしては出ないため
「なんとなく読めないことがある」という形で表面化する種類の欠陥である。

CSSの `padding:6px` があるので実際の表示では白が確保されるが、**SVGは
そのpaddingを持たずに配布される**（別の資料に貼る、印刷するなど）。規格どおり4に直した。

なお既存の `/ai-tags/` のQRは最初から4モジュールだった。**先例の方が正しく、
私が横展開する際に劣化させていた。**

### ついでに分かったこと

`/ai-tags/` のQRだけ、キャンペーントークンの流儀が違う:

```
/ai-tags/      ct=ai-tags-qr-ja      ← <slug>-qr-<lang>
今回の9ページ    ct=vs-logseq-jp__qr   ← <slug>-<lang>__<placement>（サイトの他CTAと同じ）
```

App Store Connect 側で並べたときに揃わない。**今回は触っていない**（現に動いている
トークンを変えると、それまでの集計と繋がらなくなるため）。統一するなら、
次にAI-tagsのQRを作り直すタイミングで行うのがよい。

### 再生成できるようにした

QRは手作りのアセットのままにせず、`scripts/generate-qr-codes.mjs` に集約した。
**この repo には package.json が無い**ため CI には組み込んでいない。
トークンを変えたときやページを足したときに手で回す:

```sh
npm i --no-save qrcode jsqr
node scripts/generate-qr-codes.mjs          # 生成
node scripts/generate-qr-codes.mjs --check  # デコードして検証
```
