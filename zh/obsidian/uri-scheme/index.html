obsidian:// URI方案完整指南 — 全部动作和陷阱

obsidian://是从其他应用程序或启动器打开、制作、搜索Obsidian笔记的URI。 首先选择适合用途的动作，每个值进行URI编码。 对现有正文的补充，可以从这次确认保存的new+append=true的例子开始。

输入正文复制URI时，也请参考将语法和固定Linux观测分开的免费URI生成器。

这里整理了官方正文的6动作一览表中添加了Hook用的别节7节・38的动作参数项目，对应传递给Linux Obsidian1.13.7的58个记录。 也刊登了无法获得结果的输入，以便将规格的描述和实际的保存地址分开阅读。

确认的范围：作者用的本地Vault，官方Linux应用程序1.13.7，英语UI，隔离的Xorg画面。 向执行文件传递URI，确认了应用程序收到后的操作。 来自浏览器链接的OS关联、物理iPhone、iOS快捷键、SimpleMemo、同步未验证。 58件并不意味着全价、全组合、全终端的保证。

想要制作URL的话，请到现有的URI生成器。 iPhone无法启动、快捷键停止的症状请前往快捷键处理指南。 这个页面是用来查询标准URI的含义和输入结果的参考。

obsidian://action?param1=value&param2=value

正文的#和标题的#都编码为值

官方正文说明空白为%20，斜杠为%2F。 在混合了日语、换行、# & ? + % / =的作者正文按值转换的I:N1中，保存Markdown与输入一致。 URL整体转换一次的话，分隔也会改变，所以vault、file、content的值单独处理。

const vault = encodeURIComponent('練習Vault');
const file = encodeURIComponent('ノート/日本語 メモ');
const content = encodeURIComponent('本文 # & ? + % / =\n二行目');
const uri = `obsidian://new?vault=${vault}&file=${file}&content=${content}`;

上面是说明组装方法的代码。 不包括保存在终端上的笔记中的执行。 将练习Vault和保存地址替换为自己的名字。

在留下生#的输入中后半部分掉了

I:W1只留下了content途中的#。 保存的只有开头的句子，后半部分的正文没有在文件中。 这件事不是“Obsidian擅自删除正文”的证据，而是URI的分隔和数值混合的输入结果。

将新建、补充、覆盖分开

new的name是新的笔记名，将保存地址委托给Obsidian的“Default location for new notes”。 file是包含Vault路线的保存目的地的值。 官方记载file优先于name，I:N2也保存到file指定目的地。 S:N01中只有name，保存在预先设置的默认文件夹中。

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Hello%20World

保留现有正文添加时，会传递append=true。 I:N3保留了现有的正文并追加了。 overwrite=true是替换现有正文的指定，I:N5有另外的原文/保存后的记录。 官方记载了“只有在没有设置append的情况下才overwrite”，在S:N03的两个指定中都追加了。 不需要在日常的正文添加中混合覆盖指定。

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Another%20line&append=true

silent=true的I:N4，在制作保存文件的同时保持了显示中的笔记。 clipboard=true的S:C01/C02/C03将专用画面的作者正文保存在new/daily/unique中。 同时交出content的S:C04保存了clipboard正文。 这组的优先结果，不能扩展到所有终端的所有形式。

S:M03将记录的new、append、content交给了现有的作者笔记。 在实际的保存文件中，标题是添加方的值，保留现有的kept，tags同时包含，正文被添加到末尾。 接下来是121bytes的保存Markdown全文。 我没有尝试过这组以外的类型、重复键、复杂的YAML。

绝对path的新建不计入成功案例

官方new节说明了globally absolute path。 S:N02无法通过输入冲突的vault/name/file来创建文件。 别计划T:P1将path和content交给了已注册作者Vault内的未制作文件。 即便如此，6秒后没有目标文件，画面还是索引。 这是一个Linux应用程序接收路径的记录，不是断定原因或所有环境的故障的结果。

## 対象の節

ブロック移動を確認する著者用本文です。 ^target-01

T:B1的长原Markdown全文下载

缩写obsidian://vault/Vault名/ノート名和obsidian:///絶対パス是open的省略记法。 S:H01/H02分别显示了作者笔记。 值的日语、空白、分隔符的处理和普通的参数一样进行确认。

每日笔记、固有名笔记也确认插件和保存地址

官方记载了daily需要Daily notes，unique需要Unique note creator核心插件。 首次I:D1/U1无法创建文件，原封不动地留下了失败记录。 在之后的另一个计划中，准备了真实存在的作者用保存文件夹，观测了从索引中创建日次文件的I:D2，创建固有名文件的I:U2。 并不是只断定这个前提变更是失败的原因。

obsidian://daily?vault=Practice&content=Daily%20entry
obsidian://unique?vault=Practice&content=Unique%20entry

固定的官方正文说明了daily接收与new相同的参数。 但是S:D01/D02/D03不能指定name、file、path，被添加到Daily notes设置的日次/2026-09-30.md中。 指定名称的新笔记是new，日期笔记的输入是daily，用实际文件确认最终保存地址，这是从这个观测开始可以引导的范围。

S:D04在silent保持索引显示的同时保存在日次上。 S:D05同时指定了append和overwrite并保留了原文，但是由于没有标志的daily也追加了，所以append单独的贡献和overwrite的动作尚未确认。

选择显示目的地paneType

针对 open/new/daily/unique，分别记录了 paneType=tab、split 和 window 的 12 次输入（S:P01〜P12）。官方说明 window 仅适用于桌面端。我们读取了实际主标签页、标签组和独立弹出窗口，并保留了截图。由于已关闭窗口的元数据仍然存在，因此并未仅凭全局 leaf 总数判断成功与否。

x-success・x-error在退货地址确认接收

官方解释说，退回x-success包括name（无扩展名）、url（obsidian URI）、桌面的file（file URI）。 保存成功和呼叫方收到退货是分开的。 S:X01/X02/X03观测到笔记的保存，但作者拥有的localhost HTTP接收地址没有接收。 准备好的BROWSER适配器也没有运行，连OS、调用源交接都无法确认。

Hook用hook-get-address有x-success的话会返回那里，如果省略的话，官方记载了现在笔记本的Markdown链接复制到clipboard。 在S:K01中，作者clipboard的番兵值没有变化，S:X04也没有返回。 Hook本体没有执行。 S:X05的不存在Vault显示了实际的“Vault not found”对话框，但没有接收x-error。 错误显示不会用退货成功或全部callback的产品故障代替。

38项目的输入和实际结果对应

38/38是“有包含各动作参数的输入记录”这个数字。 不是“规格的效果全部成功”这个数字。 open的附加标志，new的绝对path，daily的指定目的地，两个标志的贡献，Hook/callback仍然存在不足。 I是第一个19件，S是追加37件，T是有效块・无冲突path的2件。 从各个ID进入原来的JSON。

常见问题

obsidian://和普通的Web URL有什么不同？

obsidian://是Obsidian接收的独自URI。 不是获取网页的URL。 终端端的关联和Obsidian之后的笔记操作要分开确认。 这篇报道的实际测量是在收到Linux应用程序的URI之后。

日语、空白、#怎么写？

按值进行URI编码。 空白是%20，#是%23，/是%2F。 标题、块指定的#也在file值中编码。 在本文留下原始#的作者例子中，#之后没有保存。

在现有笔记本上追加记的话使用open吗？

正文补充的确认例子是给new传递file、content、append=true。 open节也有append/prepend的记载，但content没有列举在同一节中，在这个验证的探索性输入中，正文没有改变。

给daily交file或name的话，可以更改保存地址吗？

固定的官方正文记载了daily接收与new相同的参数。 另一方面，在这次的Linux输入中，没有创建name、file、path的指定目的地，而是添加到了Daily notes设置的日期笔记中。 请用实际设置和文件确认保存地址。

指定x-success的话，已经确认退货了吗？

不。 new、daily、unique也有观测保存的输入，但拥有的HTTP寄回地址没有接收。 接收到应用程序的URI和CLI结束0不能成为返回给调用方的证据。 Hook、OS的交接、实际的调用源应用程序尚未确认。

iPhone也是同样的结果吗？

本文没有执行物理iPhone、iOS快捷键、SimpleMemo。 这是Linux Obsidian1.13.7的作者用Vault的结果。 iPhone固有的症状请参考现有的快捷键处理指南，在终端上确认。
