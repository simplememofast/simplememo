Git・File Recovery・单独保存的作用

在丢失笔记之前，决定要留下哪些正文和设置，从哪个位置可以返回。 通过作者制作的小例子，确认了Git的旧版本、File Recovery的旧正文、保管库外的副本的恢复。 将三种方法所发挥的作用和在这个练习中没有确认的范围分开。

将“恢复到以前的版本”和“其他保存场所”分开设计

在备份计划中，决定留下什么，恢复到哪个时间点，保存目的地在哪里，如何确认实际恢复的内容。 仅仅因为有同步设置，或者现在能看到文件，就不知道必要的旧版和保存范围是否齐全。

  1. Git的过去版commit中包含的一个正文，提取到别名文件
  2. File Recovery从应用程序的本地历史中选择旧的正文，恢复并重新显示
  3. 保管库外的复印件选择的三个Markdown，在新的其他地方打开

三个都是实际确认的局部例子。 保管库外的副本也不是在同一文件系统中使用独立物理设备或云的结果。 不把有三种方法作为保存在三个独立的媒介中的证据来处理。

首先决定留下的范围和保存地址

将自己的保管库中需要的东西列为列表，并连接到在复原处确认的项目。 以下是用于计划的项目，不是这个练习保存、恢复所有内容的表格。

决定的项目确认的内容这次的实演
笔记正文需要的Markdown的名字、相对路径、哪个时间点的正文三个副本恢复，一个Git履历，另一个File Recovery笔记
附件和参考图像、PDF等的保存地点和可以从正文中参考附件未验证。 内部链接只有复制例中的三个Markdown
设置・插件.obsidian的设置，包含必要的插件及其数据的范围设置和插件数据的备份、恢复尚未验证
保存地点与原来的保存装置的独立性、可以读取的权限、保管方法保管库外也是同样的执行文件系统。 独立媒体、云未验证
频率和保持想要恢复的时间点，保留的旧版，删除旧版的方针单发副本和两个Git commit，File Recovery的两次自然保存。 长期保留和定期运用尚未验证
恢复练习其他复原目的地、正文、设置、附加、链接的核对步骤和日程确认选择的正文、相对路径、真实链接、重新显示。 恢复所需时间和故障时的恢复未测量

还应按自己的用途确定“需要保留到什么时间点的更改”以及“恢复所需的时间”。本次没有测量是否达到 RPO/RTO 或恢复时间目标。确定制作副本的频率，与确认能否将旧版本保留一定时间，是两项独立的检查。

1。 Git：将commit的正文之前的版本，取出别名

Git的例子，以一个练习用Git履歴メモ.md为对象。 第一个正文commit，在实际的Obsidian编辑器中更改并保存确认项目后，制作了第二个commit。 在此基础上，将上一个commit的实blob取出到新的Git復元メモ.md，用实软件打开。 保留变更后的原始文件。

两个commit有亲子关系，本文的blob也不同。 在Git上追踪的只有这个Markdown，恢复目的地的新笔记，File Recovery用笔记，设置未被追踪。 并不是整个保管库都进入了履历的结果。

返回的实Markdown的全文。 演示之前的blob、恢复文件、分发原件是相同的98字节的UTF-8。

# Git履歴メモ

著者作成の練習です。

- 確認項目: 保存前の本文を読む。

在手边确认时，首先读取目标的状态和履历，选择想要返回的commit和路径。 接下来是显示读取形式的例子。 <commit>替换为自己的履历值。

git status --short -- "Git履歴メモ.md"
git log --oneline -- "Git履歴メモ.md"
git show "<commit>:Git履歴メモ.md"

取出的目的地是选择可以与原来的笔记本区分的未使用的新名字，阅读旧的正文后决定采用的内容。 这个演示的Git操作是本地shell，没有尝试Obsidian Git插件、remote、push/pull、自动commit、其他终端的反映。 不处理没有包含在commit中的文件可以恢复。

2。 File Recovery：选择本地历史的旧正文并恢复

补充演示的设定画面是英文UI。 实际上激活了Settings → Core plugins → File recovery的开关，打开了File recovery的设置。 Snapshot interval的初始值5分，为了验证暂时改为0.05分，之后改为0.5分。 History length显示为7天，但是没有验证七天的保留。

0.5分钟设置的是历史记录之间的最短间隔，不能理解为一定每30秒保存一次。该版本的核心有一个60秒的待处理保存重试计时器。本次确认了：在实际编辑器中保存的A、B进入待处理状态，然后由正常运行的计时器加入历史记录。测试者没有写入历史数据库，也没有调用创建历史记录的API。

  1. A在实际编辑器中保存。 输入包含“先确认留下的正文”的A。 核对了保存文件，确认了保留状态和还没有A的履历。
  2. 确认自然保存。 大约60秒后A进入了履历。 接下来对B进行实际编辑并保存，大约58秒后的另一个自然保存进入了B。 两次观测不能保证普遍的所需时间。
  3. 在画面上选择旧的正文。 按View搜索恢复备忘录，分别选择最新的B和以前的A阅读了正文。
  4. 恢复后重新显示。 在选择A的状态下按下了实际的Restore。 保存文件与A一致，移动到其他笔记后，在实际文件浏览器中重新打开恢复备忘录也是同样的正文。

UI显示A为“44 B”，B为“47 B”。 用于核对分发文件的实际UTF-8是A是110字节，B是119字节。 UI的显示值没有作为UTF-8的byte数使用。 Restore之后，恢复的A也被添加到了新的履历行中。 这个附加行是恢复操作的结果，与前面A・B的自然保存证据有区别。

复原的A的实Markdown全文。 显示的旧A和最终保存的文件是相同的110字节。

# 回復メモ

著者作成の練習です。

- 保存する項目: 先に残した本文を確認する。

这个结果是从这次本地profile中存在的履历中返回的正文。 File Recovery的履历不是可以保存到独立的备份设备的结果。 没有尝试过profile的转移、应用程序的重新安装、历史DB损坏、长期保留、删除的文件的恢复。

3。 保管库外的复印件：在其他地方确认正文、层次、链接

在原始副本演示中，将作者制作的三个Markdown保存在保管库外，回到与原始不同的新复原处。 从索引.md到ノート/観察メモ.md和ノート/確認メモ.md的连接构成。 保留了文件名和相对路径。

索引.md
ノート/
  観察メモ.md
  確認メモ.md

复制完成后，验证者仅在自己的练习用笔记库中修改了一份正文并删除了一条笔记，副本中的三份原始正文均予以保留。恢复在另一个新位置进行，没有覆盖原有状态。读者练习时也可以保留原始笔记，另行准备练习副本和恢复位置。

这是恢复的观察备忘录的全文。

# 観察メモ

コピー前の本文です。これは実際の利用者のデータではありません。

関連する確認は [[ノート/確認メモ|確認メモ]] に残します。

点击从索引到确认备忘录的真实链接，原来删除的对象显示在恢复目的地。“ 按“返回索引”可以返回索引。 之后，从真实文件浏览器重新打开索引，确认了三个保存Markdown没有变化。

索引的实Markdown也刊登全文。

# 索引

著者作成の復元練習です。

- [[ノート/観察メモ|観察メモを開く]]
- [[ノート/確認メモ|確認メモを開く]]

对象只有三个Markdown，没有复制设置和附件。 副本在保管库外也同样在执行文件系统中。 独立的保存装置、云、故障、灾害的确认可以恢复，是备份计划中单独留下的项目。

在自己的保管库里练习复原的顺序

  1. 列出要保存的项目。决定只保存 Markdown，还是同时包含设置、附件及所需的历史记录，并记下文件名和相对路径。
  2. 确认保存地址和旧版。 确认留在哪里，是否独立于原来的设备，是否保留想要恢复的时间点的版本。
  3. 保留元在别的地方尝试。 在新的恢复目的地，读取是否回到需要选择的正文、设置、附加的状态。
  4. 确认链接和重新显示。 从正文中打开参考地址，重新打开文件，核对保存的内容。
  5. 留下结果和未确认项目。 记录使用的版本、保存范围、保存地点、恢复的时间点、需要的时间，决定定期确认的日程。

这是读者自己计划的步骤。 读者的保管库、定期备份、同步服务、独立媒体不能通过这个练习进行验证。 调查与同期的组合的入口是Obsidian的同步方式指南。

保存原件，比较版本和正文

八个Markdown是各个演示的保存原件。 复制例子中的三个以原来的日语名字保存，观察备忘录、确认备忘录放在ノート 文件夹内。 浏览器不会自动创建那个文件夹。 比较用文件和Git・File Recovery的例子用别名保存，在不覆盖三个恢复集的地方进行比较。

演示・状态分发原件和保存名
复制恢复：索引.md索引.md
复制恢复：ノート/観察メモ.md観察メモ.md
复制恢复：ノート/確認メモ.md確認メモ.md
比较专用：变更后的观察备忘录変更後-観察メモ.md
Git：从过去的blob恢复到别名的正文Git復元メモ.md
Git：第二个commit变更后的正文Git変更後-履歴メモ.md
File Recovery：旧的A（与最终恢复一致）FileRecovery旧版-回復メモ.md
File Recovery：变更后BFileRecovery変更後-回復メモ.md

英文字母的分发URL是区分状态的别名。 复制例的正文内wikilink保留日语的原始相对路径。 如果原封不动地放英文名字的话，也会确认链接。 没有将分发文件导入到读者实际应用程序的操作和Git的履历本身的分发。

常见问题

如果同步在移动的话，不需要确认备份吗？
仅凭设置了同步的事实，不知道能不能回到以前的正文，或者有没有独立的保存处。 确认使用方式的履历、可恢复的范围、保存地点。 这个练习没有使用同步，也没有尝试恢复Obsidian Sync和iCloud。
Git和File Recovery，实际使用确认了吗？
在Git中，制作了一个练习用Markdown的两个commit，将以前的blob放回新的别名文件，实际用Obsidian读取。 在File Recovery中，用实际编辑器保存的A・B通过自然的计时器进入历史记录，在屏幕上选择旧的A进行Restore，确认保存和重新显示。 自动Git备份、remote、长期保留尚未验证。
您确认了整个保管库和故障时的恢复吗？
复制例子只有三个Markdown，不包括设置和附加。 保存地址也是同一个执行文件系统内。 没有尝试过独立的物理设备、云、故障和灾难、历史保留期、整个保管库的恢复。 将Git和File Recovery的局部恢复结果和保管库整体的恢复分开确认。
分发Markdown，以什么名字和位置保存？
复制例子放置索引.md，ノート 文件夹内放置観察メモ.md和確認メモ.md。 浏览器不会自动创建文件夹。 变更后的比较文件，Git和File Recovery的例子以可区分的别名保存，不覆盖恢复集。 使用英文的分发名称时，也请确认本文的链接。

验证方法和结果范围

  • 实际应用：Linux版Obsidian 1.13.7。 在设置的General画面中确认app/installer，使用作者制作的日语笔记。 没有使用社区插件。
  • 复制示例：选择的Markdown的准备、复制、练习用正文的更改、删除、复制到其他恢复目的地是shell操作。 用实际GUI确认了正文、链接、重新显示。
  • Git：seed和本地Git的commit/过去的blob的取出是shell。 变更在实际编辑器中保存，从实际文件浏览器中打开并读取了恢复地址。 Git插件和remote没有使用。
  • File Recovery：激活和设置是实UI。 A/B在实际编辑器中输入、保存，在实际画面中选择自然核心计时器的履历，确认了Restore、保存和重新显示。
  • 辅助和原件：profile初期构成直接设置，应用程序状态、保留状态、履历内容的核对读取API。 没有由验证者创建履历API和DB写入。 刊登的PNG是未经加工的实画面，Markdown是和原件一样的bytes。
  • 剩余范围：保管库整体、设置、附加、独立装置、云、长期保留、故障、同步、多个终端、iOS/Android/macOS、SimpleMemo配送、速度、生产力、流入效果未验证。

验证记录和原件的对应中，记录了复制演示和补充演示的原件、实际UI和辅助、初期操作selector的问题和结束确认的范围。 保持正常结束的试验，没有追溯到没有结束代码的初期试验。
