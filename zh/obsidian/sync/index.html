Obsidian 同步方法的比较

Obsidian在多个终端上同步4的方法

保管库没有特殊格式，只是Markdown文件夹。 所以同步方法不受Obsidian本身的束缚，可以自由选择iCloud Drive等OS标准同步、付费官方Obsidian Sync、Git等版本管理、Syncthing等自托管型同步工具。 这里通过费用、对应OS、冲突时的行为比较了4方式，Git和Syncthing实际碰撞了2台的离线编辑，确认了破损方式。

一言以蔽之

如果仅用Apple产品完成的话iCloud Drive（默认运行，没有额外费用）就足够了。 Windows/Android也一样，或者想要官方版本历史和支持的话Obsidian Sync（收费）。 如果熟悉Git并想将变更履历作为提交留下的话Git（免费・需要设置）。 如果想不通过云运营商免费同步的话Syncthing（免费・需要设置。 iPhone・iPad官方不支持）。 实测发现的区别是“发生冲突（冲突编辑）时的破坏方式”，Git在笔记正文中直接插入冲突标记，需要手动解决，Syncthing自动保留一个，将另一个作为单独的文件保存。

从iPhone用声音说话留给Obsidian最短的方法，总结为4方式的比较（附带不需要插件的步骤）。

4个同步方法

无论哪个都做“在多个终端上整理保管库文件夹的内容”的同样的工作，但是结构不同。

☁️ iCloud驅動器
Apple纯正的文件同步。 只需将保管库文件夹放在iCloud Drive内，Mac/iPhone/iPad之间无需追加设置即可齐全。 无法到达Windows/Android/Linux。设置步骤在另一页中。
🔄 Obsidian Sync（官方・收费）
Obsidian开发者提供的官方服务。 拥有E2E加密・Version History功能，对应所有平台。 费用是在另一篇报道中已实测在、Standard/Plus需要哪个也在另外的页面上整理。
🌿 Git
将保管库视为Git存储库，通过提交、push、pull进行同步的方式。 使用社区插件（Obsidian Git等）也可以实现自动化。 所有变更都作为履历留下的同时，解决冲突需要Git的知识。
🔁 同步
开源的自托管型文件同步。 不通过云企业，终端之间直接（P2P）同步。 免费，有面向电脑（Windows・Mac・Linux）的官方版。 Android官方应用程序的开发结束，使用社区版（Syncthing-Fork）。 iPhone・iPad在Obsidian的官方帮助中是“官方不支持”的处理，通过其他公司制造的应用程序（Synctrain等）回避的形式。 在各个终端上安装应用程序进行配对也很麻烦。

比较破损方式 — 实际发生了冲突

虽然经常看到同步方式的目录式比较，但“同时用2台编辑的话实际会怎么样”移动手确认的报道并不多。 在这里，在这个验证环境（Ubuntu 24.04・GitHub Actions）中实际设置了Git和Syncthing，在模仿2台终端的文件夹中离线添加单独的1行后重启同步。 iCloud Drive和Obsidian Sync，因为这个环境下没有macOS/iOS，所以实机无法再现，是基于官方帮助的记载。

实测 — Git

在笔记正文中直接插入碰撞标记

制作了1个中央存储库，将2的clone分别视为不同的终端。 两者都处于“离线”状态，在同一笔记的末尾加上另一个1行并提交，按顺序push。 

# デバイスAを先にpush → 成功
$ git push origin master
   ba48c62..f0be52e  master -> master

# デバイスBをpush → 拒否される
$ git push origin master
 ! [rejected]  master -> master (fetch first)

# デバイスBがpull（マージを試み、衝突）
$ git pull origin master --no-rebase
Auto-merging Daily Notes/2026-08-26.md
CONFLICT (content): Merge conflict in Daily Notes/2026-08-26.md

# ノートの中身（Obsidianで開くとこのまま見える）
# 2026-08-26

- 08:00 起床
<<<<<<< HEAD
- 09:15 買い物メモ
=======
- 09:00 会議メモ
>>>>>>> f0be52e...

数据不会丢失但是，带有碰撞标记状态的笔记本直接用Obsidian打开。 如果不注意地阅读的话，可能会误读自己的文章，为了解决，需要在理解<<<<<<< / ======= / >>>>>>>的意思后手动编辑，重新提交。 即使使用像Obsidian Git这样的插件，这个最终的冲突解决也是需要Git知识的工作。

实测 — Syncthing

留下一边，把另一边退到其他文件

按照同样的步骤（通过apt安装的Syncthing v1.27.2启动2实例，用本地TCP直接配对）尝试的话，与Git的破坏方式完全不同。 

# 同期再開後のvault-a
Daily Notes/2026-08-26.md
Daily Notes/2026-08-26.sync-conflict-20260825-212901-P2RW67Y.md

# 2026-08-26.md（採用された側）
# 2026-08-26

- 08:00 起床
- 09:15 買い物メモ（デバイスBで追記）

# 2026-08-26.sync-conflict-....md（退避された側）
# 2026-08-26

- 08:00 起床
- 09:00 会議メモ（デバイスAで追記）

Syncthing自动将其中一个保留原文件名，将另一个保存为名为*.sync-conflict-日時-デバイスID.md的另一个笔记。 正文中不会混入标记，也不需要Git知识。 但是不会自动合并，如果在没有注意到被撤离的笔记的情况下放置的话，同一话题的笔记会分裂成2的文件。 保管库的搜索结果中不熟悉的文件名增加，这可能会造成操作上的噪音。

官方信息・未验证 — iCloud Drive

Apple官方帮助上有编号的重复文件

Apple官方的Mac帮助说明，在iCloud Drive上文档的版本冲突时，可以在冲突解决对话框中选择并保留各个版本，如果保留多个版本，则像“Seven Wonders”“Seven Wonders 2”一样末尾带有编号的文件名。 但是这个对话框是针对Apple的文件版本化API对应的应用程序（Pages等）的行为，像Obsidian一样直接读写到文件系统的应用程序不一定会出现相同的对话框。 这个环境中没有macOS/iOS，Obsidian+iCloud Drive没有进行实机验证。

现有报道的“不进入每日笔记”章节中处理的同步延迟（即使写入即时也需要几秒钟~数十秒才能反映），与这种竞争是不同的现象。 了解两者的话，通过iCloud的故障分类会更快。

官方信息・未验证 — Obsidian Sync

冲突的解决算法不公开。 可以依靠的是Version History

官方帮助（obsidian.md/help/sync，2026年8月26日获取）中，没有同时编辑时采用哪个版本的具体算法记载。 另一方面“Obsidian Sync与Dropbox、Google Drive、OneDrive等其他云存储同时使用的话，可能会发生同步冲突（sync conflicts），请备份保管库”的官方注意事项，Obsidian Sync也存在竞争的概念本身。 作为恢复手段明确说明的是Version History功能，可以以笔记为单位从列表中选择过去的版本进行恢复。 保留期限为Standard计划1个月，Plus计划12个月，附件不分计划2周。

在这个环境下，因为需要付款，所以无法创建Obsidian Sync的账户，无法再现实际的竞争。

共同的教训

4方式中，实测的Git・Syncthing都没有丢失数据。 破坏方法的区别在于“标记是否混入正文”和“是否分裂成其他文件”，两者如果不注意就会安静地放置这一点是共同的。 1的保管库不要以多个同步方式进行双重同步（Obsidian公式明确提醒这一点）是最可靠的预防措施。

选择方法的基准

🍎 仅使用Apple产品
iCloud Drive就足够了。 已经打开了，不需要额外的费用和设置。
🖥️ Windows/Android也一样
如果想在没有技术知识的情况下获得官方支持和版本履历的话，Obsidian Sync。 如果免费的话，Syncthing是对手。
🌿 习惯了Git
如果想要将保管库的变化本身作为提交履历留下的话，Git。 前提是能够自己解决冲突。
🔒 不想通过云企业
4中，终端之间直接同步的只有Syncthing。 虽然是免费的，但iPhone・iPad在Obsidian的官方帮助中作为“官方不支持”的处理，各个终端的设置也是自己进行的。

无论哪种同步方式，保管库都只是文件夹

选择哪种同步方式，只是决定保管库文件夹的“排列方法”而已。 SimpleMemo将发送的备忘录留在自己的邮件中，直接在iCloud Drive上的保管库文件夹的每日笔记中进行补充。 以iCloud Drive同步的保管库为对象，仅通过Git和Syncthing操作（不通过iCloud Drive）的保管库文件夹，目前不在对象之列。

常见问题

最终选哪个好呢？
如果只用Apple产品的话，已经打开的iCloud Drive是最省事的。 也使用Windows/Android，或者官方要求版本历史和支持的话，付费的Obsidian Sync。 熟悉Git，如果想作为提交履历留下保管库的变化的话，Git。 如果不想免费通过云企业的话，就选择Syncthing（iPhone・iPad在Obsidian的官方帮助中“官方不支持”的处理）。
不使用Obsidian Sync可以在多个终端上同步吗？
可以。 保管库只是没有特殊格式的Markdown文件的集合，所以iCloud Drive・Dropbox・Google Drive等OS标准的文件同步，以及Git和Syncthing等通用的同步工具可以直接使用。 Obsidian Sync是同步方法的选择之一，不是必须的。
同时用2台编辑会怎么样？
根据方式不同，破损方式也不同。 在本报道中实际测量后，Git将冲突标记（<<<<<<<）直接写入同一文件中，需要手动解决。 Syncthing自动采用一边，一边将另一个作为名为“sync-conflict”的单独文件保存，数据没有丢失。 iCloud Drive和Obsidian Sync在这个环境下（没有Linux・macOS/iOS）无法实机验证。
可以同时使用多种同步方法吗？
Obsidian官方帮助建议将Obsidian Sync与Dropbox、Google Drive、OneDrive等其他云存储同时使用时会发生同步冲突（sync conflicts），建议备份保管库。 避免将双重同步结构叠加在同一文件夹中，在1个保管库中使用1个同步方法比较安全。
用Obsidian Sync覆盖错误的话可以恢复吗？
根据官方帮助，通过Version History功能可以浏览、恢复每个笔记的过去版本。 保留期限为Standard计划1个月，Plus计划12个月，附件为2周（2026年8月26日在官方帮助中确认）。 恢复选择文件，从“Open version history”开始。
验证环境和验证范围

验证日期：2026年8月26日/环境：Linux桌面（Ubuntu 24.04・GitHub Actions执行环境）。 实测（在这个会话中实际移动确认）: Git 2.x — 中央存储库1个和2个clone离线同时编辑→push的拒绝→pull时的合并冲突→再现插入正文的冲突标记。 Syncthing v1.27.2（通过apt安装）—在本地TCP中直接配对的2实例之间再现相同的场景，确认sync-conflict-*.md文件的生成。 基于官方信息的记载（未验证）：Obsidian Sync版本履历的保留期限・其他云同时使用时的注意事项（obsidian.md/help/sync从本会话直接获取・2026年8月26日）、iCloud Drive上文件冲突时的带编号文件名（Apple官方Mac帮助）、Syncthing的对应终端（obsidian.md/help/sync-notes和Syncthing的文档・2026年10月1日确认）。 在这个环境下无法验证的事情：iCloud Drive和Obsidian组合的实际竞争行为（没有macOS/iOS），Obsidian Sync的实际竞争再现（因为是收费服务，所以未签约）。 Obsidian的版本和各工具的行为在未来可能会发生变化，所以最新信息请在各官方网站上确认。
