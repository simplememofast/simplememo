Copilot：即使选择模型，附加功能的路径也会另外留下

固定版的指南分为hosted・Cloud BYOK・Local BYOK・opencode・Claude・Codex的处理对象。 例如，Local BYOK的模型是local endpoint的解释，根据使用的Skill和project context，也有涉及其他服务的情况。 Q03

将笔记的参考和Miyo的索引分开

资料中有说明，agent阅读笔记，将必要的部分放入选择模型的prompt中。“ 仅仅打开Agent Chat就上传了整个Vault”的行为没有说明。 Miyo有local连接和remote server连接，分别选择索引和搜索目的地。 通过搜索找到的摘录也进入了模型的语境。 仅仅使用local的索引，不能说摘录不会传到模型provider。 Q03 / Q05

文件处理也不是统一的。 资料上，Agent Chat的Miyo处理使用local CLI，Quick Chat使用连接的Miyo service，remote的话使用那个server处理。 使用Web・YouTube・binary file的saved project context有使用hosted project service的情况，与Miyo的选择是不同的路径。 Q03

不保证Self-Host Mode会切断通信

指南明确指出，即使是Self-Host Mode，cloud也不会失效。 发送到选定的Claude、Codex、cloud model和搜索provider等的路径仍然存在。 这是为了确认每个功能是否与想要使用的功能和允许的处理对象一致的设置。 Q04

关键的getter、初期定数、诊断的方针，根据各自的依据来阅读

确认的KeychainService的范围是，确认有没有app.secretStorage，如果没有就会出错的getter。 不是实际保存密钥的结果，也不是验证OS加密的记录。 enableMiyo=false、enableMiyoSearchSkill=false、activeBackend=opencode、debugFullFrames=true是源内的初始值，不显示已转移的设置或读者GUI的值。 Q07 / Q08 / Q09

README说明了hosted request的随机UUID和读者选择upload的诊断ZIP。 ZIP的60天后删除，hosted request的临时处理、非保留、非学习是提供者说明的方针。 并不是在这里审核backend的运用。 不能判断只从debugFullFrames=true开始自动发送诊断ZIP。 Q02

Smart Connections：local embedding的说明和，全部通信的有无分开

README称，内置本地模型会为Vault建立索引，无需API密钥。这可作为查找相关笔记机制的说明，但在本次比较中，我们没有运行模型，也没有观察实际索引过程或网络通信。README关于“private”“offline”和移动端的说明也仅作为提供方的声明。Q10 / Q11

另一方面，自己的src/main.js有从initialize后的更新确认到GitHub latest-release的GET预约代码。 首次用户的StoryModal会传递smartconnections.app的URL。 这是与通信相关的代码路径的确认。 StoryModal的实现在依赖方，实际读取URL，以及传递什么样的payload尚未确认。 Q12 / Q13

model・settings・HTTP等部分参考了Smart Environment/jsbrains相关的外部package。 仅凭这个范围，不能断定“所有功能都在终端内”“没有telemetry”“笔记本一定会被发送”。 将本地索引的说明、更新确认的代码、未确认的依赖、实际通信分开的话，可以知道追加调查的对象。 Q14

Text Generator：确认上下文的候选人和密钥保存的分支

可以获取剪贴板的设置和实际prompt是不同的

固定版的初始设置有includeClipboard=true，context builder如果其值为true，则具有可以获取clipboard的分支。 另一方面，引用的初期template是title、starredBlocks、tg_selection，不是clipboard placeholder。 Q15 / Q17

根据template、frontmatter、context options、选择范围，解决的值会发生变化。 请不要将可用的值一览表和实际请求中的值视为相同的。 这个代码确认不是“clipboard一定会被发送”“Vault全部会一直被发送”的结果。 Q17 / Q18

plain key栏的空文字不能成为加密的证据

初始值是encrypt_keys=false。 有保存时将plain key栏清空的处理和准备其他secret相关字段的处理。 getEncryptedKey在加密不可用或encrypt_keys无效时，返回连接固定prefix和输入key的值。 即使字段名称中包含encrypted/hashed，也不能仅凭这一点判断为加密的bytes。 Q15 / Q19 / Q20 / Q21 / Q22

键，所以实际保存的内容和这个终端的safeStorage动作尚未确认。 在共享包含密钥的配置文件和诊断记录之前，不仅需要关注plain栏，还需要关注保存的其他值。

将初期provider和local对应分开选择

源的初始provider是OpenAI Chat (Langchain)，endpoint是https://api.openai.com/v1。 Ollama provider有接收设定的basePath的实现。 仅凭有local对应provider的事实，并不能证明其他功能的处理目的地和全通信都没有。 Q15 / Q23 / Q24

附加request、automatic suggestions、slash suggestions、JavaScript执行在引用的初始值中是OFF。 这些也不是现行GUI的实际测量值。 请在自己的环境中确认使用的template和已保存的设置。 Q15 / Q16

常见问题

选择本地模型的话，插件完全不通信吗？
模型的处理目的地和索引、Web搜索、文件转换、更新确认是不同的路径。 Copilot的资料区分了附加功能的路径，Smart Connections的自前代码有GitHub更新确认GET。 在这次资料确认中，没有确认所有功能没有通信和实际发送内容。
Smart Connections会把笔记本发送到外部吗？
固定版README说明了通过内置的本地模型制作embedding和索引。 这是提供者的说明。 自己的来源有更新确认和首次介绍的URL，模型、设置等有一部分是外部依赖。 这个比较没有测量实际的笔记发送和全部通信的有无。
Text Generator的includeClipboard=true，是一定要发送剪贴板的意思吗？
在源代码中，当该设置为true时，context builder可以获取剪贴板的分支。 另一方面，刊登的初期模板使用title、starredBlocks、tg_selection，没有指定clipboard。 可用的值和实际组装的请求内容是不同的。 实际payload未测量。
如果保存数据的api_key是空的，密钥已经加密了吗？
仅凭空键栏无法判断。 在Text Generator 0.8.7中，有清空plain key栏的保存处理和单独的保存字段，如果无法使用加密或encrypt_keys无效时，有返回固定prefix和输入键的分支。 没有尝试过实际的密钥保存和平台的加密动作。
这篇报道是否比较了AI的回答质量和费用、iPhone的动作？
比较对象是固定的3版的官方资料和代码中显示的数据路径和设置。 插件的安装、设置画面的实际操作、模型生成、收费、实际通信、包括iPhone在内的终端动作、提供者的保存、非学习方针的遵守没有确认。
