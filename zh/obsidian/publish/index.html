是委托托管，还是自己管理生成物

Publish是Web公开笔记的官方托管服务。 Quartz是从Markdown生成网站的工具，另外选择生成物的发送目的地。 GitHub Pages是其发送目的地之一。 结合Quartz和GitHub Pages时，处理生成和发送两个角色。

选择想要公开的笔记，如果想要将网站的托管委托给服务的话，请确认Publish的条件。 如果能自己执行命令、更改设置、管理发送目的地的话，用小笔记尝试Quartz等静态生成。 如果只保存的笔记不需要在Web上公开的话，在选择公开用的附加服务之前决定目的。

角色的比较费用确认实际构建的输入生成步骤画面和链接练习用文件

Publish・Quartz・GitHub Pages，负责的范围不同

选择角色和自己要做的事情这次确认
Obsidian Publish官方的云托管。 准备账户和Publish合同，管理公开的笔记和网站。用固定来源确认官方Introduction/Set up。 合同、Publish实际操作、实际公开未实施。
石英从Markdown等生成网站的工具。 自己处理Node/npm、设置、输入文件、生成物。v4分支的固定commit，在package 4.5.2中实际npm ci・本地构建・浏览器显示。
GitHub 页从存储库发送静态网站的服务。 管理存储库、公开来源、workflow、公开/非公开和计划条件。用固定来源确认官方资料。 未实施新存储库的制作、设置、部署、实际发布。

这个表不是比较所有功能的排名。 用Quartz构建，并不意味着与Publish相同的服务功能，以及GitHub Pages的发布成功。

费用，将合同、发送地址、运用分开确认

Publish的现行金额，在这次的环境下尚未再次确认。 最新的金额和年付、月付的申请期限请在Obsidian官方费用上确认。 从这个实际构建的成功来看，没有得到Publish免费的结果。

固定的Quartz源是MIT许可证。 这是软件的使用条件，并不是发送地址、独立域名、更新工作等费用一律为零的条件。 这次的执行费用也不清楚。

固定的GitHub官方资料，在GitHub Free和面向组织的GitHub Free中可以在公开存储库中使用Pages，在Pro/Team/Enterprise的条件下对应公开・非公开存储库。 确认实际选择的账户的计划、公开范围、限制和合同条件。 这边这次也没有改变账户和托管的设置。

现有费用一览表是2026年9月9日确认官方标识的报道。 这次不将其作为现行费用的独立确认，将最新的购买条件作为需要官方确认的信息进行划分。 Publish和终端之间同步的Sync也是另外的服务。

# 著者作成の公開前メモ

これはローカルビルドのための架空の短文です。利用者の記録ではありません。

次は [[手順/確認|確認ノート]] を開きます。

![[assets/fixture-diagram.svg]]

展开固定源，确认依赖和设置后构建

  1. 确认了官方Quartz的v4分支，在scratch中展开了commit d25a6eabf96751ffca56f8a8139272def7a65041的源档案。
  2. 确认了README、MIT许可证、package.json、package-lock.json、CLI的构建处理。 Package version是4.5.2，必要版本是Node 22以上・npm 10.9.2以上。 实际环境是Node 24.19.0・npm 11.9.0。
  3. 用固定的lockfile运行了npm ci。 安装了491 packages，exit 0。 lockfile的597 entries是包含对应OS等依赖的记录，与安装显示件数的意思不一样。 原lockfile的bytes没有变化。
  4. 更改了私人设置，以三个笔记为对象用Quartz CLI生成。 接下来说明设置变更和第一次失败。

执行的命令形式如下。 例子的输入输出文件夹，指定自己准备的地方。

npm ci --no-audit --no-fund
node quartz/bootstrap-cli.mjs build   --directory /path/to/fixture   --output /path/to/generated   --concurrency 1

在执行日志中留下了scratch内的绝对路径和隔离的npm cache指定。 这里显示的path是说明用的替换。 省略了audit的命令，并不意味着通过了依赖的安全审计。 报道不是执行到公开服务器的部署程序的记录。

在这个本地例子中更改的设置

项目这次的设定和确认范围
显示・连接地址日语locale，作者制作标题，localhost base URL，analytics null，不使用外部font的system font。
日期frontmatter/文件属性优先。 使用源档案，没有将Git履历作为日期的证据。
任意OG生成CustomOgImages emitter失效。 Quartz的独自OG生成尚未验证。
数式第一次标准Latex要求外部KaTeX CSS/JS，在环境方面被屏蔽了。 用没有数学公式的相同fixture，使未使用的Latex失效后重新构建了。

两次的构建都生成了exit 0，每个20文件。 保留首次生成物和失败的浏览器记录，在另一个文件夹中确认设置变更后的生成物。 不会扩大标准Quartz不进行外部通信的结论和数式的兼容性。

生成的HTML，wiki链接，实际打开附件

在本地服务器上打开生成物，确认了320/390/768/1440 px的四幅。 阅读title、日语正文、验证标签、SVG，入口→确认→参考→入口在各个宽度上实际点击。 总共12点击的有限确认。

生成HTML三件、CSS、JS二件、contentIndex、SVG共八件，localhost的实HTTP响应和生成原件的bytes/SHA256一致。 附加的SVG也与输入原件的内容相同。 设置变更后的四幅没有横向突出和该页面的console/page/resource错误。

虽然显示了图像中的图表和反向链接widget，但其全部功能都没有尝试过。 因为在fixture中也写了正文标题，所以和Quartz那边的报道标题重叠显示。 现行费用确认、SEO性能、大Vault、Web公开的证明不计入。

常见问题

要在网上公开Obsidian的笔记，必须有Publish的合同吗？
使用Publish时，官方指南中需要Obsidian账户和有效的Publish合同。 另一种方法是，在Quartz中将Markdown生成的网站放在自己选择的发送目的地。 这次确认了Quartz的本地生成，没有尝试Publish合同和外部发布。
Quartz和GitHub Pages是同一种类的服务吗？
Quartz是将Markdown转换为HTML、CSS、JavaScript等的工具，GitHub Pages是从存储库发送静态网站的服务。 将用Quartz制作的产物放在GitHub Pages等的构成。 GitHub Pages的设置、部署、实际发布这次没有进行。
Publish和替代方法的费用，应该在哪里确认呢？
Publish的最新金额和请求期限将在官方费用页面确认。 在这次的环境下无法重新获得现行费用页面，现行金额尚未确认。 Quartz的固定来源是MIT许可证，但发送地址、域名、运用费用另行确认。 GitHub Pages的公开、非公开存储库的计划条件也参考官方资料。
仅通过这次Quartz确认，就能判断Web公开和所有功能的兼容性吗？
无法判断。 关于三个作者制作的Markdown和一个SVG，确认了固定commit的本地构建、四画面宽度、内部链接和生成文件。 有使未使用的Latex和任意OG生成无效等设置变更。 数式、大保管库、全Obsidian功能、外部发送、同步、SimpleMemo配合、速度和生产率尚未验证。
