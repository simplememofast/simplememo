Obsidian / Example of Git conflict recovery

Leave the original text and select the content

Resolve Git conflicts in Obsidian
Keep the originals, compare, and save

If conflict markers appear in the text, keep both original versions separately and decide which content to retain. In this small exercise, we selected two checklist items and saved them in Obsidian, then verified that the local Git merge completed and the content could be displayed again.

The order of confirmation is the original text, selected content, and saving results

This example covers conflict markers appearing in the same Markdown note during a Git merge. We edited one author-created note on two local Git branches and observed an actual merge failure, compared the original texts, and corrected the conflict manually. This was not a result of synchronization across multiple devices.

  1. Manually leave both original textsPrepare a copy that can distinguish which one is the content
  2. Compare the differencesCheck the unusual lines and common parts
  3. Decide the content to adoptThis example puts two compatible items into separate lines
  4. Edit and saveConfirm the completion of the merge on the text and Git side
  5. Re-display and checkCheck the selected content and save Markdown

This order is a diagram that organizes this exercise. It is not a diagram that shows the guarantee of automatic restoration and loss prevention, and the operation procedure for each synchronization service.

First, check the form of your conflict

In this example, Git merge stopped with exit code 1, and 作業メモ.md was marked UU. Git’s index retained the common base and both edited versions. The note contained the conflict markers <<<<<<< HEAD, =======, and >>>>>>> draft-b.

If a screen of alias competing files or history appears in your environment, please check it according to the synchronization method. The entrance to check the method is Obsidian's synchronization method guide. The results of Git in this article cannot be read into the behavior of Obsidian Sync or iCloud.

The text saved in this conflict state is shown below. The complete contents of the actual file, including its markers, are reproduced.

# 作業メモ

ローカルの競合を確かめるために著者が作った練習用ノートです。

## 次の確認
<<<<<<< HEAD
- 確認する項目: 見出しの順番を確認する。
=======
- 確認する項目: 内部リンクの保存先を確認する。
>>>>>>> draft-b

1. Leave the two original texts at hand separately

Before starting editing, save each version at hand separately with a name that shows the original version. If you only have one of them at hand, do not treat the other as being able to save it, and check the status of Git and the history of the method you are using. I have not tried to retrieve from the history of each service this time.

If you want to make sure you are prepared to return to the previous text before fixing the conflict, please also refer to Git, File Recovery, and out-of-store copy recovery example.

In this exercise, the author manually kept copies of versions A and B before merging. We also placed 原文の控え/案A.md and 原文の控え/案B.md in the vault and opened them for comparison. These were not conflicted copies automatically generated by a synchronization tool.

versionChanged confirmation itemCommon part
Draft ACheck the order of headingsTitle, explanation of practice notes, heading for next confirmation
Draft BCheck where to save the internal linkSame as Plan A

Instead of judging only by the update time, read the text and check the necessary information. Since the two are compatible as separate confirmation items this time, the author decided to adopt both lines in the order of A and B. If the actual sentence is contradictory or duplicated, you need to choose according to the content.

2. Edit the chosen content in Obsidian and verify that it was saved

We opened 作業メモ.md in the actual Obsidian editor and entered the chosen content. In this example, we kept the shared explanation, put the two items on separate lines, and removed the conflict markers. After waiting for autosave, we verified that the actual file contained the complete text below.

# 作業メモ

ローカルの競合を確かめるために著者が作った練習用ノートです。

## 次の確認
- 確認する項目: 見出しの順番を確認する。
- 確認する項目: 内部リンクの保存先を確認する。

In addition to the fact that the marker has disappeared, I will re-read the selected content, the order of the lines, and the common parts that I decided to leave. The decision to summarize the text and the operation to complete the merge on the Git side will be confirmed separately.

3. Check the unresolved status of Git and complete the merge

In this exercise, even after saving the text with Obsidian, the Git state was UU. After that, I explicitly git add with only the target note and made a merge commit locally. The two original commits remain as parents, the git ls-files -u is empty, and the Git state is clean.

The following is an example of the command to check the target file in the local Git. Check the actual note name and repository before using it. Before git add, please check the text to be adopted and other working status.

git status --short -- "作業メモ.md"
git ls-files -u -- "作業メモ.md"
# 採用する本文を確認した後、対象ノートをstageする
git add -- "作業メモ.md"
git commit
# merge完了後の未解決indexと状態を確認する
git ls-files -u
git status --short

Git operation was performed with a local command. Obsidian Git plug-in is not used, and remote, push/pull, and reflection on other terminals have not been confirmed. The fact that the condition is clean does not prove the durability of the backup or the delivery to all terminals.

4. Reopen the notebook and read the selected content

After creating the merge commit, we reopened 作業メモ.md from the actual file explorer. Reading view showed both items with no conflict markers. The Markdown file had the same SHA256 before and after reopening, and the original A and B copies and the content of each commit were retained.

This result was confirmed by this author's note and one local restoration. It is not a result that shows that information will not be lost in all conflicts and all synchronization methods.

Frequently Asked Questions

Are the conflict markers in the text and the conflicted copy the same?
In this test, we inspected the conflict markers Git inserted into the working Markdown body. The author manually made the copy of the original text. This recovery example did not test a synchronization method automatically creating a separate file. Consult the instructions for the method you use.
Can I solve it if I leave both sentences?
The two confirmation items in this example are compatible, so the author decided to leave them as separate lines. If the content is inconsistent or the same explanation overlaps, please check the meaning and the necessary information and re-select. It is not always a procedure to add both.
If I delete and save the conflict marker, will the Git merge be completed?
In this exercise, the Git state was UU even after saving it with Obsidian. After checking the contents, git adding the target note, and creating a merge commit, I confirmed that the unresolved index was empty and the Git state was clean. Please separate the editing of the text and the completion of the Git side.
Has this procedure been verified on Obsidian Sync and iCloud?
The Linux version of Obsidian 1.13.7 and one offline local Git repository were verified. Obsidian Sync, iCloud, other synchronization services, two terminals, iPhone, SimpleMemo linkages have not been tried. Please check the history and conflict mechanism according to the actual method.

Verification environment and confirmation range

  • Real application: 2026 year 9 month 30 Linux version Obsidian 1.13.7. Japanese notes created by the author, one offline local Git repository, no community plug-in.
  • Actual Git results: merge failure, UU, three levels of unresolved index, conflict marker, merge commit with explicit target stage and two parents, unresolved index is empty, state clean.
  • Real GUI: Check the real file explorer operation of the original text A, competing notes, and post-saved notes, input and save the selected text in the real editor, read the view, and re-display of the note.
  • Auxiliary: The composite note and the copy of the original text have been prepared directly as a file. I used the app API to divide left and right, display B, sidebar, setting window, and read the status. Git is a local shell operation.
  • Unverified:Automatic conflicted-copy generation, Obsidian Sync, iCloud, other synchronization services, remote, simultaneous editing on two devices, iOS/Android/Mac, SimpleMemo delivery, long-term backup, speed, productivity, inflow effect.
