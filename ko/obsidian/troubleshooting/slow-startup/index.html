설정을 변경하기 전에 원래 보관함을 보관하십시오

노트·첨부 파일·설정의 백업을 확보하고, 원본 보관함이 아니라 검증용 복사본으로 시도합니다. 커뮤니티 플러그인을 한 번에 비활성화하고, 같은 노트가 표시될 때까지의 시간을 비교한 뒤, 차이가 있으면 하나씩 되돌려 확인합니다.

먼저 백업하십시오. Obsidian을 닫고, 자신의 보관함을 다른 장소로 복사합니다. 숨겨진 폴더의 .obsidian 도 설정으로 포함합니다. 복사본이 존재하고, 알려진 노트를 읽을 수 있는지 확인한 후 설정을 변경하십시오. 원본 노트나 플러그인 파일을 삭제하는 절차가 아닙니다.

여기부터의 구분은 독자를 위한 제안입니다. 독자의 단말기 원인을 진단한 결과가 아닙니다. 후반부 실측은 저자가 준비한 1 노트의 고정 조건만을 다룹니다.

  1. 보관하기원래 노트·첨부·설정
  2. 증상을 구분시작·본문 표시·편집 중
  3. 복사본으로 비교하기같은 노트·같은 기준
  4. 하나씩 되돌리기버전과 변경을 기록합니다
안전하게 자르다9회의 실측값측정 방법과 한계원 CSV·화면자주 묻는 질문

“무거워”를 구분하여 검증용 복사본으로 확인합니다

  1. 어느 단계가 느린지 적어 두십시오.
    앱을 실행할 때까지, 보관함을 열어 본문이 보일 때까지, 검색·링크·편집 중에는 각각 다른 증상이 나타납니다. OS, Obsidian 버전, 보관함의 대략적인 규모, 직전에 변경한 설정 및 유효한 플러그인을 기록합니다.
  2. 백업을 확인하고, 검증할 복사본을 분리합니다.
    앱을 닫고 복사본을 만든 뒤, 원본은 보관된 상태로 유지합니다. 검증용 복사본을 자동 동기화 대상과 혼동하지 않도록 배치 위치를 확인하고, 두 개를 동시에 열어 둔 상태에서 설정을 변경하지 않도록 합니다. 모르는 사람의 보관함나 확인되지 않은 플러그인을 사용할 필요가 없습니다.
  3. 복사하여 커뮤니티 플러그인을 비활성화하고 비교합니다.
    유효한 목록과 설정을 기록한 후, 커뮤니티 플러그인 설정에서 비활성화하거나 Restricted mode(제한 모드)를 사용하여 재시작 후 동일한 알려진 노트가 표시될 때까지 비교합니다. 메뉴 표시를 버전·언어로 확인해 주세요. 플러그인이 중지된 동안에는 해당 플러그인이 담당하는 기능을 사용할 수 없게 됩니다.
  4. 차이가 보이면 하나씩 유효하게 되돌립니다.
    동일한 복사본, 노트, 핵심 기능, 측정 기준을 유지하고, 플러그인의 이름·버전·활성화 순서를 기록합니다. 같은 조건을 여러 번 측정하고, 첫 번째만의 시간이나 한 번의 빠른 값으로 결론을 내리지 않도록 합니다.
  5. 차이가 보이지 않으면, 보관함과 환경을 구분하여 비교합니다.
    제가 준비한 작은 노트의 별도 보관함에서도 같은 단계가 느린지 확인합니다. 동시에 동작하는 앱 및 OS 부하, 동기화·스토리지 상태 등도 기록합니다. 여기서 설정이나 파일을 한 번에 변경하면, 어떤 변경이 관련되었는지 알 수 없게 됩니다.

백업 생성, 제한 모드 전환, 리더 플러그인 복원, 동기화·스토리지 진단은 이 9회 측정에서 시연한 작업이 아닙니다. 실제 측정에서는 사전에 준비한 활성화 목록을 사용했으며, 실행 중의 작업이나 노트를 수정하지 않았습니다.

고정된 작은 보관함에서, 0·1·2개를 각 3회 측정합니다

동일한 Linux 환경과 저자 작성 노트를 사용하여 실제로 로드된 커뮤니티 플러그인이 0개, Templater 전용 1개, Templater+QuickAdd의 2개가 되는 조건을 비교했습니다. 본문 표시까지의 중앙값은 각각 약 0.92초·0.95초·1.02초였습니다.

이 순서에서 나온 중앙값을 플러그인 수만의 인과관계나 ‘늘어날수록 반드시 느려진다’는 일반 법칙으로 볼 수 없습니다. 개수와 함께 플러그인 종류도 달라졌고, 측정은 각 3회로 적으며, 공유 CPU와 캐시도 일정하지 않았습니다. 독자의 큰 보관함이나 기기에 이 차이를 그대로 적용하지 마세요.

시작의 “어디까지”를 측정했는가

연결 준비와 본문 표시를 구분합니다

단조롭게 증가하는 시계로, Obsidian 프로세스를 시작하기 직전부터 경과 시간을 측정했습니다. 표시 환경 준비는 시작 전에 완료했습니다. CDP ready는 측정용 연결 대상이 응답하고 연결 대상 정보를 얻은 시점입니다. 이것만으로는 화면에 노트가 표시되었다고 말할 수 없습니다.

GUI text ready는 해당 연결을 사용하여 실제 화면을 확인하고, 起動確認.md의 제목 “起動確認”와 알려진 확인 표시가 표시된 시점입니다. 시작부터 연결·읽기 처리까지 포함합니다. 첫 번째 렌더링, 모든 플러그인의 초기화 완료, 편집 가능해지는 시점과는 별개의 지표입니다. 읽기 개수 상태 확인은 이 본문 표시를 관측한 후 별도로 기록했습니다.

같은 입력과 순서를 사용합니다

  • 공식 Obsidian 1.13.7. 실제 일반 화면에서 앱과 설치 프로그램의 버전을 확인했습니다.
  • Templater 2.25.1, QuickAdd 2.29.0의 동일한 공식 배포 파일을 전체 조건에 복사합니다. 이번에는 새로운 획득·종속성 설치가 없습니다.
  • 입력은 저자가 직접 준비한 148바이트의 Markdown 1건입니다. 동일한 보관함 설정, 코어 기능 5종, 두 플러그인의 배포 파일을 사용하여, 활성화 목록 외의 보관함 파일을 실행 전에 대조했습니다. 시작 후에도 본문의 바이트/해시가 변하지 않았습니다.
  • 코어 기능은 file-explorer, backlink, outline, properties, bookmarks입니다. Templater의 시작 template와 QuickAdd의 choice·macro·AI 설정 등은 실행하고 있지 않습니다.
  • 사전에 0·1·2개의 3 조건과 각 3회를 정하고, 0,1,2 / 1,2,0 / 2,0,1 순서대로 측정합니다. 예정한 9회를 모두 게재했으며, 빠른 값만 선별하거나 이탈한 값은 삭제하지 않았습니다.
  • 측정 중에는 GUI 클릭, 노트 열기·쓰기 API, 플러그인 명령을 실행하지 않고, 읽기로 상태를 확인했습니다. 각 회마다 실제 화면을 저장하고, 측정에 사용한 앱만 정상적으로 종료하고 있습니다.

캐시 부하 프로파일의 한계

처음에 미계측 준비용 프로파일에서 실제 신뢰 확인과 General 버전 확인을 수행하고, 준비된 설정을 각 회에 복사했습니다. 각 회마다 새로운 프로파일·캐시용 디렉터리를 만들고 있지만, OS의 페이지·디스크 캐시는 준비와 반복을 통해 워집니다. 재부팅이나 OS 캐시 삭제를 하지 않았으며, 물리적인 콜드 실행이나 최초의 미사용 설정이 아닙니다.

각 회차의 전체 글로벌 프로파일에 대해, 시작 직전의 전체 해시 목록은 기록하지 않습니다. 공통의 준비된 원본 설정 및 복사 방법, 각 보관함의 시작 전 파일 대조는 남겨두고 있지만, 모든 프로파일의 모든 바이트가 동일했다고 주장하지 않습니다.

공유 환경에서는 CPU 사용률 관측값이 약 35–44%이며, 다른 앱도 실행되고 있었습니다. 보이는 논리 CPU는 5이며, CPU 할당은 4 CPU에 해당하고, 메모리 상한은 16 GiB입니다. CPU의 관측 구간에는 측정·상태 획득·이미지 저장도 포함되며, 개별 플러그인의 CPU 사용률은 아닙니다. 준비 전에 다른 빌드 작업도 확인했지만, 전체 9회 중에 동일한 빌드가 동작했음을 나타내는 기록은 아닙니다.

측정 전 정지와 기록 수정에 관하여

측정되지 않은 준비 단계에서 정상적으로 종료된 앱의 연결 대상이 해제되었는지 확인하는 검사가 TCP의 TIME_WAIT를 대기 중인 연결과 혼동하여 중지되었습니다. 실패 기록은 보관하고, 대기 없음·연결 거부를 확인하여 체크를 수정한 후, 미실행 예정이었던 9회를 측정했습니다. 준비 단계의 시간을 측정 샘플에 포함하지 않았습니다.

원본 이미지 목록을 확인했을 때, 준비용 신뢰 확인 화면을 세어 놓친 11건이라는 기대값을 12건으로 수정했습니다. 이미지·GUI·시간은 다시 생성하지 않고, 기존 CSV 등의 바이트를 유지한 채 기록 건수를 수정하고 있습니다.

원하는 CSV, 노트, 실제 화면을 확인합니다

CSV는 라운드되지 않은 9회의 시각, 실행 시의 읽기 개수와 버전, 공유 부하, 종료 결과를 포함하는 원본 파일입니다. 표의 정수와는 별도로 원래 값을 확인할 수 있습니다. Markdown은 저자가 사전에 직접 준비한 입력이며, 앱을 통한 본문 저장의 결과가 아닙니다.

9회 원본 CSV를 다운로드고정 입력의 Markdown을 다운로드
# 起動確認

著者作成の固定ノートです。プラグインの起動比較にだけ使います。

表示確認印 C21-STARTUP-20260930

에 게재된 4 이미지와 CSV·Markdown은, 동결된 원본과 bytes·SHA256가 일치하는 복사본입니다. 원본 검증 영수증은 23 항목의 확인과 82 파일의 바이트/해시를 포함하며, 영수증 자체를 포함하는 대조 범위는 83건입니다. 이번 9 회에서는 Windows·macOS·iOS, 대형 실용 보관함, 동기화, SimpleMemo의 속도·생산성 및 유입 효과를 측정하지 않았습니다. 측정 조건과 원본의 대조 기록。

자주 묻는 질문

시작이 느린 원인은 플러그인 수에 따라 결정됩니까?
수만으로는 판단할 수 없습니다. 이 고정된 작은 보관함에서는 0·1·2개를 각각 3회 측정했지만, 개수와 함께 플러그인 종류도 변하여 공유 환경의 부하와 캐시도 영향을 미칩니다. 독자의 보관함 원인이나 개수만을 특정한 인과관계를 특정한 결과가 아닙니다.
플러그인을 중지하기 전에 무엇을 백업하시겠습니까?

아니오. Templater와 QuickAdd의 동일한 공식 배포 파일을 모든 조건에 두고, 활성화하는 목록만 변경했습니다. 0개는 커뮤니티 플러그인이 비활성화되어 있으며, 실행 시에도 로드된 인스턴스가 0개였던 조건입니다. 핵심 기능은 동일한 5종입니다.
표의 CDP 준비 시간과 본문 표시 시간은 동일합니까?
별입니다. CDP 준비는 측정용 연결 대상이 응답한 시점입니다. 본문 표시는 그 후 연결하여 알려진 Markdown의 제목과 확인 표시가 실제 화면에 나타난 것을 읽은 시점입니다. 두 경우 모두 프로세스 시작 직전부터 측정하며, 본문 표시에는 연결 및 확인 처리 시간도 포함됩니다. 초기 렌더링이나 전체 플러그인의 초기화 완료를 측정한 것이 아닙니다.
이 기사(문서)의 초를 다른 단말기나 큰 보관함에도 사용할 수 있습니까?
사용할 수 없습니다. Linux 버전 Obsidian 1.13.7, 작은 저자 작성 노트, 고정 설정, 준비된 프로파일 복사본에서 9회만 해당됩니다. OS 캐시가 가열되고 있으며, 공유 CPU 부하는 약 35–44%였습니다. Windows, macOS, iOS, 대형 실용 보관함, 물리적인 콜드 실행, SimpleMemo의 속도는 측정하지 않았습니다.
