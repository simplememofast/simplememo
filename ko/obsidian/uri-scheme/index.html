Obsidian / URI 스킴

공식 사양의 참조와 저자 작성 Linux 샘플 · 확인일 2026년 9월 30일

obsidian:// URI 스킴 완전 가이드 — 전체 액션 및 함정

obsidian://은 다른 앱이나 런처에서 Obsidian의 노트를 열고, 만들고, 검색하기 위한 URI입니다. 먼저 용도에 맞는 액션을 선택하고, 각 값을 URI 인코딩합니다. 기존 본문에 대한 추가는 이번에 저장까지 확인한 new+append=true의 예에서 시작할 수 있습니다.

본문을 입력하여 URI를 복사하려면, 구문과 고정 Linux 관측을 구분하는 무료 URI 생성기도 참조하십시오.

여기에서는 공식 본문의 6 액션 목록에 Hook용 별도 절을 추가한 7 절·38의 액션별 파라미터 항목을 정리하고, Linux Obsidian1.13.7에 전달한 58건의 기록을 대응합니다. 결과를 얻지 못한 입력도 게시하고, 사양 설명과 실제 저장 위치를 구분하여 읽을 수 있도록 하고 있습니다.

확인한 범위:저자용 로컬 Vault, 공식 Linux 앱 1.13.7, 영어 UI, 격리된 Xorg 화면입니다. 실행 파일에 URI를 전달하고 앱이 수신한 후의 작업을 확인했습니다. 브라우저 링크에서의 OS 연관, 물리 iPhone, iOS 단축키, SimpleMemo, 동기화는 아직 검증되지 않았습니다. 58건은 전체값·전체 조합·전체 단말에 대한 보증을 의미하지 않습니다.

입력하여 URL을 만들고 싶다면 기존 URI 생성기로. iPhone에서 실행되지 않거나 단축키가 멈추는 증상은 단축키 대처 가이드로 진행해 주세요. 이 페이지는 표준 URI의 의미와 입력 결과를 조사하기 위한 참고용입니다.

용도에 따라 액션을 선택합니다

기본형은 다음과 같습니다. ? 이후에 파라미터를 배치하고, 여러 항목을 &로 연결합니다. 값 안에 있는 &는 구분점으로 취급되지 않으므로 %26으로 변환합니다.

obsidian://action?param1=value&param2=value

choose-vault에는 고정된 공식 본문에 매개변수 열거가 없습니다. 38 항목이라는 수는 그 외의 작업들의 열거를 세고, daily의 “new와 동일하다”는 규정을 11 항목으로 전개한 것입니다. 플러그인의 Advanced URI(obsidian://adv-uri)는 이 표준 사양의 대상이 아닙니다.

본문의 #도, 제목의 #도, 값으로 인코딩합니다

공식 본문은 빈칸을 %20, 슬래시를 %2F로 하도록 설명하고 있습니다. 일본어, 줄바꿈, # & ? + % / =가 혼합된 저자 본문을 값별로 변환한 I:N1에서는 저장된 Markdown이 입력과 일치했습니다. URL 전체를 한 번에 변환하면 구분도 달라지므로, vault, file, content의 값을 개별적으로 처리합니다.

const vault = encodeURIComponent('練習Vault');
const file = encodeURIComponent('ノート/日本語 メモ');
const content = encodeURIComponent('本文 # & ? + % / =\n二行目');
const uri = `obsidian://new?vault=${vault}&file=${file}&content=${content}`;

위는 조립 방법에 대한 설명용 코드입니다. 단말기의 노트에 저장하는 실행은 포함되지 않습니다. 연습 Vault와 저장 대상을 자신의 이름으로 교체합니다.

생의 #를 남긴 입력에서는 후반부가 떨어졌습니다

I:W1에서는 content의 중간에 있는 #만 생생으로 남겼습니다. 저장된 것은 서두 문장만 있었고, 후반부의 본문은 파일에 없었습니다. 이 사건은 “Obsidian이 본문을 무단으로 삭제했다”는 증거가 아니라, URI 구분과 값을 혼합한 입력 결과입니다.

새로 만들기·추가·위키를 구분

new의 name은 새 노트 이름이며, 저장 위치를 Obsidian의 “Default location for new notes”에 위임합니다. file는 Vault 루트의 저장 대상을 포함하는 값입니다. 공식에서는 file이 name보다 우선한다고 기재했으며, I:N2에서도 file 지정 대상에 저장했습니다. S:N01에서는 name만 사용하고, 사전에 설정한 기본 폴더에 저장하고 있습니다.

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Hello%20World

기존 본문을 남겨두고 추가하는 경우 append=true을 전달합니다. I:N3에서는 기존 본문을 유지하여 추가했습니다. overwrite=true는 기존 본문을 교체하는 지정이며, I:N5에 별도의 원문/저장 후 기록이 있습니다. 공식은 “append가 설정되지 않은 경우에만 overwrite”라고 기재했으며, S:N03의 두 지정 모두에 대해 추가되었습니다. 일상적인 본문 추가에 덮어쓰기 지정을 섞을 필요가 없습니다.

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Another%20line&append=true

silent=true의 I:N4은 저장 파일을 만들면서 표시 중인 노트를 유지했습니다. clipboard=true의 S:C01/C02/C03은 전용 화면의 저자 본문을 new/daily/unique에 저장하고 있습니다. 동시에 content도 전달한 S:C04에서는 clipboard 본문이 저장되었습니다. 이 한 세트의 우선 결과를 모든 단말기의 모든 형식으로 확장할 수 없습니다.

본문과 속성을 병합한 예시

S:M03은 문서화된 new·append·content을 기존 저자 노트에 전달했습니다. 실제 저장 파일에서는 제목이 추가 측의 값이 되고, 기존 kept는 유지되며, tags는 양쪽을 모두 포함하고, 본문은 끝에 추가되었습니다. 다음은 121bytes의 저장 Markdown 전체 텍스트입니다. 이 한 세트를 제외한 타입·중복 키·복잡한 YAML은 시도하지 않았습니다.

---
title: 追加の題
kept: 元の値
tags:
  - 初期
  - 追加
source: URI
---

元の本文。

追加の本文。

S:M03의 원본 Markdown을 다운로드

open의 추가 플래그는 이번에 효과를 확정할 수 없었습니다.공식 open절에는 append/prepend가 있지만, content은 같은 절에 열거되어 있지 않습니다. 탐색적으로 content도 전달한 S:M01/M02에서는 노트를 열어 바이트가 변하지 않았습니다. 미기재된 본문 운반을 전제로 “공식대로 전달했는데 결함”이라고 판단할 수 없습니다. 본문 추가 확인된 예는 new+append을 참조하십시오.

절대 path의 신규 생성은 성공 사례에 포함하지 않습니다

공식 new 절은 globally absolute path을 설명하고 있습니다. S:N02는 경쟁하는 vault/name/file에서도 전달된 입력으로 파일을 만들 수 없었습니다. 별도 계획 T:P1은 등록된 저자 Vault 내의 미작성 파일에 path와 content만을 전달했습니다. 그럼에도 불구하고 6초 후에 대상 파일이 없었고, 화면은 인덱스 그대로였습니다. 이는 하나의 Linux 앱 수신 경로에 대한 기록이며, 원인이나 전체 환경의 오류를 단정하는 결과가 아닙니다.

제목·블록으로 이동

제목은 file 값에 ノート名#見出し을 넣고, 블록은 ノート名#^block-id를 넣어 그 값을 인코딩합니다. I:O5은 저자 노트의 제목으로 이동한 것을 확인했습니다. 블록 ID에는 영문자·숫자·대시만 사용합니다(고정 Internal links 원문의 문자 규칙).

ノート/長い対象 メモ#^target-01
↓ fileの値をエンコード
%E3%83%8E%E3%83%BC%E3%83%88%2F%E9%95%B7%E3%81%84%E5%AF%BE%E8%B1%A1%20%E3%83%A1%E3%83%A2%23%5Etarget-01

첫 번째 S:O01은 일본어가 포함된 ^著者block이라는 저자 샘플이며, 이동 위치를 나타내는 유효한 증거를 얻지 못했습니다. 제품의 실패를 계산하지 않고, 별도의 Vault의 긴 노트에 유효한 ^target-01을 준비한 T:B1를 추가했습니다. 다른 인덱스 노트에서 URI를 전달하면 대상 노트가 열리고 화면 밖에 있던 단락이 표시 범위로 이동했습니다.

실제 읽기에서는 대상 단락의 top이 1905.65625px부터 467.59375px(표시 높이 1000px)이며, scrollTop은 1438이었습니다. 원본 2Markdown은 bytes와 SHA256가 불변입니다. 사전 위치·별도 노트의 기준·이동 후를 세 개의 화면에 남겨두고 있습니다.

## 対象の節

ブロック移動を確認する著者用本文です。 ^target-01

T:B1의 긴 원본 Markdown 전체를 다운로드

축약형 obsidian://vault/Vault名/ノート名과 obsidian:///絶対パス은 open에 대한 생략 표기법입니다. S:H01/H02은 각각 저자 노트를 표시했습니다. 값의 일본어·공백·구문 처리는 일반 매개변수와 동일하게 확인합니다.

일일 노트와 고유명 노트는 플러그인 및 저장 대상도 확인합니다

daily에는 Daily notes, unique에는 Unique note creator 코어 플러그인이 필요하다고 공식적으로 명시되어 있습니다. 첫 번째 I:D1/U1는 파일을 생성할 수 없었으며, 실패 기록을 그대로 남겼습니다. 이후의 별도 계획에서는 실제 저자용 저장 폴더를 준비하고, 색인에서 일일 파일을 생성하는 I:D2와 고유명 파일을 생성하는 I:U2를 관찰했습니다. 이 전제 변경만을 실패의 원인으로 단정하고 있지 않습니다.

obsidian://daily?vault=Practice&content=Daily%20entry
obsidian://unique?vault=Practice&content=Unique%20entry

고정된 공식 본문은 daily이 new과 동일한 파라미터를 받는다고 설명하고 있습니다. 하지만 S:D01/D02/D03에서는 name·file·path 각각의 지정 대상을 할 수 없으며, Daily notes 설정의 日次/2026-09-30.md에 추가되었습니다. 이름 지정 신규 노트는 new이며, 날짜 노트 입력은 daily으로 구분하여 사용하고, 최종 저장 대상을 실제 파일로 확인하는 것이 이 관측에서 안내할 수 있는 범위입니다.

S:D04은 silent에서 인덱스 표시를 유지하면서 일일 데이터를 저장했습니다. S:D05는 append와 overwrite를 모두 지정하여 원문을 유지했지만, 플래그가 없는 daily도 추가했기 때문에 append 단독 기여와 overwrite만의 동작은 확인되지 않았습니다.

표시 대상 선택 paneType

open/new/daily/unique에서, paneType=tab, split, window의 12 입력을 각각 기록했습니다(S:P01〜P12). 공식적으로 window는 데스크톱 전용입니다. 실제 메인 탭, 탭 그룹, 별도의 팝업 화면을 읽어 스크린샷을 남기고 있습니다. 닫힌 화면의 메타데이터가 남아 있기 때문에, 전역의 leaf 총수만으로 성공 여부를 판단하지 않습니다.

x-success·x-error은 반송지에서 수신을 확인합니다

공식은 x-success으로의 반송에 name(확장자 없음), url(obsidian URI), 데스크톱용 file(file URI)를 포함한다고 설명하고 있습니다. 저장 성공과 호출자가 반송을 받은 것은 별개입니다. S:X01/X02/X03는 노트 저장을 관측했지만, 저자가 소유한 localhost HTTP 수신 대상에는 수신이 없었습니다. 준비한 브라우저 어댑터도 실행되지 않았으며, OS·호출자 핸드오프까지 확인하지 못했습니다.

Hook용 hook-get-address은 x-success이 있으면 그곳에 반환하고, 생략하면 현재 노트의 Markdown 링크를 clipboard에 복사하면 공식적으로 명시되어 있습니다. S:K01에서는 저자 clipboard의 번병값이 변하지 않았으며, S:X04에서도 반환이 없었습니다. Hook 본체는 실행하고 있지 않습니다. S:X05의 존재하지 않음 Vault에서는 실제 “Vault not found” 대화 상자를 표시했지만, x-error의 수신은 없습니다. 오류 표시를 반송 성공 및 전체 콜백 제품 고장으로 교체하지 않습니다.

자주 묻는 질문

obsidian://와 일반 웹 URL은 무엇이 다릅니까?

obsidian://은 Obsidian이 수신하는 고유 URI입니다. 웹 페이지를 가져오는 URL이 아닙니다. 터미널 측의 연관과 Obsidian으로 넘어간 후의 노트 작업은 별도로 확인합니다. 이 기사 실측은 Linux 앱의 URI를 받은 후입니다.

일본어, 공백, #는 어떻게 씁니까?

값마다 URI를 인코딩합니다. 공백은 %20, #는 %23, /는 %2F입니다. 제목·블록 지정 #도 file 값 안에서 인코딩합니다. 본문의 생 #를 남긴 저자 예에서는 # 이후가 저장되지 않았습니다.

기존 노트에 추가하려면 open을 사용합니까?

본문 추가에 확인된 예는 new에 file, content, append=true를 전달한 것입니다. open 절에도 append/prepend에 대한 기재가 있지만, content은 같은 절에 열거되지 않았으며, 이 검증의 탐색적 입력에서는 본문이 변하지 않았습니다.

daily에 file이나 name를 전달하면 저장처를 변경할 수 있습니까?

고정된 공식 본문은 daily이 new과 동일한 파라미터를 받는다고 기재하고 있습니다. 한편, 이번 Linux 입력에서는 name·file·path의 지정 대상을 만들지 않고 Daily notes 설정의 날짜 노트에 추가했습니다. 저장 대상은 실제 설정과 파일에서 확인해 주세요.

x-success을 지정하면 반송까지 확인되었습니까?

아니요. new·daily·unique에서는 저장을 관측한 입력도 있지만, 소유하고 있는 HTTP 반송 대상에는 수신이 없었습니다. 앱에 대한 URI 수신 및 CLI 종료 0는 호출자에게 반환된 증거가 되지 않습니다. Hook, OS 핸드오프, 실제 호출 원본 앱은 확인되지 않았습니다.

iPhone도 같은 결과인가요?

이 기사에서는 물리 iPhone, iOS 단축키, SimpleMemo를 실행하고 있지 않습니다. Linux Obsidian1.13.7의 저자용 Vault만의 결과입니다. iPhone 고유의 증상은 기존의 단축키 대응 가이드를 참고하시고, 단말기에서 확인하십시오.
