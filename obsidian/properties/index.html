プロパティは、ノート先頭のYAMLを扱うUI

Propertiesで入力した名前と値は、ノート先頭のfrontmatterに保存されます。例えばstatus: 進行中を揃えておくと、DataviewのWHERE条件で「進行中」のノートを選べます。本文に書いた普通の文章とは扱いが違います。

まず、何を比較したいかを決めて少数の項目を使います。この例では、状態をstatus、優先度をpriority、完了をdone、期限をdue、分類をtagsとしました。著者作成の架空記録で、利用者のデータではありません。

GUIで入力保存YAMLTABLE・LIST変更と結果練習用原本

名前、型、値を順に決める

  1. ノートを開き、Add propertyまたは公式のCtrl/Cmd+;から項目を追加します。実機例ではAdd propertyをクリックしてpriorityを追加しました。
  2. 項目名の横の型アイコンを押し、Property typeを開いて型を選びます。実機ではNumberを選び、3を入力して保存しました。
  3. 既存のstatusはTextを選び、「未着手」から「進行中」へ変更しました。チェック、Date入力、Tags入力も実際のUIで変更し、保存YAMLへ反映されることを確認しました。
  4. Tagsは文字を入力するだけで終わらせず、フォーカスした入力でEnterを押して確定します。今回の補助操作も一度確定できず、再度Enterとフォーカス移動で保存を確認しました。
名前この例の型と値実機で行ったこと
statusText / 進行中Text選択、未着手→進行中
priorityNumber / 3項目追加、Number選択、3入力
doneCheckbox / trueまたはfalsefalse→true→false、最後にtrue
dueDate / 2026-10-0310月1日→10月3日
tagsTags / 検証、プロパティプロパティを追加し確定

公式資料では、同じ名前の型は保管庫全体で共通です。別の意味の値へ同じ名前を使い回す前に、型と用途を確認します。ListやDate & timeなど、ここで扱っていない型は今回の動作確認に含みません。

# 調査A

著者が検証用に作成した架空の記録です。顧客データではありません。

公式資料では、frontmatterはファイル先頭を---で囲み、名前: 値のYAML形式で記述します。プロパティ名は一つのノート内で重複させません。この例の数値3とチェックtrueは、それぞれ数値とbooleanとして保存されています。Dateはこの値を保存した確認であり、あらゆる日付形式や入力の正しさを検証した結果ではありません。

同じ値をTABLEとLISTの条件にする

実機では、公式Dataview安定リリースの三ファイルを隔離した保管庫へ事前にコピーし、実際の信頼確認でプラグインを有効にしました。これはBrowse/Installの画面操作を検証した記録ではありません。プラグインは第三者コードを実行するため、配布元と利用条件を確認して選びます。

リリース名は0.5.70、配布manifestと実画面の表示版は0.5.68でした。必要なObsidian最小版はmanifest上0.13.11、実際に動かしたObsidianは1.13.7です。DataviewJS設定はfalseで、次のDQLを実際のエディターへ入力し、Reading viewで表示しました。

フォルダー名記録、項目名、状態文字列を一致させます。調査A/Bは進行中、Cは完了です。

# Properties接続検証

著者が作成した架空の3件だけを表示します。

## 進行中の表

```dataview
TABLE status AS "状態", priority AS "優先度", done AS "完了", due AS "期限"
FROM "記録"
WHERE status = "進行中"
SORT file.name ASC
```

## 未完了の一覧

```dataview
LIST
FROM "記録"
WHERE done = false
SORT file.name ASC
```

## 保留の該当なし

```dataview
LIST
FROM "記録"
WHERE status = "保留"
SORT file.name ASC
```

TABLEは進行中の二件を表へ、LISTはdoneがfalseのノートを一覧へ出します。最後のLISTは保留のノートを選び、対象がない場合の実表示も確認しました。DQLの全機能、インラインフィールド、DataviewJSはここで試していません。

完了チェックを変えると、未完了一覧が2件から1件へ

変更前のTABLE二件は実Reading DOMで確認しましたが、そのときのPNGは表より下へスクロールしていました。上の変更後PNGでは表二件と未完了一覧一件が見えます。表示位置や画像を作り直して置き換えていません。

ファイル一覧から調査Aと一覧ノートを再度開き、保存MarkdownのbytesとSHA256が同じことも確認しました。同じアプリ起動中の再表示で、アプリ全体の再起動や別端末の確認ではありません。今回の条件で値が表示へ反映された結果で、作業速度や生産性が上がるという因果は計測していません。

よくある質問

Obsidianのプロパティとfrontmatterは別のデータですか？
プロパティはノートの構造化された値を操作するUIで、値はファイル先頭のYAML frontmatterとして保存されます。今回の実機ではstatus、tags、done、due、priorityをGUIで操作し、保存されたMarkdownの値と照合しました。
プロパティの型はノートごとに設定しますか？
公式資料では、同じプロパティ名には保管庫全体で同じ型が使われます。名前の横の型アイコンからProperty typeを開いて型を選びます。今回の実機ではpriorityにNumberを選んで3を保存しました。すべての型や日付入力の検証を行ったわけではありません。
Dataviewでプロパティを一覧にする基本形は？
dataviewコードブロックにTABLEまたはLIST、FROMとWHEREを書きます。今回の三件では、FROM "記録"でフォルダーを対象にし、status = "進行中"のTABLEは二件、done = falseのLISTは完了チェック変更前に二件、変更後に一件でした。
ダウンロードした例はどの状態ですか？
GUIで調査Aのdoneをtrueに変更した後の保存原本です。記録フォルダー内に調査A・B・C、同じ保管庫の直下に一覧.mdを置く構成を示しています。今回の実機結果はTABLE二件、未完了LISTは調査C一件、保留は該当なしでした。読者の保管庫への取り込みや別環境の動作は未検証です。

公式資料と、この実機確認の範囲

GUI確認のUTC日は2026年9月30日、日本時間は2026年10月1日です。実画面、保存原本、固定ソース、補助の訂正、終了記録の不足は検証記録にまとめます。終了Closeは送信しましたが、記録器の終了順によりObsidianの終了コードは未記録です。

  • 公式説明：Propertiesの保存形式・型の共有、Dataviewのfrontmatter/QUERY/TABLE/LIST/WHEREを固定資料で確認。
