Obsidian / URIスキーム

公式仕様の参照と著者作成Linuxサンプル · 確認日2026年9月30日

obsidian:// URIスキーム完全ガイド — 全アクションと落とし穴

obsidian:// は、別のアプリやランチャーからObsidianのノートを開く・作る・検索するためのURIです。まず用途に合うアクションを選び、各値をURIエンコードします。既存本文への追記は、今回保存まで確認した new＋append=true の例から始められます。

本文を入力してURIをコピーする場合は、構文と固定Linux観測を分ける無料URIジェネレーターも参照してください。

ここでは公式本文の6アクション一覧にHook用の別節を加えた7節・38のアクション別パラメータ項目を整理し、Linux Obsidian1.13.7に渡した58件の記録を対応づけます。結果が得られなかった入力も掲載し、仕様の記述と実際の保存先を分けて読めるようにしています。

確認した範囲：著者用のローカルVault、公式Linuxアプリ1.13.7、英語UI、隔離したXorg画面です。実行ファイルへURIを渡してアプリが受け取った後の操作を確認しました。ブラウザのリンクからのOS関連付け、物理iPhone、iOSショートカット、SimpleMemo、同期は未検証です。58件は全値・全組合せ・全端末の保証を意味しません。

入力してURLを作りたい場合は既存のURIジェネレーターへ。iPhoneで起動しない・ショートカットが止まる症状はショートカット対処ガイドへ進んでください。このページは標準URIの意味と入力結果を調べる参照用です。

本文の#も、見出しの#も、値としてエンコードする

公式本文は空白を %20、スラッシュを %2F にするよう説明しています。日本語、改行、# & ? + % / = が混在する著者本文を値ごとに変換したI:N1では、保存Markdownが入力と一致しました。URL全体を一度に変換すると区切りも変わるので、vault、file、content の値を個別に扱います。

const vault = encodeURIComponent('練習Vault');
const file = encodeURIComponent('ノート/日本語 メモ');
const content = encodeURIComponent('本文 # & ? + % / =\n二行目');
const uri = `obsidian://new?vault=${vault}&file=${file}&content=${content}`;

上は組み立て方の説明用コードです。端末上のノートへ保存する実行は含みません。練習Vaultと保存先を自分の名前に置き換えます。

新規作成・追記・上書きを分ける

new の name は新規ノート名で、保存先をObsidianの「Default location for new notes」に委ねます。file はVaultルートからの保存先を含む値です。公式は file が name より優先すると記載し、I:N2でもfile指定先へ保存しました。S:N01ではnameのみで、事前設定した既定フォルダに保存しています。

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Hello%20World

既存本文を残して追加する場合は append=true を渡します。I:N3では既存本文を保持して追加しました。overwrite=true は既存本文を置き換える指定で、I:N5に別の原文/保存後の記録があります。公式は「appendが設定されていない場合だけoverwrite」と記載し、S:N03の両指定では追記になりました。日常の本文追加に上書き指定を混ぜる必要はありません。

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Another%20line&append=true

silent=true のI:N4は、保存ファイルを作りながら表示中のノートを維持しました。clipboard=true のS:C01/C02/C03は、専用画面の著者本文をnew/daily/uniqueに保存しています。同時にcontentも渡したS:C04ではclipboard本文が保存されました。この一組の優先結果を、全端末のすべての形式へ広げることはできません。

絶対pathの新規作成は成功例に含めない

公式new節はglobally absolute pathを説明しています。S:N02は競合するvault/name/fileも渡した入力でファイルができませんでした。別計画T:P1は登録済み著者Vault内の未作成ファイルに、pathとcontentだけを渡しました。それでも6秒後に対象ファイルはなく、画面は索引のままでした。これは一つのLinuxアプリ受け取り経路の記録であり、原因や全環境での不具合を断定する結果ではありません。

## 対象の節

ブロック移動を確認する著者用本文です。 ^target-01

T:B1の長い原Markdown全文をダウンロード

短縮形 obsidian://vault/Vault名/ノート名 と obsidian:///絶対パス はopenへの省略記法です。S:H01/H02はそれぞれ著者ノートを表示しました。値の日本語・空白・区切りの扱いは通常のパラメータ同様に確認します。

日次ノート・固有名ノートはプラグインと保存先も確認する

daily にはDaily notes、unique にはUnique note creatorコアプラグインが必要と公式に記載されています。初回I:D1/U1はファイルを作成できず、失敗記録をそのまま残しました。後の別計画では実在する著者用保存フォルダを準備し、索引から日次ファイルを作成するI:D2、固有名ファイルを作成するI:U2を観測しました。この前提変更だけを失敗の原因と断定してはいません。

obsidian://daily?vault=Practice&content=Daily%20entry
obsidian://unique?vault=Practice&content=Unique%20entry

固定した公式本文はdailyがnewと同じパラメータを受け取ると説明しています。しかしS:D01/D02/D03ではname・file・pathの各指定先はできず、Daily notes設定の 日次/2026-09-30.md に追加されました。名前指定の新規ノートはnew、日付ノートへの入力はdailyとして使い分け、最終保存先を実際のファイルで確認するのが、この観測から案内できる範囲です。

S:D04はsilentで索引表示を維持しながら日次に保存しました。S:D05はappendとoverwriteを両方指定して元本文を保持しましたが、フラグのないdailyも追記したため、append単独の寄与やoverwriteだけの動作は未確認です。

表示先を選ぶpaneType

open/new/daily/uniqueで、paneType=tab、split、window の12入力をそれぞれ記録しました（S:P01〜P12）。公式でwindowはDesktop onlyです。実際のメインタブ、タブグループ、別ポップアウト画面を読み取り、スクリーンショットを残しています。閉じた画面のメタデータが残るため、グローバルなleaf総数だけで成否は判定していません。

x-success・x-errorは返送先で受信を確認する

公式はx-successへの返送に name（拡張子なし）、url（obsidian URI）、デスクトップの file（file URI）を含むと説明しています。保存の成功と、呼び出し元が返送を受け取ったことは別です。S:X01/X02/X03はノートの保存を観測しましたが、著者が所有するlocalhost HTTP受信先には受信がありませんでした。準備したBROWSERアダプターも実行されておらず、OS・呼び出し元ハンドオフまで確認できていません。

Hook用 hook-get-address はx-successがあればそこに返し、省略すれば現在ノートのMarkdownリンクをclipboardにコピーすると公式に記載されています。S:K01では著者clipboardの番兵値が変わらず、S:X04でも返送はありませんでした。Hook本体は実行していません。S:X05の不存在Vaultでは実際の「Vault not found」ダイアログを表示しましたが、x-errorの受信はありません。エラー表示を、返送成功や全callbackの製品障害に置き換えません。

38項目の入力と実結果を対応づける

38/38は「各アクション別パラメータを含む入力記録がある」という数です。「仕様の効果がすべて成功した」という数ではありません。openの追加フラグ、newの絶対path、dailyの指定先、両フラグの寄与、Hook/callbackには不足が残ります。Iは最初の19件、Sは追加37件、Tは有効ブロック・競合なしpathの2件です。各IDから元のJSONに進めます。

よくある質問

obsidian:// と普通のWeb URLは何が違いますか？

obsidian:// はObsidianが受け取る独自URIです。Webページを取得するURLではありません。端末側の関連付けと、Obsidianに渡った後のノート操作は別々に確認します。この記事の実測はLinuxアプリのURI受け取り後です。

日本語、空白、#はどう書きますか？

値ごとにURIエンコードします。空白は%20、#は%23、/は%2Fです。見出し・ブロック指定の#もfile値の中でエンコードします。本文の生の#を残した著者例では、#以降が保存されませんでした。

既存ノートへ追記するにはopenを使いますか？

本文追記の確認済み例はnewにfile、content、append=trueを渡したものです。open節にもappend/prependの記載がありますが、contentは同節に列挙されておらず、この検証の探索的入力では本文は変わりませんでした。

dailyにfileやnameを渡せば保存先を変えられますか？

固定した公式本文はdailyがnewと同じパラメータを受け取ると記載しています。一方、今回のLinux入力ではname・file・pathの指定先を作らず、Daily notes設定の日付ノートに追加しました。保存先は実際の設定とファイルで確認してください。

x-successを指定すれば返送まで確認済みですか？

いいえ。new・daily・uniqueでは保存を観測した入力もありますが、所有するHTTP返送先には受信がありませんでした。アプリへのURI受領やCLI終了0は呼び出し元への返送証拠にはなりません。Hook、OSのハンドオフ、実際の呼び出し元アプリは未確認です。

iPhoneでも同じ結果ですか？

この記事では物理iPhone、iOSショートカット、SimpleMemoを実行していません。Linux Obsidian1.13.7の著者用Vaultだけの結果です。iPhone固有の症状は既存のショートカット対処ガイドを参照し、端末で確認してください。
