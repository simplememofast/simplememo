**件名**

```
さくナレ著者希望：スマホから送ったメモを落とさないための送信キュー設計（2000〜6000字）
```

**本文**

```
さくらのナレッジ編集部 御中

はじめまして。株式会社ユリカのSimpleMemo Developerと申します。
著者募集のページを拝見し、「さくナレ著者希望」としてご連絡しました。

■ 書きたいテーマ（案）
「送ったつもりが送れていない、をなくす ― モバイルアプリの送信キューと再試行の設計」

スマートフォンから短いテキストを送るだけの機能でも、電波が切れる、アプリが落ちる、
バックグラウンドに落とされる、といった条件が重なると簡単に取りこぼします。
しかも厄介なのは、失敗を握りつぶすと利用者は「送れた」と思い込んだまま内容を失う点です。

記事では次を扱う予定です。

・端末側に送信キュー（Outbox）を置く構成と、置かない構成の違い
・再試行の間隔と打ち切り条件をどう決めるか
・同じ内容が二重に届かないようにする冪等キーの持たせ方
・オフライン復帰時に順序が崩れたときの扱い
・「まだ送れていない」を利用者にどう見せるか（黙って消さない）
・中継APIを挟む場合の責務分離と、失敗をどちら側で保持するか

いずれも実装して運用している内容で、再現条件と失敗例を添えて書けます。

■ すでに公開している下地
・送信キュー（Outbox）の設計
　https://simplememofast.com/devlog/outbox-architecture
・中継APIの設計
　https://simplememofast.com/devlog/relay-api-design
・MITライセンスで公開している最小実装（ソース公開・登録不要で動きます）
　https://simplememofast.com/memo-inbox/

■ 立場の開示
筆者は自社のiOSアプリ「シンプルメモ」（https://apps.apple.com/jp/app/id6758438948 ）の
開発者です。募集ページに自社情報の告知も可とありましたが、記事の主題は設計の話にし、
自社アプリは実装例として必要な範囲でのみ触れる構成を考えています。
宣伝色が問題になる場合は、自社アプリへの言及を外して汎用のサンプル実装だけで書くこともできます。

■ 分量・進め方
3,500〜4,500字程度を想定しています。構成案を先にお送りして、テーマの可否や切り口を
ご相談させていただければと思います。ご不要であればその旨だけご返信いただければ追いません。

SimpleMemo Developer
株式会社ユリカ
support@simplememofast.com
https://simplememofast.com/
```
