## 1. 「代替ページ」バケット: 重複スラッシュを301で畳む

7件中5件が末尾に余分なスラッシュを持つURLだった:

```
/en/vs/note-to-self-mail//
/en/vs/notion//
/en/vs/obsidian//
/en/vs/apple-notes//
/en/vs/evernote//
```

Cloudflare Pages は余分なスラッシュを解決して **200 を返す**。つまりこれらは
canonical タグだけが支えている真の重複URLで、canonical は「ヒント」でしかないため
Googleは律儀に「代替ページ」として計上し続けていた。

`functions/_middleware.js` の最初のステップとして `/{2,}` → `/` の畳み込みを追加し、
**301で正規URLへ寄せた**。他の正規化（`?lang=`剥がし・`.html`剥がし・退役パス解決）より
前に走るので、`//en//vs//notion//?lang=ja` のような組み合わせでも1ホップで終わる。

内部リンクに `//` を含むものは **0件**（実測）。発生源は外部リンクとGoogleの
URL推測なので、コード側で新規発生を防ぐことはできない。301が唯一の恒久対策になる。

副次効果として、`/docs/` `/scripts/` `/tools/` の非公開判定も畳み込み後のパスで
行うようにした。従来は `//docs//seo/...` のようにスラッシュを1つ足すだけで
判定を迂回できた（Pagesは同じファイルを返す）。

## 2. `.html` 剥がしを全パスへ拡大（1ホップ化）

従来 `.html` の除去は `/blog/*.html` だけに限定していた。ルート直下や `/devlog/` の
`.html` は「Pagesが自前で308するから不要」という判断だったが、これには2つの問題があった:

1. **308はGSCの「ページにリダイレクトがあります」に計上される**（301と同じ扱い）
2. **`?lang=` との組み合わせで2ホップになる** — Middlewareが `?lang=` を剥がして301
   → その先でPagesが `.html` を308、という2段構えになっていた

`/404.html` を除く全ての `.html` を Middleware 側で処理するようにし、`?lang=` 剥がし・
退役パス解決と**同一の301にまとめた**。`index.html` はディレクトリ形式へ畳む
（`/vs/notion/index.html` → `/vs/notion/`。`/vs/notion/index` にすると404になる）。

**安全性の根拠**: 拡張子を落としても曖昧にならないのは「`X.html` と同名ディレクトリ `X/` が
共存しない」場合だけ。現状 **共存は0件** で、この不変条件は
`scripts/check-url-normalization.mjs` が全HTMLを走査して毎回検証する。

## 3. 404バケット7件目: `/cdn-cgi/l/email-protection` の発生源を断つ

07-25レポートでは「Cloudflareが前段で処理するためコード側で触れない／自然消滅を待つ」と
判断したが、これは **原因の取り違えだった**。

このURLは Cloudflare の **Email Address Obfuscation** が生成する。設定が有効だと、
CloudflareはHTML中の `mailto:` を検出して `href="/cdn-cgi/l/email-protection#<hex>"` に
書き換える。Googlebotは生HTMLからそのhrefを読んで辿り、404を受け取る——
これが7件目の正体である。実際サイトには `mailto:` が **13箇所** あった
（`faq` `legal` `contact` `privacy` `terms` `about` の日英計10ファイル）。

「サイトHTMLに `email-protection` リンクは0件」という前回の実測は正しいが、
それは**書き換えがCloudflare側で起きるため、リポジトリのHTMLには現れない**というだけだった。

対応: 13箇所すべてを Cloudflare 公式のオプトアウト `<!--email_off-->…<!--/email_off-->` で
囲んだ。これで書き換え自体が起きず、`/cdn-cgi/l/email-protection` へのリンクは生成されない。
表示・`mailto:` の動作は不変。

`scripts/check-internal-redirects.mjs` が未ラップの `mailto:` を**CIエラーとして検出**する
ので、将来コンタクト先を追加しても404が再発しない。

robots.txt の `Disallow: /cdn-cgi/` は従来どおり維持（発生源を断ったので不要になったが、
外すと他のCloudflare内部パスがクロール対象になるため触らない）。

## 4. 「クロール済み-インデックス未登録」: 実ページの内部リンク補強

67件のうち大半は `.html` / `?lang=` 変種と退役パスで、§1-2と07-25対応で解消済み。
残る「正規URLなのに未登録」の実ページについて内部被リンク数を実測し、
1〜2本しかない5ページに文脈上自然なリンクを追加した。

| ページ | 被リンク | 追加元 |
|---|---|---|
| `/siri/` | 2 → **4** | `/voice-input/`, `/fastest-voice-memo/` |
| `/blog/iphone-memo-katsuyou` | 1 → **3** | `/blog/iphone-memo-tips`, `/blog/iphone-memo-app-fast` |
| `/blog/business-memo-kakikata` | 1 → **3** | `/blog/work-efficiency-memo`, `/blog/business-memo-apps-2026` |
| `/blog/travel-planning-memo` | 1 → **3** | `/blog/memo-taking-tips`, `/use-cases/moving/` |
| `/vs/goodnotes/` | 2 → **3** | `/blog/digital-vs-handwritten-notes`, `/vs/apple-notes/` |

追加先は既存の `関連記事 / Related Articles` ブロック。サイト内には
**3種類のアンカー記法**（日英2スパン / JAスパンのみ / 素のテキスト）が混在しているため、
各ページの最後のアンカーを雛形として複製し、記法を合わせている。

これは「未登録＝品質シグナル」への万能薬ではない（Googleの判断はコンテンツ側にも依る）が、
被リンク1本のページは発見性・重要度シグナルの両面で不利なので、まず潰すべき下限だった。

## 5. 「robots.txt によりブロックされました」78件は残像

78件すべてが `?lang=` などのパラメータURLで、旧robots.txtの
パラメータDisallowでブロックされていたもの。この6行は **07-25に撤去済み**
（当時のレポート §3-2）。GSCの「不合格: 2026/07/25」はまさに撤去当日の判定で、
掲載URLの前回クロール日も大半が 05-15〜05-16 に固まっている。

現行 robots.txt に該当URLをブロックする記述は **無い**（実測）。
再検証を押せば消えるバケットなので、コード変更は行っていない。

## 6. Ahrefs の3問題

### 6-1. リダイレクトするリンクのあるページ（208ページ / 380リンク）

**内部リンク由来は0件であることを実証した。** 新規スクリプト
`scripts/check-internal-redirects.mjs` が全HTMLの内部 `href`/`src` を
**11,268本** 収集し、Middlewareの規則とファイルシステムの両方に通して解決した結果、
**すべてが直接200**（リダイレクト0・404が0）だった。

したがって380本はすべて**外部リンク**で、内訳は Ahrefs のエクスポートを見るかぎり:

- **App Storeリンク**（`https://apps.apple.com/{jp,us}/app/id6758438948?ct=…`）が大多数。
  Apple はスラッグ無しのID形式を正規形（`/app/{slug}/id{id}`）へ301する
- **DOIリンク**（`https://doi.org/…`）— DOIリゾルバは仕様上必ず302する
- 少数の第三者サイト（`francescocirillo.com`, `fellow.app`, `opensignal.com`,
  `upwork.com`, `jpwa.or.jp`, 競合アプリのApp Storeページ）

**いずれも本PRでは変更していない。理由**:

- **App Store**: `/{cc}/app/id{id}` は Apple公式の**アプリ名変更に強い**形式。
  スラッグを埋め込むと、アプリ名を変えるたびに全1,012箇所が再び301（最悪404）になる。
  リポジトリ内の記録では旧スラッグ `captio-style-simple-memo` が見つかるが、
  その後サイト・ASO側の名称は変わっており、**現在の正規スラッグは未確認**。
  本セッションの実行環境は `apps.apple.com` への外部通信が
  ネットワークポリシーで遮断されているため検証できなかった。
  **未検証のスラッグに主要CTA 1,012本を賭けるのは割に合わない**ため据え置いた
- **DOI**: 302は永続識別子の仕様そのもの。解決先URLに置き換えるのは学術リンクとして退行
- **外部リンクの301はSEO上の実害がない**（PageRankの減衰は2016年に廃止済み、
  クロールバジェットも自ドメインの話）。Ahrefsのスコア上の指摘であって順位要因ではない

オーナーが解消したい場合の検証コマンドを残しておく（要ネットワーク）:

```sh
curl -sI -A "Mozilla/5.0" "https://apps.apple.com/jp/app/id6758438948" | grep -i '^location'
curl -sI -A "Mozilla/5.0" "https://apps.apple.com/us/app/id6758438948" | grep -i '^location'
```

返ってきた `location` のスラッグが現行のもの。置換する場合も、**アプリ名変更のたびに
再発する運用コスト**を織り込んで判断すること。

### 6-2. 3XXリダイレクト（3件）

`http://simplememofast.com/`、`http://www.simplememofast.com/`、
`https://www.simplememofast.com/` → `https://simplememofast.com/`。
**HTTPS化とwww正規化そのもの**であり、あるべき姿。修正対象ではない。
内部リンク数は3件とも0（`check-internal-redirects.mjs` で確認済み）。

### 6-3. メタディスクリプションが短すぎます（59件）

Ahrefsの閾値は **100文字未満**（レポートの最大値が98文字だったことから逆算）。
本対応では余裕を見て **110文字以上** を基準にし、全ページを再監査して
**90ページ**を書き換えた（Ahrefsの59件はクロール範囲の差）。

方針は **前寄せ（front-loading）**:

- 冒頭 **約70文字で意味が完結**するように書く — 日本語のSERPスニペットは
  デスクトップで概ね80文字前後、モバイルでは50文字前後で切られるため
- そのうえで **110〜135文字**まで、H2から拾った具体語（手法名・件数・アプリ名）で伸ばす
  — Googleがクエリに応じてスニペットを組み立てる材料が増える

`og:description` は原則据え置き（SNSカードは短い方が読みやすく、Ahrefsの指摘対象でもない）。
例外は `en/vs/notion-vs-obsidian/` で、description / og / twitter / JSON-LD の
4箇所が同一文字列だったため4箇所とも更新した。

#### 付随して発見した `seo-check.js` のバグ2件

1. **アポストロフィで値が切れていた** — `content=["']([^"']*)["']` は
   `content="…memos aren't. Set up…"` を **35文字**と誤測定していた（実際は141文字）。
   英語ディスクリプションの多くが該当し、**160文字超チェックを素通り**していた
2. 1を素朴に `[\s\S]*?` へ広げると**逆方向に過剰マッチ**した — 属性順が
   `content` 先行の15ページ（`<meta content="…" name="description"/>`）で、
   より手前の `<meta content="…">` に食いつき **1,400文字超**と誤検出した

最終的に、`<meta>` タグ単位で属性をパースする `getMetaContent()` に置き換えた。
属性順・引用符種別のどちらにも依存しない。
併せて **110文字未満を警告する条件を追加**し、今回の是正がCIで維持されるようにした。

## 7. 追加した検証スクリプト（CIゲート）

`.github/workflows/seo-check.yml` に2本追加。どちらも **exit 1 でCIを落とす**。

### `scripts/check-url-normalization.mjs`（172アサーション）

`functions/_middleware.js` を data: URL 経由でESMとして読み込み、
**GSCが実際に報告したURL形状**を投入して検証する:

- 正しいステータス（301 / 410 / 404 / パススルー）と正しい遷移先
- **1ホップであること** — 301の遷移先をもう一度通して、再度リダイレクトしないことを確認
- `X.html` と `X/` が共存しないという構造的不変条件

### `scripts/check-internal-redirects.mjs`（11,268リンク）

全内部リンクをMiddleware＋静的解決の両方に通し、直接200でないものを落とす。
未ラップの `mailto:`（§3）も同時に検出する。

## 8. sitemap の lastmod を更新していない理由

`scripts/generate_sitemap.py` は `MECHANICAL_SWEEP_THRESHOLD = 40` を持ち、
40ページ超を一度に触るコミットを「機械的な一括変更」として lastmod 算出から除外する
（コメントに `meta cleanups` と明記されている）。本PRのディスクリプション書き換えは
90ページの一括変更で、まさにこの定義に当てはまる。

07-25レポートと同じ方針 — **コンテンツ更新を偽装しない** — に従い、
sitemapは再生成していない。
