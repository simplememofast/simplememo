# 公開窓口へ送る掲載依頼の下書き（2026-09-19）

## この文書の位置づけ

`docs/seo/directory-registration-2026-09.md` §5.6 で**公開窓口の実在を確認できた媒体**について、
**そのまま送れる状態の本文**を媒体ごとに個別に書いたもの。

**まだ1通も送っていない。** 送信には人の承認が要る（→「送信前の確認事項」）。

守っている条件：

- **一斉送信ではない。** 5媒体すべて本文が違う。使い回している段落は署名だけ。
- **リンクを要求しない。** どの本文にも「リンクを貼ってください」に相当する依頼は書かない。
- **確認できない数字を書かない。** 起動時間は測定条件と全試行を公開しているページを添え、
  「第三者検証は受けていない」と本文に明記する。
- **E2EEと書かない。** 端末内はAES-GCM-256、送信はSMTPなのでE2EEではない、と本文で先に断る。
- **Captioとの関係を誇張しない。** 「着想を得た」までにとどめ、公認・後継・承認とは書かない。
- **原稿の事前確認を求めない。** 各媒体の編集権に踏み込まない。
- **有料PR記事・有料掲載枠は依頼しない。**

## 送信前の確認事項

1. 送信者名は「安宅 基（株式会社ユリカ）」、返信先は `support@simplememofast.com` を使う。
2. 送る直前に App Store のアプリ名・価格・対応OSを `data/site-constants.json` と突き合わせる。
　 価格は機械検証できていない項目なので、古くなっていないか目視で確認する。
3. 1媒体ずつ送る。同日中に5通まとめて送らない。
4. 返信不要と明記している媒体（Macお宝鑑定団）には催促しない。
5. 送信したら `growth/plans/ja-editorial-links-2026-09-18.json` の該当候補の
   `status` / `sent_at` / `verification` を更新する。掲載を確認できるまで
   `verification` は `listing_not_confirmed` のままにする。

- 方針：題材は「iOSアプリから外部のMarkdownファイルへ安全に追記する」という実装の話にし、

**お問い合わせ内容**

```
gihyo.jp 編集部様

株式会社ユリカの安宅と申します。記事寄稿のご相談です。

■ 提案する題材
「メモを1行追記するだけの処理が、なぜ失敗するのか ― iOSからMarkdownファイルへ安全に追記する」

短いメモを外部のMarkdownファイル（Obsidianの保管庫など）へ追記する処理は、一見すると
ファイルを開いて末尾に書くだけです。実際には次の条件で壊れます。

・保存先フォルダのセキュリティスコープ付きブックマークが失効している
・ユーザーが保管庫ごと別の場所へ移動した
・同じファイルを別プロセスが開いている
・送信中にアプリが落ち、再試行で同じ行が二重に入る
・オフラインで送信キューに積まれたまま復帰時の順序が崩れる

これらを「失敗として見せる」か「黙って握りつぶす」かで、利用者が失う情報量が変わります。
記事では、再現条件・失敗時の表示・再試行と重複防止の設計を、動くサンプルとともに説明します。
```
