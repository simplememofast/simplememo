## 2. 実装したもの（2026-09-03）

**6件。どれも「率を上げる」ではなく「止まらない・届く・繰り返さない」側。**

### D1 — 連続出荷／無介入出荷（`scripts/autopilot-runs.mjs`）

稼働の隣に、**切れる指標を2本**並べた。定義は `data/kpi-definitions.json` に置いてある
（`shipping_day_streak` / `hands_off_shipping_streak`）。

- **連続出荷** … 出荷のある日だけが続く。停止・失敗・スキップ・行の無い日はすべて切る
- **無介入出荷** … 出荷があり、かつその日のどの行にも介入が無い日の連続

**無介入出荷に「出荷があること」を入れてあるのが要点。**入れないと、
**壊れたまま誰も直しに行かない日**が無介入として積み上がる（08-30・08-31 がその形）。
触っていないのは自律していたからではない。**放置で伸びる自律指標は作らない。**

`activeStreaks` の定義は1文字も変えていない。共通の `streakWalk()` に移して
3本が同じ歩き方をするようにしただけで、既存の8ケースはそのまま通る。

### A3 — 経路の沈黙と全停止を起票する（`scripts/autopilot-act.mjs` D5b）

- `act-route-silent-<route>` … その経路が**3日ぶん出荷していない**
- `act-shipping-outage` … **どの経路も2日以上出荷していない**

閾値を3日にしたのは、2日だと「副系が先に当日ロックを取った」だけで鳴るから。
それはこの設計では正常系にある。3日目からは「譲り続けている」ではなく「出せていない」と読む。

**実物で当ててある。**台帳を 08-29 で打ち切って導出を回すと:

```
  act-route-silent-actions :: actions が 3日ぶん出荷していない（08-27〜08-29・最後の出荷 08-26）
```

当時これが台帳に載ったのは 08-31 23:27。**2日早く、機械が言えるようになった。**
08-31 で打ち切ると `act-shipping-outage`（3日連続で出荷なし）も立つ。

**なぜ既存の監視で拾えなかったか**も書いておく。`cron-health` は
`conclusion=failure` だけを集計し、`skipped_gate` は *success* で終わる。
`autopilot-health` は status JSON の日付だけを見るが、**副系が出荷すれば当日分は更新される。**
どちらの監視も、経路単位では何も見ていなかった。

### C1 — 取り残しの自動再投入（`apply-orphan-ledger`）

`ledger_only` の取り残しに `auto` を付けた。**手順は 2026-08-28 に4段で書いてあり、
保留の条件は「まず日次runが実際に内訳を出すのを見る」だった。**
08-28 以降に立った7行すべてで `paths` が出ている（うち3行が `ledger_only: true`）ので、条件は満たされた。

手順は飛ばしていない:

1. `ledger_only === true` の行だけ（`false` と `null` は人が読む）
2. **追記型と状態型を分ける** —— `runs` / `cost` は run_id で冪等な `--append`、
   `status` は**写しを当てず台帳から再生成**、`actions` は**このエンジン自身の出力なので触らない**
   （古い写しを当てると閉じた行が開き直る）
3. **まず「本当に欠けているか」を見る**
4. 直接 main を触らない（PRはワークフローが作る）

**`AUTOPILOT_LOG.md` は追記型だが、対象に入れていない。**散文の差分は run_id のような
冪等な鍵を持たないので、「欠けているか」を機械が判定できない。書くのは人のまま。

**実物で確かめた結果、いま対象の1件は「何も欠けていない」。**
`claude/obsidian-auto-20260827` のブランチ側 `autopilot-runs.json` を取って照合すると、
**欠けている行は0件**（内容は別コミットで着地済み・取り残しの判定はSHAで行うため行だけが残る）。
**このハンドラはそういう日には1行も書かない。**走査が消えないことを、書く理由にしない。

あわせて `merge()` が導出値（`auto` / `touches`）を open な行に追従させるようにした。
しないと、内訳が取れずに `ledger_only: null` で先に立った行が、翌日 `true` になっても
古い判定のまま残る。**人が固定する口は `force_owner` で、そちらは上書きしない。**

### B1 — `owner_direct` を実在させる（`simplememo-api/src/owner-direct.ts`）

日報とは**別便**の単発メール。毎時 tick に相乗りし、
`emergency-stop.json` と `autopilot-actions-report.json`（どちらも公開・PIIなし・認証不要）を読む。

鳴る条件は3つ:

| 事象 | 期限 | 中身 |
|---|---:|---|
| `emergency_stop` | 1h | 全体停止／経路ごとの停止。**AIは解除できない** |
| `shipping_outage` | 24h | A3 が立てた「どの経路も出荷していない」 |
| `owner_blocked` | 24h | オーナー待ちが3日以上滞留している |

**なぜ日報に足さないか。** 日報には毎朝すべてが載る。未処理も実費も問い合わせも
緊急停止も同じ本文に等しく並ぶ。2026-08-25 に実測された壊れ方がそれで、
**12件中6件が解消済みのまま毎朝再送され、その日いちばん重要な1件がその中に埋もれていた。**
同じ器に足すと、足したものも埋まる。**届いたこと自体が信号になる便**を別に立てる。

**うるさくしない仕掛けが本体。**状態の指紋を KV に持ち、**指紋が変わったときだけ送る。**

- 同じ状態が続く間は送らない（日報が毎朝それを載せている）
- 悪化すれば指紋が変わるので送る（「1日1回まで」だと悪化しても翌日まで黙る）
- 解消したら `ok` を書き戻す。だから**同じ事象が再発したときは必ず鳴る**
- 送信に失敗したときは指紋を進めない（進めるとその事象は二度と鳴らない）
- `OWNER_DIRECT_DISABLED=true` で、デプロイなしで黙らせられる

**`emergency_stop` の経路を `gh_issue` から `owner_direct` へ移した。**
`within_hours` は前から1時間と書いてあったが、**Issue は誰かが見に行かないと届かない。**
規則に書いてあることと、届くことは別だった。

**過大に書かない。** `crisis`（個人情報事故・法的請求・重大障害・炎上）は
同じ `owner_direct` に割り当てられているが、**機械の信号が無いので経路ができても検知できない。**
人が気づいて止める側のまま。`escalation-rules.json` にもそう書いた。

### I — 主系のゲート判断を `.yml` の外へ出した

判断が**インライン bash と `scripts/autopilot-gate.mjs` に二重にあった。**
09-02 に `isAbandonedClaim()`（死んだ占有の引き継ぎ）を入れたとき、
**同じ判定を bash へ移す push が GitHub に拒否された** —— GH_PAT に
`workflow` scope が無いため（`act-gh-pat-scope-and-rotation` で意図的に足さないと
決めてある）。結果、Runbook を読む経路だけが新しい判定になり、**主系は旧判定のまま**だった。

前日のログは bash 版のパッチを「次の副系セッションがそのまま `git apply` すること」と
残していた。**当てなかった。**当てると二重実装が続き、その二重化こそが片方だけ直った原因だから。
中身（3条件・90分・読めなければ引き継がない）はそのまま `--preflight` に入っている。

- `.yml` の Gate から bash を消し、**checkout を先にして** `node scripts/autopilot-gate.mjs --preflight` を呼ぶ
- **権限は1ミリも広げていない。**以後この判定の修理は `scripts/` への普通のPRで主系にも届く
- 代償はスキップする日も checkout ぶんのランナー時間を使うこと。**払わない代わりに払っていたのは「片方だけ直る」ことだった**

**bash 版に無かった判定を1つ足した。** compare の 404 は「ブランチが無い」と
「リポジトリに届いていない（鍵が失効した）」の**両方で返る。**先に `/repos/{repo}` が
200 かを見て分ける。分けないと、権限を失った日に毎回「当日分は無い」と判定して走る。

実 API で5通り確かめた —— `claude/obsidian-auto-20260829`（事故の当日・差分0/PR0/7127分）
→ `run_takeover`、`…-20260902`（作業のある占有）→ `skip_branch_claimed`、
`…-20260903`（本日・作業中）→ `skip_branch_claimed`、存在しない当日ブランチ → `run`、
壊れたトークン／届かないリポジトリ → `fail_api`。

### 取り残しの根因 — 書く先を機械が拒否する

C1 は起きた後の始末で、根因は別にある。`outcome: shipped` も `pr: <番号>` も
**マージされるまで確定しない**ので、運転台帳を書くのはマージの後になる ——
順序としてはそれで正しい。**間違えやすいのは書く先で、マージ済みの当日ブランチに積むと
そのまま取り残しになる。**アクション台帳41件のうち17件が、この1つの形だった。

`scripts/autopilot-runs.mjs --append` が、マージ済みの当日ブランチ上では**書く前に落ちる。**

**祖先判定だけでは1回も発火しない。** auto-merge は `merge_method: 'squash'` なので、
マージ済みのブランチは main の祖先にならない。最初そう書いて、**効かないガードを作りかけた。**
`delete-branch.yml` と同じ二段構え（祖先か、変えたファイルが main と同内容か）に直し、
**サンドボックスで実際に squash マージを作って発火することを確かめた**
（マージ済み → 拒否 / `--allow-merged-branch` → 通る / 未マージの当日ブランチ → 通る /
当日ブランチでない → 通る）。

**判定できない日は止めない。** git が読めない環境で台帳が書けなくなるほうが害が大きい
（「落ちた回ほど記録されない」を再現しない）。

## 3. A1（実行枠）— 検証だけ先にやった

**問い:** 週次の実行枠（usage limit）の残量は、上限に当たる前に観測できるか。
できるなら、当たってから止まるのではなく、当たる前に縮退できる。

**答え: 状態は読める。残量（数値）は読めない。**

2026-09-02 22:12 UTC 時点で、CCR セッションの `get_session` が返した:

```
    rateLimitType   seven_day
    status          allowed_warning      ← **拒否される前の警告状態**
    resetsAt        1788822000（2026-09-08 08:00 JST）
    isUsingOverage  false
```

08-31 に主系・副系を同時に落としたときの台帳の記録は同じ形の `rejected` だった。
つまり **`allowed` → `allowed_warning` → `rejected` の3値が、事後ではなく事前に読める。**
そして**いま現に `allowed_warning` が立っている**（リセットまで約5日）。

**ただし、そのまま A1 の実装にはならない。3つ確かめていないことがある。**

1. **主系（GitHub Actions）からは、この形では読めない。** `get_session` は
   CCR セッションのメタデータで、Actions のランナーには相当するものが無い。
   実装するなら「副系が観測して台帳に書き、主系が台帳を読んで縮退する」形になる
   —— つまり**観測者と縮退する側が別**になる。
2. **スケジュール起動の副系セッションが `get_session` を持つか未確認。**
   `docs/routine-snapshot-setup.md` が同じ問題（MCP 接続子が Routine に引き継がれない）で
   2経路とも閉じている。ここも実測が要る。
3. **⑤「副系CCRの実費観測」は、これでは覆らない。**
   枠の状態と実費は別物で、台帳が書いている
   「セッション自身も自分のトークン費を知らない」は**そのまま残る。**
   `allowed_warning` は「あといくら使えるか」を言わない。**分類を動かす材料ではない。**

**次にやるなら**（オーナー判断が要らない範囲）: 副系が毎回 `get_session` を撃って
`rateLimitType` / `status` / `resetsAt` を台帳へ落とす。1週間ためれば
「`allowed_warning` が立ってから何時間で `rejected` になるか」が出る。
**縮退の実装はその後**——予告なしに縮退すると、出荷が減った理由が読めなくなる。

## 6. この文書の使い方

- **実装したものは「本番でまだ1回も鳴っていない。」** A3 は過去の台帳で当ててあるが、
  発火は明日以降の日次runが最初になる。B1 も同じ。
  **門を作った日ではなく、門を通って何かが動いた日に「動いた」と書く**
  （`autonomy-95-gap.md` の規律）。
- 数字はこの文書に手で書き足さない。`autopilot-runs.mjs` と `autonomy-gap.mjs` が正。
- 5節の3件に着手するときは、`autopilot-roadmap.md` の Phase のどこへ入れるかを先に決める。
