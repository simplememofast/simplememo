# 課金失敗回復の運用準備と採点条件

2026-09-13。所有者が返金と同様の「テストで運用準備を完了し、本番初回は自動監視」方式を
課金失敗回復にも指定した。対象はautomation-coverageのtask145、1業務だけ。

## 何を完了とするか

既存のアプリ内支払い情報更新案内とApple通知の保存経路を再利用し、案内の状態遷移・
検証済み通知の受信/保存/重複抑止・DB障害からの再送・本番監視の接続を検証する。
本番の自然な毎時実行と既存の継続監視まで確認した時点で、準備完了として計上する。
実行時刻、コミット、CI、配信、本番cronの結果は
[機械可読の完了証拠](../data/billing-recovery-readiness-20260913.json)に記録する。

実機でAppleの支払い情報を変更し、実際の決済問題が解消したという従来の完了条件からの
変更である。この違いを隠して「実回復済み」とは報告しない。他の未実装業務へ一般化しない。

| 指標 | この変更の直前 | この変更の後 |
|---|---:|---:|
| AI実行件数 / 実施中業務 | 161 / 177 | 162 / 178 |
| AI実行率 | 90.9604519774% | 91.0112359551% |
| AI実行件数 / 定義対象 | 161 / 192 | 162 / 192 |
| 総合自動化率 | 83.8541666667% | 84.375% |
| 全棚卸し / 定義対象 | 203 / 192 | 203 / 192 |

増分は約0.050784ポイント。誰も実施していなかった1業務を準備完了として実施中に移すため、
AI実行率の分子と分母は両方1増える。月次予算の別セッションによる160→161件の加点は
既に直前値に含み、本変更の成果へ付け替えない。
返金・課金回復の準備2件を実例必須として除いた参考値は160/176=90.909091%。
旧スコープ系列や配信済みプレス原稿は変えない。

## 実行した検証

- API PR318: Node22、単体2,922件・workerd/D1統合203件・typecheck。
  追加分は13件ずつ。HTTP受信から実D1を経て監視までを通す。署名境界だけはfixture。
- iOS PR503: SimpleMemoQA / SimpleMemo-FastUnit / SubscriptionLogicTests 26件。
  iPhone17 Pro Simulator、iOS26.5で、状態判定と実Settingsセルを通した
  請求再試行/猶予→不明→再試行→検証済み購読の表示/消去を確認。
  復元行と表示済み支払い行の意味も維持する。製品コードは変更していない。
- 既存の暗号テストはApple実署名TEST通知と公開rootの照合・改ざんを検査する。
  本番Apple TEST通知の配達確認は別の証拠として記録する。

初回iOSビルドの容量不足、続くテスト成功後の結果束保存失敗は私的な実行記録に保持。
キャッシュ整理後、同じビルドで26件を再実行し、終了コード0とxcresultの保存を確認した。
都合の悪い試行を削除して最初から成功したことにしない。

## 本番の監視と残る観測

既存の毎時cronに `billing_recovery_monitor` を追加した。
管理者認証を要求する `/admin/subscription-events/billing-recovery-monitor` と同じ読取処理を使う。
Productionの保持済み180日窓を集計し、
[Appleが定義する](https://developer.apple.com/documentation/appstoreservernotifications/subtype)
`DID_RENEW/BILLING_RECOVERY` の組み合わせだけを回復通知として数える。

通常更新、再購読、猶予期間終了、Sandboxは回復に代用しない。DB読取失敗は
503/counts=null、cron errors=1/eligible未設定にする。過去の回復通知が存在しても、
現在全顧客の課金問題が解消したことや、案内UIの効果を推定しない。
受信順や同じ商品という理由で別契約を結び付けず、回復率も算出しない。

本番初回回復は別の観測として保持する。保存された通知が0件でも過去に問題が無かったとは言えない。
Apple支払い画面での本人入力、実StoreKit通信によるforeground再取得、Apple Sandboxでの
実購入→請求失敗→回復、TestFlight実機の全工程は今回のfixtureテストでは実行していない。
既存のforeground再取得・世代番号による古い応答破棄はコードで確認した。
支払い・購入・権利・価格・返金方針を変更せず、TestFlightも追加配布しない。

既存の継続実行 `ai-90` が本番cronの鮮度2時間以内、errors=0、eligibleの数値を確認する。
欠測・失敗・古い観測は正常0件としない。初回の正の回復を検出したら、出所を照合して
私的な証拠を残し、準備分の再加点はしない。機密の取引ID、生通知、認証情報は公開しない。

## 戻し方

APIの監視追加を通常のrevert PRで戻す。元のApple通知保存・保持や顧客処理は維持する。
準備条件が失われた場合は未確認を記録し、この行の採点条件も再評価する。
