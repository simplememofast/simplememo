## 3. 見出し（確定稿ではない。候補と、選び方）

`docs/pr-discover-strategy-2026-09-04.md` §6-1'' の3案を、出荷実態に当てて絞ってある。

**A（②の完全同型・本命）**

    新機能「Notion連携」を提供開始、Obsidian連携シンプルメモ
    ―話したメモを"アプリを開かず"Notionのデータベースへ

**B（両対応を主にする）**

    新機能「Notion連携」を提供開始
    ―Obsidian連携シンプルメモ、話したメモをNotionとObsidianの両方へ

**C（ギミックを冒頭に）**

    "Notionを開かずに"追記できる
    ―Obsidian連携シンプルメモ、新機能「Notion連携」を提供開始

| | S1 | S2 | S3 | S4 | 必要条件 | 出荷実態との整合 |

## 4. この弾の弱点（**採点で埋めずに、書いておく**）

**S4（変化）が 10。**乗車2本は 15 と 12、非乗車4本は 8・10・5 で、
**10 は非乗車側の帯に入る。**しかも S4 は**乗車を分離する軸**である。

理由は訴求ではなく**出荷形**である —— 「置き換え」ではなく「追加コピー」だから、
「保存先が変わる」という強い変身を書けない。**S4 は出荷形が変わらない限り上がらない。**

伸ばせるのは別の2つ:

    S7  0 → 5   受け皿ページ・コミュニティ投下・プリテストが実在したら
    S3  8 → 15  見出しに生活名詞を入れられたら（ただし S3 は乗車を分離しない）

**S7 を取りに行って配信を遅らせない**（`docs/pr-action-router-launch-plan.md` §5）。

## 5. 本文に必ず書くこと

### 5-1. できることと、できないこと（同じ節に並べる）

PR⑥ で唯一よく効いた設計は「**できていないことを表で出す**」だった。それは残す。

| | 状態 |
|---|---|
| 話したメモが Notion の「SimpleMemo Inbox」に1件1ページで残る | できる |
| iPhone の文字・音声、Siri、Apple Watch（iPhone経由） | **同じ経路を通る** |
| メールに加えて Notion にも保存 | **既定の挙動** |
| メールを送らず Notion にだけ保存 | **Premium** |
| 思いつきは今までどおり Obsidian へ | 変わらない（「Notionのみ」ON のときは止まる） |
| Notion 側からの同期・双方向 | **無い。**一方向の保存だけ |
| DB選択・タグ・分類・本文加工・添付 | **無い**（`docs/notion-v1.md` の役割の絞り込み） |
| 保存の確認 | Notion の page ID が返ってから「保存しました」。**HTTP 202 は保存完了ではない** |

### 5-2. 所有していないものの明示

アプリの中に **Notion のビューアも編集画面も作っていない**（VISION §9）。
Notion は Destination であって、書き込むだけである。**この一文はブランディングそのもの**なので削らない。

### 5-3. プライバシー

**実装を確認してから書く。**確認済みの事実:
relay の `notion_deliveries` が持つのは `payload_mac`（HMAC）だけで、
**メモ本文を保持する列が無い**（`migrations/0032_notion.sql` を実測）。
Notion の access/refresh token は端末へ返さず、D1 で接続IDを AAD とする AES-GCM で暗号化する。
