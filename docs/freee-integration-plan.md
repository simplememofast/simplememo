## 0. なぜこれが効くか

いま資金繰りは**出ていく側だけ**で、`runway_months` を出せない。
2026-08-25 に検査が名指ししている足りない材料は2つ:

```
  **ランウェイ（月数）は出さない。**足りない材料: 手元資金 / 収入の履歴（0/28日）
```

**収入の履歴は放っておけば貯まる**（日次の取り込みが積む）。
**手元資金だけは、誰かが繋がないと永久に埋まらない。**
`⑦ 法人経営 :: 仕訳・請求・領収書・銀行・カード・月次締めの統合` は
現在 `nobody`（3リポジトリに証跡ゼロ）で、⑦の総合は 30.8%。
**ここが13領域で下から2番目**である直接の原因になっている。

## 1. できること（freee 会計 Public API）

## 2. ⚠️ ここが本題 — トークンの持ち方を間違えると90日で死ぬ

| | 値 |
|---|---|
| アクセストークン | **6時間**（24時間から短縮された） |
| リフレッシュトークン | **使い捨て。**払い出しのたびに新しいものが返る |
| リフレッシュトークンの有効期限 | **発行から90日** |

**1つのリフレッシュトークンで2度アクセストークンを取れない。**
つまり**毎回、返ってきた新しいリフレッシュトークンを保存し直す必要がある。**

### これが効いてくる理由

このリポジトリの既存の資格情報は**すべて静的**（ASC の .p8、Resend の API キー、
GitHub の PAT）。GitHub Actions の Secrets に置いて読むだけで済む。
**freee だけが「実行のたびに書き換わる秘密」**になる。

GitHub Actions から Secrets を書き戻すには `secrets` 権限を持つ PAT が要る。
**秘密を更新するために、より強い秘密を置く**ことになり、
`data/injection-surface.json` と `check-credentials.mjs` が守っている方向と逆に働く。

### 置き場所は Cloudflare KV（`simplememo-api`）

- Workers は既に **cron を3本**持っている（`crons = ["0 * * * *", "0 1 * * *", "30 22 * * *"]`）
- KV は Worker から**書ける**。ローテーションの保存先として自然
- 鍵が増えない —— freee の client_secret を1つ足すだけで、
  回転するトークンはリポジトリにもGitHubにも置かない

```
  Cloudflare Worker (cron)
    ├── KV: freee:refresh_token       ← 毎回書き換わる。**リポジトリに置かない**
    ├── env: FREEE_CLIENT_ID / SECRET ← 静的。wrangler secret
    └── KV: freee:balance:<date>      ← 残高の観測（金額だけ。明細は置かない）
                    │
                    └→ simplememo 側が読んで cash_on_hand_connected を埋める
```

### 90日は「期限」なので、期限台帳に載せる

`data/credential-expiry.json` に14件ある資格情報と同じ扱いにする。
**ただし他の13件と性質が違う**ので、そう書く:

- 他の資格情報 … 期限が来たら人が更新する
- freee のリフレッシュトークン … **自動運転が回っている限り自動で延びる。
  止まると90日で死ぬ**

つまり**「自動運転が止まったこと」の遅効性の罰**になる。
`breaks_if_expired` は「再認可（人がブラウザでOAuth同意）が必要」で、
これは**AIには実行できない**（⑬アナログ領域と同じ性質）。

## 3. 権限の非対称 — 読むのは自律、書くのは承認

`rollout-guard.ts`（kill は自律 / promote は承認）と
`check-stoploss.mjs`（revert は自律 / expand は返さない）と**同じ形にする。**

| 操作 | 可逆性 | 誰が |
|---|---|---|
| 残高・明細・仕訳を**読む** | 完全に可逆（何も変えない） | **AIが自律実行** |
| 勘定科目の**推定** | 提案どまり | AIが提案 |
| 仕訳を**作る/直す** | 会計帳簿が変わる | **人が承認** |
| 支払・振替の**実行** | **金が動く。不可逆** | **人が承認（`spend-approvals.json` の二者承認）** |

`data/authority-matrix.json` は⑦を `requires_approval: true` と定めているので、
**この分割はその中に収まる。**「読むだけ」を足すのに権限表の緩和は要らない。

## 4. 最初にやらないこと

- **仕訳の自動作成。**勘定科目の推定は誤りうるし、直すのは人。
  **読めるようになってから、しばらく読むだけで回す。**
- **freee アプリストアへの公開。**自社利用ならプライベートアプリで足りる。
- **人事労務・freeeサイン。**⑦の穴は会計側なので、まず会計だけ。

## 5. 着手前に確かめること（**私では確かめられない**）

1. **freee 会計を実際に使っているか。**3リポジトリに freee の言及は
   `evidence.md` の「grep 0件」の記録**1件だけ**で、ベンダー台帳10社にも入っていない。
   **使っていないなら、この計画は「freee を導入するか」から始まる別の話。**

   （スターター 約3,000回/日 / アドバンス 約5,000 / エンタープライズ 約10,000）。
   **無料プランで使えるかは確認できていない。**日次の残高取得なら数回/日なので
   上限そのものは問題にならない。
3. **法人か個人事業主か。**`corporate-obligations.json` は決算期・課税事業者かどうかが
   **6件すべて未把握**のままで、これは freee 側にある情報でもある。
   繋がれば同時に埋まる可能性がある。

## 6. 見積り

| 段階 | 中身 | 規模 |
|---|---|---|
| 1 | OAuth 初回認可（**人がブラウザで1回**）→ refresh token を KV へ | 人の作業15分 |
| 2 | Worker cron で残高取得 → KV。ローテーション保存つき | 実装半日 |
| 3 | `cash_on_hand_connected` を埋め、`check-financial-policy` の材料を1つ減らす | 小 |
| 4 | `wallet_txns` で `monthly_outflow_usd` の「実測ではない」を実測に | 小 |
| 5 | 仕訳の読み取り → 月次締めの状態を⑦の台帳へ | 中 |

**1 は人にしかできない。**そこだけ渡してもらえれば、2以降は自律で回せる。

## 7. この計画が満たしていない条件

`pr-autopilot-2026-09-rsi-audit.md` の基準に自分で当てる。

- **⑤ Self-correction**: 残高取得が失敗したとき、**古い残高を返さない**設計にすること。
  `up_to_date: false` を「最新」と読むと、**壊れたデータで資金判断をする**。
  ASC で実際に起きた誤り（`note: "取得完了"` と `reports: []` の両立）と同じ型。

- **未確認**: freee 側の `up_to_date` が false のとき何が返るかは**叩いていない。**
