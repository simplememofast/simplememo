# 成果監視の定期起動欠落を検知する

2026-09-04。Decision Monitor は15分間隔の schedule とマージ後の workflow_run を持つ。
GitHub APIではworkflow ID `350001848` は active、作成日時は08:09:35 UTC。
11:43:24 UTCの実測では直近3時間のscheduled runが0件だった。
一方、マージ後の実行は成功している。実装が動くことと、定期的に起動することは別である。

従来の Cron Health は24時間内の `conclusion=failure` だけを新規検知していた。
一度も起動しない状態には失敗runがなく、成果契約の決済や本番再確認が止まっていても
この監視からは正常に見えた。

## 変更

`scripts/lib/cron-silence.mjs` で Decision Monitor の定期起動を観測し、既存の
Cron Health から呼ぶ。15分間隔の12回分に相当する3時間を猶予とし、新設直後も
同じ時間は待つ。猶予を過ぎて直近3時間にscheduled runが存在しない場合、既存の
`ops/cron-failure` Issueへ起動欠落を記録する。起動周期・支出上限・権限は変更しない。

- 対象workflowのID・パス・active状態・作成日時をAPIで確認する。
- `event=schedule` と期間を指定し、実際のrunのevent・ID・期間も照合する。
- 期間内の起動が1件あれば起動欠落とはしない。失敗した実行は従来の失敗検知が担当する。
- 手動・マージ後の実行は、定期起動の証拠にしない。
- APIエラー・不正応答・期間や対象の不一致は観測不能としてジョブを失敗させ、Issueを更新しない。
- Issueには対象workflowと観測日時、観測経路を機械可読のコメントとして残す。
  同じ対象への日々の追記は、復旧確認時に最新の欠落日時へまとめる。
- 復旧は、最新の起動欠落観測以降に作成されたscheduled runがcompleted/successに
  なったことを確認する。古い成功やworkflow_runの成功、queuedだけでは閉じない。
- 起動欠落と既存の失敗runが混在するIssueでは、両方の復旧を要求する。

## 検証

`health-intake.mjs --check` から新しい観測処理と復旧処理の検体を実行する。
APIのみを差し替えて実際の `cron-health.yml` のscriptも実行し、起動欠落のIssue作成、
観測不能時の無変更、復旧前の保持、再開後の成功証拠による閉鎖まで照合した。

隔離したコピーで、workflowから観測呼び出しを外す・空一覧を無視する・観測前の成功を
受け入れる・手動実行を復旧とみなす、の4変異を実行し、全て `--check` が非0終了した。
実際のIssueを検体として作成・閉鎖していない。

実データの読み取りでも、上記11:43:24 UTC時点の起動欠落を同じ関数が検知した。
これはローカルでの調査による観測であり、無人の検知や復旧実績として加点しない。

## 限界と完了条件

Cron Health自身は既存の毎朝07:00 JSTの実行を維持するため、3時間を超えた直後に
通知する仕組みではない。次の監視時に検知する。同じGitHub基盤のscheduleが全て
止まった場合を、同基盤のscheduleだけで検出できるとは主張しない。

定期起動が来ない原因は未特定。この変更は欠落を検知して既存の修復台帳へ運ぶもので、
GitHubのスケジューラ自体を修理した証拠ではない。実際のscheduled runの再開・成功と、
その後の契約決済が確認できるまで定期運転を実証済みとは扱わない。
自律スコアの配点・過去の実績・契約件数は変更しない。

## 出荷CIで検知した集計時刻の不具合

この変更のCI run `33869604354` は、既存のコード著者率の実Git検体で失敗した。
9月1日12:00 UTCに作った5コミットが、実行時刻12:00 UTCを過ぎると0件になった。
ローカルのUTC実行でも再現した。日付だけの `git log --since=2026-09-01` が
実行時刻を引き継ぐためで、既存の集計処理にも影響する。

`code-authorship.mjs` はJSTの開始日00:00から終了日翌日00:00未満までを明示し、
宣言していたauthor dateを `%aI` で取得して範囲を判定するよう修正した。
従来のGitによるcommitter dateの絞り込みは使わない。新しい計測には方法v4と
日付基準を記録し、保存済みの公開値は当時の方法のまま保持する。

実Git検体で日付境界の前後とauthor/committerの日時が異なるケースを検査し、
UTC・Asia/Tokyo・America/Los_Angelesで通過した。AI著者の識別条件は同じで、
100点の自律スコア定義は変更していない。CIの検査も維持している。
