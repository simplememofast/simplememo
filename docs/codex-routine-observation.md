# Codexへの移管後の実行記録

2026-09-08、既存の毎時処理に scripts/codex-routine-observer.py を追加した。
対象は codex-autopilot-execution.md で役割を確認した obsidian と obsidian-2。
既存のClaude登録19件の観測と停止履歴は保持する。
新しいCodex予約を増やした際は、その役割を確認して登録する。

Codexのローカル予約DBを読み取り専用トランザクションで全件検索し、対象の
実行IDに結び付いた通常・アーカイブ済みログを読む。台帳の codex_observation
に保存するのは予約状態、実行時刻、各ターンの開始・終了・エラーの有無、
ツール呼出と結果の対応件数、ログのハッシュとサイズだけ。
本文、プロンプト、出力、エラー詳細、端末のパス、資格情報、推定費用は保存しない。
原ログはCodexの既存の非公開保管場所に残る。APIへアップロードしない。

予約DBのARCHIVEDやACCEPTEDは画面上の扱いであり、実行の成功と読まない。
配列の先頭が元の予約による実行、後続が同じタスクで起きた追加ターンである。
初回失敗のあとに確認ターンが正常終了しても、初回の失敗を更新しない。
正常終了も記事公開や問題解決の証明には使わず、業務結果は推定しない。
9月8日の補完運転では、この「初回失敗・後続正常終了」が実ログに存在した。

DBが無い、登録予約が無い、以前の実行が消えた、終了済みターンが変わった場合は
更新を止める。初めて観測する実行のログ欠測・末尾の不完全行はunavailableとして
実行自体を記録し、0回成功と扱わない。ログが復元されると次回に再取得する。
実行中と応答の無いツール呼出も記録する。CIは許可したメタデータ、全件列挙の宣言、
時刻、呼出件数の対応と3日以内の鮮度を検査する。
原ログをCIから読めるという意味ではない。

ローカル処理は両ソースの取得と検査が通った場合だけ、既存の台帳1ファイルを
通常のPRへ送る。状態が変わるか24時間経つまではPRを追加しない。
どちらかが読めない間は古い観測日時を保持し、CIの鮮度検査が異常を示す。
古い失敗を閉じたり、別の認証で回避したりしない。

検証と配置はコードのCI成功・mainへの反映、ローカル実行ファイル更新、
毎時の自然起動、実際の観測PRとmainの一致を順に確認する。
これらが終わるまでは、副系の実行記録の移管完了として加点しない。

既存の運用・停止方法は [routine-observer.md](routine-observer.md) を参照。

## 起動元を推定しない

同日の05:58 UTCの自然起動で、サービスの実行回数は21から22へ増え、
正常終了とCodexの3実行・6ターンの取得を確認した。元の失敗1回も保持されていた。
状態は前回と同じだったため、通常の更新抑制が働き、PRは追加されていない。

この実行では、子プロセスへサービス名の環境変数が届くという初版の仮定が外れた。
自動起動をinteractiveと表示したので、環境変数が識別できない場合の値を
unidentified_processへ訂正した。名前が一致した場合も、示すのは環境変数の観測までである。
自然起動はlaunchdの実行回数、予定時刻に対応した実ログ、正常終了の一致で確認する。
確認のためにサービスを手動起動したり、環境変数を偽装したりしていない。

呼出件数は原ログのresponse_item単位であり、その内部のHTTP・SQLの回数ではない。
今後のメタデータPRとmainへの反映も別に確認し、取得成功だけで出荷成功としない。

訂正後の取得はschema_version=2で保存する。既存のversion 1は履歴として読み、
検査の表示では起動元をlegacy_unverifiedとする。版だけを台帳で書き換えず、
次の実取得で原ログを読み直した結果を移す。旧観測の日時を更新して鮮度を作らない。
