# 会計の対応候補検索（2026-10-01・ドラフト）

狙いは、銀行等の明細から既存取引の支払行を探し、その取引の公式仕訳を参照する人の検索作業を減らすこと。`growth/lib/accounting-candidates.mjs` の `findAccountingCandidates(input)` は、既存 owner 内の取得結果をメモリ内で照合し、配列位置による候補対応を返す純粋関数である。

現在は合成検体で検査した未接続のドラフト。原票・実データ・認証を取得していない。行120「仕訳・請求・領収書・月次締めの統合」の部分改善であり、完全自動の完走数への加点は **0**。残高読取りの行119、単一サービスの照合の行126を再実装・再加点しない。固定192業務・同11除外、同じ対象で93%以上を4週連続維持する判定へ、この実装やテストを実績として入れない。

## 公式契約と関係の限界

2026-10-01に [公式会計API reference](https://developer.freee.co.jp/reference/accounting) と、そこから案内される [公式 OpenAPI schema](https://raw.githubusercontent.com/freee/freee-api-schema/master/v2020_06_15/open-api-3/api-schema.json) を確認した。バージョンディレクトリの名称だけから仕様の古さを判断せず、公式の現行 master にある契約を参照した。

- `wallet_txns` に取引・支払への直接外部キーはない。明細の `due_amount` は取引登録待ち金額で、未入金・未送金を表す値ではない。明細の登録待ち・登録済み・無視・部分登録・対象外を区別する。
- `deals.payments` は決済行単位で、1回の決済でもタグの組合せにより複数要素になる。更新後に支払行IDが変わることがあり、更新による決済行は `payments` に含まれず `renews` にある。支払行なしを、支払完了または未払いの証拠へ変換しない。
- 明細一覧・取引一覧にはページングがある。取引の発生日だけで当月を絞ると、以前に発生して当月に支払った取引を落とし得る。呼出元は対象支払日を含む取得範囲を別に確認する。

[公式仕訳CSV仕様](https://support.freee.co.jp/hc/ja/articles/204615564)（2026-08-04更新）の標準 `generic_v2` を対象とする。取引IDを取引へ直接関連付け、複数仕訳・複数行を保持する。口座振替ID・振替伝票ID・仕訳ID・管理番号・仕訳番号を取引IDへ読み替えない。テンプレートはヘッダーを変更できるため、この関数は標準ヘッダーと型を検査する。行番号・行数・参照先・日付が矛盾する仕訳群や、欠落行は未確定として残す。

仕訳取得APIの GET は非同期の帳票生成要求である。単なる読取と同じものとして新たに呼び出さない。この関数はAPI呼出し、帳票生成、CSVファイル読取りを実装せず、既存 owner が正当な権限で取得した結果だけを受け取る。

## 入力契約

入力はパース済みオブジェクトの `context`、`wallet_txns` 配列、`deals` 配列、`journal_rows` 配列。任意の自由記述・原本・添付・残高・氏名・タグ・未知フィールドを戻り値へ転記しない。原票のある既存 owner から、この入力を別環境・公開リポジトリ・ログへ渡さない。

| 入力 | 関数が使う項目 |
| --- | --- |
| `wallet_txns` の行 | `id`, `company_id`, `date`, `amount`, `due_amount`, `entry_side`, `walletable_type`, `walletable_id`, `status` |
| `deals` の行 | `id`, `company_id`, `type`, `payments` 配列、`renews` の有無 |
| 支払行 | `id`, `date`, `amount`, `from_walletable_type`, `from_walletable_id` |
| `journal_rows` の行 | 標準CSVの文字列セル：取引ID、口座振替ID、振替伝票ID、仕訳ID、取引日、取引支払日、仕訳行番号、仕訳行数 |

APIのIDと金額は数値型の安全な整数を要求する。整数として解析できることと、一度丸められた int64 が正しいことは別であり、安全範囲を超える値を受け入れない。比較対象金額は正の整数、登録待ち金額は0以上とし、負額・端数・型違い・矛盾を推測修正しない。CSVのIDは正の10進文字列として検査する。API日付は実在する `YYYY-MM-DD`、CSV日付は同形式または `YYYY/MM/DD` に限定する。

`context` は次の確認を明示する。これらは呼出元の宣言であり、関数自身が実運用の証拠を確認したことにはならない。

| `context` | 条件 |
| --- | --- |
| `company_id` / `same_subject_confirmed` | 事業所IDが安全な正の整数で、既存 owner が同一主体を確認済み。各取得元とAPI行の主体も一致すること |
| `window` | `kind` は `calendar_month` または `rolling_28_days`。`from` / `through` は月初～月末、または両端を含む28日間 |
| `comparison` | `confirmed: true`, `currency: 'JPY'`, `unit: 'yen'`。公式レスポンスに無い通貨フィールドを補わず、実際の比較通貨・単位を既存 owner が確認すること。未確認・他通貨・異なる単位では候補探索を止める |
| `sources.wallet_txns` / `sources.deals` / `sources.journal` | 各々の `company_id`, `from`, `through`, `sync_current`, `range_complete`。対象窓を含む源の範囲、同期の鮮度、網羅性を宣言する |
| 明細・取引のページング | `all_pages_read: true`。少数件 probe を全件取得と扱わない |
| 仕訳の全行・形式 | `all_rows_read: true`, `format: 'generic_v2'` |
| 取引の対象支払範囲 | `sources.deals.payment_scope_confirmed: true`。窓より前に発生した取引の当窓支払も含める |
| 仕訳の対象取引範囲 | `sources.journal.deal_reference_scope_confirmed: true`。対象支払に関係する以前の発生仕訳も含める。必要なら仕訳の源期間を窓より広げる |

同一主体・比較単位・対象窓が未確認なら `input_unusable`。ページ不足・古い同期・範囲不足でも得られた行から検索はできるが、不足理由を保持し、不存在や完了を断定しない。空配列だけで全件確認したことにもならない。

## 検索と戻り値

明細と支払の主体・日付・額・収支方向・口座区分・口座IDがすべて厳密に一致する候補を索引で探す。一対一であっても `unique_candidate` に留める。両側の多重対応は `ambiguous`、候補なしは `no_candidate`、部分登録は `partial_registration`、型・主体・値・重複IDの不整合は `unusable`。分割額の合算、手数料の相殺、日付幅、名義や摘要の類似による確定はしない。

出力の `wallets` は `wallet_index` と候補の `deal_index` / `payment_index`、固定の状態と理由のみ。逆方向は `payments.wallet_indexes`。`deals` には取引の配列位置、検査状態、支払行の配列位置、固定理由を残し、支払行が空でも主体・ID・型の不正を隠さない。対応はこの呼出しで渡した配列に限られ、次の取得や並替えへ持ち越す識別子ではない。支払IDが変わっても継続性を推測せず、履歴や対応表を保存しない。

候補の `journal` は、取引IDに対応する仕訳行の `row_indexes` と `linked_by_deal_id` / `not_observed` / `incomplete_or_invalid` を返す。これは支払行との同日同額候補関係と別の直接参照である。取引ID参照の存在だけから、特定支払に対応する仕訳を確定しない。無効な支払入力からは仕訳対応を返さない。

外へ出せるのは `summary` の件数・固定状態・固定の不足理由だけ。元ID・口座・日付・金額・自由記述・資格情報・原本・ハッシュは返さない。配列位置による詳細対応も既存 owner のメモリ内に留め、外向け報告や保存へ含めない。関数には外部通信、ファイル操作、ログ、保存・シリアライズ機能、raw projection を返すAPIが無い。呼出元にも入力・詳細結果をログやエラーへ流さない義務が残る。

どの戻り値にも実行の許可は無い。仕訳登録・修正、税区分の選択、請求送付、契約、支払・送金、月次締めは既存の承認境界のまま。`summary.full_completion_credit` は常に0。貸借一致、税判断、請求書原本の妥当性、法人全体の会計網羅性を検査したとは言わない。
