## リード文（約240字）

株式会社ユリカ（所在地：日本）は、iOSアプリ「**Obsidian連携シンプルメモ**」の開発・運用に
おいて、**利用データの計測から施策の提案・実装・検証・配信準備までをAIが循環実行する
運営基盤**を構築しました。2026年8月11日から連続稼働しており、毎朝6時にAIが検索データを
読んで当日の施策を1件だけ選び、実装し、48種の自動検証を通し、**検証に合格したコミット
だけ**が本番へ反映されます。同社は運営業務を13領域175タスクに分解して自動化率を測っており、
**ローンチ時点の3.5%から現在58.7%**（未実装を分母に含む最も厳しい数え方）。一方で
**アプリの公開・価格・広告・契約は人間の承認制**として残しています。

## 本文

### ■ 4か月で、運営の自律度は17倍になった

同社は運営業務を**13領域175タスク**に分解し、それぞれを「AIが単独で実行 ／ ゲートを
通ったときだけ実行 ／ 提案まで ／ 人間 ／ 誰もやっていない ／ 意図的にやらない」に
分類した台帳を持っています。**証跡ファイルを指せないタスクを「AIがやっている」側に
数えることはCIが禁止しています。**

```
   2026-04（ローンチ）    3.5%
   2026-05                6.4%
   2026-06                7.6%
   2026-07               14.5%
   2026-08              58.7%   ← 現在
```

**この曲線には注意書きが要ります。**月次で測っていた期間は無く、**実測は2026年8月の1点だけ**です。
それ以前は、各工程の証跡ファイルが最初にコミットされた月から遡って再構成しています。
**分母（172タスク）も現在の棚卸しを過去へ固定したもの**で、当時は「やるべきことの一覧」
自体が存在しませんでした。

いっぽう**コードを書く部分は、最初から高いままです。**同期間のコミットの約99%、
変更行の94〜96%がAI著者によるもので、こちらは2026年2月からほぼ横ばいです。
**伸びたのはコードではなく、コード以外**——計測・広報・QA・予算・権限・監視の側でした。

### ■ 「58.7%」は、いちばん厳しい数え方をした結果です

同社は自動化率を**4つ同時に**出します。分母を1つに選べば、同じ現実が59%にも87%にもなるからです。

| 指標 | 値 | 分母 |
|---|---:|---|
| **総合自動化率** | **58.7%** | 未実装を含む全タスク（**最も厳しい**） |
| AI実行率 | 67.3% | 誰かがやっているタスクのみ |
| AI関与率 | 87.3% | 同上（提案・下書きまで含める・**最も甘い**） |
| カバー率 | 87.2% | そもそも誰かがやっているタスクの割合 |

**総合自動化率とカバー率を隠してAI関与率だけを出すことを、同社は運用規約で禁じています。**
正しい要約は「**AIが関わっている領域では実際に手を動かしているが、そもそも手が
付いていない領域が1割強ある**」です。

### ■ 何が動いているのか：毎朝6時の1サイクル

```
06:00  まず運転台帳を読む。未修理の故障があれば、その日は修理に切り替える
   ↓   検索データ（Google Search Console）を読み、当日の施策を「1件だけ」選ぶ
   ↓   ・期待クリック数が基準未満の根拠では書かない
   ↓   ・書く理由がなければ書かない。保守作業とログだけで終えてよい
   ↓   実装 → 内部リンク配線 → 台帳登録 → OG画像生成 → QRコード生成
   ↓   48種の自動検証（サイト検証263ファイル／内部リンク13,273件の直接200確認／
   ↓   広報原稿の事実検査／権限表の整合／資格情報の期限／依存ベンダー台帳 ほか）
   ↓   Pull Request を作成 →**検証に合格したコミットを指定して**自動マージ
10:00  実行結果と当月のAI実費を集計して日報メール
12:00  「緑のまま何もしていない」状態を検知する別系統の見張り
```

**「毎日1本出す」ことは目標にしていません。**手順書には「**毎日出すために基準を下げる、
はこの運用の失敗定義そのもの**」と書かれており、基準を通らなかった日はスキップし、
**その理由が日報に載ります**。

### ■ 人が成果物に手を入れた回数は、0回

**2026年8月11日〜22日（12日間・23実行）の実測です。**

| 指標 | 実測 |
|---|---:|
| AI完走率（着手した実行のうち本番へ出荷できた割合） | **76.9%** |
| 人間介入率（人の判断・修正・代走が入った実行の割合） | **53.8%** |
| └ うち **成果物への介入**（人が記事を書いた・書き直した） | **0.0%** |
| └ うち 実行基盤の修理（ワークフロー・手順書・スクリプト） | 30.8% |
| 出荷日率（12日のうち本番に何かが出た日） | **83.3%** |
| 障害の検知まで／修理まで（中央値） | 2.1時間 ／ 0.9時間 |

**人間介入率53.8%を、同社はそのまま公開します。**半分以上の実行に人が入っています。
ただし内訳を見ると、**出荷された10件すべてをAIが書いており、人間は一度も中身に
手を入れていません。**人がやったのは基盤の修理——そしてその修理を書いたのもAIで、
人間がやったのは**「壊れていることに気づいて、直せと言うこと」だけ**でした。

そこで同社は、**未修理の故障が残っていればその日の最優先を修理に切り替える工程**を
追加しました。自分のCIを自分で直す仕組みは放っておくと必ず
**「通らないチェックを消して緑にする」**に流れるため、**必須の自動検証37本が
1本でも消えるとCIが落ち**、**自分の権限を広げる変更もCIが検出します**。

### ■ AIに渡していない権限を、理由つきで公開しています

同社が今回もっとも公開したいのは、できることの一覧ではなく**境界**です。
「どこまでAIがやり、どこから人間か」を**機械可読な権限表**として持ち、
**15領域のうち10が承認制**です。

いちばん設計が出ているのは、**同じ機能の「引っ込める」と「広げる」を分けたこと**です。

| 操作 | 可逆性 | 誰が決めるか |
|---|---|---|
| 段階公開の**撤回**（不具合を検知して止める） | 可逆 | **AIが単独で実行してよい** |
| 段階公開の**拡大**（配る割合を引き上げる） | **不可逆** | **人間の承認が要る** |

広げてから戻しても、**見た人が見なかったことにはなりません。**

アプリのリリース経路（ビルド → TestFlight配信 → App Review提出）も自動化されて
いますが、**その連鎖を起動する権限を開発用のAIワークフローには与えていません**。
設定ファイルには理由がこう書かれています。

> この権限があれば、確認を求めない設定のAIが出荷ワークフローを直接呼び出し、
> **人間を一切介さずApp Storeへ出荷できてしまう**。

Appleの審査通過後にApp Storeへ公開する操作も、設定上ハードコードで無効化されており、
**恒久的に人間の操作**として残す方針です。

### ■ できていないこと

**この基盤はまだ「全領域が自動で完結する」状態ではありません。**

| 領域 | 現状 |
|---|---|
| 機能開発 | 分析と提案はAI。**自動選定→段階公開→効果測定→継続／撤回まで通した実績はまだ無い** |
| 障害の検知 | 監視13系統のうち**1系統（課金）に気づく経路が無い**。Apple Watch同期と問い合わせは2026-08-22に検知経路を作った — **計測はあったのに誰も見ていなかった**という形の穴だった |
| 実機テスト | **シミュレータ・実機の操作、撮影、計測はできない**（macOS環境が必須） |
| 広告運用 | **未実装**。この予算規模では日次の自動入札がノイズ最適化になるという自社分析があり、着手していない |
| カスタマーサポート | 受け口と自動分類は実装済み。**返信の自動化が無い**ので、CSAT計測もレビュー返信もまだ発火しない |
| 法人領域 | **13タスク中3が未実装、5が提案止まり。**台帳と検査は作ったが、決算期・従業員の有無・課税事業者かどうかがリポジトリから取れず、**法定期限6件はすべて未把握のまま**。経理・税務・労務は依然として証跡ゼロで、**無人化しない** |

さらに、**この12日間に自動実行の主系が一度も成果物を出せていないことも記録に残って
います。**主系は4種類の異なる理由で連続して失敗しており、**その間の出荷はすべて
副系が担っていました。**同社はこれを、二重化が実際に効いた実例として公開します。

**同社は「完全自動化できた」とは主張していません。**主張しているのは、
「**AIが日々の運営を継続実行できる構造にしたこと**」と
「**自動化が止まったことに気づける形にしたこと**」です。
