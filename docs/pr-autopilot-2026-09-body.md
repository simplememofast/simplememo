## リード文（約290字）

株式会社ユリカ（所在地：日本）は、iOSアプリ「**Obsidian連携シンプルメモ**」の開発・運用に
おいて、**AIの担当をコードから運営そのものへ広げる基盤**を構築しました。毎朝6時にAIが検索
データを読んで当日の施策を**1件だけ**選び、実装し、**67種の自動検証**を通し、**合格した
コミットだけ**が本番へ出ます。2026年8月11日からの**17日間で30回実行し、本番に出た15件は
100%がAIの執筆、人が中身に手を入れた回数は0回**でした。同社はこれと同時に、運営業務を
**13領域201タスク**に分解した総合自動化率も公開しています——**現在65.2%**（未実装を分母に
含む最も厳しい数え方）。さらに「**この分母では95%に到達できない**」ことを、到達可能な上限
**81.3%**とあわせて先に発表しました。App Storeへの公開・価格・広告・予算の権限は、
AIに渡していません。

## 本文

### ■ 17日間・30実行・出荷15件。人が中身に触った回数は、0

**2026年8月11日〜27日の実測です**（`data/autopilot-runs.json`。1実行1行で、
出荷した回と失敗した回を同じ列に書く）。

| 指標 | 実測 |
|---|---:|
| 出荷（本番に出た成果物） | **15件** |
| └ うち **人が中身に手を入れたもの** | **0件（0.0%）** |
| AI完走率（着手した実行のうち出荷まで届いた割合） | **75.0%**（15 / 20） |
| 人間介入率（何らかの形で人が入った実行の割合） | **35.0%** |
| └ 内訳：基盤の修理 20.0% ／ 代走 5.0% ／ 立ち上げ 5.0% ／ 起票のみ 5.0% | |
| 出荷日率（17日のうち何かが出た日） | **82.4%** |
| 障害の検知まで／修理まで（中央値） | **2.7時間 ／ 6.7時間** |
| 観測できたAI実費 | **$20.04**（5実行分。副系12実行は**観測手段が無い**＝0ではない） |

**人間介入率35.0%を、同社はそのまま公開します。**3回に1回は人が入っています。
ただし**入った先は一度も成果物ではありません。**人がやったのは基盤の修理で、
**その修理を書いたのもAI**でした。人間の仕事は
**「壊れていることに気づいて、直せと言うこと」**だけです。

**17日のうち2日（8月16日・17日）は、どの経路も動きませんでした。**
基準を通らずスキップした日とは別で、**台帳はこれを「正常系ではない」と記録しています。**
「連続稼働」と書けたはずの場所で、書いていません。

### ■ 65.2%は、いちばん厳しい数え方をした結果です

同社は自動化率を**4つ同時に**出します。分母を1つ選べば、同じ現実が65%にも88%にもなるからです。

| 指標 | 値 | 分母 |
|---|---:|---|
| **総合自動化率** | **65.2%** | 未実装を含む全タスク（**最も厳しい**） |
| AI実行率 | 75.0% | 誰かがやっているタスクのみ |
| AI関与率 | 87.8% | 同上（提案・下書きまで含める・**最も甘い**） |
| カバー率 | 86.9% | そもそも誰かが手を付けているタスクの割合 |

**総合自動化率とカバー率を隠してAI関与率だけを出すことを、同社は運用規約で禁じています。**
正しい要約は「**AIが関わっている領域では実際に手を動かしているが、そもそも手が
付いていない領域が1割強ある**」です。

台帳は**13領域201タスク**（うち3件は「意図的にやらない」として分母から外す）。
**証跡ファイルを指せないタスクを「AIがやっている」側に数えることは、CIが禁止しています。**

```
   2026-04（ローンチ月）    7.1%
   2026-05                  7.1%
   2026-06                  8.1%
   2026-07                 11.1%
   2026-08                 65.2%   ← 現在
```

**この曲線には注意書きが要ります。実測は2026年8月の1点だけです。**
それ以前は各工程の証跡ファイルが最初にコミットされた月から遡って再構成したもので、
**分母（198タスク）も現在の棚卸しを過去へ固定**しています。当時は「やるべきことの一覧」
自体が存在しませんでした。**倍率は書きません**——分母の取り方で何倍にでも動くためです。

いっぽう**コードを書く部分は、最初から高いままです。**同期間のコミットの**99.5%**、
変更行の**94.2%**がAI著者によるもので、2026年2月からほぼ横ばい。
**伸びたのはコードではなく、コード以外**——計測・広報・QA・予算・権限・監視の側でした。

### ■ 公表している自律率が、下がった月があります

公表値は **61.3% → 58.6%**（8月22日→25日）、直近でも **65.3% → 64.6% → 65.2%** と動きました。
**どちらも一度下がっています。**

**自動化をやめたからではありません。**「できていない」と気づいた項目を棚卸しに足したので、
**分母が増えました**（8月25日に足した13件のうち10件が未実装。直近の分は196→198）。
1行にまとめてあった作業を3行に分けた回もあります——まとめたままだと、
3つのうち1つができた時点で行全体が「できた」側へ動いてしまう。

**率を上げるいちばん簡単な方法は、できていないことを一覧に書かないことです。**
そうしなかったことを、下がった数字そのものが示しています。

### ■ 「95%」は、この設計では永久に達成できません

同社は自社の**到達可能上限**を先に公開しています。

```
   現在              129/198  = 65.2%
   到達可能な上限    161/198  = 81.3%   ← 実装・外部接続・書類で届く範囲
   境界を全部渡しても 185/198  = 93.4%   ← 人へ残した24件をすべてAIに渡した場合
   目標 95.0%        189/198
```

**App Storeへの公開も価格変更も危機対応も全部AIに渡して、なお4件届きません。**
残る13件は物理・対人・観測不能・検出力不足で、**渡しても実行できない**
（実機の操作、現地設営、採用面談、対照群の検出力、副系セッションのログ）。

**つまり95%に到達する方法は無く、到達したことにする方法だけがあります。**
分母を組み替える、AI関与率87.8%に乗り換える、証跡の無い行を実行側に数える——
どれもこの台帳が最初から禁じているもので、`--check` が落とします。

### ■ 何が動いているのか：毎朝6時の1サイクル

```
06:00  まず運転台帳を読む。未修理の故障があれば、その日は修理に切り替える
   ↓   検索データ（Google Search Console）を読み、当日の施策を「1件だけ」選ぶ
   ↓   ・期待クリック数が基準未満の根拠では書かない
   ↓   ・書く理由がなければ書かない。保守作業とログだけで終えてよい
   ↓   実装 → 内部リンク配線 → 台帳登録 → OG画像生成 → QRコード生成
   ↓   67種の自動検証（サイト検証267ファイル／内部リンク12,845件の点検／
   ↓   広報原稿の事実検査／権限表の整合／資格情報の期限／依存ベンダー台帳 ほか）
   ↓   Pull Request を作成 → **検証に合格したコミットを指定して**自動マージ
09:00  日次アクチュエータ。ファネルを読み、機械が実行してよい手当てだけを自律実行する
10:00  実行結果と当月のAI実費を集計して日報メール
12:00 / 16:00 / 20:00  「緑のまま何もしていない」状態を検知する別系統の見張り
```

**「毎日1本出す」ことは目標にしていません。**手順書には「**毎日出すために基準を下げる、
はこの運用の失敗定義そのもの**」と書かれており、基準を通らなかった日はスキップし、
**その理由が日報に載ります**。

### ■ 67本の自動検査すべてについて、「わざと壊すと落ちる」ことを実際に見ました

自分のCIを自分で直す仕組みは、放っておくと必ず
**「通らないチェックを消して緑にする」**に流れます。同社の対策は2段構えです。

- **必須の自動検証が1本でも消えるとCIが落ちる。**自分の権限を広げる変更もCIが検出する
- **検査そのものが効いているかを、検査している。**`data/check-selftests.json` は
  **CI配線67本すべて**について「判定器をわざと壊すと落ちること」を実測した記録で、
  **未観測の許容枠は0本**。以後この数は下げる方向にしか動かしません

**「実装した」と「落ちるのを見た」を同じ語で呼ばない**——これが規約です。
実際、規則を足したのに一度も発火しない検査を踏んだことがあります。
（同時に、これが証明するのは「壊れたら気づく」ことだけで、
「見るべきものを見ている」かは別問題であることも明記しています。）

### ■ AIに渡していない権限を、理由つきで公開しています

同社が今回もっとも公開したいのは、できることの一覧ではなく**境界**です。
「どこまでAIがやり、どこから人間か」を**機械可読な権限表**として持ち、
**19領域のうち13が承認制**です。

いちばん設計が出ているのは、**同じ機能の「引っ込める」と「広げる」を分けたこと**です。

| 操作 | 可逆性 | 誰が決めるか |
|---|---|---|
| 段階公開の**撤回**（不具合を検知して止める） | 可逆 | **AIが単独で実行してよい** |
| 段階公開の**拡大**（配る割合を引き上げる） | **不可逆** | **人間の承認が要る** |

広げてから戻しても、**見た人が見なかったことにはなりません。**

アプリのリリース経路（ビルド → TestFlight配信 → App Review提出）も自動化されて
いますが、**その連鎖を起動する権限を開発用のAIワークフローには与えていません**。
設定ファイルには理由がこう書かれています。

> この権限があれば、確認を求めない設定のAIが出荷ワークフローを直接呼び出し、
> **人間を一切介さずApp Storeへ出荷できてしまう**。

Appleの審査通過後にApp Storeへ公開する操作も、設定上ハードコードで無効化されており、
**恒久的に人間の操作**として残す方針です。

### ■ できていないこと

**この基盤はまだ「全領域が自動で完結する」状態ではありません。**

| 領域 | 現状 |
|---|---|
| 機能開発 | 分析と提案はAI。**設計への落とし込みとPRD作成は提案どまり**で、自動選定→段階公開→効果測定→継続／撤回まで通した実績はまだ無い |
| 実機テスト | **シミュレータ・実機の操作、撮影、計測ができない**（macOS環境が必須） |
| 対照群 | **母数が足りない。**App Storeのクリックは2.1件/日で、対照群を割ると両群とも検出力不足。**前週比は「区別できない」と書く週がほとんど** |
| 広告運用 | **未実装**。この予算規模では日次の自動入札がノイズ最適化になるという自社分析があり、着手していない |
| マネタイズ | 総合 **27.3%**。11タスク中 **5件が未実装**（＝誰も手を付けていない） |
| 法人領域 | 総合 **30.8%**。決算期・従業員の有無・課税事業者かどうかがリポジトリから取れず、**法定期限6件はすべて未把握**。経理・税務・労務は依然として証跡ゼロで、**無人化しません** |
| アナログ領域 | 総合 **0.0%**。営業・採用・イベント・公的資金は、AIに渡す設計そのものを作っていない |
| 副系の実費 | **観測手段が無い。**台帳は0ではなく `null` と書いています |

さらに、**この期間に自動実行の主系は8回中3回しか出荷できていません。**
残る12件は副系・代走が担いました（12/12）。
同社はこれを、**二重化が実際に効いた実例**として公開します。

**同社は「完全自動化できた」とは主張していません。**主張しているのは、
「**AIが日々の運営を継続実行できる構造にしたこと**」と
「**自動化が止まったことに気づける形にしたこと**」、そして
「**自分に都合の悪い数字を、自分から先に出す形にしたこと**」です。

**起動0.4秒**（ウォーム起動・タップからキーボードが入力を受け付けるまで。

App Storeから削除された「Captio」の代替として2026年にリリース（旧名「Captio式シンプルメモ」）。
※エンドツーエンド暗号化ではありません（メールは標準のSMTPで届きます）。
