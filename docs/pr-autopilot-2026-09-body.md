### ■ 66.8%は、いちばん厳しい数え方をした結果です

同社は自動化率を**4つ同時に**出します。分母を1つ選べば、同じ現実が67%にも88%にもなるからです。

| 指標 | 値 | 分母 |
|---|---:|---|
| **総合自動化率** | **66.8%** | 未実装を含む全タスク（**最も厳しい**） |
| **AI実行率** | **76.4%** | 誰かがやっているタスクのみ（**見出しはこれ**） |
| AI関与率 | 87.9% | 同上（提案・下書きまで含める・**最も甘い**） |
| カバー率 | 87.4% | そもそも誰かが手を付けているタスクの割合 |

**総合自動化率とカバー率を隠してAI関与率だけを出すことを、同社は運用規約で禁じています。**
正しい要約は「**AIが関わっている領域では実際に手を動かしているが、そもそも手が
付いていない領域が1割強ある**」です。

台帳は**13領域203タスク**（うち4件は「意図的にやらない」として分母から外す）。
**証跡ファイルを指せないタスクを「AIがやっている」側に数えることは、CIが禁止しています。**

```
   2026-04（ローンチ月）    8.0%
   2026-05                 11.1%
   2026-06                 12.1%
   2026-07                 18.6%
   2026-08                 66.8%   ← 現在
```

> 50コミットしか無い状態だと**初出が実際より後ろに出る**ので、

>
> **同時に `code_lines` が下がった**（2026-08: 809,744 → 295,069）。こちらは逆に、
> **`git log --all` が「いま残っている ref」しか見ない**ため。マージ後に消された
> `claude/*` ブランチのコミットは `--all` から消えるので、**この値は時間とともに縮む。**

**この曲線には注意書きが要ります。実測は2026年8月の1点だけです。**
それ以前は各工程の証跡ファイルが最初にコミットされた月から遡って再構成したもので、
**分母（199タスク）も現在の棚卸しを過去へ固定**しています。当時は「やるべきことの一覧」
自体が存在しませんでした。

**この曲線は、証跡を差し替えると動きます。**各点は「その工程の証跡ファイルが最初に
コミットされた月」から再構成しているので、証跡の指す先を変えると過去の点も変わる ——
実際、2026年8月27日に証跡を手順書から実装ファイルへ差し替えたところ、
**2026年7月の点が3ポイント下がりました**（当時の値で 11.1% → 8.1%）。当時の実態が変わったわけではなく、
**当時を推定する材料が変わった**だけです。終点（実測）だけは動きません。

**同じ日のうちに、この点は 11.1% へ戻りました。**8.1% を出した証跡の状態は現在の台帳には残っておらず、
**なぜ戻ったかは、ここでは特定できていません**（複数の変更が同じ日に入っています）。
そして9月2日の再計算で、同じ7月の点は **18.6%** になりました（上の表）。中身が良くなったのではなく、
再構成に使う履歴が浅いクローンで欠けていたのを、3リポジトリの全履歴で引き直したためです。
書けるのは観測だけです —— **この曲線は1日のうちに3ポイント動いて戻り、1週間後にさらに7ポイント動いた。**
注意書きとして弱めるのではなく、むしろ**この段落の主張そのものの実例**として残します。**倍率は書きません**——分母の取り方で何倍にでも動くためです。

いっぽう**コードを書く部分は、最初から高いままです。**同期間のコミットの**99.5%**、

### ■ 「95%」は、この設計では永久に達成できません

同社は自社の**到達可能上限**を先に公開しています。

```
   現在              133/199  = 66.8%
   到達可能な上限    165/199  = 82.9%   ← 実装・外部接続・書類で届く範囲
   境界を全部渡しても 185/199  = 93.0%   ← 人へ残した20件をすべてAIに渡した場合
   目標 95.0%        190/199
```

**App Storeへの公開も価格変更も危機対応も全部AIに渡して、なお5件届きません。**
残る14件は物理・対人・観測不能・検出力不足で、**渡しても実行できない**
（実機の操作、現地設営、採用面談、対照群の検出力、副系セッションのログ）。

**つまり95%に到達する方法は無く、到達したことにする方法だけがあります。**
分母を組み替える、AI関与率87.9%に乗り換える、証跡の無い行を実行側に数える——
どれもこの台帳が最初から禁じているもので、`--check` が落とします。

### ■ 何が動いているのか：毎朝6時の1サイクル

```
06:00  まず運転台帳を読む。未修理の故障があれば、その日は修理に切り替える
   ↓   検索データ（Google Search Console）を読み、当日の施策を「1件だけ」選ぶ
   ↓   ・期待クリック数が基準未満の根拠では書かない
   ↓   ・書く理由がなければ書かない。保守作業とログだけで終えてよい
   ↓   実装 → 内部リンク配線 → 台帳登録 → OG画像生成 → QRコード生成
   ↓   81種の自動検証（サイト検証268ファイル／内部リンク13,218件の点検／
   ↓   広報原稿の事実検査／権限表の整合／資格情報の期限／依存ベンダー台帳 ほか）
   ↓   Pull Request を作成 → **検証に合格したコミットを指定して**自動マージ
09:00  日次アクチュエータ。ファネルを読み、機械が実行してよい手当てだけを自律実行する
10:00  実行結果と当月のAI実費を集計して日報メール
12:00 / 16:00 / 20:00  「緑のまま何もしていない」状態を検知する別系統の見張り
```

**「毎日1本出す」ことは目標にしていません。**手順書には「**毎日出すために基準を下げる、
はこの運用の失敗定義そのもの**」と書かれており、基準を通らなかった日はスキップし、
**その理由が日報に載ります**。

### ■ 81本の自動検査すべてについて、「わざと壊すと落ちる」ことを実際に見ました

自分のCIを自分で直す仕組みは、放っておくと必ず
**「通らないチェックを消して緑にする」**に流れます。同社の対策は2段構えです。

- **必須の自動検証が1本でも消えるとCIが落ちる。**自分の権限を広げる変更もCIが検出する
- **検査そのものが効いているかを、検査している。**`data/check-selftests.json` は
  **CI配線81本すべて**について「判定器をわざと壊すと落ちること」を実測した記録で、
  **未観測の許容枠は0本**。以後この数は下げる方向にしか動かしません

**「実装した」と「落ちるのを見た」を同じ語で呼ばない**——これが規約です。
実際、規則を足したのに一度も発火しない検査を踏んだことがあります。
（同時に、これが証明するのは「壊れたら気づく」ことだけで、
「見るべきものを見ている」かは別問題であることも明記しています。）

### ■ AIに渡していない権限を、理由つきで公開しています

同社が今回もっとも公開したいのは、できることの一覧ではなく**境界**です。
「どこまでAIがやり、どこから人間か」を**機械可読な権限表**として持ち、
**19領域のうち15が稼働中で、10が承認制**です。

いちばん設計が出ているのは、**同じ機能の「引っ込める」と「広げる」を分けたこと**です。

| 操作 | 可逆性 | 誰が決めるか |
|---|---|---|
| 段階公開の**撤回**（不具合を検知して止める） | 可逆 | **AIが単独で実行してよい** |
| 段階公開の**拡大**（配る割合を引き上げる） | **不可逆** | **人間の承認が要る** |

広げてから戻しても、**見た人が見なかったことにはなりません。**

アプリのリリース経路（ビルド → TestFlight配信 → App Review提出）も自動化されて
いますが、**その連鎖を起動する権限を開発用のAIワークフローには与えていません**。
設定ファイルには理由がこう書かれています。

> この権限があれば、確認を求めない設定のAIが出荷ワークフローを直接呼び出し、
> **人間を一切介さずApp Storeへ出荷できてしまう**。

Appleの審査通過後にApp Storeへ公開する操作も、いまは設定上（`automatic_release=false`・
ゲートの `enabled=false`）無効で、**AIが公開を実行する経路はありません**。2026年8月28日に権限表の上では
「承認制」から「機械ゲート付き」へ移しました（実機確認の記録が無ければ止まる・段階リリース必須・
1日1回まで）が、**そのゲートを有効にする操作そのものは、人にしか渡していません**。

### ■ できていないこと

**この基盤はまだ「全領域が自動で完結する」状態ではありません。**

| 領域 | 現状 |
|---|---|
| 機能開発 | 分析と提案はAI。**設計への落とし込みとPRD作成は提案どまり**で、自動選定→段階公開→効果測定→継続／撤回まで通した実績はまだ無い |
| 実機テスト | **シミュレータ・実機の操作、撮影、計測ができない**（macOS環境が必須） |
| 対照群 | **母数が足りない。**App Storeのクリックは2.1件/日で、対照群を割ると両群とも検出力不足。**前週比は「区別できない」と書く週がほとんど** |
| 広告運用 | **未実装**。この予算規模では日次の自動入札がノイズ最適化になるという自社分析があり、着手していない |
| マネタイズ | 総合 **30.0%**。10タスク中 **4件が未実装**（＝誰も手を付けていない） |
| 法人領域 | 総合 **50.0%**。決算期・役員報酬・インボイス登録はオーナーが台帳に入れ、**法定期限6件は9月2日に全件が機械の監視下に入った**（申告そのものは人）。銀行・カード残高の読み取りと契約の定型／非定型の分類は機械。仕訳・請求・支払いの照合は手つかずで、**無人化しません** |
| アナログ領域 | 総合 **0.0%**。営業・採用・イベント・公的資金は、AIに渡す設計そのものを作っていない |
| 副系の実費 | **観測手段が無い。**台帳は0ではなく `null` と書いています |

さらに、**この期間に自動実行の主系は12回中5回しか出荷できていません。**
残る14件は副系・代走が担いました（16回中14回。**副系も2回落ちています**）。
同社はこれを、**二重化が実際に効いた実例**として公開します。

**同社は「完全自動化できた」とは主張していません。**主張しているのは、
「**AIが日々の運営を継続実行できる構造にしたこと**」と
「**自動化が止まったことに気づける形にしたこと**」、そして
「**自分に都合の悪い数字を、自分から先に出す形にしたこと**」です。
