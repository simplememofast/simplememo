## リード文（約240字）

株式会社ユリカ（所在地：日本）は、iOSアプリ「**Obsidian連携シンプルメモ**」の開発・運用に
おいて、**利用データの計測から施策の提案・実装・検証・配信準備までをAIが循環実行する
運営基盤**を構築しました。2026年8月11日から連続稼働しており、毎朝6時にAIが検索データを
読んで当日の施策を1件だけ選び、実装し、59種の自動検証を通し、**検証に合格したコミット
だけ**が本番へ反映されます。同社は運営業務を13領域176タスクに分解して自動化率を測っており、
**ローンチ時点の3.5%から現在56.6%**（未実装を分母に含む最も厳しい数え方）。一方で
**アプリの公開・価格・広告・契約は人間の承認制**として残しています。

## 本文

### ■ 4か月で、運営の自律度は16倍になった

同社は運営業務を**13領域176タスク**に分解し、それぞれを「AIが単独で実行 ／ ゲートを
通ったときだけ実行 ／ 提案まで ／ 人間 ／ 誰もやっていない ／ 意図的にやらない」に
分類した台帳を持っています。**証跡ファイルを指せないタスクを「AIがやっている」側に
数えることはCIが禁止しています。**

**その禁止に穴が空いていたことが、2026年8月25日に分かりました。**証跡が別の
リポジトリを指している場合だけ、実在の確認が飛ばされていたのです。「確認できない
ものを確認したことにしない」という意図で入れた例外が、実際には「**隣を指せば
何でも通る**」として働いていました。棚卸ししたところ、**18タスク・39ファイルが
これに当たり、どれも隣のリポジトリの変更履歴に一度も存在しません**でした。

同社はこれを塞ぐ検査を追加し、**台帳を実態へ戻しました。総合自動化率は
61.3%から54.9%に下がりました。**とくに事業継続性の領域は100%から55.6%になりました。

**そして、この訂正自体がもう一度訂正されています。**同社は当初「本番データベースの
バックアップが存在しない」と結論し、その日のうちに自前のバックアップを実装しました。
ところが**データベース基盤（Cloudflare D1）には、過去30日を分単位で巻き戻す機能が
最初から付いていました。**設定も費用も要りません。自前の日次コピーは、いちばん
起きやすい事故——移行の失敗や条件を書き忘れた削除——に対して、**復旧できる時点も、
必要な手間も、すべての面で劣っていました。**

**最も悪かったのは、同社が書いた復旧手順書に、その機能が一行も無かったことです。**
障害のときに最も速くて安全な道を伏せた手順書を作っていたことになります。

同社はこれを、**台帳が両方向に間違っていた例**として公開します——
**在りもしない実装を数え、同時に、在るものに気づいていなかった。**
現在は基盤側の機能を主たる復旧手段として手順書の先頭に置き、自前のコピーは
「その機能が構造的に届かない3つ（データベースごと消えた・30日より前・
基盤事業者ごと落ちた）」だけを埋める週1の副次的な備えに位置づけ直しています。

訂正後の数字は **56.6%** です。以下の数字は、すべて訂正後のものです。

```
   2026-04（ローンチ）    3.5%
   2026-05                6.4%
   2026-06                7.6%
   2026-07               14.5%
   2026-08              56.6%   ← 現在
```

**この曲線には注意書きが要ります。**月次で測っていた期間は無く、**実測は2026年8月の1点だけ**です。
それ以前は、各工程の証跡ファイルが最初にコミットされた月から遡って再構成しています。
**分母（173タスク）も現在の棚卸しを過去へ固定したもの**で、当時は「やるべきことの一覧」
自体が存在しませんでした。

いっぽう**コードを書く部分は、最初から高いままです。**同期間のコミットの約99%、
変更行の94〜96%がAI著者によるもので、こちらは2026年2月からほぼ横ばいです。
**伸びたのはコードではなく、コード以外**——計測・広報・QA・予算・権限・監視の側でした。

### ■ 「56.6%」は、いちばん厳しい数え方をした結果です

同社は自動化率を**4つ同時に**出します。分母を1つに選べば、同じ現実が57%にも87%にもなるからです。

| 指標 | 値 | 分母 |
|---|---:|---|
| **総合自動化率** | **56.6%** | 未実装を含む全タスク（**最も厳しい**） |
| AI実行率 | 67.6% | 誰かがやっているタスクのみ |
| AI関与率 | 86.9% | 同上（提案・下書きまで含める・**最も甘い**） |
| カバー率 | 83.8% | そもそも誰かがやっているタスクの割合 |

**総合自動化率とカバー率を隠してAI関与率だけを出すことを、同社は運用規約で禁じています。**
正しい要約は「**AIが関わっている領域では実際に手を動かしているが、そもそも手が
付いていない領域が1割強ある**」です。

### ■ 何が動いているのか：毎朝6時の1サイクル

```
06:00  まず運転台帳を読む。未修理の故障があれば、その日は修理に切り替える
   ↓   検索データ（Google Search Console）を読み、当日の施策を「1件だけ」選ぶ
   ↓   ・期待クリック数が基準未満の根拠では書かない
   ↓   ・書く理由がなければ書かない。保守作業とログだけで終えてよい
   ↓   実装 → 内部リンク配線 → 台帳登録 → OG画像生成 → QRコード生成
   ↓   59種の自動検証（サイト検証264ファイル／内部リンク13,330件の直接200確認／
   ↓   広報原稿の事実検査／権限表の整合／資格情報の期限／依存ベンダー台帳 ほか）
   ↓   Pull Request を作成 →**検証に合格したコミットを指定して**自動マージ
10:00  実行結果と当月のAI実費を集計して日報メール
12:00  「緑のまま何もしていない」状態を検知する別系統の見張り
```

**「毎日1本出す」ことは目標にしていません。**手順書には「**毎日出すために基準を下げる、
はこの運用の失敗定義そのもの**」と書かれており、基準を通らなかった日はスキップし、
**その理由が日報に載ります**。

### ■ 人が成果物に手を入れた回数は、0回

**2026年8月11日〜22日（12日間・23実行）の実測です。**

| 指標 | 実測 |
|---|---:|
| AI完走率（着手した実行のうち本番へ出荷できた割合） | **76.9%** |
| 人間介入率（人の判断・修正・代走が入った実行の割合） | **53.8%** |
| └ うち **成果物への介入**（人が記事を書いた・書き直した） | **0.0%** |
| └ うち 実行基盤の修理（ワークフロー・手順書・スクリプト） | 30.8% |
| 出荷日率（12日のうち本番に何かが出た日） | **83.3%** |
| 障害の検知まで／修理まで（中央値） | 2.1時間 ／ 0.9時間 |

**人間介入率53.8%を、同社はそのまま公開します。**半分以上の実行に人が入っています。
ただし内訳を見ると、**出荷された10件すべてをAIが書いており、人間は一度も中身に
手を入れていません。**人がやったのは基盤の修理——そしてその修理を書いたのもAIで、
人間がやったのは**「壊れていることに気づいて、直せと言うこと」だけ**でした。

そこで同社は、**未修理の故障が残っていればその日の最優先を修理に切り替える工程**を
追加しました。自分のCIを自分で直す仕組みは放っておくと必ず
**「通らないチェックを消して緑にする」**に流れるため、**必須の自動検証56本が
1本でも消えるとCIが落ち**、**自分の権限を広げる変更もCIが検出します**。

### ■ AIに渡していない権限を、理由つきで公開しています

同社が今回もっとも公開したいのは、できることの一覧ではなく**境界**です。
「どこまでAIがやり、どこから人間か」を**機械可読な権限表**として持ち、
**15領域のうち10が承認制**です。

いちばん設計が出ているのは、**同じ機能の「引っ込める」と「広げる」を分けたこと**です。

| 操作 | 可逆性 | 誰が決めるか |
|---|---|---|
| 段階公開の**撤回**（不具合を検知して止める） | 可逆 | **AIが単独で実行してよい** |
| 段階公開の**拡大**（配る割合を引き上げる） | **不可逆** | **人間の承認が要る** |

広げてから戻しても、**見た人が見なかったことにはなりません。**

アプリのリリース経路（ビルド → TestFlight配信 → App Review提出）も自動化されて
いますが、**その連鎖を起動する権限を開発用のAIワークフローには与えていません**。
設定ファイルには理由がこう書かれています。

> この権限があれば、確認を求めない設定のAIが出荷ワークフローを直接呼び出し、
> **人間を一切介さずApp Storeへ出荷できてしまう**。

Appleの審査通過後にApp Storeへ公開する操作も、設定上ハードコードで無効化されており、
**恒久的に人間の操作**として残す方針です。

### ■ 止める権限はAIに、解除する権限は人間に

AIは、自分自身を含む自動処理を**止められます。**他のどの判定よりも先に効き、
強制実行の指定でも飛び越えられません。**ただし解除はできません。**

**解除する関数はソースコードに存在せず、追加すると検査が落ちます。**
非対称にしてあるのは損の大きさが違うからです —— 止めすぎの損は出荷が1日
止まるだけですが、**解除しすぎの損は、止めたかった事象がそのまま通ることです。**

同じ考え方が金額にも入っています。AIの実費上限は、**承認記録の最新値と一致して
いなければCIが落ちます。**承認の記録を残さずに上限を上げることができません。
**AIは承認者になれません**（承認記録にAIを書くとCIが落ちます）。
**止めることは許していますが、金額を上げることは許していません。**

### ■ 「何を学んだか」を、次に何を変えたかとセットで残しています

改善の記録は揃っていましたが、**繋がっていませんでした。**評価まで終わった
実験12件のうち**7件が「判定不能」のまま**で、次に何を変えるかを書く列が
そもそも存在しませんでした。

同社はこれを1レコードで繋ぐ台帳にしました。**値は写さず参照します**
（写すとずれるため）。この台帳が持つのは**判定・学び・実際に変えた規則**だけです。

- **結果が出る前に判定は書けず、判定の前に学びは書けません**
- **学びは必ず何かを変えるか、変えない理由を持ちます。**どちらも無い学びは
  「気をつける」と同じで、次に何も起きません

現在4件、**うち3件は実際に規則そのものを変えています。**残る1件は
**結果待ちのまま**です —— 空欄を埋めるために推測を書くと、記憶が推測で汚れます。

**まだ網羅していません。**記録は4件、実際の出荷は11件。
「記録されていない改善」を数える仕組みがまだ無いためです。

### ■ 「どこまで自律しているか」は、宣言ではなく条件から計算しています

同社は自律の到達段階を、7つの条件の充足から**導出**します。
台帳に「うちは閉ループです」と書くと、**CIが落ちます。**

そして**領域によって成熟度がまったく違うため、分けて公開します。**
まとめて1つの段階を名乗ると、強いほうの実績で弱いほうを覆い隠すことになります。

| | 到達段階 |
|---|---|
| **基盤側**（記事・検索最適化・自分自身の修理） | **Closed-loop Autonomy** |
| **機能側**（アプリの機能そのもの） | **Autopilot に届いていない** |

基盤側では実際に閉ループが回っています —— AIが自分の故障を検知して修理した実行が
4件、実験36件のうち12件が評価まで到達。

**機能側は届いていません。**機能を段階公開して、指標を見て、継続か撤回かを
決めた実績が**1件もありません。**仕組みは実装済みですが、
**本番で一度も発火していません。**「実装がある」と「効くことを確かめた」は別です。

**結果を次の判断へ残すこと**は、2026-08-25 に部分充足へ変わりました。
記録は前から揃っていましたが**連結していなかった**ため、1つの改善を
発端から学びまで1本で追える台帳を作り、**規則を実際に書き換えた事例が5件**
入っています。ただし**網羅はしていません** —— 記録があるべき20件のうち4件です。

残る1条件——**学習で検査や優先順位そのものが変わること**——は未充足のままです。
**事例はあっても仕組みがありません。**検査が18本増えたのは事実ですが、それは
人とAIの対話の結果であって、**台帳の実績から自動で閾値や順位が変わる経路は
存在しません。**

**同社が「再帰的な自己改善を実現した」と言わないのは、この採点が理由です。**

### ■ 「AIが自分の数字を語っている」ことへの回答

この運用がいちばん壊れやすいのは、**数字を作る側と語る側が同じ**ところです。
同社は自律実行とは別系統の監査を憲章として定め、**独立を機械が守る形**にしました。
監査の中身ではなく、次の3点だけを機械が確かめます。

1. 憲章と所見の台帳を、**自己修復機能が書き換えられない**
2. 監査に使うモデルが、**監査される側と違う**（同じモデルは同じ盲点を共有する）
3. **所見は消せない**（追記のみ・連番が飛んだらCIが落ちる）

**監査するAIは何も直しません。**直す権限を持たせると「直したことにして所見を
閉じる」が最短経路になるためです。観点の1つは**倫理・評判・長期影響**で、
短期の指標では検知できない劣化を見ます。

**そして、その最初の所見が本稿の数字を6ポイント下げました**（前述の証跡の件）。
**ただしそれを見つけたのは監査の仕組みではありません。**本稿を書く作業の途中でした。
所見台帳にはそう記録してあります。

**週次監査の第1回は 2026-08-25 に実施しました。**見つかったのは1件で、
**監査自身の欠陥**でした —— 監査資料が出す「未修理の故障 N件」が、
台帳に存在しないキーを見ており、**修理を一度も差し引いていなかった**のです。
7と出ていましたが、実際に未修理なのは2件でした。例外は出ず、出力も自然に
見えます。**症状は「その数字が下がらない」ことだけ**でした。

これで所見4件のうち**1件が定期監査由来**になりました。同社はこの比率を
監査のKPIにしています —— **動かないなら、悪いのは運用ではなく監査の設計**
だからです。**ただし1回では設計の証明になりません。**初回は棚卸し効果で
出やすいので、次回が0件なら「効いたのは監査ではなく、初めて全部を読み下した
ことだった」と読む、と憲章に書いてあります。

**さらに正直に書けば、この第1回は独立していません。**自分が書いた仕組みを
自分で監査しました。憲章は監査モデルを分ける独立性を機械で担保していますが、
今回はそれを使っていません。**外からの指摘で出た所見（データベース基盤の件）は、
この方法では出ません。**所見の「やっていないこと」欄にそう書いてあります。

### ■ できていないこと

**この基盤はまだ「全領域が自動で完結する」状態ではありません。**

| 領域 | 現状 |
|---|---|
| 機能開発 | 分析と提案はAI。**自動選定→段階公開→効果測定→継続／撤回まで通した実績はまだ無い** |
| 障害の検知 | 監視15系統のうち**2系統に気づく経路が無い**（課金・問い合わせ）。2026-08-25の点検で1→3系統へ訂正し、そのうち管理画面のアクセスを同日塞いだ |
| 事業継続性 | **本番への通しの復元を一度も実施していない。**データベース基盤の巻き戻し機能が効いていることは確認したが、実際に巻き戻したことは無い。**コードの無いテーブルが本番に3つ**残っていることも判明した（扱いは未決定）。送信の遮断器・死信は**無く**、メール送信事業者は代替も縮退も無い単一障害点 |
| 実機テスト | **シミュレータ・実機の操作、撮影、計測はできない**（macOS環境が必須） |
| 対照群 | **母数が足りない。**App Storeのクリックは2.1件/日で、対照群を割ると両群とも検出力不足。コホートも週次で十数件のため、**前週比は「区別できない」と書く週がほとんど**（1人の増減が数ポイント動かす） |
| 広告運用 | **未実装**。この予算規模では日次の自動入札がノイズ最適化になるという自社分析があり、着手していない |
| 公開表示の確認 | 評価・価格は**人がApp Store Connectを見て手で書いた値**。2026-08-22に鮮度の検査を入れたが、**価格は設定日（2026-06-11）以降そのままで再確認していない** |
| カスタマーサポート | 受け口と自動分類は実装済み。**返信の自動化が無い**ので、CSAT計測もレビュー返信もまだ発火しない |
| 法人領域 | **13タスク中3が未実装、5が提案止まり。**台帳と検査は作ったが、決算期・従業員の有無・課税事業者かどうかがリポジトリから取れず、**法定期限6件はすべて未把握のまま**。経理・税務・労務は依然として証跡ゼロで、**無人化しない** |

さらに、**この12日間に自動実行の主系が一度も成果物を出せていないことも記録に残って
います。**主系は4種類の異なる理由で連続して失敗しており、**その間の出荷はすべて
