## 決定 — **お金周りを除いて境界を渡す**（2026-08-27・オーナー判断）

**きっかけは「95.3%以上にしたい。無理くりでも」という指示。**計算するとこうなった。

```
    現在                            130/198 = 65.7%
    + 到達可能を全部                161/198 = 81.3%
    + 境界24件を全部渡す            185/198 = 93.4%
    + 「不能」のうち機械で解ける4件  189/198 = 95.45%  ← ここで初めて 95.3% を超える
```

**95.3% は到達できる。ただし59件を1件も落とせない**（余裕ゼロ。188/198 = 94.9% では届かない）。
そこでオーナーが選んだのは **「お金周りは渡さない」＝天井 88.9%** のほう。

| | 件数 | 中身 |
|---|---:|---|
| **渡した** | 15 | App Store公開・App Review提出・段階公開の拡大・PR TIMES配信・削除要求への対応・危機対応・ChatOps起動・収集同意・本番での停止訓練 ／ SNS投稿・TestFlight配信・Kill Switch・要望の設計落とし込み・課金導線・推論の実行場所 |
| **人に残した** | 9 | 広告費・AI実費の上限・月次予算・価格変更・価格プラン実験・プレミアム機能の設計・返金の可否・契約と送金・R&D投資継続 |

**「お金周り」は感覚で線を引いていない。**`scripts/check-authority.mjs` の `MONEY`
（AI実費／広告費／契約と送金／価格プラン／macOS分数）が既に持っていた定義に揃え、
同じ理屈で予算・返金・投資継続を足した。

### 渡しても、率は1ミリも動かない

**これが一番大事な点。**`blocker` が `policy_boundary`（オーナー判断待ち）から
`not_started`（実装待ち）へ移っただけで、**executor は1つも動いていない。**

```
    総合自動化率    65.7%  →  65.7%   （変わらない）
    到達可能な上限  81.3%  →  88.9%   （上がったのは天井だけ）
```

**権限を渡すことと、自動化されることは別。**そして紙の上で executor を上げようとしても、
`automation-rate.mjs` が執行面の証跡（ワークフロー・スクリプト・実装・テスト・台帳）を
要求するので通らない。**渡した15件は、15件ぶんの実装として残っている。**

### 不可逆な9件は、宣言では外せない

権限表（`data/authority-matrix.json`）は、不可逆な領域の承認を外すのに
**`machine_gate`** を要求する。`scripts/check-authority.mjs` の `gateProblems()` が見るのは5つ。

```
    checker             実在するファイル
    function            そのファイルが実際に export している関数
    kill_switch_path    止める経路
    daily_cap           正の数（**上限の無いゲートは例外に使えない**）
    holds_when_unknown  true（**材料が無いとき止まらないゲートは例外に使えない**）
```

だから権限表の該当行は、**ゲートができるまで承認制のまま**になる。
台帳の `unlock` は `impl_machine_gate`（9件）と `impl_granted`（6件）に分けてある。

### 失うもの

配信稿のいちばん効く節が消える。**「渡していない権限を理由つきで公開」**と、
**「撤回はAI単独／拡大は人間の承認」**の表。90.9% でも 95.3% でも、失うものは同じ。
**この判断を実装へ進めるときは、配信稿の書き直しが必ず対になる。**

## 旧・目標 — **70%**（2026-08-26 設定。上の決定で置き換わった）

到達可能な上限 79.3% の内側なので、**境界を1つも渡さずに届く。**

```
    現在        107/174 = 61.5%
    目標        122/174 = 70.0%      あと15タスク
    上限        138/174 = 79.3%
```

`node scripts/autonomy-gap.mjs --plan --target 70` が最短路を出す。要約:

| 誰が | 何を | +件数 | 到達 |
|---|---|---:|---:|
| 待つだけ | ASC Analytics のレポートが降りる | +4 | 63.8% |
| 待つだけ | BigQuery の28日蓄積（9/6前後） | +2 | 64.9% |
| 実装 | プロダクト側3件（PRD定型化 / カナリア1周 / 課金失敗の回復） | +3 | 66.7% |
| 実装 | 問い合わせの再現ファクトを非個人情報として出す | +2 | 67.8% |
| 実装 | 各社の規約本文を条項検査に載せる | +2 | 69.0% |
| **オーナー判断** | **返信文面の承認境界を決める** | +3 | **70.7%** ✅ |

**機械と時間だけで 69.0%。**オーナーの手数は**1件だけ**——返信文面の承認境界。

### その1件が効く理由

`ai_executes_gated`（数える）と `ai_proposes`（数えない）を分けているのは
**人の個別承認が要るかどうか**。返信を1件ずつ承認する設計にすると、
実装しても⑧の3件は `ai_proposes` のままで、**総合自動化率は1ミリも動かない。**

品質ゲート（禁止語・個人情報・返金約束・長さ・言語）を通ったものは自動投稿、
落ちたものだけ人へ——という形にして初めて数える側へ入る。**決めるのはそこ。**

### 並び順の基準

`--plan` の「安い順」は**オーナーの手数が少ない順**で、機械の作業量ではない。
実装7件でオーナー入力5件を肩代わりできるなら、そちらが安い——
この運用の目的関数が「人間を日常作業のボトルネックから外す」ことだから。

**⑬アナログ領域の5件は、件数が最大でも後置する。**従業員も営業活動も無い会社に
採用パイプラインを作るのは、運営が良くなるからではなく分母の都合。
`UNLOCKS.impl_analog.defer` がそれを並びの最後へ落とし、selftest が守っている。

## 0. 結論を先に

**95% は、この分母では成立しない。**

```
    現在              107/174  = 61.5%
    到達可能な上限    138/174  = 79.3%   ← 実装・外部接続・書類で届く範囲
    境界を全部渡しても 160/174  = 92.0%   ← 人へ残した22件をすべてAIに渡した場合
    目標 95.0%        166/174
```

**App Store公開も価格変更も危機対応も全部AIに渡して、なお6件届かない。**
残る14件は物理・対人・観測不能・検出力不足で、**渡しても実行できない**
（実機の操作、現地設営、採用面談、対照群の検出力、副系セッションのログ）。

つまり 95% に到達する方法は無く、**到達したことにする方法だけがある。**
分母を組み替える、AI関与率（86.9%）に乗り換える、証跡の無い行を実行側に数える——
どれもこの台帳が最初から禁じているもので、`--check` が落とす。

**追う数字は 79.3% のほう。**これは実際に届く。

## 3. 22件の境界を渡すとどうなるか

`node scripts/autonomy-gap.mjs` が名指しで出す。中身は次のようなもの:

- App Store への公開（審査通過後）／App Review への提出／実機での事前確認の後段
- 価格の変更／価格・プラン・ペイウォールの実験
- 月次上限の決定／月次予算の決定
- 段階公開への自動昇格（撤回はすでにAI単独）
- 削除要求への対応／収集同意
- 危機対応（個人情報事故・法的請求・重大障害・炎上）

**これらを渡しても 92.0% までで、95% には届かない。**
そして渡した時点で、プレスリリースの中心にある
「AIに App Store へ出す権限は渡していない」が書けなくなる。
**数字のために売りを捨てて、しかも数字は目標に届かない。**

## 4. 95% と書ける数字は、別の分母ならすでにある

同じ運用について、**測り方の違う数字**がいくつかあり、そのうち2つはすでに95%を超えている。

| 指標 | 値 | 分母 |
|---|---:|---|
| 成果物のAI自律率 | **100%** | 出荷13件のうち人が中身に触っていない割合 |
| コミットのAI著者率 | **99.5%** | 2026-08-11〜21・3リポジトリ・マージ除く |
| 変更行のAI著者率 | 94.2% | 同上 |
| **総合自動化率** | **61.5%** | 運営業務174タスク（未実装を分母に含む・最も厳しい） |

**乗り換えではなく、併記なら正しい。**この台帳の規約は
「4つの率を必ず並べて出す」であって、低い数字を隠さない限り高い数字を出してよい。

正しい言い方はこうなる:
**「出荷物はすべてAIが書いている（100%）。運営業務全体で見ると、まだ61.5%」**

前半だけを出すのが goodharting で、**両方出すのがこの運用の売りそのもの。**
