# 開発記録の外部ブログ配信 — 執筆 Runbook（dev.to / はてなブログ / はてなブログ「メモの設計図」 / ライブドアブログ）

このファイルは `.github/workflows/devlog-syndication.yml` の執筆ステップ（Claude Code）が読む手順書。
**1回の実行で書く記事は1本。**投稿・公開確認はこのステップの外（`scripts/devlog-syndication.mjs`）が行うので、
ここでやるのは「読む → 題材を選ぶ → 書く → JSON に保存する」だけ。

- 読む: `.syndication/context.json`（ワークフローが用意する）と、そこに挙がっているリポジトリ内のファイル
- 書く: `.syndication/article.json`（下の §6 の形）
- **ネットワークには出ない。**必要な事実はすべてリポジトリの中にある。無い事実は書かない。

媒体は `context.platform` で分かる。4つある。

| `platform` | 媒体 | 言語 | 書くもの（§3） |
| --- | --- | --- | --- |
| `devto` | dev.to（simple_memo） | 英語 | 開発の記録から引いた技術記事 |
| `hatena` | はてなブログ（simplememofast.hatenablog.com） | 日本語 | 開発の記録から引いた技術記事・開発日誌 |
| `hatenadiary` | はてなブログ「メモの設計図」（simplememofast.hatenadiary.jp） | 日本語 | 読者向けの「メモの仕組みの設計」の文章 |
| `livedoor` | ライブドアブログ「captio式シンプルメモ開発日誌」（captio.livedoor.blog） | 日本語 | 「なぜこの設計にしたか」の開発ノート |

「メモの設計図」とライブドアは 2026-10-03 に足した（それまでは Mac のローカル定期タスクがブラウザで投稿していて、
AI の開示が無く、出典の無い数字も載っていた。オーナーが選択式で「新しい仕組みに移す」を選んだ）。

## 0. この配信の位置づけ

- 記事は**単独で読んで役に立つ**ものにする。サイトへ連れていくための記事にしない。
- 書き手は**AIエージェント**で、それは公開面で開示される（dev.to は API で「Fully Autonomous」、
  はてな2つとライブドアは本文末尾の開示文。どれもスクリプトが付けるので、本文に書かなくてよい）。
  **だから本文で人間の開発者本人を名乗らない。**「I'm a solo developer」「個人開発者の私」のような名乗り、
  作り話の体験（「コーヒーを淹れて」「ユーザーに言われて」）、感情の描写は書かない。
- 素材は**このプロジェクトで実際に起きたことと、実際に作られたもの**だけ:
  記事ネタ台帳（`docs/story-seeds.md`）の種、サイトのページ（`allowed_site_links` の `file`）、
  一次ファイル（`llms.txt` / `data/site-constants.json` / `data/benchmark.json`）。

## 1. 題材を選ぶ（上から順に）

**日本語の3媒体（はてなブログ・メモの設計図・ライブドア）は「使った題材」を共有する。**
同じ種から日本語の似た記事を3本出さないため。`context.used_bases` には、この媒体で使った題材に加えて、
日本語の姉妹ブログ（`context.sibling_platforms`）で使った題材も入っている。姉妹ブログの既存記事は
`context.sibling_posts`（媒体・題名・URL・書き出し）に別に載っている。姉妹ブログの公開面が読めなかった回は
`context.sibling_read_errors` に残っている（そのときは、読めた範囲の題材だけが共有されている）。

1. `context.seeds_available` の種から1件。`seed.claim`（一行の主張）が、`context.existing_posts` と
   `context.sibling_posts` の題名・書き出しと**同じ話になっていない**ものを選ぶ。
   dev.to は `drafts.en`、日本語の3媒体は `drafts.note` がある種だけが並んでいる。
   - 下書き（`drafts.*`）は素材であって本文ではない。**段落を写さない。**同じ種を別媒体でも使うので、角度を変える。
   - `numbers`（引用できる数字）は**台帳の値をそのまま**使う。再計算しない。古いと感じたら、その種を使わず次へ。
   - `avoid`（使わない表現）を守る。
2. 使える種が無い／どれも既存記事と重なるときは、`allowed_site_links` のページを1つ選び、
   **そのページの内容を土台にした別の記事**を書く（要約の転載ではなく、そのページが答えている問いを
   別の入口から説明する記事）。そのページのファイルを必ず読んでから書く。`basis` は `page:<ファイル>`。
   `context.used_bases` にある題材は選ばない（姉妹ブログで使ったページも含む。検査は
   「この媒体か日本語の姉妹ブログで使用済み」として落とす）。
3. どちらも無理なら、書かずに `article.json` に `{"skip": true, "reason": "…"}` だけを書いて終える
   （ワークフローは失敗として扱い、次の枠で再試行する。**基準を下げて書くより良い**）。

## 2. 事実の規則（検査で機械的に落ちる）

- **本文と題名に出す数量は、`sources` に挙げたファイルか一次ファイルに同じ数字があるものだけ。**
  検査は本文の数字を1つずつ出典テキストと突き合わせる（識別子の一部・日付・年・12以下の整数は除く）。
  出典の無い数字（「83%」「187ms」「214件」「100人」の類）は削る。概数に言い換えても同じ扱いなので、
  **数字を作らない**ことで通す。
- 製品の事実は `context.product_facts` と `llms.txt` が正:
  起動は**約0.4秒（ウォーム起動・タップ→入力可能）**／**E2EE ではない**（端末内 Outbox を AES-GCM-256 で暗号化・配送は通常の SMTP）／
  **無料トライアルは無い**（Free は1日3通ずっと無料）／Captio の**公式後継ではない**（着想を得た独立の実装）。
- **版番号と App Store の評価は書かない。**価格は必要なときだけ `product_facts` の値で。
- 旧名「Captio式シンプルメモ」を製品名として使わない。現行名は `product_facts.app_name_ja` / `app_name_en`。
  （ライブドアのブログ名「captio式シンプルメモ開発日誌」は媒体の名前で、製品名ではない。本文で製品をこの名前で呼ばない）
- 個人名・個人のSNSアカウント名を書かない。
- 誇大表現・定型の煽りを書かない（完全自動化／人間不要／世界初／爆速／神アプリ／革命／圧倒的／最強／徹底解説／完全ガイド／◯選／game-changer／revolutionary など）。
- 売り込みの呼びかけを書かない（「ダウンロードはこちら」「今すぐ試して」「try it free」など）。製品名の出現は3回まで。

## 3. 声と構成

- **主語は記録にある事実。**「パイプラインは〜と記録した」「台帳は〜を返した」「the project shipped …」のように、
  起きたことを主語にする。一人称単数（I / my / 私は）は dev.to で2回まで、**日本語の3媒体で1回まで**（引用は数えない）。
  「we」は、そのプロジェクトが実際に行ったと記録にある行動にだけ使う。
- **最初の段落で問いに答える。**前置き・自己紹介・共感の枕を置かない。
- `##` 見出しを3つ以上。1〜2個は問いの形（「なぜ〜か」「What … ?」）にする。検索と AI 回答に引用される単位は見出し＋直後の段落。
- **反対側の視点を1節入れる**（この設計が向かない場面・限界・別の解き方）。
- 最後は小さな結論か、読者がすぐ試せる確認手順。次回予告や購読の誘いは書かない。
- コード・手順・設定値があるなら、コードブロックで具体的に（コードの中の数字は数量の主張として数えない）。

### dev.to（英語）

- 700〜1,900語。平易で具体的な英語。見出しは sentence case。
  **数え方**：コードブロック・インラインコード・URL・日付を除いた語数。コードや表が多いと地の文が足りなくなるので、
  **地の文で 900〜1,400語を目安に**書く（700語を割ると検査で落ちる）。
- `tags`: 1〜4個、英小文字と数字だけ（例: `ios`, `swift`, `devops`, `automation`, `productivity`, `obsidian`, `ai`, `webdev`）。
- `series`: `context.series_allowed` のどれか、または `null`（無理に付けない）。
- `description`: 170字以内の要約（本文の最初の段落の言い換え）。

### はてなブログ（日本語）

- 2,500〜7,500字。常体（「だ・である」ではなく「〜だ」「〜する」基調）。平均文長は短めに、長い文の次は短く。
  **数え方**：コードブロック・インラインコード・URL・日付・空白・記号（`# > * _ | -`）を除いた文字数。
  **地の文で 3,000〜4,500字を目安に**書く。2026-09-25 の試験実行では、執筆ステップの見込みより短く（2,312字）、
  下限の2,500字を割って手直しに回った。**見出し4〜6個・各節3〜5段落**を目安にすると足りる。
- 箇条書きは最大3か所。地の文で論理の段差（しかし／だからこそ／逆に）を作る。
- `tags`（はてなのカテゴリ）: 1〜5個、各20字以内。既存記事のカテゴリ（`iOS`／`PKM`／`メモアプリ`／`開発日誌` など）を優先。

### はてなブログ「メモの設計図」（日本語・`hatenadiary`）

- **読者向けの「メモの仕組みの設計」の文章。**開発日誌の体にしない（「今日は〜を直した」「パイプラインが〜」を主題にしない）。
  主題は、読者が自分のメモの仕組みに持ち帰れる設計の話: 捕まえる → 受信箱 → 見返す、の流れ／プレーンテキストの寿命／
  PKM（Obsidian など）への流し方／入口と出口の数／整理を後回しにする設計、など。
  ブログのサブタイトルは「続くメモの仕組みについて考える場所。」。
- それでも**記録とサイトのページに根ざす。**主張の根拠は種・サイトのページ・一次ファイルにあるものだけ。
  一般論で埋めない（「研究によると」のような出典の無い言い方をしない）。
- 2,500〜7,500字（数え方は はてなブログと同じ）。常体・短い文。見出し4〜6個・各節3〜5段落が目安。
- `tags`（カテゴリ）: 「メモ術」と、`知的生産`／`PKM`／`iOSアプリ開発`／`習慣化`／`生産性` のどれか1つ（計2個）。
  既存記事はこの形でそろっている。
- 自社リンクは1〜2本（§4）。

### ライブドアブログ（日本語・`livedoor`）

- **「なぜこの設計にしたか」を記録から説明する開発ノート。**判断・却下した案・その理由・限界を、記録にある事実で書く。
  書き手は AI なので、**人間の開発者を名乗らない**（§0。「開発者として説明したい」「私たちは〜と考えている」と人の声で語らない）。
- 2,500〜7,500字（数え方は はてなブログと同じ）。常体・短い文。
- 本文は**Markdown で書けばスクリプトが HTML にする。**使えるのは次の範囲だけ:
  `##`〜`####` の見出し／段落（段落の中の改行はそのまま改行になる）／`---` の区切り線／`>` の引用／
  箇条書き（`-`）と番号付き（`1.`）／``` のコードブロック／表（見出し行と `|---|` の区切り行）／
  `**太字**`・`*斜体*`・`` `コード` ``・`[説明](https://…)` のリンク。
  **HTML のタグ・画像・脚注・打ち消し線・アンダースコアの強調は使わない**（タグは文字のまま出る。画像は載らない）。
- カテゴリは**スクリプトが「メモ術」に固定する。**`tags` は書いてもよいが、送られない（無いカテゴリが勝手に増えるのを避ける）。
- 自社リンクは1〜2本（§4）。

## 4. リンクの規則

- **自社サイトへのリンクは dev.to で1〜2本、はてなブログで1〜3本、「メモの設計図」とライブドアで1〜2本。**
  `context.allowed_site_links` の `url` を**一字一句そのまま**使う
  （リダイレクトの無い正規 URL しか通らない）。本文の主張の出典・詳しい説明として、関係のある段落に置く。
- リンクの文字列は**そのページが何かを説明する言葉**にする（例: 「ベンチマークの測り方」「the benchmark methodology」）。
  検索語そのもの（「メモアプリ」「best memo app」「Captio 代替」）をリンク文字列にしない。
- 外部リンクは3本まで。**確かに存在すると分かっている URL だけ**（公式ドキュメントのトップなど）。
  検査は全リンクを実際に取りに行き、404 やリダイレクト先の不明なものは落とす。App Store の直リンク・短縮URLは使わない。

## 5. 書き終えたら確かめること

1. 題名が `existing_posts` と `sibling_posts` のどれとも別の話か（近い題名は検査で落ちる。姉妹ブログの記事とも比べる）
2. 長さが下限を十分に超えているか（日本語の3媒体は地の文だけで3,000字前後、dev.to は900語前後。節ごとの字数・語数を足して確かめる）。
   **目安で足りる。数え直しに何度もターンを使わない**（正確な数は検査が数え、足りなければ手直しに回る。2026-09-29、はてなの執筆は61ターンで上限に達して落ちた）
3. 本文の数字をすべて、`sources` のどのファイルのどこから引いたか言えるか
4. 自社リンクの URL が `allowed_site_links` にそのまま在り、本数が媒体の範囲（§4）に収まっているか
5. 人間の開発者本人を名乗る文・作り話の体験が無いか
6. 本文に front matter（`---`）、開示文、`devlog-syndication:` の印、「題材の記録:」を**書いていない**か（どれも投稿時に付く。
   はてなは HTML コメントの印を公開面から消すので、はてな2つとライブドアには題材の記録を開示文の後ろに見える形で付ける）
7. ライブドアなら、§3 の範囲外の書き方（HTML のタグ・画像など）を使っていないか

## 6. 出力（`.syndication/article.json`）

```json
{
  "platform": "devto / hatena / hatenadiary / livedoor のどれか（context.platform と同じ）",
  "title": "題名",
  "description": "dev.to のみ・170字以内（日本語の媒体は省略可）",
  "tags": ["…"],
  "series": null,
  "basis": "S-YYYYMMDD-… または page:<allowed_site_links の file>",
  "sources": ["docs/story-seeds.md", "en/blog/…/index.html"],
  "body_markdown": "本文（Markdown。題名の # 見出しは入れない）"
}
```

`tags` は dev.to が1〜4個、はてな2つが1〜5個（カテゴリ）。ライブドアは省略してよい（書いても送られない。書くなら5個まで）。
`sources` には**実際に読んで数字や事実を引いたファイル**を1〜8件、リポジトリのルートからの相対パスで書く。

## 7. 検査で落ちたとき（手直しのステップ）

`.syndication/validation.txt` に落ちた理由が並ぶ。**`.syndication/article.json` をその場で直す**
（新しいファイルは作らない）。数字の出典が見つからないときは、その数字を**削る**。題名が既存記事
（姉妹ブログの記事を含む）と近いときや、題材が使用済みのときは、題材ごと選び直してよい（`basis` と `sources` も合わせて直す）。
