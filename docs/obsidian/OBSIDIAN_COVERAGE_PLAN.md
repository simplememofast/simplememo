# Obsidian Coverage Plan — まとめサイト化のバックログ駆動（2026-08-12）

**オーナー指示:** 「このペースでObsidian情報まとめサイトできるの？遅すぎる」
（2026-08-12）。本計画はこの指示に基づき、**カバレッジ構築を独立レーンとして解禁**する。

## 1. 何を直したか — ゲートの適用範囲の誤り

ノイズフロア（期待クリック3未満は根拠にしない）は2026-08-09に
**既存ページのCTR回収施策**の誤判定を止めるために作られた物差しで、そこでは正しい。

しかしこれを**新規カバレッジ**にまで適用すると鶏と卵になる:
**GSCは既に露出している需要しか観測できない**。ページが無い領域はimpが出ず、
impが無いから書けず、書かないから永遠にimpが出ない。
`OBSIDIAN_TOPIC_MAP.md` Tier D自身がこう書いている:
「需要が無いのではなく、**このサイトがまだ何も持っていないだけ**の可能性が高い」。

**新しい整理:**

| 施策の種類 | ゲート |
|---|---|
| Refresh / CTR回収（レーンA-1） | ノイズフロア（従来通り・変更なし） |
| **新規カバレッジ（レーンE）** | ①coverage-queue.json に載っている ②品質ゲート80点 ③検証規約（§28） ④固有価値（実機検証/実カウント/一次情報）を1つ以上含む |

量産スパムとの境界は「クリック期待値」ではなく**品質と固有価値**で守る。
このサイトで実際にAIOに引用されているのは「測った・断定できる」ページであり、
薄いページを速く並べても資産にならない（それは競合リスト記事と同じ土俵に降りること）。

## 2. Month 3 凍結の解除

`OBSIDIAN_TOPIC_MAP.md` 結論5「Plugins / Sync / AI / Beginner は Month 3 まで
着手しない」は、週1本・人間監督体制での期待値判断だった。毎日運転＋
オーナーの明示指示により**2026-08-12で解除**。ただし:

- **VISION.md（Capture OS）に従う**: ObsidianはDestinationとして書く。
  AIクラスタの記事でもSimpleMemoの訴求は「AIが賢い」にしない。
- 検証ゲートは緩めない: プラグイン記事は**このLinux環境で実際にインストールして
  動かして**書く（Obsidianデスクトップは動作実績あり）。できない検証は書かない。
- EN拡張はしない（既存判断のまま）。

## 3. バックログ

機械可読の正: `growth/content/coverage-queue.json`（36項目・優先順）。
毎日の実行はキュー先頭から。**「キューが枯れて書けない日」はこれで消える。**

構成（フェーズは目安・キュー順が正）:

- **P1 まとめサイトの骨格（〜2週間）**: 比較ハブ＋Obsidian軸比較、
  入門セット（とは/始め方/Vault/料金）、同期セット（まとめ/iCloud/公式Sync/Git）
- **P2 定番深掘り（〜4週間）**: プラグイン総覧＋定番4本（実機検証）、
  PKM（セカンドブレイン/Zettelkasten のObsidian軸）、ジャーナリング、AI連携概観
- **P3 トラブルシュート・運用**: 同期されない/重い/開かない系
  （既存2本のトラブルページと同型・実証済みパターン）

## 4. ペースの見通し（正直な算数）

- 1日1本 × キュー36本 ＋ 既存Refresh → **骨格（P1の12本）は8月末**、
  **キュー消化は9月下旬**。この時点でJA圏の「Obsidian情報まとめサイト」の
  体裁（入門/同期/プラグイン/比較/運用/トラブルの6系統）が揃う。
- 立ち上がり3日間（8/11-12）が遅く見えたのは、記事1本＋**基盤**（自動運転・
  日報・content-graph・レーン制）を並行構築していたため。基盤は完成済みで、
  明日からの毎日は全てコンテンツに使われる。
- 2本/日へ上げることは技術的には可能（GHAのスケジュール枠を増やすだけ）。
  ただし1本ごとの実機検証の深さがこのサイトの唯一の差別化なので、
  **推奨は1本/日を維持**し、枯れない供給をこのキューで保証する形。

## 5. 運用への接続

- Runbook §2 に**レーンE（Coverage）**を追加済み。レーンA/Bに足切り超えの
  案件が無い日は、迷わずキュー先頭を実装する（= 事実上毎日1本が出る）。
- 各項目の実装時は Existing Page First を個別に確認（キューの `collides_with` 欄）。
  既存ページが主題を持っている場合は新規でなくRefreshに切り替える。
- 完了したらキューの `status` を done にし、`content-graph.json` に登録
  （/obsidian/ 配下はCIが登録漏れを落とす）。
