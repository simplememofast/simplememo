## オーナーが行う操作

1. GitHub の `simplememofast/simplememo` → Settings → Secrets and variables → Actions → **Variables**
2. **New repository variable**: 名前 `AUTOPILOT_RECOVERY_ONCE`、値は試したい日の **JST の日付**（例 `2026-10-15`）
3. その日の 07:30 JST の定時 run（配信は2〜3時間遅れることがある）が、封じ込めを1回だけ越える
4. 終わったら変数を消してよい（消さなくても、日付が過ぎれば効かない）

Claude Code のセッションは、この変数を読むことも書くこともできない（Actions variables の API は
プロキシが 403 を返す。2026-10-13 に実測）。ただし、オーナーの資格情報を共有する別のエージェントまでは
技術的に排除できない。これは 09-30 の主系の許可（`NATIVE_RECOVERY_ONE_USE.md`）と同じ限界で、
**変数を入れること自体がオーナーの判断の記録**になる。

## 越える条件（`scripts/autopilot-selfheal.mjs` の `actionsRecoveryOnce`）

全部を満たしたときだけ越える。1つでも外れたら、今までどおり止まる。

- 変数の値が `YYYY-MM-DD` で、**今日の JST の日付**と一致する
- `schedule` で起きた run の**1回目**（`workflow_dispatch` と再実行は越えない。AI のセッションも手動起動はできるため）
- リポジトリが `simplememofast/simplememo`、参照が `refs/heads/main`
- 全体停止も `actions` の停止も立っていない
- 台帳と権限表の整合に問題が無く、上限が 3 のまま
- 修理が必要な故障（レーンFの対象）が無い。人に渡すだけの行（usage_limit など）は残っていてよい
- 封じ込めの対象が**ちょうど** `ap-20261005-actions-37249907984` と `ap-20261006-actions` の2行で、
  どちらも route `actions`・`no_artifact`・修理5回
- その2行の中身が、許可を出した時点（#2063 のマージ `9d67f58c5`）から1バイトも変わっていない（指紋で照合）
- #2062 のマージ（`a35323d7b`）が HEAD の祖先にある

**新しい故障が1件でも増えたら効かない**（封じ込めの対象が変わるため）。試運転が失敗して
新しい `no_artifact` が記帳されると、それ以降この許可は効かなくなる。もう一度試すかは、
その結果を見てオーナーが決める（コードを変える新しい判断になる）。

## 試運転の日にしないこと（2026-10-21 追記）

- **試運転の日は、その日の定時 run が終わるまで、Obsidian Autopilot を手動起動（workflow_dispatch）も再実行もしない。**
  再実行は定時の1回目ではないので封じ込めを越えず、手動起動が同じ concurrency group に並ぶと
  待機中の定時 run が取り消されることがある（取り消された定時 run も `cancelled` の行として記帳されうる）。
- **publish ジョブだけを再実行しても回復にならない。**引き渡し（handoff）の artifact 名が
  `run_attempt` を含むので、「Re-run failed jobs」の2回目からは見つからない（`rejected_handoff_missing`）。
  publish が途中で落ちたら、再実行ではなく、残った当日ブランチ・PR を見てオーナーが次の手を決める。
- 公開運転表の点数は JST の日付で決まる。記帳（publish）と PR の SEO Validation が JST の日付をまたぐと、
  運転表が記帳時の日付のままになり、成果物の無い日でも価値契約が要る扱いで落ちる（`check-autopilot-page --check` も同じ境目で落ちる）。
