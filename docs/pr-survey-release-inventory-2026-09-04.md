# 調査リリースの素材棚卸し —— **接木すれば必要条件を通る。ただし数字はまだ1つも取れていない**

**2026-09-04。**`pr-discover-strategy-2026-09-04.md` §6-2 の「実装ゼロで撃てる唯一の形」を、
実際に撃てるところまで詰められるかを測った記録。

> **結論を先に。**
> 1. **接木の道具は揃っている。** `input_method` が **`watch` / `siri` / `voice` / `keyboard` /
>    `sample_chip`** を区別して記録している（iOS 実測）。つまり
>    **「Apple Watch から送られたメモの◯%」「AirPods（Siri）経由の◯%」は、原理的に出せる。**
>    これが S2 を 8 → 15 に上げる接木の実体で、**必要条件（S2 >= 10）はこれで通る。**
> 2. **しかし、この環境からは数字が1つも取れない。** `ADMIN_API_KEY` がセッションに無い
>    （env 実測）。**数字は全部 null のまま報告する。**
> 3. **台帳にある既存の数字は、そのままでは配信に使えない。**「first send の 77% が音声」は
>    **5日間・n=62・内部アカウント未除外の生値**で、95%信頼区間は **[65.6%, 86.0%]**（幅 20.5ポイント）。
>    **「77%」と書くと、実測が持っていない精度を主張することになる。**

## 1. 接木の道具 —— `input_method` は端末と経路を区別している

iOS が送信イベントに載せる `input_method` の実値（`grep` 実測・2026-09-04）:

| 値 | 何を意味するか | 見出しで使える固有名詞 | S2 |
|---|---|---|--:|
| `watch` | Apple Watch から送られた | **Apple Watch** | **15** |
| `siri` | Siri / App Intents 経由（AirPods からの発話を含む） | **AirPods / Siri** | **15** |
| `voice` | iPhone 本体の音声入力 | iPhone | 10〜15 |
| `keyboard` | キーボード入力 | ——（対照として使う） | — |
| `sample_chip` | オンボーディングのサンプル | ——（**除外する**） | — |

**これが分かったことが、この棚卸しの最大の収穫。**
追記D-3 は調査リリースを「S2 が弱点（メモ＝無形）で 8点」と採点していたが、
**その採点は「メモの話をする」前提のもの**だった。
**Apple Watch / AirPods を主語にできるなら、同じ調査が S2 15 になる。**

    調査リリース（接木なし）  S1 30 / S2  8  → 必要条件 ✕（S2 < 10）
    調査リリース（接木あり）  S1 30 / S2 15  → 必要条件 ○○

**サーバ側も受けている。**`ANALYTICS_PROPERTY_KEY_ALLOWLIST` に `input_method` があり、
`funnel-core.ts` に `by_*_input_method` の集計クエリが実在する
（クエリ#7 = `input_method` 別の RAW `memo_send_success` 件数）。**新規実装は要らない。**

> ⚠ **`source` は別物。**allowlist にある `source` は Universal Links の
> 由来（`universal_link` 等）で、`ObsidianManager.sendIfEnabled(_:source:)` の
> `source`（keyboard / siri / watch）とは**同名の別フィールド**である。
> **混ぜると集計が静かに壊れる。**使うのは `input_method` のほう。

## 3. 台帳にある既存の数字と、その限界

| 数字 | 出所 | **そのまま書けるか** |
|---|---|---|
| **first send の 77% が音声（48/62）** | `GROWTH_ROI_PLAN_2026-08-20.md` §2-4。**5日間（8/15–19）・生値** | **書けない。**§3-1 |
| 活性 58%（新規100→活性58） | 同 §2-2。同じ5日窓・生値 | 同上 |
| Obsidian 設定済みコホートの活性 97.6%（40/41） | 同。**n=41** かつ**逆因果の注記つき** | **書けない。**因果に読める書き方になる |
| D1 40.28% / D7 8.33% | ASC ベンチマーク。**ASC オプトインのみ**の母集団 | 母集団を併記しない限り書けない |

### 3-1. 「77%」は、実測が持っていない精度を主張する

n=62 の 48件。**Wilson 95%信頼区間は [65.6%, 86.0%] —— 幅 20.5ポイント。**
（`simplememo-api` の `src/stats.ts` の `wilson95` と同じ式で計算・2026-09-04 実行）

- **「77%」と書くと、幅 20.5ポイントの推定を小数第0位まで確定した値として出すことになる**
- **「約8割」（80%）なら区間の内側に収まる**（追記B の仮タイトルが「約8割は『話して』残す」なのは正しい）
- **母数 62 と窓 5日を併記しない数字は、配信物に出さない**

計算は `simplememo-api` の `src/stats.ts`（Wilson / Fisher）が持っている。
**散文で再計算しない** —— `simplememo-api/CLAUDE.md` が「単日の率では何も決めない」
「分母が 20 に達した累積だけ」と定めているのと同じ規律。

### 3-2. 内部アカウントが除外されていない

上の 77% は**生値**で、R12-1（ファネル正史の再取得・内部除外）は
`GROWTH_ROI_PLAN_2026-08-20.md` の W4 タスクとして置かれたまま。
**開発端末の送信が混ざった率を、プレスリリースで外へ出さない。**

`internal-accounts.ts` の resolver は実装済みなので、**鍵さえあれば除外後の値が取れる。**

## 4. 撃てる状態にするために要ること（**順番どおり**）

1. **鍵を通す** —— `ADMIN_API_KEY` を持つ実行系で `POST /admin/analytics/funnel` を叩く。
   **内部除外あり**で、**90日窓**（保持の上限）で取る

   `sample_chip` は**除外**する（オンボーディングのサンプルであってユーザーの発話ではない）

4. **見出しを決めて採点する** —— §5 の型。**採点は見出しが決まってから**
   （PR⑥ が落ちた穴。`pr-discover-strategy-2026-09-04.md` §3-3）
5. **`growth/experiments/experiments.json` に `pr_release` レコードを起こす** ——
   `status: planned`・ゲートは配信物ができてから 0/1
