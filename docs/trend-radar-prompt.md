# トレンドレーダー — 朝ルーチン/autopilot用プロンプト文面（v4 追記E準拠）

**位置づけ:** D-SCOREのS5（時流・10点）を運任せにせず「配信日の設計で買う」ための
毎朝の監視項目。実測に正直に: 当たり2本（6/1・7/6）は外部トレンドに乗っていない——
**新規性（S1×S2）が主・時流は増幅器**。トレンドはS1の代わりにならない。

**組み込み先:** オーナーの朝ルーチン/autopilotのRoutine（オーナー環境の作業のため、
本書は文面まで。実組み込み時はこのプロンプトを1項目としてそのまま貼る）。

**記録の宿命:** 検知→対応→結果は必ず `growth/data/annotations.json` に残す
（P6の系列アノテーション。type: feature か pr。検知だけで対応しなかった日は残さない）。

## プロンプト文面（ここから下をそのまま貼る）

```
【トレンドレーダー】次の3面を順に確認し、指定の形式だけで報告する。

(a) Googleトレンド急上昇（日本・過去24時間）を確認し、次の関連語のいずれかに
    掛かる急上昇があるかを見る:
    メモ / ノート / Obsidian / Notion / Evernote / LINE / リマインダー /
    カレンダー / 音声 / AIレコーダー / iPhone
(b) はてなブックマーク「テクノロジー」上位を確認し、隣接サービス
    （LINE・Notion・Evernote・Google Keep・Slack・Apple標準アプリ）の
    「終了・値上げ・障害・大幅仕様変更」の話題があるかを見る。
(c) App Store 仕事効率化カテゴリの無料ランキング上位50を確認し、
    前日から10位以上動いたメモ・キャプチャ系アプリ、または新規に
    ランクインしたメモ・キャプチャ系アプリがあるかを見る。

報告形式（これ以外を書かない）:
- ヒットなしの日 → 1行だけ:「トレンドレーダー: 本日ヒットなし」
- ヒットあり → 波ごとに1〜3行:
    1. 何の波か（一次ソースへのリンク込み・1行）
    2. 自社との交点（勝ち筋クラスタ=Obsidian/音声/Watch/Siri・LINE Keep資産・
       調査データ /data/voice-shift/ のどれに接続できるか。無ければ「交点なし」・1行）
    3. 推奨アクション（下の対応SLAから選ぶ・1行）

対応SLA（二段構え・v4 追記E-2）:
- 当日: サイト記事＋X＋note でSEO/AIO資産化（PRより先にここ。LINE Keepで実証済みの型）
- 2〜5日内: 「データか機能で語れる角度」がある場合のみPR起案。角度が無ければPRは撃たない。
  起案時は必ずD-SCORE採点から（growth/experiments の pr_release レコード型を複製）。
  突発波はS5=8〜10に加え「その波への応答としての初出」でS1=20が取れることがある——
  それでも採点してから撃つ。60未満は撃たない。

規律:
- 交点の無い波に記事を書かない（混雑窓を避ける: Appleイベント週に無関係弾を出さない）
- 対応した場合は growth/data/annotations.json に
  {date, type, label（何の波か＋何をしたか）} を追記し、結果（PV/転載/順位）が
  出たら同じ行のnoteに追記する。検知→対応→結果を1行の履歴として残す
```

## 運用ノート（プロンプトの外側）

- **年間カレンダーとの併用**（v4 追記E-1）: 9月Appleウィーク（年間最大の窓）・
  11月〜1月手帳シーズン・3〜4月新生活は予測可能な波なので、レーダー（突発波）とは
  別に配信計画側で先に押さえる。レーダーの仕事は突発波だけ。
- **待つ/待たない**（追記E-3）: S1が時間減衰する弾（先行者の窓が閉じ得る）は
  トレンド窓を待たずに撃つ。S5のためにS1を失うのは常に損。
- **結果の読み方**: レーダー起点の対応が価値を生んだかは、アノテーション経由で
  full-funnel月次（growth/scripts/full-funnel.mjs）の山谷と突合して判定する。
  3ヶ月ヒットゼロなら監視対象語を見直す（消すのではなく入れ替える）。
