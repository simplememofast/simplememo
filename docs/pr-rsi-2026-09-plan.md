## 2. D-SCORE 事前採点（案）と G1〜G4

**基準:** `experiments.json` の `pr_release` レコード型（n=5バックテストで較正・合格60）。
配信前の暫定採点であり、**見出し確定稿で必ず再採点する**。

| 軸 | 満点 | 採点案 | 根拠 |
|---|---:|---:|---|
| S1 新規性 | 30 | **26** | 「個人開発のiOSアプリが12日連続で無人出荷」は日本語ニュース面での初出性が高い。ただし「AIが開発する」自体は2026年に珍しくない → 満点は取れない。**取り分は「止まったことを検知する仕組みまで公開する」側にある** |
| S2 エンティティ到達 | 20 | **12** | App Store / Obsidian / GitHub Actions / Cloudflare は届く。ただし**「自律運用」に相当する市場語が弱い**（RSI・オートパイロットはどちらも一般語ではない）。PR②のObsidian（12,188PV）ほどの牽引エンティティが無い |
| S3 具体名詞 | 15 | **13** | 261ファイル／13,195リンク／9チェック／1,236行の実行ログ／12日連続 — 具体数値は十分。**実測に限定した分だけ強い** |
| S4 変化 | 15 | **10** | 「人がやっていた→機械がやる」の変化は明確。ただし**変化の受益者が読者ではない**（自社の運用が変わっただけ）ので満点にならない |
| S5 時流 | 10 | **3** | Appleウィークとは無関係。A案（9月下旬）ならさらに落ちる。**S5は捨てて撃つ弾**（trend-radar §E-3と同じ判断） |
| S6 ニュース動詞 | 5 | **2** | 「公開します」は弱い動詞。「初めて外部公開」等に寄せられれば+1〜2 |
| S7 ローンチ設計 | 5 | **0 → 5** | 受け皿ページ `/autopilot/`・図解・実行ログ抜粋が揃えば満点。**現時点で未着手なので0**。§1の8/24-8/26で埋める |
| **合計** | 100 | **66**（S7充足時） / **61**（未充足時） | **合格ラインすれすれ。S7を落とすと事実上ギリギリ** |

> **読み方:** 事前95の案2に比べて明確に低い。これは原稿の出来ではなく
> **S2（市場語の弱さ）とS5（時流の無関係さ）が構造的に低い**ため。
> 66は「撃ってよいが、大当たりは期待しない」水準。**PR②/③の1万PV級は狙いにくく、
> 転載20〜34本の床は取れる**というのが実績n=5から読める妥当な期待値。

## 3. 配信前に潰しておくべき穴

### 3-1. 【オーナー】`docs/GROWTH_ROI_PLAN_2026-08-20.md` がリポジトリに無い

D-SCOREの較正根拠（n=5バックテスト・合格60の由来）が入っている文書が
**4箇所から参照されているのに、リポジトリに存在しない**。

- `growth/experiments/experiments.json:1198` / `:1238`
- `growth/reports/2026-08-canonical-funnel-0815-0819.md:9`
- `data/cpp-map.json:4`

**このリリースは「判断の根拠をファイルに落としてCIに監視させている」ことが売り。**
その根幹の文書が欠けている状態で「散文は手を挙げない」と書くのは、記者に確認されたら
崩れる。オーナーのローカルにあるなら**コミットする**、無いなら**再構成する**。

### 3-2. 【オーナー・最優先】主系オートパイロットが「緑のまま成果物ゼロ」

2026-08-22の主系run（`32528028588` / job `96914156036`）が
`conclusion: success` なのに `permission_denials_count: 14` で**成果物ゼロ**。
`allowed_bots` 修正（PR #522/#523）は効いており、以前の「3秒で落ちる」とは別の壊れ方。

**毎朝ジョブが緑のまま推移するため、最も気づきにくい故障。**
`obsidian-autopilot.yml` の `permissions:` / `additional_permissions` /
`claude_args` のツール許可リストを確認してほしい（副系の実行ログにも同じ依頼を積んである）。

> **配信との関係:** 現状は副系CCR Routineが代走して連続稼働を維持しているが、
> 「主系が動いていない」まま「12日連続稼働」と書くと不正確。
> **配信日までに主系を直すか、原稿を「主系・副系の二重化で維持している」と書き換えるか**、
> どちらかが要る。後者のほうがむしろ話として強い（冗長化の実例になる）。

### 3-3. 【AI】受け皿ページ `/autopilot/` が無い（S7 = 0点の原因）

PR TIMESからの流入を受ける場所が無い。過去実績では
**被リンク獲得がPR TIMES単発配信に全面依存**しており（`GROWTH-AUDIT-2026-08-09.md`）、
受け皿の有無が転載後の資産化を左右する。

必要な要素：1サイクルの図解、実行ログの実物抜粋、「AIに与えていない権限」の該当箇所引用、
できないことの一覧、`data/autopilot-status.json` へのリンク（**生きている状態が見える**）。

**`content-graph.json` 登録とデスクトップQRが必須**（CIが強制する）。

### 3-4. 【AI】原稿の数字は配信日時点で更新が必要

本文の「12日連続」「261ファイル」「13,195リンク」「1,236行」はすべて2026-08-22時点。

## 4. 「書けない」を「書ける」にするための開発項目（配信後でよい）

台帳 §10 で落とした11項目のうち、**実装すれば次回以降のPRで使えるもの**。
今回の配信には間に合わないので、**間に合わせようとしないこと**（急いで作った実装で
主張すると、記者に確認された瞬間に一番痛い）。

### A. ⑤ トークンマネジメント（証跡ゼロ → 実装可能）

材料はすでにある。`total_cost_usd` は主系runのログに出ており、
`cron_run_log` と同じ様式で D1 に貯めれば「週次の実費とアロケーション」が作れる。

```
最小実装:
  1. obsidian-autopilot.yml の Claude Code ステップ出力から total_cost_usd を抽出
  2. data/autopilot-status.json に cost セクションを追加（既存の日報経路に相乗り）
  3. simplememo-api の autopilot_report に週次集計を足す
  4. 上限を超えたら次回runをスキップする（既存の *_DAILY_CAP / KILL_SWITCH と同じ様式）
```

**4まで作って初めて「予算に応じた自己制御」と言える。**1〜3は可視化にすぎない。

### B. ⑥ App Store 売上データの自動取得（受け皿だけある → 鍵は既にある）

`AUTOPILOT_LOG.md` 2026-08-11 に結論が出ている：
「**iOSリポジトリが既に持つ App Store Connect APIキー（fastlane/nominations用）で
Analytics Reports API を叩く道がある＝新種のキーは不要**（オーナー判断待ち）」。

**→ オーナーが「やる」と決めるだけで着手できる。**ただし同ログが指摘する
構造的な壁（流量がAppleの表示閾値未満でキャンペーン別が出ない）は残るので、
**取れるのは総数側**であることを織り込む。

### C. ③ 広告運用（調査済み → 資格情報待ち）

`APPLE_ADS_AUTOMATION_2026-08-17.md` §12 のオーナー作業2つ：
Apple Ads 管理画面でAPIユーザーを作成 → GitHub Secretへ登録。
**その後まず `/v1/suggestions/target-cpas/query` を1本叩く**（レポート §9 Step 0）。
返ってきた推奨CPAが¥40前後か¥100超かで、**作るものが変わる**。
作ってから気づくと作ったものが無駄になる。

### D. ② 複数AIモデルによる多重監査（単一モデル → 拡張可能）

`ai_triage.sh` は `QA_TRIAGE_MODEL` を環境変数で受けているので、
**別モデルで2回走らせて食い違いを検出する**のは小さい改修。
食い違った回だけ人間に上げる設計にすれば、「多重監査」と言えるようになる。

### E. ③ SNS自動投稿の復旧（原因特定済み → 未着手）

`x-post-scheduled.yml` 冒頭に修理手順が2案書かれている
（Zero Trustのサービストークン発行 or `/admin/api/*` のAccessバイパス）。
**X英語のBAN回復とTikTokの品質基準は別問題**なので、まず日本語経路だけ戻す。
