# AI実行率90%超への実行計画

2026-09-07更新。オーナーの依頼は「AI実行率90%超えを目指して新たな施策機能も含めてデプロイまで」。既存の最大権限の委譲を引き継ぐ。これは達成記録ではない。

## 分母と判定

現在はAI実行143 / 実施中176 = 81.25%。総合自動化率143 / 199 = 71.9%、AI関与率157 / 176 = 89.2%、カバー率176 / 199 = 88.4%。実測を起点とした単純化候補の登録・採点を1件の既存業務として開始した。タスクの新設や細分化はしていない。

AIが既存の実施中業務を k 件引き受け、未着手から n 件を開始すると、AI実行率は `(143+k+n)/(176+n)`。90%ちょうどではなく、厳密に90%を超えることを要件とする。

- n=0なら k=16 が必要。159/176 = 90.3%。
- n=10なら k=15 が必要。168/186 = 90.3%。
- n=23なら k=14 が必要。180/199 = 90.5%。
- 未着手23件だけをすべてAI化しても166/199 = 83.4%。

再計算: `node scripts/autonomy-gap.mjs --execution-plan --target 90`。
機械可読出力: 同じコマンドに `--json` を付ける。
従来の `--plan --target` は総合自動化率用で、その動作は変えない。

## 既存業務を移す候補

現在の到達可能分類は既存実施中9件・未着手16件。全件を満たした楽観上限でも168/192 = 87.5%。実装や観測が終わったという意味ではない。

既存実施中9件の候補:

1. D7/D28・課金・解約を含む評価。解約までの取得・照合が必要。
2. 製品バグの問い合わせから再現テスト生成。操作手順と実際の再現が必要。
3. App Review提出。対象コミットの実機確認と提出実行が必要。
4. 審査後のApp Store公開。審査通過と公開実行が必要。
5. 段階公開の昇格。母数・経過時間・実際の昇格が必要。
6. CAC・LTV・回収期間・粗利の統合。期間を合わせた実測が必要。
7. 契約の責任上限・知財・個人情報・準拠法の条項検査。
8. AI事業者のDPA・データ利用・SLA・撤退計画の審査。
9. 定型契約・条項比較・リスク抽出。

意思決定の実行条件を整える候補8件:

- 要望の設計採否: VISIONとの適合、利用者の根拠、受入条件を残して決定する。
- Remote Feature Flag: 対象フラグ・影響範囲・復旧方法を確認して実行する。
- ChatOpsリリース起動: 検証した版と実行結果を結ぶ。実機確認の捏造はしない。
- AI費用の月次上限: 実費と必要作業から決め、実際の予算ゲートへ適用する。
- アプリ運営の月次予算: 収支と必要費用を照合して配分し、決定を記録する。
- オンボーディング改善: 価格や既存契約を変更せず、導線変更を検証・配信する。
- プレミアム機能の設計判断: 有料範囲・既存利用者への影響を確認して設計を確定する。
- 推論の実行場所: データの扱い、端末要件、費用から決め、設定・実装と一致させる。

9件と8件がすべて実行に移れば、現在の分母では90%超に届く。ただしこれは条件付きの候補経路で、実機・審査・標本数・原資料の不足を解決できた保証ではない。

## 着手順と証拠

まず既存の調査を使える契約・DPAの審査を進め、AI自身の判定・根拠・未確認を人の過去判定と区別して保存する。並行ではなく、その後に予算・設計判断の実行条件と適用経路を作る。価格変更や不要な新規支出を目標達成のために発生させない。

プロダクト側では課金失敗からの回復、アプリ内障害案内、Zero-decision Capture Rateの計測を進める。これらは未着手からの開始なので、分母増加を含めて再計算する。

加点は実行結果・適用先・対象版を確認した既存タスクだけに行う。新しいタスクが業務上必要なら棚卸しに追加するが、細分化で率を上げない。合成テストは動作検証であり、実際の返金・実機確認・契約同意・利用者同意の代用にはしない。
