# 全サイト観測と記事別事前計測の共存方針

作成日: 2026-09-15。状態: **ユーザーが「反映させてデプロイ」と明示承認。PR #1398で実装・移行し、マージ後に運用へ適用する。**
依頼: 「全サイト実験と記事別の事前計測を共存させるルールの整理」。

## 結論

全サイトの推移を読む**観測**と、変更の効果を評価する**介入実験**を分ける。
観測の対象が全サイトであることだけを理由に、すべての記事実験を永久に止める設計にはしない。
一方、「観測」と名前を変えただけで既存実験の保護を解除しない。

記事実験を自動で許可するのは、次の両方を満たす場合に限る。

1. 全サイト側が、記録された方針変更を経て非排他的な観測として明示されている。
2. 記事側が、対象範囲・実測baseline・比較方法・母数・評価日・停止条件を実装前に固定し、別の有効な介入実験と重ならない。

**指標名が違うだけでは共存を認めない。** 記事変更は検索流入、ブランド検索、回遊、獲得に同時に影響し得る。単純な前後比較で各変更の単独因果を主張しない。

## 共存の判定表

| 全サイト側 | 記事側の作業 | 判定と条件 |
|---|---|---|
| 既存の排他的実験が有効 | データを読むだけ | 許可。新しい介入や成果認定を作らない |
| 既存の排他的実験が有効 | 記事別の介入を新規登録 | 現行どおり停止。移行完了または既存実験の正式終了を待つ |
| 明示移行済みの非排他的観測 | 記事別の介入実験 | 条件付き許可。記事側の事前契約と干渉確認が必要 |
| 全サイトに適用する介入実験 | 同じ期間の関連する記事介入 | 原則停止。独立した割付・対照群など、分離可能な設計を事前レビューした場合だけ個別判断 |
| 任意 | 同じ記事・共有部品・同じ評価対象へ二つの介入 | 後発を停止。URLや指標を変えただけでは独立としない |
| 任意 | 明示依頼による公開や事実訂正 | 実施権限を確認し、影響範囲と公開時刻を記録。実験ゲート通過や自律運転成功へ読み替えない。既存の停止条件に該当するなら、その実験側も正式に処理する |

非排他的観測は「サイト全体がどう動いたか」を継続して読むためのもの。
その増減から、一つの記事やブランド統一施策の単独効果を認定しない。
観測への移行が許すのは重複判定上の共存であり、予算・品質・権限・対象ページの別実験・価値契約の免除ではない。

## 記事別の事前計測で固定するもの

- **変更の全範囲:** 記事URLだけでなく、ハブへのリンク、既存関連記事、共通CTA、テンプレートなど変更対象を列挙する。新しい記事だけを申告して既存ページの干渉を隠さない。
- **指標と出典:** GSC、GA4、AI観測などを混ぜず、期間・タイムゾーン・フィルター・集計単位・原本ハッシュを保持する。
- **比較設計:** 対照群または前後比較を明示。前後比較なら同時変更、季節性、検索更新等の限界も固定する。
- **母数と判断:** 必要母数、評価日、データ遅延、判断基準、ガードレール、停止条件を実装前に固定する。
- **再確認:** 選定時と実装確定時に、元台帳の最新状態と全変更範囲を照合する。後から実験が入ったら古い許可を使わない。

新規URLには変更前のページ実測が存在しない。欠測を0としてCTRの改善実験を作らない。
新規記事は公開後の初期値を観測として蓄積し、最初の改善介入の前にbaselineを固定する方法、または実際に取得できる別の事前指標・比較群を用いる方法を選ぶ。
後者も関連性と既存の適格性基準を満たす必要があり、都合のよい別指標へ置き換えて公開を通す用途には使わない。
既存の事前baseline要件を満たせない新規記事を、自律実験として通す変更は本案に含めない。

## 既存の全サイト記録を移行する場合

推奨は、ブランド・回遊の全サイト集計を今後も継続しつつ、将来の運用を非排他的な観測として明示すること。
ただし現在の停止条件を含む運用契約が変わるため、次の記録と検証をそろえた別の実装変更として扱う。

1. 元の実験ID、開始日、評価日、baseline、source、仮説、停止条件、既知の交絡をそのまま保存する。過去を観測だったことに書き換えない。
2. 移行元ID、決定者、決定日、発効時刻、変更前後の保護、理由を追記する。過去の所有期間へ遡って適用しない。
3. 既存の実験台帳内で、将来期間の役割・排他性・許容される結論を型として表す。二重の実験台帳や別の収集スケジュールを作らない。未指定の古い記録は排他的扱いを保つ。
4. 元の評価日を残して評価責任を維持する。移行前後と同時変更を区別し、分離できない結果を成功と断定しない。母数不足、原本欠測、因果分離不能を別の理由として記録する。
5. 選定、計測準備、実装確定、follow-up、重複監査が同じ判定を使うように変更する。一箇所だけ許可する抜け道を作らない。

現行スキーマは`planned/running/frozen/evaluated/cancelled`でライフサイクルを管理している。
未実装の`observation_only`等を今すぐ台帳へ書き足して運用可能とみなさない。
`evaluated`にするのは実際の評価完了時だけであり、ロック解除を目的に完了扱いにしない。

## 実装時の受け入れ条件

- 明示移行済みの非排他的観測と、条件を満たす記事実験は共存できる。
- 未移行global、frozen、稼働中follow-up、同記事、共通変更部品の競合は拒否される。
- 不明・壊れたスコープは許可にならない。サイト外の対象も消さない。
- 指標名の違い、候補名・URL末尾・routeの変更で拒否を回避できない。
- 移行の発効前や、選定後に所有状態が変わった場合は誤って許可されない。
- baseline欠測、母数不足、計測失敗を0または成功へ変換しない。
- 元の履歴・日付・指標定義・過去の失敗は不変。両方の成果台帳に同じ出荷や効果を二重計上しない。
- 自律運転での自然起動・選定・公開・後日の評価を別々に検証する。単体テスト成功だけで無人運転再開を宣言しない。

## 実装と検証の境界

`experiment-coexistence.mjs`が移行記録と元契約ハッシュを検証し、`experiment-overlap.mjs`の共通判定を選定・準備・登録・CI・配信照合で使う。実験台帳の2件にだけ`coexistence`を追記し、元のフィールドは変えていない。新規計測planはschema2で`change_paths`を固定する。HTML以外の画像・配布物・実行コード・データ変更は、依存先の分離を証明する仕組みがないため、新規ファイルも含め全サイト影響として保守的に判定する。docs・contentキュー・sitemapは運転用の例外。同時期の別のページ実験に阻まれる場合も、対象ファイルを申告から外さない。schema1は過去の証拠として引き続き読める。

発効時刻は各移行記録のUTC値を正とする。コード配備前に遡って過去の許否を再判定しない。凍結中と継続評価は、親に移行記録があっても保護する。既存の停止条件は過去の契約として保持され、発効後のrunning全サイト観測に限って新しい非排他ルールが優先する。

このPRの完了条件は移行・テスト・配備確認。次回の自然な定期実行での選定・公開・後日評価は別の実証であり、配備成功だけでは達成扱いにしない。新規記事のbaselineや固有品質の不足は、共存ルールが通っても引き続き停止理由になる。

## 記事に付随する共有ファイルの限定変更（2026-09-20）

配信候補は記事の公開時に必須だが、共有JSON全体を変更対象とすると、別の記事の排他的実験とも競合する。今後作る計測planには任意の`supporting_changes`を事前宣言できる。単なるファイル名の除外ではなく、対象記事に限定した実際の差分を検証する。

```json
"supporting_changes": [
  {"path":"data/distribution-queue.json","kind":"distribution_seed","id":"20260920-example"},
  {"path":"sitemap-ja.xml","kind":"sitemap_lastmod"},
  {"path":"sitemap.xml","kind":"sitemap_index"},
  {"path":"docs/story-seeds.md","kind":"story_seed","id":"S-20260920-example"}
]
```

各パスは`change_paths`にも含める。IDは説明用で、実行時は未使用のものを選ぶ。対象URLはplanの`page`で固定する。
この限定契約を使う新規planでは、宣言していないHTML以外の変更はすべて全サイト影響として扱う。sitemap・docs・contentキューも従来の例外へ戻らない。

- 配信候補は宣言したID・対象URLの1件だけを先頭へ追加する。既存項目・順序・上位設定を保持し、100件に達した場合だけ末尾の最古1件を落とせる。未知フィールドや重複JSONキーは拒否する。
- 記事用サイトマップは既存の対象URLの`lastmod`だけ、索引は宣言した子サイトマップの`lastmod`だけを更新する。他のXMLは保持し、未来日・日付の巻戻し・URL追加は拒否する。
- 記事ネタは宣言したIDの1節を末尾へ追記し、`- **対象URL**: https://simplememofast.com/...`を1行含める。本文は既定の太字項目の箇条書きと2字下げの事実箇条書きに限る。タブ・別見出し・HTML・既存本文の書換え・項目の重複は拒否する。100節に達した場合の整理はこの限定契約では許可せず、別途扱う。
- 準備・登録時に元ファイル、未使用ID、対象URLを確認する。CIでは元ブランチとの差分、配信照合では事前宣言から検証済みheadと実際のmergeへの差分を検証する。シンボリックリンクや実行可能ファイルは拒否する。

宣言のない古いplan、画像・コード・未知のデータファイルは従来の保護を維持する。自律実行で既存実験の`supporting_changes`を変更することはできない。同記事・未移行global・凍結中の同対象実験・継続評価の保護も維持する。

封印済みplanは変更せず、新しいIDと事前宣言から始める。この仕組みは将来の独立した記事変更を証明するもので、既存実験の終了や過去の`no_artifact`の訂正ではない。自然起動・実出荷・後日の効果評価はそれぞれ原証拠で確認する。

## 全ページ共通の生成物（2026-09-24 オーナー判断）

- **決定者:** オーナー。AIセッションが判断を転記したもので、GitHub上の記録（コミット・PR）からは決定者本人を識別できない。
- **決定日:** 2026-09-24。
- **内容:** sitemapのような全ページ共通の生成物は、実験の対象ページの行（エントリ）が変わらない限り、排他実験の所有に当たらない。
- **発効:** この規則を実装した変更がmainに入った時点。CIはbaseブランチ側の規則で判定するため、それより前のPR・plan・判定には適用しない。コードに発効時刻は持たせていない。

### 対象は閉じた一覧

`growth/lib/experiment-coexistence.mjs`の`SHARED_GENERATED_ARTIFACTS`に完全一致のパスで列挙する。パターンで広げない。

| ファイル | 行の単位 |
|---|---|
| `sitemap-ja.xml` / `sitemap-en.xml` / `sitemap-locales.xml` | `<url>`エントリ（`<loc>`の正規化URL） |
| `sitemap.xml` | 子サイトマップの`<sitemap>`エントリ。ページの行ではない |
| `data/distribution-queue.json` | `items`の各項目（`url`の正規化URL） |

一覧に無いファイルは従来どおり。`docs/story-seeds.md`は生成物ではないのでファイル単位の所有が残る。`llms.txt`は行を検証する仕組みが無いので、従来どおり全サイト影響として扱う。

### 変更前後の保護

| 場面 | 変更前 | 変更後 |
|---|---|---|
| 一覧のファイルを`supporting_changes`で宣言した変更と、同じファイルを`change_paths`に持つ既存実験（稼働中・凍結中・継続評価の親を含む） | 両方が宣言していなければファイル単位の競合 | 新しい変更側が宣言していれば、ファイル単位では競合しない。自分の行は`target.pages`に入る |
| 宣言せずに一覧のファイルを変える変更 | 配信ファイルは全サイト影響。sitemapは他の実験の`change_paths`と競合 | 変更なし。行を確かめられないので許可しない |
| 配信候補の100件保持で最古の1件を落とす | 落とす項目のURLを見ていなかった | 落とす項目の行を所有判定に加える。稼働中の実験・凍結中・継続評価の対象ページなら拒否 |
| 落とす項目のURLが読めない（欠落・別オリジン・クエリ付き・正規化できない） | 確認していなかった | 拒否 |
| 未移行global、凍結中、継続評価、同じ記事、共通の変更部品 | 拒否 | 拒否。変わらない |

準備・Companyの決定・登録（いずれも実装前のbaselineを読む。100件なら落ちる1件はここで決まる）、CI、配信照合（検証済みheadと実際のmergeの両方）は同じ`ownershipConflict`で判定する。支えの差分証明（`verifySupportingBaseline` / `verifySupportingDiff`）は、対象ページ以外に変わる行を`rows`として返す。呼び出し側はそれを対象範囲に足して、既存と同じ判定に通す。mainからsitemapの日付を引き継いだsquash（`verifyMeasurementMergeScope`の来歴証明が通る場合）では、merge側の差分証明の代わりに来歴証明が同じ事前宣言から支えを検証し直す。保持で落ちる行は事前宣言の配信ファイルだけで決まるので、merge側もheadと同じ`rows`を、mergeの台帳に対して判定する。選定と重複監査はページ単位で、ファイルの所有を見ていないため変更はない。

- 配信ファイルが100件に達していて、落ちる最古の1件が稼働中・凍結中・継続評価の実験の対象ページなら、宣言した配信変更はその実験が閉じるまで通らない。拒否側に倒す設計で、エラーには行を所有する実験のIDが出る。
- 凍結中の既存実験も稼働中と同じ扱いにする（ファイル全体は所有させず、自分の行は保護する）。オーナー判断は凍結中を例外にしていない。2026-09-25、AIセッションの選択式の質問に、オーナーが「同じ扱いでよい」と答えて確認した（AIによる転記で、GitHub上では人の操作と識別できない）。
- CI（`scripts/decision-ci.mjs`）の差分証明と所有判定は、台帳に新しい実験行を加えるPRでだけ走る（前からの動作）。登録と実装を別のPRに分けた場合、実装側の差分証明と所有判定は合流後の配信照合が行う。

### 理由

2026-09-20の定期実行は、記事1本の変更に必須のsitemapと配信ファイルを申告して拒否された。その回の`change_paths`そのものは公開の記録に残っていない。当時のコードと台帳で申告の形を変えて再現すると、`data/distribution-queue.json`を含む申告はすべて全サイト影響と判定されて拒否され、記事とsitemapだけの申告は通った。`aio-2026-08-11-answer-blocks`がファイルを所有していたのではない。台帳の順で最初に当たった排他実験がこれだっただけで、稼働中の排他実験11件のすべてと競合していた。sitemapは当時の規則では全サイト影響の例外だった。

同日の`supporting_changes`（前節）で、宣言して差分を証明すれば通る経路はできていた。本節で追加したのは次の2つ。宣言のない古い既存実験が`change_paths`にsitemapを持つ場合でも、ファイル全体は所有させない。100件保持で落ちる1件が他の実験の行なら拒否する。

### 過去に遡らない

2026-09-15と2026-09-20の拒否は、当時の規則どおりの正しい拒否として残す。誤検知には書き換えない。`no_artifact`の記録、既存実験の`change_paths`・`supporting_changes`、評価日も変えない。配信ファイルは履歴上最大19件で、100件保持の削除は一度も起きていない。したがって保持の厳格化で、過去に通った配信照合の結果が変わることはない。
