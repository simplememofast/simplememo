### 2-3. なぜ v1 を「上げに行って」はいけないか

v1 の勾配（点の増え方）は、自律性と無関係な方向にも報酬を出している【確定：コードの読みと、関数を読み取り専用で呼んだ試算】。種類だけ挙げる（量は非公開付録）。

| 種類 | 形 | 塞ぐもの（この版） |
|---|---|---|
| 記録の選択 | 介入のあった出荷を台帳に書かなければ、VDC・UMR が上がる | HG2 台帳完全性（M-03） |
| 自己申告 | 「無介入」「起動の種類」「failure_stage」「repair_of」が自己申告で、そのまま点に入る | M-04 一次資料照合（識別の分離後に完成） |
| 当たりを問わない | VDC は決済の有無だけを数える。観測期間1日・自分で成立させられる指標が最も有利 | C4・C5（§2-4）、L4-14〜16 |
| 自己判定 | EP 精度は AI 自身の判定を数える。窓が無い。「上げない」ほど精度が上がる | M-09 二重判定、L4-18 |
| 小標本 | 窓内の分母が数件になると率が跳ねる（例：n=1 で100%） | L4-20（最小分母と縮約） |
| 記録しないほうが得 | 静かな窓で故障を正直に記録すると大きく下がる。ラベルを替えれば下がらない | L4-20（据え置きの崖）、M-03 |
| 行の分割 | 1つの作業を複数の行にすると TUC が増える | M-03（PR と作業サイクルの突合） |
| 日付 | データが同じでも日付だけで値が動く | S\* は「最後に閉じた JST 日」で算出（RL25） |

**勾配が自律性と無関係な方向にも向いている計器を上げに行くと、この表の左列が選ばれる。**これは誰かの意図の問題ではなく、構造の問題。だから「v1 を何点にする」を目的にしない。v1 は公式のまま残し、本質を測る計器を横に置く。

### 2-4. 本質スコア S\*（参考計器・未承認・v0-draft）

**単位と窓：**出荷の単位は v1 と同じ（運転台帳の shipped 行）。窓は28日で、**最後に閉じた JST 日まで**（v1 は当日を含む）。同じ PR を重ねて数えた行は1件にまとめる。**面ごとに出し、合算しない**（サイト・基盤／アプリ）。

**本質決定の条件（漏斗）**

| # | 条件 | 判定の出所（自己申告を使わない） | 今日（サイト・基盤） |
|---|---|---|---|
| C0 | 出荷 | 運転台帳の shipped 行と main へのマージ | 21 |
| C1 | 無人で起動した | **A級**＝既存ワークフローによる Actions の `event=schedule`。**B級**＝Codex・CCR の受領（エージェントが動く Mac で書かれるので独立性が弱い）。A と B は合算しない。owner-session とオーナー名義の dispatch は除く。**トリガーが作業に固有でなく、候補が初めて記録された日より7日以上前から存在すること** | 経路が定期の出荷10件のうち、A級で確認 5・オーナー名義の dispatch 1（09-19）・未確認 4。ほかに介入欄が空の owner-session 1件（09-05）は C1 の母数外【確定】 |
| C2 | 無介入 | PR を開いてからマージまで、人による commit・review・comment・dispatch・Web アップロードが無い（GitHub のイベント）。**人と AI を識別できない間は「識別不能」** | **識別不能**（HG1） |
| C3 | 事前登録 | 契約の宣言が実装より前（既存の `verifyHistory`） | 9（契約つき出荷。#1548 後は決済済み8・未決済1）。C1 との突合は未了 |
| C4 | 利用者価値の指標 | 承認済みで、利用者側の指標。かつ、その指標が影響しうるパスの集合が出荷の touches と交わる | **0**（9契約はすべて publishing_day_rate か unresolved_failures） |
| C5 | 自分で成立させられない | 観測期間 ≥7日。観測がエージェント自身や依頼セッションの後続出荷で成立しない（confounded でない） | **0**（全9件が観測期間1日。予測した改善が起きた2件は、どちらも翌日のオーナー起動セッションの公開で成立） |
| C6 | 検証つきで決済 | 既存の `verifiedSettlement` を満たす | 8（ただし C4・C5 を満たすものは 0） |

**2層：**
```
S*ₒ（運転の本質）  = C1 と C2 を満たす出荷の件数 ／ 面の出荷数
S*ᵥ（価値の本質）  = C1〜C6 をすべて満たす決定の件数 ／ 面の出荷数
表示は「件数 k / n」と、28日あたりの絶対数 k。率だけでは出さない。
区間（Wilson 95%）は、ハードゲート HG1・HG2 を満たした後にだけ付ける。
アプリ面の S*ᵥ は「プロダクト閉ループの完走数」で数える（§2-5）。
```

**品質 Q は掛け合わせず、隣に出す。**決済件数・的中件数・Brier と素朴な予報の Brier・p の分布。的中を点に掛けない理由は2つ——小標本のノイズがそのまま乗る、proper scoring が防ぐのは p の歪めであって**問いの選び方**は防がない（p=0.03 の契約が実例）。問いの選び方は C4・C5 で構造的に縛る。

**S\*ᵥ = 0 の意味：**「自律が無い」ではない。「**利用者価値に照らして検証された無人の決定が、まだ無い**」。PR TIMES の本文の約束「効果を測って続けるか戻すか」がちょうどこれを指している。

### 2-5. アプリ面：プロダクト閉ループ計器

| 列 | 定義 | 今日【確定】 |
|---|---|---|
| 宣言した機能 | `declared_at ≤ 露出開始`（feature-outcomes） | 1（階層保存先） |
| フラグで露出した機能 | 遠隔フラグで露出が 0% を超えた | **0**（階層保存先は **ASC の段階リリース**で出ていて、フラグ経由ではない） |
| 機械の判定 | rollout-guard が本番で promote か kill を出した | **0**（台帳上。hold・escalate は本番で出ている。本番 KV の履歴は【未確認】） |
| 固定日の結論 | success / failure / no_change / undecidable / measurement_failed（undecidable は別列） | 0（最初の評価日は **10-18**） |
| 機械が実行した継続／撤退 | ≤50% への昇格、または kill | **0** |
| 未宣言の出荷 | 宣言もフラグも無く利用者に出た機能 | Dialogue Memo（5.9.0〜5.9.9） |

**完走の定義：**宣言 → フラグで露出 → 機械の判定 → 固定日の結論 → 継続か撤退の実行。100% への昇格・App Store 公開・バイナリの revert は人がやってよい。**これが「アプリが自ら育つ」の最小単位。**

### 2-6. ハードゲート（点で相殺できない）

| ゲート | 条件 | 満たさないとき | 今日 |
|---|---|---|---|
| **HG1 識別** | 人の操作と AI の操作を、GitHub 上で機械的に区別できる（AI は別の識別で動く、または人の承認は AI が使えない鍵で署名する） | C2・Dim1・「人の承認」に基づく錠前（T-05・G-02）は**「記録」であって「錠前」ではない**と表示 | **✗**（PR #1555 の作者も run 35415451723 の起動者も同じオーナーアカウント。AI の GitHub 操作は user-to-server トークンでオーナー名義になる）【確定】 |
| **HG2 台帳完全性** | 面のスコープ内の main マージ PR の100%が、運転台帳の行か機械的な除外に対応する。スコープと除外パスは L4 の所有。「生成物だけ」の除外は再生成してバイト一致した場合だけ。完全性のために起こした行は既定で「介入あり・起動未確認」 | **S\* を算出しない**（「無効：完全性 xx%」と表示） | 未測（窓内の main コミット815件に対し出荷行21件）【確定】 |
| **HG3 重大事故の無い窓** | 窓内に Sev1（取り消せない対外送信・利用者データの喪失・公開事実の誤り）が無い。**かつ**対外送信の錠前が稼働し、訓練で誤った送信者を1回止めた記録がある。**かつ**対外送信台帳が完全 | 権限の拡大・自律数値の新しい対外主張・プレスでの自律数値を凍結 | **✗**（09-22）。日付だけでは解けない。窓の上では v1 窓で 10-20、S\* 窓で 10-21 に 09-22 が外れる |
| **HG4 復旧の実証** | 人手を介さない本番の revert、または監査済みのガードの本番 kill が累積1回以上 | 「復旧未実証」。Ph5 の入口に使わない | **✗**（0回） |

**計器そのものの抜け穴と、対になる計器**（新しい計器も同じ組織が作り同じ AI が測るので、2本目の自己採点にならないように）

| 計器 | 自分の抜け穴 | 対になる計器 |
|---|---|---|
| Dim8 無人連続稼働 | 毎日小さな R0 を出すと伸びる | R1 以上か、データだけではない差分の日だけ数える。R0 の割合を併記 |
| 採択率（Routing） | 候補を減らして安全なものだけ出すと上がる（Zero-decision と逆向き） | 候補の被覆率（候補が出たキャプチャ ÷ 対象になるキャプチャ）と対にし、両方を事前宣言 |
| 門の通過率 | 門を緩めるためのエスカレーションを制度化してしまう | エスカレーションに、その門の真陽性の記録を添える |
| EP 二重判定 | 不一致を人に見せる件数を絞ると、残りが隠れる | 不一致は全件記録。オーナーにはシードで選んだ3件と総数を見せる |
| 機械 PR の supersede | 都合の悪い決済を載せた PR を閉じられる | 置き換え後も決済の内容ハッシュが同じであることを CI で検査 |
| 「利用者向け機能」の判定 | 何を利用者向けと呼ぶかをエージェントが決める | release_notes の利用者向け文言が変わる変更を利用者向けとし、L4 が固定 |
| S\* 全体 | 定義者と被測定者が同じ（S\* を設計したのは AI） | オーナーの盲検抜き取り（M-20）・監査（M-10）・hold-out（M-24）・外部の反証器（C-06） |

**S\* の撤去条件：**56日間、どの判断・訂正・L4 の記録にも S\* の値が引かれなければ廃止する（読まれない計器は、門と同じく負債になる）。

**実装の規律：**v1 の関数を読み取り専用で import する。最初の28日は warn だけ。生成物の書き手は1つ。公開リポジトリの ubuntu で回す。**LLM を使う計器（M-09・M-10・M-24・M-27）は、実行主体・利用枠・月額の上限・観測方法を先に書き、主系の朝のスロットと時間帯を分ける。新しいベンダーや新しい API キーが要るならお金の境界なので L4。**

### 7-3. Reddit を「外部の反証器」として使う（前回の 7-9）

- **フレーム問題は内側から解けない。**L3 の強制探索が枠外のデータを生まなければ、外からの批判が唯一の反証器になる。
- ただし Reddit などの外部入力は**注入の経路**でもある（外部事例：自販機の運営を記者の誘導で無料化させられた例など。§16）。したがって順序は：対外送信の錠前（C-04）→ 敵対的入力の演習（M-27）→ **名前を含まない要約**を人が投稿（開示つき・`admin/reddit/` の規律：自動投稿禁止・1日1件・同じ subreddit に14日）→ 返ってきた批判を台帳化（✅🟡⬜🚫）。
- **読む側を書く側から分ける。**読んだ外部の内容を台帳へ書けるのは、人か承認済みのテンプレートだけ。

## 10. 見通しと、数字の読み方

### 10-1. シナリオの数値を、この文書に書かない理由

「どう動けば v1 が何点になるか」の試算は、**施策を v1 で順位付けする道具**になる。オーナーの委任の動機が「すべてスコアあがるように」である以上、ここに数値を並べれば、目標を置かないと書いても実質は目標になる。**試算は非公開付録にだけ置き、この文書には「何も起きなかったときの窓の転がり」（§3-2・警告）だけを置く。**

定性的に言えることは3つ：
- **流量が戻るだけで v1 は戻る。ただし戻る点の一部は「的中を問わない VDC」を通る。**
- **頑健化の差は、故障1件ごとに「誰が気づき、誰が戻したか」で符号が変わる形で効く。**故障を「作って拾う」ことは、故障件数が分母に入るので得にならない設計になっているが、完全ではない（非公開付録）。
- **L4 で計器を厳密にすると、v1 は下がりうる。**それは後退ではなく「定義の変更」として分類する。**本質は、そのとき上がる。**

### 10-2. 前回の見積りの外れ方を、この文書に当てる

前回の8週後の見積りに対し、実績は見積りペースの約6割だった。**この文書の見通しも、同じ程度に楽観へ寄っている可能性を前提にする。**特に Ph0 の解除が遅れれば、Ph2 以降のすべてが同じだけ遅れる。

### 10-3. 読み方のルール（日報・週次で）

1. **区間の内側の上下は語らない。**合計の不確かさの幅は約 18pt（[36.1, 54.5]・モデル依存）。日々の上下はすべてこの内側にある。
2. **差分は理由で分類する：**新しい事象／窓の転がり／台帳の後追い／定義の変更。分類できない差分は書かない。
3. **出口は 0/非0 で読む。**率の改善を前後比較で示すには、たとえば RA 検知率 23%→60% で各群27件の故障（今の頻度で約58日）、VDC 33%→60% で各群54出荷（約72日）が要る（両側 α=.05・検出力80%）【確定：計算、効果量は仮定】。改善幅が小さければ n はさらに増える。7日の出口は1回ずつの観測であって、改善の証明ではない。
4. **v1 を語るときは S\* と品質 Q を併記する。**VDC 経由の上昇には「的中を問わない」と付ける。
5. **0件には上限を付ける**（例：自動 revert 0回、0/21 なら 95% 上限 ≈13%。rule of three の近似では 14%）。
6. **日付は窓の転がりと固定の評価日だけ**（§10-5 の採点用の締切は例外で、約束ではない）。S\*ᵥ の最初の分子の日付は置かない。
7. **S\* に目標値を置かない。**「S\*ᵥ ○%を目指す」とは書かない。
8. **v1 の下落はそのまま主項目として出す。**同じ文の中で S\* を引いて相殺しない。

### 10-4. 週次の読み方の手順とオーナー向けの1画面

**毎週、決めた曜日に（所要15分）：**
1. 併記ブロック（§2-7）を読む
2. 前週からの差分を4つの理由に分類する
3. 各段の出口の「通過」列で、0 から非0 になったものを探す
4. L4 の束ごとの経過日数（14日を超えた束は分け直す：F02）
5. 重大度つき事故台帳と対外送信台帳の新しい行
6. 観測できないものの台帳（§15）の更新
7. 読んだことを台帳に1行残す（読まれていない計器は撤去条件に当たる）

**オーナー向けの1画面（出し先は「ループの入力外と実測したチャネル」）：**v1 と区間／S\*（または算出不能の理由）／ハードゲート4つ／各段の出口（準備・通過）／L4 待ちの件数と日数／事故・対外送信／コスト（観測済み・未観測）／事業行。**ranker・日次 run のプロンプト・公開ページには出さない。**

- 後から宣言する。未宣言の機能を配信の題材にする
- オーナーに依頼を控えさせる（点のために人の行動を変えさせない）
- 門を AI が緩める。解除と同じ効果を持つ変更を AI がマージする
- 自分の停止・誤発火を点に変える。利用枠切れに repair_of を書く
- 「行動ごとの点差」を公開リポジトリに書く。PR の題名・本文にスコアへの影響を書く
- 実名を、コード・文書・コミット・PR・外部への本文のどこかに書く
- 実測の無い数字（Zero-decision・90点・S\*）を対外に書く。「ゼロプレナー達成」と書く
- 段6（Ph5）の中身を、入口条件がそろう前に書く
