# TestFlight で `kill` が効くことを実証する — 実行手順

**これはカナリアではない。** 統計的な判定は一切しない。
確かめるのは1つだけ ——

> **サーバで `kill` を叩いたら、実機のアプリで機能が消えるか。**

`docs/canary-first-run.md`（本番の段階公開）とは目的が違う。あちらは
「指標を見て判断できるか」、こちらは「**止められるか**」。
止められることを確かめずに本番へ配るのは順番が逆なので、こちらが先。

---

## 最初に: 前に書いていた手順は間違っている

このセッションで私は「`tf04_progress` を **rollout 50 / max_stale 300** で配って
kill を実証する」と何度も書いた。**それでは kill を実証できない。**

クライアント側の実装（`../simplememo-ios/SimpleMemo/`）はこうなっている。

| | 値 | 出典 |
|---|---|---|
| 再取得のスロットル | **24時間** | `FeatureFlags.swift:395` `now - last > 24 * 60 * 60` |
| キャッシュ期限切れの扱い | **オフに倒す** | `FeatureFlagRollout.swift:120` `isFresh` |

つまり `max_stale_seconds: 300` にすると:

1. 起動して取得 → フラグ ON
2. **5分後、キャッシュが期限切れ → フラグは勝手に OFF**
3. 端末は24時間、再取得しない

**kill を叩いても叩かなくても同じ結果**になる。これは fail closed の設計どおりの
正しい挙動で、欠陥ではない。欠陥だったのは**その上で kill を実証しようとした手順**のほう。

`max_stale` を短くするほど、kill ではなく**期限切れ**が先に効く。

---

## 正しい手順

> **前提: `ADMIN_API_KEY` が GitHub Secrets に入っていること。**
> **2026-08-22 に登録済みで、この手順は通っている**（下の実測を参照）。
>
> 通らなくなったら `Flag Ops → action: diagnose` を1回撃つ。鍵を使わず、
> 値も出さずに、**「無い」のか「見えていない」のか**を切り分けられる
> （見えている secret 名・長さ・混入文字・塩付き指紋を出す）。
>
> 2026-08-22 はここで丸1時間使った。**Worker Secret は一度入れると読み出せず、
> `wrangler secret put` の対話プロンプトで入れた値はシェル履歴にも残らない。**
> 3つの候補を試して全部 401 になり、最後は作り直した。
> **生成した値は必ずパスワードマネージャへ控えること。**

### 1. 定義する（rollout 100）

```
Actions → Flag Ops → Run workflow
  action: set
  key: tf04_progress
  rollout: 100
  max_stale_seconds: 86400        ← 既定のまま。短くしない
  description: TestFlight で kill の実証を行うための一時配布
```

**rollout は 100。** ここでも前に書いた 50 は誤りだった。理由は2つ。

- **対照群が要らない。** 統計判定をしないので、群を割る意味が無い
- **50 だと誰も当たらないことがある。** テスターが数人のとき、
  決定論的ハッシュで全員が非露出側に落ちる確率は無視できない。
  「機能が出ない」のがバケット外れなのか不具合なのか**区別できなくなる**

### 2. 実機で ON を確認する

TestFlight ビルドを入れて、`tf04_progress`（「今日 1/3」進捗表示）が
**見えている**ことを目視で確認する。

ここが見えない場合、先に進んでも意味がない。確認すべきは:

- そのビルドが **2026-08-22 以降**か（段階公開の欠陥修正が入っているか。
  `docs/canary-first-run.md` §0）
- アプリが一度でも `/v1/config` の取得に成功しているか

### 3. `kill` を叩く

```
Actions → Flag Ops → Run workflow
  action: kill
  key: tf04_progress
```

### 4. 実機で OFF を確認する — **アプリを入れ直す**

**ここが手順の要。** 待っても消えない。

再取得は端末側で24時間スロットルされていて（`FeatureFlags.swift:395`）、
**サーバからは短縮できない**。TestFlight は Release ビルドなので、
DEBUG の強制再取得ヘルパも入っていない。

したがって:

> **アプリを削除して入れ直す。** そのとき初回取得が走り、`killed` が届く。

入れ直して機能が**消えていれば、kill が効いたことの実証**になる。

### 5. 片付ける

```
Actions → Flag Ops → Run workflow
  action: unkill    ← 先に kill を解除
  key: tf04_progress

Actions → Flag Ops → Run workflow
  action: set
  key: tf04_progress
  rollout: 0        ← 配布を止める
  max_stale_seconds: 86400
  description: 実証完了。本番の段階公開まで配布停止
```

`unkill` を先にするのは、`killed` を立てたまま `rollout: 0` にすると
**次に配りたくなったときに理由の違う2つの停止が重なる**ため。

---

## これで実証できること / できないこと

| | |
|---|---|
| ✅ **できる** | サーバの `kill` が実機のアプリまで届き、機能が消える |
| ✅ **できる** | `/v1/config` → クライアントの解決順序が期待どおり動く |
| ❌ **できない** | ガードの**自動判定**（TestFlight の人数では `min_installs_per_cohort: 30` に届かない） |
| ❌ **できない** | kill が**何分で**届くか（入れ直しで届かせているので、自然な伝播時間は測っていない） |

4行目が特に大事で、**「kill は即座に効く」とは言えない**。
言えるのは「**次に取得したとき効く**」まで。自然な伝播は最長24時間かかる。

3行目があるので、これを終えても主張検査の「循環」は 67% のまま。
100% にするには本番で `docs/canary-first-run.md` を1周させる必要がある。

---

## やってはいけないこと

| | 理由 |
|---|---|
| **`max_stale_seconds` を短くして「速く消えた」と言う** | それは kill ではなく**期限切れ**。何も実証していない |
| **入れ直さずに待って「消えない＝壊れている」と言う** | 24時間スロットルの想定どおりの挙動 |
| **`min_installs_per_cohort` を下げてガードを動かす** | 3人中2人の差は偶然と区別できない。**都合のよい分母そのもの** |
| **本番の段階公開をこの手順で代用する** | 目的が違う。止められることと、判断できることは別 |

## AI だけで完了できない部分

**2 と 4（実機での目視確認とアプリの入れ直し）は人の手が要る。**
1・3・5 は `Flag Ops` から機械が叩ける。

`data/authority-matrix.json` の「段階公開の拡大」は不可逆・承認制だが、
**この手順の配布先は TestFlight の内部テスターだけ**なので本番の配布とは別扱い。
`rollout: 100` にしているのもそのため。

### この日に分かった落とし穴

**`tf04_progress` は画面のどこかに常時出るものではない。**
送信直後のトースト（2.6秒）の文言が変わるだけで、

- OFF … 「いいですね。もう1つ書いてみましょう」
- ON  … 「いいですね。もう1つ書いてみましょう**（今日 1/3）**」

しかもトースト自体を出すのは **`tf04_next_memo` という別のフラグ**
（`ComposeViewController.swift:3473`）。そちらが OFF だと
`tf04_progress` を 100% にしてもトースト自体が出ず、
**「フラグが届いていない」と「トーストの条件を満たしていない」を取り違える。**
次に別のフラグでやるときは、**先に「どこに何が出るか」をコードで確認する。**

### まだ実証していないこと（再掲）

  今日 kill を押したのは**人**であって、ガードではない
- **自然な伝播時間** — 入れ直しで届かせたので、放っておいて何分で届くかは測っていない

したがって主張検査の「循環」は **67% のまま**。100% にするには
`canary-first-run.md` を本番で1周させる必要がある。
