## 0. 先に、訴求の前提で衝突している3点

**この3つは「表現の好み」ではなく、自分たちで作った検査に引っかかる。**
黙って寄せずに、衝突として先に置く。

### 0-1. 「RSI／再帰的自己改善」は名乗らない — CIが落とす

`scripts/check-pr-facts.mjs` の `rsi-claim` 規則が、配信原稿
（`<!-- fact-check: draft -->`）に「RSI」「再帰的自己改善」が出た時点で **exit 1**。
つまり **RSIを名乗った原稿は、自社のCIを通らないので配信段取りに乗らない。**

理由は §0-1 に書いたとおりで、RSIは「AI自身が自らの知能・能力を改良する」という
強い意味で受け取られる。この運用がやっているのは**アプリ改善サイクルの継続実行**で、
**AIモデル自身は一切改良していない。**（用語も正しくは「再**帰**的」であって
「再起的」ではないが、そもそも対外文言に使わない。）

**代わりに使える3つ**（この3つなら、いまある証跡だけで最後まで書ける）:

- **ガードレール付き自律型アプリ運営基盤**
- **AIがアプリ改善サイクルを継続実行する仕組み**
- **再帰的プロダクト改善ループ**（技術者向けの説明でのみ）

### 0-2. 「人いらず」「勝手にアプリ機能が拡張され」は禁止表現

同じ検査の `overclaim` 規則が「完全自動化 / 完全無人 / 人間不要 / 世界初 / AIが経営」
を落とす。事実としても、公開・価格・広告・契約・実機確認は人間が持っており、
**それは意図的な設計**（`data/authority-matrix.json`）。

**革命性の置き所を変えると、同じ強さで、崩れずに書ける:**

> 人間を日常作業のボトルネックから外し、人が担うのを
> **「目的設定・権限管理・高リスク判断・例外対応」に絞った運営構造**にした。

### 0-3. 「集客や運用が自動化されてグロース」— 増分効果は測っていない

対照群を置いた増分効果の測定をしていないので、**「AIが売上／集客を伸ばした」は書けない**。
段階公開そのものが対照群つき実験になる仕組み（`rollout-guard.ts` の `bucketOf`）は
2026-08-22 に入ったが、**本番でまだ1回も発火していない**。

書けるのは「**この期間にこれだけ出荷され、人が中身に触ったのは0件だった**」という
**運転の実測**まで。それは十分に強い（§2）。

### 列挙に無かった追補

1. **機能バックログの機械的な優先順位付け**（`scripts/feature-score.mjs` / `data/feature-backlog.json`）
   期待効果 × 確信度 ÷ 工数。手で置けないようにしてある点が2つ:
   - **確信度は根拠の強さから機械的に決まる**（自社実測 1.0 / 外部実測 0.7 / 観察 0.5 / 類推 0.3 / 思いつき 0.15）。
     ここを主観にすると順位はいくらでも動かせて、台帳の意味が消える
   - **リスクは点数を下げるのではなく承認を要求する。**掛け算で効かせると
     **期待効果が大きければ危険な案が1位になる**
   - 根拠が弱い候補は「やらない」ではなく **「まず測る」** に落ちる。

   **`SURVEY_ENABLED` の既定は false** で、有効化されるまで「いま受け付けていません」と出す
   （**成功したふりをしない**）
3. **要望の母集団を自分で作った** — 国内App Storeの主要18アプリから**レビュー7,279件**を取得

   - 速度・安定性 466件（★1〜2が259件・**18アプリすべてで発生**）／データ保全 340件（★1〜2が195件）が
     **どの機能要望よりも多い**
   - **AI言及105件は肯定42・否定63**。「AIを消せるように」「AIより軽快さを」のほうが多い
   - → **当初計画に無かった「送信保証」を5つの前に置き直した。**VISION §11 は Phase 1 を
     Routing から始めるので方針と測定が食い違うが、**黙ってどちらかに寄せず**ページに

4. **AIに「分からない」と答えさせる仕様** — `insufficient_evidence` を明示的な選択肢として持たせ、

   （経路ごとにmessageIdが別UUIDになるためサーバ側の冪等性も効かない）。
   `WatchRequestLedger` を追加して入口でclaim
6. **自己修復（レーンF）とその歯止め**（`scripts/autopilot-selfheal.mjs`）
   毎朝の実行は記事を書く前に運転台帳を読み、**未修理の故障が残っていれば最優先を修理に切り替える**。
   歯止めは文章ではなくCIが実検出する:
   - 触ってよいファイルを **13件に限定**（権限表そのものは含めない＝自分で書き換えさせない）
   - **必須CIチェック31本が1本でも消えると落ちる**
   - **対象ワークフローに `actions: write` が現れると落ちる**（コメント行での言及は許す —
     「与えていない理由」を書くのは正しいから）
   - **同一 `failure_class` を3回直しても再発するなら、修理をやめて人間に上げる**
   - **判定と実装を分ける。**「今日修理に入るべきか」を判定するスクリプトは修理を行わない
     （同じ場所に置くと判定の側を都合よく変えられる）
   - 「修理済み」の定義は `repair_of` で名指しされていることだけ。
     **「あとで同じ経路が成功したから直った」とは扱わない**（主系は秘密鍵未設定で毎日
     success を返していた前例がある）
7. **統合監視の棚卸し**（`data/monitoring-coverage.json`・13系統）

     記録から分かる  3系統（気づくのは人）
     気づく経路が無い 3系統 ← Apple Watchアプリ・課金・問い合わせ

8. **検知と修理を別指標にした** — 検知まで中央値2.1h/最大50.7h、修理まで中央値0.9h/最大25.6h。

## 8. ⑥ アプリ運営意思決定

### 列挙に無かった追補

1. **機械可読な権限表**（`data/authority-matrix.json` / `scripts/check-authority.mjs`）
   **15領域中11が稼働中・10が承認制**。CIが見るのは3つだけ:
   ① 不可逆な領域が承認不要になっていないか ② 稼働中の領域が根拠のファイルを**実在確認つきで**指せているか
   ③ 金額が動く領域が上限を持つか（未設定なら「未設定と決めた」と書かせる。**空欄と未設定は違う**）
   **実際に人が承認したかは機械では見られない**ので、そこは表の側に正直に書いてある
2. **段階公開の撤回と拡大で権限を非対称にした**
   ```
     段階公開の撤回（カナリアガード）… 可逆 ・ 承認なし ・ AI自律
     段階公開の拡大（rollout引き上げ）… 不可逆 ・ 承認制 ・ 人間のみ
   ```
   **「広げてから戻しても、見た人が見なかったことにはならない」**ので拡大を不可逆に分類している。
   逆にすると誤検知が「**勝手に全員へ配る**」形で顕在化する
3. **段階公開そのものが対照群つき実験になる**（`bucketOf(flagKey, installId)` の決定論的ハッシュで、
   サーバが後から露出群/対照群を復元できる。**クライアントを一切変えずに作れる**）。
   有意（z>1.96）かつ実害2pt以上でだけ kill、**サンプル不足・正規近似の不成立・計測が読めない場合は hold**。
   **本番でまだ1回も発火していない**
4. **データ不足時に「何もしない」と判断する規律**（ノイズフロア＝期待クリック3未満／28日窓未満では
   スナップショットを作らない）
5. **運営ダッシュボード**（`scripts/dashboard.mjs`）— 設計で守っているのは2つだけ:
   - **単一のヒーロー数値を置かない。**4つの分母を同じ大きさで並べる（分母を変えれば51%にも87%にもなる）
   - **測れていないものを空欄や0で描かない。**未測定に専用の状態（破線＋独自色）を与え、
     「測っていない」と「測って問題が無かった」を視覚的に別物にする。**現在8件を明示**
   - 出力は `.gitignore`（`docs/` は robots で Disallow していても Cloudflare Pages が200で配信するため、
     コミットすると予算・障害・未解消件数が推測可能なURLで公開される）
6. **App Store 売上データは未接続**（列挙にある「売上・マーケデータの自動取得」は書けない）。
   鍵は既にある（fastlane/nominations用）が、使う判断が未了。
   加えて**構造的な壁**も判明済み — App Storeクリック2.1件/日 × インストール率 × 共有オプトイン率が
   **Appleの表示閾値未満**なので、キャンペーン別の数字はそもそも出ない
