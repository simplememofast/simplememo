### Phase 1 — 次: 閉ループを1本閉じる

**目標: ①機能開発と②バグ修正のどちらかで、本番の閉ループを完走させる。**
（検知 → 判断 → 実行 → 検証 → 継続/撤回）

| # | やること | 動く未実装 | 状態 |
|---:|---|---:|---|
| 1a | **Feature Flag のサーバ側** | — | ✅ **2026-08-22実装**（`simplememo-api/src/flags.ts`）。同日 `/v1/config` に統合（並行実装を解消） |
| 1b | **同・クライアント側（iOS）** | — | ✅ **同日実装**（`FeatureFlagRollout.swift`・35テスト）。段階公開・キャッシュ期限・取得経路のテスト |
| 1c | **指標 → 判断 → kill を叩く経路** | — | ✅ **2026-08-22実装**（`rollout-guard.ts`・24テスト）。露出群/対照群を `bucketOf` で復元して比較。**kill は自律実行 / promote は承認制** |
| **1d** | **本番で1回発火させる** | **4件** | ⬜ **ここが残り。**段階公開中のフラグがゼロなので、まだ1回も判定していない |
| 2 | カナリア公開と自動ロールバック | — | ✅ 1c に含まれる |
| 3 | 障害の検知時刻の自動記録 | 2件 | 統合監視と一体（検知の中央値2.1h・最大50.7hがここ） |
| 4 | 統合監視（Crash / API / Watch / 課金） | 1件 | 実装 |

**なぜ #1c が最優先か。** 引っ込める仕組みは 8/22 にできた（1a/1b）。
だが**引っ込めるかどうかを決めているのは、いまも人間**で、そこは自動化されていない。
「AIが機能を出す（自動選定 → 段階公開 → 効果測定 → 継続/撤回）」の最後の一手が
機械の手に渡らない限り、①②の閉ループは閉じない。
④の2件（段階公開の自動昇格・Crash-free率による自動停止）も同じ一手で動く。

**そして 1a/1b にも完了条件が残っている: 本番で kill を1回通すこと。**
止まることを確かめていない停止機構は、無いのと同じ。これはサーバ操作と実機確認なので
AIだけでは閉じない（`data/authority-matrix.json` の承認境界）。

**サーバ側は済んだ。** 段階公開（決定論的ハッシュ）・緊急停止（rollout を保存したまま
kill）・fail closed（KVが読めない/壊れている/未定義/install_id 無しは全部オフ）・
キャッシュ上限のサーバ制御まで入っている。**残るのはアプリ側だけ。**

**完了条件は「実装した」ではなく「本番で1回 kill が効くのを見た」。**
止まることを確かめていない停止機構は、無いのと同じ。

**動く指標:** 総合自動化率 31.2% → 約 34%（+4件）。
より重要なのは **①と②のカバー率**（現在 64.3% / 75.0%）。

### Phase 5 — 法人領域（別枠）

**⑦法人経営 11件は、他のどのフェーズとも依存しない。**
そして**1つの実装では動かない。**

やる順:

1. **証跡の形を決める**（何をもって「自動化されている」と言うか）
   — 運用記録・スクリーンショット・第三者の確認のいずれか。オーナー判断
2. 支出上限と二者承認の設計（権限表に threshold を入れる。現在すべて未設定）
3. 定型契約の分類と条項検査（非定型・高額・海外・知財は人間のまま）
4. 会計・請求・照合

**原則は変えない:** 法人責任と士業判断は無人化しない。
**権限と承認境界を明確にする**ところまでが目標。

## 4. 意図的にやらないもの

**空欄にして「忘れている」と読ませないために書く。**

| やらない | 理由 |
|---|---|
| **広告のリアルタイム自動入札** | 自社分析が「この予算規模ではノイズ最適化になりCPIをむしろ悪化させる」と結論（1KWあたり判定に15〜50日かかる） |
| **X英語・TikTokの自動投稿** | アカウントBAN1回目／画像品質が公開基準未達。再開条件は各ワークフロー冒頭に記載 |
| **実機テストのヒューマンレス化** | Hard Rule。「実機で確認してから提出する。後ではなく先に」 |
| **App Store 公開の自動化** | `automatic_release` がハードコードで false。**恒久的に手動** |
| **価格変更のAI提案** | 不可逆で既存契約者への影響が読めない。権限表で human_only |
| **法人責任・士業判断の無人化** | 権限と承認境界を明確にするところまでが目標 |
| **アナログ領域の人間側**（現地設営・採用判断・法的責任・危機対応） | **設計であって未達ではない** |

## 5. 指標の目標（置くが、達成期限は置かない）

**期限を切ると、期限に間に合わせるために基準を下げる。**
Runbook が「毎日出すために基準を下げる、はこの運用の失敗定義そのもの」と
定めているのと同じ理由で、ここも順序だけ決めて期限は置かない。

| 指標 | 現在 | Phase 1後 | Phase 3後 | 最終 |
|---|---:|---:|---:|---|
| 総合自動化率 | 31.2% | 約34% | 約39% | — |
| カバー率 | 62.9% | 約66% | 約72% | — |
| 人間介入率（基盤の修理） | 30.8% | 低下（レーンF効果） | — | ゼロ近傍 |
| 成果物のAI自律率 | 100% | 100% 維持 | 100% 維持 | **下げない** |
| 検知まで（最大） | 50.7h | — | — | **1h以内** |
| 主系の出荷回数 | 0 | 1以上 | — | — |

**「成果物のAI自律率100%を下げない」が一番大事。**
自動化を広げる過程で人が成果物に手を入れ始めたら、それは
**AIの成果が信用されていない**ということで、範囲を広げる前に品質を直す合図。

**「検知まで1h以内」は数値目標として置く。** 実測で最大50.7時間かかっており、
ここが唯一「明確に壊れている」と言える指標だから。

### 3 と 4 は独立していない

**4 をやるなら、9月のプレスリリースは別物になる。**

| | 発表するもの | 読者 | 検証される点 |
|---|---|---|---|
| いまの原稿 | **自社の運営をこう変えた**という実績 | メディア・ユーザー | 数字が本当か |
| 4 を前提にすると | **他社が使える製品**の予告 | 開発者・投資家 | 他社でも動くのか |

後者は「他社のアプリでも動く」ことが暗黙の主張になる。**現時点で他社アプリでの
実績はゼロ**で、SimpleMemo 1本でしか回していない。製品として名乗ると、
そこが最初に突かれる。

順番としては、**先に 4 の輪郭（誰に何をいくらで売るか）を決めてから 3 に入る**のが
安全。逆にすると、発表してから製品の形が変わることになる。

### 4 を検討するときに先に見ておくこと

- **`docs/VISION.md` は SimpleMemo（Capture OS）の話**で、運営自動化のSaaSは
  そこに書かれていない別事業。衝突ではないが、**同じ手が2つの製品を持つ**ことになる
