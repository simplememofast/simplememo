> 受けて、`data/automation-coverage.json` の `blocker: policy_boundary` 24件を
> 1件ずつ実装に当てた記録。**結論を先に: 書き換えで上げられるものは0件。**

> 上限の計算は `node scripts/autonomy-gap.mjs`。

## 0. まず、93.4% の意味が違っていた

指示の前提は「境界24件を渡せば93.4%」だったが、**`autonomy-gap.mjs` の 93.4% は
`ceiling + owner_only`**、つまり **「到達可能な32件を全部実装したうえで、さらに
24件を渡した場合」**である。

```
   現在                            129/198 = 65.2%
   境界24件を全部渡した場合         153/198 = 77.3%   ← 実測（台帳を書き換えて計測）
   到達可能32件も全部実装した場合   185/198 = 93.4%
```

**渡すだけなら 77.3%（+12.1pt）。**93.4% には、渡す作業とは別に**32件の実装**が要る。

## 2. 実装すれば正当に上がるのは、1件だけ

**⑨ 返金の可否（refundPreference）。**台帳の note が既に設計まで書いている。

- `ConsumptionRequest` の必須欄は `customerConsented` / `deliveryStatus` /
  `sampleContentProvided` の3つで、**どれも事実**（同意の有無・配信できたか・
  購入前に無料で試せたか）。SimpleMemo は無料枠があるので3つ目は定数に近い
- **判断が入るのは `refundPreference` の1欄だけで、しかも必須ではない**

つまり **「事実だけを返して、意見欄は空で出す」**という形が作れる。これなら
「返金の可否をAIが決める」ではなく「事実の応答を機械が返す」になり、境界を
動かさずに実行側へ入る。**+1件で 130/198 = 65.7%。**

## 3. 見つかった穴 — 紙の上の書き換えを、CIは20/24で止められない

原稿は「証跡ファイルを指せないタスクをAI側に数えることはCIが禁止している」と
書いているが、**24件のうち20件は既に `evidence` が埋まっている。**
AIが提案・下書きはしているので、**提案側の実装ファイルが証跡欄に入っている**ためで、
検査は「そのパスが実在するか」しか見ない。

```
  evidence が空なのは4件だけ:
    human_only  月次予算の決定
    nobody      価格・プラン・ペイウォールの実験
    nobody      返金の可否についてAppleに意見を出す
    ai_proposes 収集同意
```

**つまり executor を書き換えるだけで、20件は素通りする。**
実測でも、24件を `ai_executes_gated` に倒すと総合自動化率は 65.2% → 77.3% に動いた。

**これは渡す・渡さないとは別の欠陥。**

### 塞いだ（2026-08-27）

`scripts/automation-rate.mjs` に **執行面の証跡**という判定を足した。
`ai_autonomous` / `ai_executes_gated` は、evidence の**少なくとも1つ**が
ワークフロー・スクリプト・実装・テスト・マイグレーション・台帳・実行ログを
指していなければ落ちる。手順書・方針・設計書・報告書は
**「やると決めた」の証跡であって「やっている」の証跡ではない。**

同じ操作（24件を `ai_executes_gated` へ倒す）を規則の追加後にやり直した:

```
   規則の追加前   0 件しか落ちない  → 65.2% が 77.3% になる
   規則の追加後  12 件で落ちる
```

**残る12件は落ちない。**そちらは**実装が在って、人が引き金を持っている**行
（App Review 提出・Kill Switch・価格変更など）で、`human_only` の理由が
「未実装」ではなく「権限」だから。**証跡の種類を見る規則では、権限の話は区別できない。**
塞げたのは「散文だけでAI実行に数える経路」までで、
**「そのスクリプトが実際に走ったか」は依然として見ていない。**
次に強くするならそこ（実行の記録＝run_id や台帳の行を指させる）。

### 既存の台帳側で見つかった10件

規則を入れたら、**渡す話とは無関係に、現行の129件のうち10件が落ちた。**
どれも散文だけを証跡にしていたもので、**執行面の実物は全部実在した**ので
証跡を差し替えた（率は 65.2% のまま動いていない）。

| タスク | 差し替え前 | 差し替え後 |
|---|---|---|
| ② オフライン・500・429の決定論再現 | QAアーキ文書 | `QAStubURLProtocol.swift` |
| ② 回帰の合否判定 | 同上 | `QATestCase.swift` ほか |
| ② セキュリティ監査と修正 | 監査**報告書** | 報告書が名指しした**修正先3ファイル** |
| ③ 施策の選定（レーンA〜E） | RUNBOOK | `autopilot-gate.mjs` / `build-queues.mjs` |
| ③ 品質ゲート | RUNBOOK | `build-queues.mjs`（ノイズフロアの実装） |
| ③ PR原稿の執筆 | 原稿そのもの | `check-pr-facts.mjs` / `code-authorship.json` |
| ⑤ 無限ループ・重複実行の防止 | RUNBOOK | `autopilot-gate.mjs` |
| ⑥ データ不足時に「何もしない」 | RUNBOOK | `autopilot-gate.mjs` / `build-queues.mjs` |

**「PR原稿の執筆」だけは生成器が無い。**原稿を書くのはセッションであって
スクリプトではないので、機械側に残るのは事実検査と著者台帳の2つだけ。
**無いことを台帳の note に書いてある。**

## 4. 結論

**境界を渡して数字を買うのは、この台帳では成立しない。**

- 渡すだけでは 93.4% に届かない（77.3%）
- そして「渡す」は書き換えではなく**実装**なので、A案8件は0件しか動かない
- 実装で正当に上がるのは1件（+0.5pt）

`autonomy-95-gap.md` §3 が先に書いていた
**「数字のために売りを捨てて、しかも数字は目標に届かない」**が、
**実際に当ててみた結果としても再現した。**

**次に効くのは率ではなく深さ**（人のmergeを経ずに本番へ出る／App Store の
正規リリース工程まで扱う）。率の側でやることは §3 で塞いだ。

**原稿の書き方は、塞いだあとなら正しい。**「証跡ファイルを指せないタスクを
AI側に数えることはCIが禁止している」は、2026-08-27 の朝までは
**指せてしまうので成り立っていなかった。**いまは散文だけでは指せない。
