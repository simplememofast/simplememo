# 境界24件を「AIに渡す」を実際に当てた — A案8件は0件しか上げられない

<!-- fact-check: internal -->

> **2026-08-27。**オーナーの指示「93.4% は十分インパクトがあるので境界をAIに渡したい」を
> 受けて、`data/automation-coverage.json` の `blocker: policy_boundary` 24件を
> 1件ずつ実装に当てた記録。**結論を先に: 書き換えで上げられるものは0件。**
>
> 正は `data/automation-coverage.json` / `data/authority-matrix.json`。
> 上限の計算は `node scripts/autonomy-gap.mjs`。

## 0. まず、93.4% の意味が違っていた

指示の前提は「境界24件を渡せば93.4%」だったが、**`autonomy-gap.mjs` の 93.4% は
`ceiling + owner_only`**、つまり **「到達可能な32件を全部実装したうえで、さらに
24件を渡した場合」**である。

```
   現在                            129/198 = 65.2%
   境界24件を全部渡した場合         153/198 = 77.3%   ← 実測（台帳を書き換えて計測）
   到達可能32件も全部実装した場合   185/198 = 93.4%
```

**渡すだけなら 77.3%（+12.1pt）。**93.4% には、渡す作業とは別に**32件の実装**が要る。

**8件すべて、いま executor を上げられない。**理由は4種類に割れた。

### 内訳

```
  台帳が既に明示的に否定している        2件（#3・#8）
```

どちらも過去に同じ検討をして「渡さない」と結論した記録が note に残っていた。
**タイトルだけを読んで分類すると、この2件は必ずまた候補に上がる。**

## 2. 実装すれば正当に上がるのは、1件だけ

**⑨ 返金の可否（refundPreference）。**台帳の note が既に設計まで書いている。

- `ConsumptionRequest` の必須欄は `customerConsented` / `deliveryStatus` /
  `sampleContentProvided` の3つで、**どれも事実**（同意の有無・配信できたか・
  購入前に無料で試せたか）。SimpleMemo は無料枠があるので3つ目は定数に近い
- **判断が入るのは `refundPreference` の1欄だけで、しかも必須ではない**

つまり **「事実だけを返して、意見欄は空で出す」**という形が作れる。これなら
「返金の可否をAIが決める」ではなく「事実の応答を機械が返す」になり、境界を
動かさずに実行側へ入る。**+1件で 130/198 = 65.7%。**

## 3. 見つかった穴 — 紙の上の書き換えを、CIは20/24で止められない

原稿は「証跡ファイルを指せないタスクをAI側に数えることはCIが禁止している」と
書いているが、**24件のうち20件は既に `evidence` が埋まっている。**
AIが提案・下書きはしているので、**提案側の実装ファイルが証跡欄に入っている**ためで、
検査は「そのパスが実在するか」しか見ない。

```
  evidence が空なのは4件だけ:
    human_only  月次予算の決定
    nobody      価格・プラン・ペイウォールの実験
    nobody      返金の可否についてAppleに意見を出す
    ai_proposes 収集同意
```

**つまり executor を書き換えるだけで、20件は素通りする。**
実測でも、24件を `ai_executes_gated` に倒すと総合自動化率は 65.2% → 77.3% に動いた。

**これは渡す・渡さないとは別の欠陥。**塞ぐなら、証跡が「提案側」か「実行側」かを
区別できる形が要る（例: `evidence` とは別に、実行の記録を指す欄を
`ai_autonomous` / `ai_executes_gated` の必須にする）。**未実装。**

## 4. 結論

**境界を渡して数字を買うのは、この台帳では成立しない。**

- 渡すだけでは 93.4% に届かない（77.3%）
- そして「渡す」は書き換えではなく**実装**なので、A案8件は0件しか動かない
- 実装で正当に上がるのは1件（+0.5pt）

`autonomy-95-gap.md` §3 が先に書いていた
**「数字のために売りを捨てて、しかも数字は目標に届かない」**が、
**実際に当ててみた結果としても再現した。**

**次に効くのは率ではなく深さ**（人のmergeを経ずに本番へ出る／App Store の
正規リリース工程まで扱う）。率の側でやることは、§3 の穴を塞ぐこと。
