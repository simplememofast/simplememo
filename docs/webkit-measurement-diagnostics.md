# WebKit測定の失敗を診断する

## 成功したCI内の未測定を自動運転へ届ける

描画検査は `SIMPLEMEMO_VIEWPORT_V1` のJSON行を出力する。Blinkの深い面、全面、
WebKitそれぞれについて予定数・実測数・測定失敗数・新しい横はみ出し数を記録する。
全予定のpage/widthが重複なく実測されて初めてcompleteになる。エンジンの未導入、
`--no-webkit`、`--no-sweep`、部分測定を「漏れなし」に変換しない。
途中でプロセスが落ちて行が出なかった場合も、観測側では未確認になる。

既存の毎日のAutopilot Actが、最新mainに対応するSEO Validationを読み、
`act-viewport-measurement` という固定IDで通常の修理候補台帳へ取り込む。
独立Codex運転が読む同じ候補台帳であり、修理コマンドをログから実行する処理はない。
描画検査のreport-only方針、検査対象、権限表、修理予算は変えない。

mainの直接pushはそのSHA、squashマージはmainのSHAに実際にマージされた自リポジトリPRの
正確なhead SHAを使う。対象ワークフロー・run・attempt・job・測定step・時間範囲を照合する。
未マージPRやfork、古いmainの緑には戻らない。取得後にmainとrun attemptを再読し、
観測中に変化した場合は未確認にする。実行中は新規修理を作らず、既存の修理も閉じない。
7日を超える結果、読めないログ、途中失敗、報告行の欠落・重複は健全とは判定しない。

全3区分の実測が揃い、新しい横はみ出しも静的問題も0なら閉じられる。
実際に観測した測定障害を閉じるには、それ以降の別runまたは新しいattemptが必要。
一時的なAPI取得不能だけなら、同じrunの検証結果を読み直して解消できる。
取得不能で、以前の実測障害のrun情報を上書きしない。再発は同じ候補を開き直す。
結果の再読は既存Actの実行時に限り、新しいworkflow_runトリガーや通知先は追加しない。

APIはreadのみ。ジョブログの署名付きURLへリポジトリのトークンは転送しない。
API本文は2MiB、ログは8MiB、通信は各20秒（ログ本体30秒）で打ち切り、
不足を成功扱いにしない。日次レポートには件数とrun/SHAの根拠だけを残す。
今回の接続テストを、実障害の無人修復実績やスコア上昇としては計上しない。

API仕様: [ジョブログの取得](https://docs.github.com/en/rest/actions/workflow-jobs#download-job-logs-for-a-workflow-run)、
[コミットに対応するPRの取得](https://docs.github.com/en/rest/commits/commits#list-pull-requests-associated-with-a-commit)。

## 過去の実測とドライバ修正

2026-09-07のSEO Validation `34110440552` と `34112088081` は、Blinkの279面×4幅を
測定した一方、WebKitは `fetch failed` で未測定だった。画面幅ステップは約13分かかった。
report-onlyのためジョブは成功したが、WebKitやiPhone実機の確認済み実績にはならない。

この時点でドライバの標準エラー出力は捨てられ、通信の処理名や原因コードも残っていなかった。
プロセス停止、接続拒否、ドライバからの応答待ちのどれだったかは、過去のログから確定できない。

`scripts/lib/webkit-driver.mjs` は失敗したポート・HTTP処理・原因コード・経過時間を記録する。
初期化失敗では、後片付けで停止信号を送る前のドライバ終了状態と、標準エラー出力の末尾も残す。
資格情報や環境変数の値、WebDriverへ渡すスクリプト本文は診断ログへ出さない。

通常の通信期限は75秒。描画スクリプトの既存60秒期限による応答を受け取れる長さとし、
応答ヘッダーだけでなくJSON本文の受信にも適用する。後片付けのセッション削除は2秒まで待ち、
応答がなくてもこの測定が起動したドライバへ終了信号を送る。既存DISPLAYは停止しない。
終了信号を送ったことを全子プロセスの終了確認と同一視しない。

`node --test scripts/webkit-driver.test.mjs` は実際に応答を止めるローカルHTTPサーバーを使い、
ヘッダー待ち・本文待ち・セッション削除が期限で止まること、失敗が成功値にならないことを検査する。
この通信検査はCIで必須とし、既存の描画対象ページ・幅・描画の判定・report-only設定は維持する。

この変更だけで過去の未測定原因が直ったとは扱わない。次の実CIでは詳細な失敗情報、
またはWebKitの測定件数と結果を確認する。今回のテスト結果を本番障害の自動修復件数には加えない。

## 仮想画面の起動を確認する

その後の実CI `34117916896` は、`POST /session`が75秒でタイムアウトした。
診断には`MiniBrowser cannot open display :99`と、起動したXvfbの終了コード1が残った。
この回は画面へ接続できなかったことが分かるが、Xvfbの標準エラーは未収集だったため、
終了した理由や、以前の2回も同じ原因だったかは確定していない。

固定`:99`の起動をやめ、Xserverの`-displayfd`で選ばれた空き画面番号と起動通知を待つ。
通知の欠落・不正・起動時の終了を検知し、起動待ちは5秒で打ち切る。起動できない場合は
WebDriverセッションを要求する前に失敗する。Xvfbの標準エラー末尾と終了状態を診断に残す。
既存のDISPLAYは利用を継続し、他のXサーバーやロックファイルを操作しない。

後片付けでは起動した直接の子プロセスへSIGTERMを送り、2秒で終了しなければSIGKILLへ進み、
さらに1秒待っても終了を確認できなければ失敗として残す。任意の孫プロセスすべてを
回収した証明ではない。元の測定失敗がある場合、その診断を後片付けのエラーで上書きしない。

テストは本物の子プロセスと専用パイプで、分割通知・起動失敗・タイムアウト・不正通知・
SIGTERM無視を検査する。LinuxでXvfbとxdpyinfoがある場合は、異なる2画面の接続、
片方の終了後ももう片方に接続できること、追加起動も検証する。環境がない場合は
実画面テストを明示的にSKIPし、測定成功とは扱わない。既存のapt失敗と広い描画検査の
report-only方針は維持する。

根拠: [Xserverのdisplayfd仕様](https://cgit.freedesktop.org/xorg/xserver/tree/man/Xserver.man)、
[Xserverの起動通知実装](https://github.com/XQuartz/xorg-server/blob/master/os/connection.c)。
