## 0. なぜこれを先に出すか

この原稿は「**証跡の無い主張を一切入れていない**」ことを売りにしています。
そして自社のCIには、**配信原稿に誇大表現が出たら落とす検査**（`scripts/check-pr-facts.mjs`）が
入っています。**出どころの無い数字をヒーローに置くと、原稿の主張そのものが自己矛盾します。**

記者が最初にやるのは、**バナーの数字1つを選んで「これはどう数えましたか」と聞くこと**です。

## 2. 95.3% は、台帳の定義では到達できない

「自律性が足りないところは数日で改修する」という前提でも、**この数字には届きません。**
理由は実装の速度ではなく、**分母の中身**です。

```
   現在（2026-08-22 の実装44件＋main合流を反映） 106 / 173 タスク  =  61.3%
   未実装 22 件を全部埋めても                         →  73.8%
   提案どまり 26 件も実行へ上げたら                    →  89.0%  ← **人間専任19件を人間に残したままの理論上限**
   95.3% に必要なタスク数                              164 件（あと 59 件）
```

**89.0% が天井。**人間専任19件を人間に残す限り、AI実行に回せるのは最大154件（89.0%）。
95.3% には164件が要るので、**人間専任19件のうち11件をAIに渡さないと届かない** —
実機での事前確認・App Storeへの公開・価格変更・事故対応のどれかを渡すことになる。

**人間専任19タスクには、意図的に人間へ残したものが含まれます** —
実機での事前確認、App Storeへの公開、価格変更、事故・法的請求・炎上時の対応。
**これらをAIへ渡すと95.3%に近づきますが、原稿の売りである「境界」が消えます。**

つまり **95.3% は「まだ達成していない数字」ではなく、「この設計では目指していない数字」**です。

## 3. 「コード変更 98.8%」も、配信前に導出をやり直したほうがいい

既存原稿は「**231,315行中228,498行・56コミット中55件**」（2026-08-11〜08-22）としています。
**今回、同じ窓で計測し直したが再現できませんでした。**

| 計測 | コミット | 変更行 |
|---|---|---|
| simplememo 単体・マージ除く | 66 / 67（98.5%） | 37,866 / 40,683（93.1%） |
| 3リポジトリ・現ブランチ・マージ除く | 126 / 127（99.2%） | 51,516 / 54,333（94.8%） |
| 3リポジトリ・全ブランチ・マージ除く（08-11〜08-21） | 193 / 194（**99.5%**） | 46,159 / 48,976（**94.2%**） |

**どの数え方でも 231,315行 にならず、98.8% にもなりません。**

### 2026-08-22: 数え方を script にしました

`node scripts/code-authorship.mjs --check` ／ 台帳 `data/code-authorship.json`。
**数字ではなく数え方を凍結**してあります（CIが台帳の算数と定義の記述を検査し、
`headline` が実測とずれていたら落ちます —— 「数字だけ良くする」経路をつぶすため）。

定義は script の冒頭に全部あります: AI著者＝`author` が Claude か本文に
`Co-Authored-By: Claude` ／ 変更行＝`git show --numstat` の追加+削除 ／
マージ除く ／ SHAで一意化 ／ **計測日そのものは窓に入れない。**

最後の1点が効きます。**08-22 を窓に含めると 94.2% → 96.6%（+2.4pt）動きます。**
計測日はAIが集中的に書いている日になりやすく、「いちばん都合のよい日で締めた」と
言われる余地を残さないために外してあります。

**配信に使うなら「コミットの99.5%、変更行の94.2%がAI著者」**
（3リポジトリ・全ブランチ・マージ除く・2026-08-11〜08-21）。

## 4. 差し替えに使える実測値

**どれも台帳から出ていて、`--check` が現在値との一致を強制しています。**

| 使える数字 | 値 | 何を言えるか |
|---|---:|---|
| **成果物への人の介入** | **0件 / 0.0%** | 「出荷10件すべてAIが書き、人は中身に触っていない」。**バナーの主張にいちばん近い真実** |
| 成果物のAI自律率 | **100%** | 同上を率で言ったもの |
| コミットのAI著者率 | **99.2%** | 「コードは人がほぼ書いていない」 |
| 変更行のAI著者率 | **94.2%** | 同上（3リポジトリ・全ブランチ・マージ除く・08-11〜08-21）。`scripts/code-authorship.mjs` で再現できる |
| AI関与率 | **87.4%** | 「誰かがやっている業務の9割近くにAIが関わる」。**最も甘い数え方であることを併記する条件つき** |
| 自律度の推移 | **3.5% → 61.3%** | **ローンチから4か月で約18倍。**バナーを「率」ではなく「変化」に振るなら、これが最も強い |
| 権限表 | **15領域中10が承認制** | 「人は重要判断だけ」の裏づけ。**バナーのこの1行は正しい** |
| 自動検証 | **51種 / 必須40本** | 「検証を通ったコミットだけが本番へ出る」 |

### バナーを直すなら、いちばん短い直し方

**ヒーローの数字を「率」から「変化」に替える。**

> **運営の自律度、4か月で3.5% → 61.3%。**
> 人は重要判断だけ。／ 出荷物に人が手を入れた回数：**0**

**61.3% は、この原稿ではそれが効きます。**
「まだ半分」と自分から言う会社が、その横で「介入0件」と言うから信用が乗ります。
**95.3% は、その効き方を丸ごと捨てることになります。**

## 5. グラフの扱い（`data/autonomy-timeline.json`）

月次の系列は**再構成であって当時の実測ではありません。**
`scripts/autonomy-timeline.mjs` が持つ制約は3つで、**グラフに出すときは必ず併記します。**

1. 証跡ファイルの追加日 ≒ 稼働開始日（実際には数日〜数週のずれ）
2. **分母は現在の棚卸し（173タスク）を過去へ固定している。**当時は一覧自体が無かった
3. 出せるのは総合自動化率だけ。AI関与率とカバー率の系列は復元していない

**終点だけは実測**で、`--check` は終点が `automation-rate.mjs` の現在値と一致しない限り
**CIを落とします**。ずれた系列は、グラフとして存在してはいけないためです。

## 6. 2026-08-25 の再計測 — **率は下がった**

外部レビューの①〜⑨を実装に当て直し、**棚卸しに13件足した**（うち10件が未実装）。

| 指標 | 08-22 | **08-25** | 動いた理由 |
|---|---:|---:|---|
| 総合自動化率 | 61.3% | **58.6%** | 分母 173 → 186。**実装は 106 → 109 で増えている** |
| AI実行率 | 70.2% | **70.3%** | ほぼ不変 |
| AI関与率 | 87.4% | **87.7%** | ほぼ不変 |
| カバー率 | 87.3% | **83.3%** | 未実装が 22 → 31 に増えた（＝気づいた分） |
| 定義タスク | 173 | **186** | +13（intentional_no 3 を除いた数） |
| 自律度の推移 | 3.5% → 61.3% | **1.1% → 58.6%** | 分母固定値が変わったので系列全体が引き直された |

### §4「差し替えに使える実測値」の更新

**§4 の表のうち、率で書いた行は下の値に差し替えること。**

| 使える数字 | **08-25 の値** | 変わったか |
|---|---:|---|
| 成果物への人の介入 | **0件 / 0.0%** | 変わらず。**バナーの主張にいちばん近い真実のまま** |
| コミットのAI著者率 | 99.2% | 変わらず |
| 変更行のAI著者率 | 94.2% | 変わらず |
| 総合自動化率 | **58.6%** | 61.3% から |
| AI関与率 | **87.7%** | 87.4% から |
| 自律度の推移 | **1.1% → 58.6%** | 3.5% → 61.3% から |
| 権限表 | 15領域中10が承認制 | 変わらず |

### §4 の「いちばん短い直し方」も引き直す

> **運営の自律度、半年で1.1% → 58.6%。**
> 人は重要判断だけ。／ 出荷物に人が手を入れた回数：**0**

**倍率は書かないほうがいい。**「約18倍」は分母の取り方に強く依存する数字で、
実際に分母が 173 → 186 に動いただけで 17.5倍 → 53倍 に変わってしまう
（始点が 3.5% → 1.1% になるため）。**倍率は分母の脆さをそのまま増幅する。**
**差の絶対値（1.1% → 58.6%）だけを書く。**

### そして、下がったこと自体を書く

**これがこの原稿でいちばん効く一行になりうる。**

> 棚卸しを増やしたので、公表している自律率は 61.3% から 58.6% へ**下がりました。**
> やめた自動化はひとつもありません。**「できていない」と気づいた項目を
> 一覧に足したぶん、分母が増えました。**

率を上げるいちばん簡単な方法は、**できていないことを一覧に書かないこと**。
そうしなかったことを、下がった数字そのものが示している。
**AppDNA も PostHog も、自社の数え方を外から再現できる形では出していない**
（`competitors-autonomous-app-ops-2026-08.md` §0）。ここが唯一の差別化なので、
**下がった回にそれを見せるのが最も強い。**
