### 0-1. なぜ「RSI」を名乗らないか

**RSI（Recursive Self-Improvement）は「AI自身が自らの知能・能力を改良する」という
強い意味で受け取られる。**この運用が実際にやっているのはそれではない。

やっているのは **「AIがアプリ改善サイクルを継続実行し、その結果を測って次に反映する」**
こと。**AIモデル自身は一切改良していない。**

用語も正しくは「**再帰的**自己改善」（「再起的」ではない）だが、そもそも
**その語を対外文言に使わない**。使う言い方は次の3つ。

- **ガードレール付き自律型アプリ運営基盤**
- **AIがアプリ改善サイクルを継続実行する仕組み**
- **再帰的プロダクト改善ループ**（技術者向けの説明でのみ）

> 内部の実験台帳のレコードIDは `pr-2026-rsi-autopilot` のまま（識別子は動かさない）。
> **IDは内部識別子であり、対外表現ではない。**

### 0-2. 革命性の置き所

**× 「人が一切いない」** — 事実でない。出荷の最終判断・実機確認・App Store公開・
価格・広告・契約は人間が持っている。しかもそれは**意図的な設計**。

**○ 「人間を日常作業のボトルネックから外し、人は目的設定・高リスク判断・
例外対応だけを担当する運営構造にした」**

この置き方なら、いま証跡があるものだけで最後まで書ける。

### 0-3. 見出しで最適化すべきは S2（エンティティ到達）

自社のPR実績n=5を D-SCORE 順に並べると、勝敗を分けているものが1つだけ見える。

PR④が沈んだのは「AI」という語のせいではなく、**固有名詞が1つも無かったから**。

**現行の正式名は `Obsidian連携シンプルメモ`（EN: `Simple Memo - for Obsidian`）**
なので、**アプリ名を書くだけで見出しに Obsidian が入る**

`data/site-constants.json` が正）。

## 1. タイトル・サブタイトル（**確定・2026-08-22**）

### タイトル

> **「アプリが、自ら育ち続ける。」Obsidian連携シンプルメモ、AIによる"自律型アプリ運営"を実現**

### サブタイトル

> **ユーザー行動の計測から機能開発、QA、SEO・ASO、PR制作、配信準備までをAIが
> 一気通貫で循環。公開・予算・契約はリスクに応じて人が承認し、自律性と安全性を両立。**

### 採用時の条件（**本文の書き方を縛る**）

**「アプリが、自ら育ち続ける。」は、取り下げたRSIの主張とほぼ同じ形をしている。**
正確には「アプリ**を**、AIが育て続ける」であって、アプリが自分で自分を書き換えて
いるわけではない。コピーとしての強さは本物なので採用するが、**次の3つを守る**。

1. **サブタイトルを必ずセットで出す。**「公開・予算・契約はリスクに応じて人が承認」が
   打ち消しになっている。タイトル単独で流通させない（SNS投稿・OGPも同様）
2. **本文の最初の見出しで、仕組みを即座に具体化する。**
   §3冒頭の担当分担表がその役目。「誰が何をやっているか」を先に見せる
3. **本文でこの比喩を拡張しない。**「アプリが自分で考えて」「AIが自己進化して」等は
   §5-1の禁止表現。**キャッチコピーは1行で終わらせる**

### なぜこのタイトルで点が上がるのか

**主張を大きくしたからではなく、コピーが良くなったから。**（§2の採点参照）

- 「自ら育ち続ける。」は**変化の描写**として強い（S4 +2）
- 「実現」は「構築」より強い動詞（S6 +1）
- **固有名詞は据え置き**（Obsidian連携シンプルメモ）。S2は変わらない
- **主張の範囲は1ミリも広げていない。**サブタイトルが承認制を明記し、
  本文の「できていないこと」表もそのまま残っている

### 差し替え候補（サブとして併記可）

- 検証を通ったコミットだけが本番へ出る。20のチェックと、通らなかった日の記録も公開
- 失敗の分類は2つのAIモデルに独立で聞き、**判定が割れたら人間に上げる**
- AIに「App Storeへ出す権限」は渡していない

> 配信前に見出し確定稿で `node growth/scripts/d-score.mjs` を回す。60未満なら撃たない。

## 3. 本文

### ■ 何が変わったのか：人がいなくなったのではなく、人の位置が変わった

今回発表するのは「無人でアプリが成長する仕組み」ではありません。
**人間を日常作業のボトルネックから外し、人が担うのを
「目的設定・権限管理・高リスク判断・例外対応」に絞る運営構造**です。

| | 担当 |
|---|---|
| 日々の計測・施策の選定・実装・検証・出荷準備 | **AI（継続実行）** |
| 目的とビジョンの設定、AIが変えてはいけない原則の固定 | 人間 |
| App Storeへの公開、価格、広告予算、契約、支払い | **人間（承認制）** |
| 実機での最終確認 | 人間 |
| 事故・炎上・法的請求・重大障害 | **人間（自動停止して移管）** |

### ■ 背景：自動化の失敗は「エラー」ではなく「静かな停止」で来る

個人・小規模チームの開発運用にAIを組み込む試みは増えていますが、多くは
「AIに書かせる」で止まります。実際に運用して分かったのは、**本当の失敗は
派手なエラーではなく、誰も気づかない停止だった**ということでした。

同社の成長計測基盤 `growth/` は、まさにその失敗から生まれています。
手順書の冒頭には、こう書かれています。

> 12ページのタイトルを変更し、評価日を報告書に書いた。その日付は過ぎた。
> 以後6週間の報告書はいずれも「その日に判断する」と繰り返して先へ進んだ。
> 壊れてはいなかったし、誰も不注意ではなかった —— **単に、期限切れになれる
> 成果物が無かった**。計画は文章の中に住んでいて、文章は手を挙げない。

以降、同社は方針を「AIに賢く働かせる」から「**判断の根拠と期限をファイルに落とし、
CIに監視させる**」へ切り替えました。今回公開する基盤はその延長線上にあります。

### ■ 何が動いているのか：毎朝6時の1サイクル

```
06:00  **まず運転台帳を読む。未修理の故障があれば、その日は修理に切り替える**
   ↓   検索データ（Google Search Console の BigQuery エクスポート）を読む
   ↓   その日に実装する施策を「1件だけ」選ぶ
   ↓   ・期待クリック数が基準未満の根拠では書かない（ノイズフロア）
   ↓   ・書く理由がなければ書かない。保守作業とログだけで終えてよい
   ↓
       実装 → 内部リンク配線 → コンテンツ台帳へ登録 → OG画像生成 → QRコード生成
   ↓
       20種の自動検証（SEO検証261ファイル／CSS・JSキャッシュ整合／URL正規化／
       内部リンク13,195件＋構造化データ5,203件＋サイトマップ576URLの直接200検証／
       実験台帳の期限監視／コンテンツ台帳の整合／サイトマップ掲載の強制／
       AI実費台帳の整合／広報企画の採点の検算）
   ↓
       Pull Request を作成
   ↓
       **検証に合格したときだけ**、合格したコミットを指定して自動マージ
   ↓
       本番デプロイ（Cloudflare Pages）
10:00  実行結果と当月のAI実費を集計してオーナーへ日報メール
12:00  「緑のまま何もしていない」状態を検知する別系統の見張り
```

**「毎日1本出す」ことは目標にしていません。**手順書には
「**毎日出すために基準を下げる、はこの運用の失敗定義そのもの**」と書かれており、
基準を通らなかった日はスキップし、**その理由が日報に載ります**。

### ■ 実際に出荷されたもの（2026年8月11日〜22日）

- Obsidian情報ハブ記事の新設（保管庫の解説、プラグイン実測ランキング、
  Logseqとの比較検証 ほか）
- **一次情報の実測**：Obsidian公式レジストリから登録6,840個のプラグインを
  当日実カウントし、ダウンロード数・最終更新日・配布版とタグの不一致まで確認して記事化
- サードパーティアプリの実挙動検証（同一フォルダ共存・往復書き込み・
  DB版の非Markdown保存をスクリーンショット付きで確認）
- スマートフォン実描画QAで見つけた横スクロールの自己修正
  （CSS Gridの `min-width: auto` が原因と特定し、そのページだけを局所修正）

### ■ 実測：AIが何回動き、何回人が入ったか

**この基盤の稼働状況を、推定ではなく台帳から出しています。**
すべての実行に共通の実行IDを振り、着手・結果・PR・介入・費用を1行で記録しています。

**2026年8月11日〜8月25日（15日間・26実行）**

| 指標 | 実測 |
|---|---:|
| **AI完走率**（着手した実行のうち本番へ出荷できた割合） | **68.8%**（11 / 16） |
| **変更失敗率**（着手したが本番に何も出せなかった割合） | **31.3%**（5 / 16） |
| **人間介入率**（人の判断・修正・代走が入った実行の割合） | **56.3%**（介入9件） |
| **出荷日率**（15日のうち本番に何かが出た日） | **73.3%**（11日 / 15日） |
| 経路別（主系 / 副系・代走） | **1 / 6** ・ **10 / 10** |
| 無運転日（どの経路も動かなかった日） | **2日**（8月16日・17日） |
| **未解消の故障** | **2件**（8月24日・25日／同一原因） |

**この表は、直前まで完走率78.6%・出荷日率84.6%と書かれていました。**
8月24日と25日に主系が連続で失敗しており、**その2件が台帳に記録されていなかった**ためです。
記録を入れた結果、**完走率は10ポイント下がりました。**

**人間介入率56.3%という数字を、同社はそのまま公開します。**
半分以上の実行に人が入っています。これは「AIが自律的に運営している」という
言葉から想像される姿とは違いますが、**それが現在地です。**

### ■ ただし「介入」は一種類ではない

56.3%という数字は「その実行に人が1回でも触ったか」を数えたもので、
**ワークフローの設定を1行直しただけの日も、丸ごと「介入あり」になります。**
そこで同社は、介入を「何への介入か」で分けて記録しています。

| 介入の種類 | 実行数 | 割合 |
|---|---:|---:|
| **成果物への介入**（人が記事を書いた・書き直した） | **0** | **0.0%** |
| 実行基盤の修理（ワークフロー・手順書・スクリプト） | 4 | 25.0% |
| 起票のみ（人に依頼した。**まだ実行されていないものを含む**） | 3 | 18.8% |
| 代走（全経路が不発で人が代わりに実行） | 1 | 6.3% |
| 立ち上げ（初回に人が通しで実演・一度きり） | 1 | 6.3% |

**出荷された11件すべてを、AIが書いています。人間は一度も中身に手を入れていません。**
同期間のリポジトリの変更行のうち **98.8%** がAI著者のコミットによるものでした
（56コミット中55件）。

**したがって実質的な介入は「基盤の修理」25.0% の一点に集約されます。**
そしてその修理を書いたのも、すべてAIでした。人間がやったのは
**「壊れていることに気づいて、直せと言うこと」だけ**です。

### ■ ただしここまでの数字は「開発領域だけ」のものです — 全領域を同じ物差しで測った

**完走率68.8%・変更行のAI比率98.8%は、記事とコードを書く工程の数字です。**
アプリ運営はそれだけではありません。カスタマーサポートも、マネタイズも、
経理も契約もあります。**そこを測らずに「自律型アプリ運営」と名乗るのは、
一番都合のいい分母を選んでいるのと同じ**です。

そこで同社は、**開発以外も含む13領域175タスクを1つの台帳に並べ、
それぞれを「誰が実行しているか」で6分類しました。**

| 分類 | 意味 | 件数 |
|---|---|---:|
| **自律** | AIが起動から完了まで単独。人の承認もゲートも待たない | **8** |
| **ゲート付き実行** | AIが実行し、CI・上限・品質基準を通ったときだけ通る。**この運用の主力** | **61** |
| 提案のみ | AIは提案・下書き・検知まで。実行は人間 | 33 |
| 人間 | 人間が実行。AIは関与しない（または意図的に関与させない） | 20 |
| 未実装 | 誰もやっていない | **51** |
| 意図的にやらない | やらないと決めた（分母から外す） | 2 |

**分母を1つに決めると、必ず都合のいい数字が出ます。**そこで4つ並べて出しています。

| 指標 | 値 | 分母 |
|---|---:|---|
| **総合自動化率** | **39.9%** | 定義タスク173（**未実装を含む・最も厳しい**） |
| AI実行率 | 56.6% | 実施中タスク（未実装を除く） |
| AI関与率 | 83.6% | 同上（提案・下書きまで含める・**最も甘い**） |
| カバー率 | 70.5% | そもそも誰かがやっているタスクの割合 |

**「AIが83.6%に関与している」だけを出すのが、この台帳で一番やってはいけないこと**と
台帳自身に書いてあります。**同社が代表値として使うのは、最も低く出る39.9%です。**

領域ごとの差は、そのまま同社の現在地です。

| 領域 | 総合自動化率 |
|---|---:|
| ③ 自律型マーケティング | **61.5%** |
| ① 次期機能開発 | 60.0% |
| ② バグ修正 | 58.8% |
| ⑩ AgentOps・ガバナンス | 58.3% |
| ⑪ データ・プライバシー | 50.0% |
| ⑤ AI予算・トークン管理 | 46.7% |

| ⑥ アプリ運営意思決定 | 23.1% |
| ⑧ カスタマーサポート ／ ⑨ マネタイズ | 12.5% |
| **⑦ 法人経営**（経理・契約・労務ほか） | **着手前**（権限と承認の設計段階） |
| **⑬ アナログ領域**（イベント・人事・営業ほか） | **着手前**（多くは人間が担う設計） |

**下2つが「着手前」であることを、同社は表から外していません。**
経理・税務・契約・支出承認は、権限と承認境界を設計している段階で、
**AIが実行に回った工程はまだありません。**
「AIで会社を回している」と読まれかねない訴求をするうえで、
**ここを曖昧にすることが、記者に対して最も高くつく**と判断しています。

**この測り方の限界も台帳に書いてあります。**「記事の実装」と「SBOM生成」が
同じ1として数えられており、**領域間の比較は傾向であって精度のある比較ではありません。**
タスクの粒度も領域で揃っていません（法人経営は粗く、マーケティングは細かい）。

### ■ そこで「自分の壊れたところを、指示を待たずに直す」機能を実装しました

介入の内訳が示したのは、**足りないのは能力ではなく起動条件だった**ということです。

同社は自律運用に**自己修復の工程**を追加しました。毎朝の実行は、記事を書く前に
まず運転台帳を読み、**未修理の故障が残っていればその日の最優先を修理に切り替えます。**
その日の記事はゼロになりますが、**壊れた基盤の上で記事を出しても翌日また止まります。**

自分のCIを自分で直す仕組みには、放っておくと必ず現れる失敗があります。
**「通らないチェックを消して緑にする」**です。そこで境界を機械が守っています。

- **触ってよいファイルを限定**（ワークフロー・手順書・自分の集計スクリプトのみ）
- **検証を弱める変更を禁止。**必須の自動検証20本が1本でも消えると**CIが落ちます**
- **自分の権限を広げる変更を禁止。**設定ファイルに特定の権限が現れると**CIが落ちます**
- **同じ種類の故障を3回直しても再発するなら、修理をやめて人間に上げる。**
  直せないものを毎日直そうとするのが、この仕組みで最も危険な無限ループだからです

**判定と実装は分けています。**「今日修理に入るべきか」を判定するスクリプトは、
修理そのものを行いません。同じ場所に置くと、判定の側を都合よく変えられるためです。

分母は「着手した実行」で、秘密鍵が無いときに意図的に何もせず終了した回
（8回）は含めていません。**意図して寝た回を失敗に数えると、
正しく働いている安全装置が失敗率として現れる**ためです。
逆に**無運転日は正常系ではない**ので、分母から外したうえで別枠に必ず出します。
ここを黙ると稼働率が100%に見えてしまいます。

### ■ 弱点は「直す速さ」ではなく「気づく遅さ」だった — 見張っていない場所を名指しする

自己修復を入れたあと、同社は**故障を「いつ気づいたか」と「いつ直したか」に
分けて計測しました。**出てきた数字は、直感と逆でした。

| | 中央値 | 最大 |
|---|---:|---:|
| 故障が起きてから**気づく**まで | **2.7時間** | **50.7時間** |
| 気づいてから**直す**まで | 3.7時間 | 25.6時間 |

**修理は速い。遅いのは検知です。**最大50.7時間、つまり丸2日以上、
壊れたまま誰も気づかなかった故障がありました。**直す能力を足しても、
この2日間は1分も短くなりません。**

そこで同社は「何が見張られていて、何が見張られていないか」を台帳にしました。
**「全部見ています」と言うための台帳ではありません。**
**空いている場所を名指しできるようにするための台帳**です。

現在13系統を棚卸しし、気づき方を4段階で分類しています。

| 気づき方 | 系統数 | 例 |
|---|---:|---|
| **機械が検知して通知まで出す** | **9** | オートパイロットの停止、定期実行の失敗、サイト検証、AI予算の超過、基盤の故障、資格情報の期限、段階公開のガードレール、Watchアプリ、課金 |
| 別の記録から後で分かる（気づくのは人） | 3 | アプリのクラッシュ ほか |
| **気づく経路が無い** | **1** | — |

**「気づく経路が無い」1系統を、台帳は消さずに残しています。**
さらにこの検査は、**実際に起きた故障の種別に検知器が無いものを名指しします。**
起きたのに誰も見ていない種別が、次に50時間気づかれない候補だからです。

### ■ 境界を1枚の表にした — 不可逆な変更が承認制かどうかを、CIが見る

「どこまでAIがやり、どこから人間か」を**機械可読な権限表**として持ち、
13領域それぞれについて可逆／不可逆・AIが実行してよい範囲・人間専任の操作・
何がその境界を守っているかを定義しています。**13領域のうち9つが承認制です。**

CIが見るのは3つだけです。

1. **不可逆な領域が承認不要になっていないか。**逆になっている行は、
   権限表の一番の存在理由が壊れています
2. **稼働中の領域が、根拠のファイルを指せているか。**
   根拠を示せない「そうなっているはず」は、次に判断する人には存在しないのと同じです
3. **金額が動く領域が上限を持っているか。**未設定なら「未設定と決めた」と
   書かせます。**空欄と未設定は違います**

**実際に人が承認したかどうかは機械では見られません。**
そこは表の側に正直に書いています。

### ■ 「AIに与えていない権限」を、理由つきでソースコードに書いてある

同社が今回もっとも公開したいのは、できることの一覧ではなく**境界**です。

アプリのリリース経路（タグ作成 → Xcode Cloud でのビルド → TestFlight配信 →
App Review提出）は自動化されていますが、**その連鎖を起動する権限を、
開発用のAIワークフローには与えていません**。設定ファイルには理由がこう書かれています。

> この権限があれば、確認を求めない設定のAIが出荷ワークフローを直接呼び出し、
> **人間を一切介さずApp Storeへ出荷できてしまう**。この機能に必要な中核用途は無い —
> リポジトリの読み取り・コミット・push・PR作成・コメントはすべて権限なしで動く。
> 必要になったら、この権限を広げるのではなく、**用途を限定した別の経路を作れ**。

加えて、リリース手順書には**人間のハードルール**が明記されています。

> **実機で確認してから提出する。後ではなく先に。**

Appleの審査通過後にApp Storeへ公開する操作も、設定上ハードコードで無効化されており、
**恒久的に人間の操作**として残す方針です。

### ■ AIが自分の実費を記録し、上限に達したら自分を止める

自律運用のコストは、放っておけば静かに膨らみます。同社は運用のAI実費を
**台帳ファイルとして持ち**、毎朝の実行前にその月の消化額を照合します。
**上限に達していれば、その日の自動実行は起動しません。**

設計上、意識的に非対称にしている点が2つあります。

- **上限は記事より優先する。** 同じワークフローの中で、日本語フォントの導入は
  「失敗しても続行」に設定されています（フォントが無い日は記事内の
  スクリーンショットの和文が崩れるだけで、記事は出るべきだから）。
  一方**予算の照合は失敗を許容しません**。
- **台帳が壊れていても止める。** 壊れた台帳は「集計できない」ではなく
  「**上限に永久に到達しない**」＝安全装置が静かに切れている状態を意味します。

なお同社は、**この仕組みで測れていない範囲も同時に公開しています。**
実行経路は主系・副系の二重構成になっており、副系はログを外部から読めないため
**実費を観測できません**。日報メールはこれを「ゼロ」ではなく「**未観測**」と
明示して区別します。上限値そのものもまだ実測由来ではないため、
**「予算に応じて最適配分している」とは主張しません。**

**上限に達する前に気づくための検知も別に持っています。**ただし判定は
**絶対額ではなく、直近の実行の中央値との比**で行います。金額の閾値を置くと、
記事が長い日や再試行が入った日に鳴り続け、**鳴りっぱなしの警報はいずれ消される**ためです。

さらに、**実績が5件に満たないうちは「異常なし」と言いません。**
台帳は「**判定していない**」と出力します。データが足りない状態を
「問題なし」と表示するのは、安全装置が静かに切れているのと同じだからです。

台帳には**モデル別・再試行別の内訳**も記録していますが、
**実行ログに費用の按分が無いため、言えるのは回数までです。**
「どのモデルにいくらかかったか」は書けません。

同社が**あえて実装していない最適化**もあります。プロンプトキャッシュや
コンテキスト圧縮は、月あたりの実費が現状の規模では
**最適化で浮く額より実装と保守の手間が上回る**という判断で見送っています。
**やらないと決めたことも、理由つきで台帳に残しています。**

### ■ 品質検証：AIが「まだ誰も報告していないバグ」を見つけた

2026年7月末に導入した自律QA基盤は、「AIに毎回画面を操作させる」方式を**採っていません**。
回帰検証は決定論的なXCTest/XCUITestが担い、AIは**テスト設計・失敗の分類・
資産化**を担当します。テストからは本番APIへ到達できないよう構造的に遮断し、
成功・オフライン・タイムアウト・500・429を再現可能な形で作り分けています。

この設計中に、AIが**ユーザーからの報告が一件も無かった不具合**を発見しました。
Apple Watchからの送信が失敗して別経路へフォールバックした際、
**同じメモが2通送られうる**（経路ごとに識別子が変わるためサーバ側の重複排除も効かない）
というものです。重複排除の台帳を追加して修正し、同時に回帰テストとして固定しました。

### ■ 失敗の分類は2つのAIモデルに独立で聞き、割れたら人間に上げる

テストが失敗したとき、その原因を「アプリの回帰」「テスト側の欠陥」
「実行環境のゆらぎ」などに分類する工程があります。同社はここを
**2つの異なるAIモデルに、同じ資料で独立に判断させています。**

- **平均も多数決も取りません。**2つでは多数決が成立せず、平均は
  「割れている」という一番価値のある情報を消してしまうためです。
- **判定が割れたら人間に上げます。**この工程で最悪の誤りは
  「実行環境のゆらぎ」の誤判定で、そう分類された本物の回帰は
  再実行で流され、そのまま出荷まで通ってしまうからです。
- **片方のモデルしか答えなかった回を「一致」とは書きません。**

分類を行うAIには、**「根拠が足りない」と答える選択肢**を仕様として持たせています。
また、**AIの合議だけで合否を決めていません。**回帰の判定そのものは
決定論的なテストが持ち、AIが持つのは分類と分析だけです。

### ■ 「止める判断」だけを機械に渡し、「広げる判断」は人に残した

新機能を段階的に配る仕組み（遠隔のフィーチャーフラグ）と、
問題が出たときに引っ込める仕組みは、2026年8月までに両方揃いました。
**しかし「引っ込めるかどうかを決めていたのは人間」**で、
そこが閉じていませんでした。同社はその最後の一手を実装しています。

**権限は意図的に非対称にしてあります。**

| 操作 | 誰が決めるか | 理由 |
|---|---|---|
| **kill（機能を止める）** | **AIが自律実行してよい** | 可逆で、安全な方向へ倒す操作だから |
| **promote（配布を広げる）** | **人間の承認が要る** | 広げてから戻しても、**見た人が見なかったことにはならない** |

「止める」と「広げる」を同じ権限にすると、**誤検知が「勝手に全員へ配る」形で
顕在化します。**逆にしてあるのはそのためです。

この設計には副産物があります。**段階公開そのものが、対照群つきの実験になっています。**
配布先の割り当ては端末IDから決まる決定論的な計算なので、サーバは後からでも
「この端末は露出群だったか対照群だったか」を復元できます。
**A/B用の基盤を別に建てる必要がありません。**

ここでも**「測れないときは判定しない」**を守っています。サンプル数が足りない場合、
判定は保留を返します。**「判定していない」を「異常なし」と書きません。**

**ただし、この仕組みはまだ本番で1周させていません。**
実装は済み、動作確認も済み、**あとは実際に回すだけ**という状態です。
同社は機能側の改善サイクル完走を**現在0件**と記録しており、
§3末尾の「できていないこと」にもそのまま残しています。
**機構が揃っていることと、回した実績があることは別**だからです。

### ■ 広報そのものも、採点とバックテストの対象にしている

同社はプレスリリースの企画を、配信前に7軸で採点し（新規性・エンティティ到達・
具体名詞・変化・時流・ニュース動詞・ローンチ設計、100点満点）、
**合格点に届かなければ配信しない**という運用にしています。採点表と
4つの配信条件はファイルとして保存され、**その算数の矛盾はCIが検算します。**

較正には自社の過去5回の実績を使っています。

| 採点 | PV | 転載 | Google Discover |
|---:|---:|---:|:--|
| 21 | 469 | 22 | 非乗車 |
| 40 | 1,347 | 28 | 非乗車 |
| 46 | 217 | 0 | 非乗車 |
| 65 | 10,434 | 28 | **乗車** |
| 71 | 12,188 | 34 | **乗車** |

**採点そのものは人間が根拠つきで置きます。**ここを自動採点にすると、
点を取るための見出しを機械が書き始め、
「煽り語を使わない」という自社の配信条件に自分から違反するためです。
**機械が持つのは算数と条件判定だけ**という線を引いています。

### ■ このプレスリリース自体が、CIの検査対象になっている

**同社は本リリースの原稿を、機械の検査を通してから配信しています。**
検査は3層あり、すべて他のコードと同じCIで走ります。

**1. 古い事実と誇大表現を落とす。** きっかけは失敗でした。2026年8月、
過去の原稿を雛形にした新しい原稿が、**古い事実を3件そのまま引き継ぎました** —
削除済みの旧アプリ名、古い起動時間、そして**すでに廃止した無料お試し表記**です。
3件目が最も重く、この表記の取りやめは景表法とストア審査上のリスク対応として
行われたものでした。**書けば、一度消したリスクを外向きに作り直すことになります。**

人が読み直して見つけたので事故にはなりませんでしたが、
**人の読み直しに依存している限り、次も同じことが起きます。**
現在は製品名・価格・無料枠・起動時間の正本ファイルと突き合わせる検査が走り、
**ずれていればCIが落ちます。**検査スクリプトに数値は直書きされておらず、
正本が変われば検査も自動で追随します。

**2. 見出しの主張を、実装台帳に1件ずつ当てる。** サブタイトルが列挙する工程
（計測・機能開発・QA・SEO・ASO・PR制作・配信準備）を分解し、
**それぞれが本当にAIによって回っているかを、前述の台帳に照合します。**
支持率が70%を割った工程は「**書けない**」と判定されます。

**現在12の主張のうち1つが「書けない」判定です。**

| 主張 | 支持率 | 埋まっていないもの |
|---|---:|---|
| 「循環」 | **67%** | **機能側で改善サイクルを完走した実績が0件** |

**この1つは、原稿の側を直して逃げることもできました。**同社がそうしなかったのは、
記者が最初に聞くのが「それは本当に自動で回っているのか」であり、
**答えられない行を1つでも残さないためにこの台帳がある**からです。

**なお、この検査は実際に原稿ではなく現実のほうを動かしています。**
直近まで「書けない」は3件ありました。**2件は原稿を弱めずに消えています。**

| 主張 | 何で消えたか |
|---|---|
| 「機能開発」60% | **実装。**要望を設計に落とす工程とPRD作成が提案止まりだったので、**PRDを書かなければ着手可にできない**ゲートを設けた（後述の「設計を書かなければ、着手可にできない」節） |
| 「契約は人が承認」67% | **人の作業。**契約条項を読む工程は誰もやっていませんでした。2026年8月25日に**経営者が10社ぶんを実際に読み**、その事実を台帳に記録したことで埋まりました |

**2件目は自動化で埋めたのではありません。**「人が承認する」と書いた以上、
そこに人の関与が実在することが条件であり、**足りなかったのは人の作業のほう**でした。
検査は「AIが何%やっているか」ではなく「**書いた通りの担当になっているか**」を見ています。

**3. 裏の取れていない主張が入った画像を、完成品として作らせない。**
PR TIMESのサムネイル画像は自動生成していますが、**文言は画像生成側に書けません。**
上記の主張検査が読むのと**同じファイル**から読みます。
画像に文字を直接書けるようにすると、原稿・検査・画像で正本が3つできて、
**一番人目に触れる画像だけが古いまま残る**ためです。

支持率が閾値を割っている状態では、**画像の生成そのものを拒否します。**
どうしても確認したいときは下書きとして生成できますが、
**その画像には消せない透かしが入ります。**下書きが完成品として
流通する事故を防ぐためです。

### ■ セキュリティ：AIが発見し、AIが修正した

### ■ ユーザーの声はどう機能に変わるか

Apple Watchの同期不具合を4回にわたり診断報告してくださった利用者の方から、
2026年7月31日に2件の要望をいただきました。同社はこれを、
**Obsidian連携を設定した利用者の7日後継続率が、未設定の2.5〜3.7倍**という
自社の実測データと突き合わせて優先度を決め、**4回のビルドに分けて納品**しています。

うち1回は、**実装は正しく動いていたのに、設定画面から機能の存在が分からなかった**
という理由で追加のビルドを出したものです。

### ■ ストアレビューを機械で取り込み、「処理していないこと」をCIが鳴らす

**上の事例は、たまたま熱心な利用者が個別に連絡をくださったから成立しました。**
それでは仕組みになりません。同社は2026年8月、App Storeのレビューを
**機械で取り込む経路**を作りました。ただし同社は、
**取り込みだけでは意思決定に繋がらない**と判断しています。

> 計画は散文の中に住んでいて、散文は手を挙げない。

冒頭で引用したこの失敗は、**ユーザーの声についても同じ**でした。
**取り込んだだけのレビューは、誰も見ません。**

そこで同社は「レビューをどう処理したか」を別の台帳に持ち、
**14日を超えて未処理のレビューが1件でもあればCIが落ちる**ようにしています。
14日という値は、リリース間隔（数日〜2週間）より長くすると
「次の版で見る」が実質の放置になるためです。

処理の種別は5つで、**「何もしないと決めた」を正式な選択肢として持たせています。**
用意しないと、称賛だけのレビューや同じ苦情の3件目が永久に未処理として残り、
**CIが鳴りっぱなしになります。鳴りっぱなしの警報は、いずれ消されます。**
ただし「何もしない」を選ぶときは**理由の記入を必須**にしています。
**「何もしないと決めた」と「見ていない」は違う**からです。

**初回の取り込みでは8件（平均4.63）が入り、その場で全件を処理しました。**

| 処理 | 件数 |
|---|---:|
| 機能バックログの候補にした | **5** |
| すでに直っている版がある | 1 |
| 何もしないと決めた（理由つき） | 2 |

**未処理0件は「判定して0件」であって、「見ていないから0件」ではありません。**
この区別は台帳の側が持っています。

### ■ 機能の優先順位から、人が「確信度」を置ける余地を無くした

レビューから生まれた候補は、機能バックログに入って順位がつきます。
ここで同社が意図的に外したものがあります。**確信度を人が手で置けません。**

確信度は「その根拠が何に由来するか」から**機械的に決まります。**

| 根拠の種類 | 例 |
|---|---|
| 自前の実測 | BigQuery・運転台帳・性能実測 |
| 外部の実測 | 検索コンソール・App Store Connect・ストアレビュー |
| 観察したが数えていない／類推／思いつき | （順に弱くなる） |

**ここを主観にすると、順位はいくらでも動かせます。**そうなった時点で
台帳の意味が無くなるため、入口で塞いであります。

さらに、**不可逆性・課金・プライバシー・審査に関わる候補は、
点数が高くても承認を外れません。**「点で消えないリスク欄」を別に持っています。

**候補にしないと決めたものにも理由が残ります。**あるレビューの
「辞書登録できると最高」という要望は候補にしていません。iOS側のユーザー辞書は
アプリから制御できないためです。**できないことを候補に置かない** —
置いた瞬間、永久に消化されない行が台帳に残ります。

現在12件の候補が並んでいますが、**上位2件はどちらも新機能ではありません。**

| 順位 | 候補 | 状態 |
|---:|---|---|
| 1 | App Storeのキーワード欄をリポジトリ管理に移す | **実装前に承認が要る**（審査リスク） |
| 2 | **カナリアガードを本番で1周させる** | 着手可 |

**首位は点数が最も高いにもかかわらず、承認を待つ側に留まります。**審査に関わるためです。
2位は、**前述の「機能側の改善サイクル完走0件」という穴そのものを潰す作業**です。
**自分に空いている穴が、機能追加より上に来ています。**

### ■ 設計を書かなければ、着手可にできない

順位がついた候補は、そのまま実装に進むわけではありません。同社は
**「設計を書いていない候補は、着手してよいと宣言できない」**という規則を機械で強制しています。

これは能力の問題ではなく、**定型化されていなかったこと**への対処です。設計文書は
以前から書かれていましたが、散文としてリポジトリのあちこちに置かれており、
**書かれなかった回に誰も気づけませんでした。**冒頭に引用した
「計画は散文の中に住んでいて、散文は手を挙げない」と同じ形です。

現在、要件定義に次のものが揃っていなければCIが落ちます。

| 要素 | 規則 |
|---|---|
| **受入条件** | **どう確かめるかを書けないものは受け取りません。**「使いやすくなっていること」は後からどうとでも読めるので、受入条件ではありません |
| **やらないこと** | 空欄は許されません。**やらないことを書いていない設計は、範囲が決まっていない**からです |
| **ビジョン適合** | 製品ビジョンの6つの問いすべてに答えます |
| 撤回条件 | 問題が出たときにどう戻すかを先に書きます |
| 多言語・UX | 未定なら「未定」と書きます。**空欄と未定は違います** |

**この検査は、答えの当否を判定しません。**「6問に答えたか」だけを見ます。
当否まで機械が判定できると称すると、**ビジョン適合の判断そのものを機械に渡した**
ことになるためです。

### ■ 4択に「衝突」を用意した — 一番効いたのはそこでした

ビジョン適合の回答は「はい／いいえ／対象外／**衝突**」の4択です。
**「衝突」を選べることが要点**で、これが無いと、ビジョンと反する要望が来たときに
黙ってどちらかへ寄せることになります。衝突と答えた場合は、**解決方針の記入が必須**です。

**実際に、最初に書いた4件のうち1件がこれに引っかかりました。**

レビュー2件が同じ箇所を指していた最有力の要望は、**保存先フォルダを選べるようにしてほしい**
というものでした。ところが同社の製品ビジョンには
**「整理するUIを作らない」**という原則があり、フォルダピッカーはその筆頭に挙がっています。
**要望をそのまま実装すると、自社の原則に正面から反します。**

要件定義にはこう記録されています。

> 素直に実装するとフォルダピッカーになる。**ピッカーは作らず、1行のテキスト入力にする。**
> 原則が禁じているのは「選択肢を大量に並べること」であって、保存先を1つ指定できること
> 自体ではない。選択肢を並べた瞬間に別物になり始めるので、そこだけを避ける。

**この判断は人間が下しています。**機械がやったのは、
**衝突していることを見逃せない形にした**ことだけです。

### ■ 「APIが無い」と思い込んでいた経路が、実は最初から在った

⑥にあたる「App Storeの実績データを機械で取り込む」工程は、
長らく**受け皿のフォルダだけがあって空**でした。理由は技術的な制約ではなく、
**手順書に書かれた誤った前提**でした。「エクスポート用のAPIが無いので人が転記する」と
書いてあり、誰もそれを疑いませんでした。

**これは事実誤認で、APIは2つありました。**片方は同期で即座に取れるレビュー取得、
もう片方は非同期で、要求を1本立てるとAppleが日次でレポートを作り始めるものです。

**誤読された理由は分かります。**後者は**要求を立てた当日には何も返ってきません。**
一度叩いて空だったものを「APIが無い」と受け取るのは自然な読み方です。
そこで現在の実装は、**「空」と「まだ取得していない」を必ず別々に記録します。**

**2026年8月22日21時32分（UTC）、初回の定期実行が通りました。**
この2回目の実行で初めて確かめられたことが1つあります。
**レポート要求を作り直していない**ことです。ここが冪等でないと
**毎日1つずつ要求が積み上がります**が、性質上**2回目の実行がないと確認できず**、
作った当日には見えませんでした。

**待ち日数の計数も始まっています。**Appleがレポートを生成しないまま5日を超えると、
**ジョブが落ちます。**「Appleの生成待ち」が永久の言い訳にならないようにするためです。

**ただし現時点で、漏斗の実データはまだ1行もありません。**（レポートの生成待ち）
また入金額は取得できていません。取得に必要な事業者番号がリポジトリに無く、
APIからも引けないためです。**取れないものを取れることにしない** — 出力は
「取得不能」のまま固定してあります。

**連携が動いていることと、判断が実データに基づいていることは別です。**
同社は前者だけを主張します。

### ■ 資格情報の期限を台帳にした — 「知らない」を「余裕がある」と書かせない

**切れた日に初めて分かる**類の停止があります。証明書、配布用のプロファイル、
APIキー、ドメインの登録期限です。これらは**壊れる前に何の兆候も出しません。**

同社は9件を台帳に載せ、**30日前に警告、7日前でCIが落ちる**ようにしました。
ただしこの台帳の要点は、警告の日数ではありません。

**期限が分からないものを、ゼロや遠い日付で埋めないことです。**
未記入のものは「**未把握**」として**別枠に必ず表示されます。**
**期限を知らないことは、余裕があることではない**からです。

現在の状態をそのまま出します。

| 状態 | 件数 | 内訳 |
|---|---:|---|
| **期限が未把握** | **4** | 配布用証明書、配布プロファイル、独自ドメインの登録、実行用トークン |
| 実測できない | 2 | 通信経路上の復号により、読み取った期限が信用できないため報告しない |
| 期限の概念が無い | 3 | — |

**9件中4件の期限を、同社はまだ把握できていません。**
検査は現在この4件では落ちない設定です（有効にすると自動マージが常時止まるため）。
**日付を埋め終えたら落ちる設定に切り替える**ことまで、台帳に書いてあります。

### ■ バックオフィス領域には、まだ「最初の一歩」しか置いていない

リード文は「**契約は人が承認**」と書いています。これは真でしたが、
**当初この文には中身がありませんでした。AIが契約に一切触れていないので、
承認する対象そのものが無かった**のです。前述の主張検査でも、この行は
現在「書けない」判定（67%）のままです。

そこで同社は、**依存している外部サービスの登録簿**を作りました。
10社を、**どの種類のデータを渡しているか**で分類しています。

| 分類 | 意味 | 社数 |
|---|---|---:|
| **個人データを渡している** | メールアドレス・メモ本文 | **2** |
| 仮名化データのみ | ハッシュ・匿名ID | 4 |
| 個人データを渡していない | — | 4 |

**この台帳で最も重要なのは、未レビュー欄の扱いです。**
データ処理契約を確認したかどうかの欄が空のとき、それは
**「問題なし」ではなく「見ていない」**として扱われます。
**個人データを渡しているのに未確認のものは、検査が名指しします。**

**2026年8月25日、10社すべてのレビューが完了しました。**これを受けて検査は
**警告から強制へ切り替えてあります** —— 以後、個人データを渡す事業者を
未レビューのまま追加すると**CIが落ちます**。有効化の意味は「いま全部埋まっている」
ことではなく、**次に足す人が素通りできない**ことです。

**ただし同社は、この状態を「レビュー済み」の一語で片づけていません。**
台帳は「**レビューされたか**」と「**何が書いてあったか**」を別の欄で持っており、
後者——責任上限・知財・個人情報・準拠法の4条項——は**10社すべて未記録**です。
検査はこの10社を「**レビュー済み・所見なし**」として毎回名指しします。

> 人は見た。**だが何が書いてあったかは誰も参照できない。**

**落としはしません。**レビュー自体は実際に行われたからです。
そこを落とすと「レビューしたのに怒られる」ことになり、記録を残す動機が消えます。
かといって黙れば、**「レビュー済み」という言葉だけが独り歩きします。**
第3の状態として数え、表示し続けるのが同社の答えです。

これは自動化された経理でも、契約審査でもありません。
**AIが下ごしらえをして、人が承認する形の最初の1つ**です。
条項の読解を行ったのは人間で、**AIはその中身に触れていません。**
バックオフィス領域は**依然として設計段階**であり、同社はそこを急いでいません。

### ■ できていないこと（同社が手順書に明記しているもの）

**この基盤はまだ「全領域が自動で完結する」状態ではありません。**
同社は、できていないことを手順書とレポートに明記しています。

| 領域 | 現状 |
|---|---|
| 機能開発 | 要望の受領・候補化・要件定義まではAIがゲート付きで実行。**自動選定→段階公開→効果測定→継続／撤回まで通した実績はまだ無い**（機構は揃い、実績が0件） |
| バグ修正 | テストと分類は自動。カナリアガードは実装済みだが**本番で1周させていない** |
| 実機テスト | **iOSシミュレータ・実機iPhoneの操作、撮影、計測はできない**（macOS環境が必須） |
| 広告運用 | **未実装**。この予算規模では日次の自動入札がノイズ最適化になるという自社分析があり、着手していない |
| 予算配分 | 上限での自己停止まで。**配分の最適化はまだ** |
| カスタマーサポート | **12.5%**。問い合わせの分類・返信・返金対応、ストアレビューへの返信はいずれも未実装 |
| マネタイズ | **12.5%**。価格・ペイウォールの実験は、AIが提案もしない扱い（不可逆で既存契約者への影響が読めないため） |
| 法人領域 | **着手前**。経理・税務・契約・支出承認は権限と承認境界の設計段階で、AIが実行に回った工程はまだ無い |

**さらに、同社は自動化の対象にすらしていない領域を別枠で持っています。**
利用者の列挙にあった「まだできていないこと」は、台帳では
**⑬アナログ領域**として、着手前のまま別枠で管理されています。

| 領域 | 現状 |
|---|---|
| リアルイベント・ブース出展 | 候補選定・見積比較・発注は**AIが担える設計だが未着手**。設営・接客・実施は**人間の担当として固定** |
| 人事的アクション | 募集・日程調整・書類作成は未着手。**採用・解雇・評価・健康情報の判断は人間に固定** |
| 公的機関からの資金調達 | 制度探索・期限管理・申請書の下書きは未着手。**表明・提出・面談・法的責任は人間** |
| 特定領域の契約 | 定型契約の条項比較・リスク抽出は未着手。**非定型・高額・海外・知財は人間の承認** |
| 新規事業開発・R&D | 調査・仮説・試作までは実績あり。**安全性・知財・投資継続の判断は人間** |
| リアル営業 | リード選定・提案書作成は未着手。**交渉・信頼形成・重要契約は人間** |

**この表の右列に「人間」と書いてあるものは、未実装ではありません。
人間が担うと決めたものです。**同社は両者を台帳の上で区別しており、
**「まだできていない」と「やらないと決めた」を混ぜていません。**

さらに、**自動実行の主系が11回連続で成果物を出せなかったことも記録に残っています。**
秘密鍵の未設定、パッケージ導入の詰まりによるジョブ上限の消尽、実行主体の判定による拒否、
権限不足による無出力——主系は4種類の異なる理由で連続して失敗しており、
**その間の出荷はすべて副系が担っていました。**
同社はこれを、二重化が実際に効いた実例として公開します。

**12回目にあたる2026年8月23日、主系が初めて自力で出荷しました。**
直前の修理を入れたのは人ではなくAI自身です。前日の「ジョブは成功なのに成果物ゼロ」を
別系統のAIが検知し、ジョブログから実行権限の設定漏れを特定して修正を出荷。
その修正は当初「開発者に確認を依頼する案件」として起票されていましたが、
**起票そのものが誤りで、AIが自分で直せるものでした。**翌朝の定時実行が、
その修理が効いていることを出荷という形で示しています。
ただし**主系の出荷は6回中1回**であり、日々の出荷は引き続き副系が担っています。
**そして8月24日以降、主系は認証が通らず2日続けて失敗しています**（後述）。

**この初出荷には後日談があります。**出荷は成功したのに、運転台帳には
「主系の出荷 0回」と記録されたままでした。台帳の検査が、行の中身が壊れていないかは
見ていた一方で、**行が書かれているかどうかを見ていなかった**ためです。
同社はこれを、自動化が自分の数字を自分で監視することの限界の実例として公開し、
検査を追加した経緯まで含めて記録しています。

**同社は「完全自動化できた」とは主張していません。**主張しているのは、
「**AIが日々の運営を継続実行できる構造にしたこと**」と
「**自動化が止まったことに気づける形にしたこと**」です。
