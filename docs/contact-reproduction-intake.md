# 問い合わせから再現手順を集める

2026-09-06、製品バグの問い合わせを読み取り専用で確認した。対象6件に操作手順、
OS、アプリ版がなく、短い同期不具合の申告だけだった。本文と識別子はこの公開文書に載せない。
この状態から手順を作ると推測になるため、「再現テストを自動生成」の実績には数えない。

## 今回の変更

`contact.html` に任意のアプリ版と、開閉できる再現情報の欄を加えた。
再現までの操作、期待した結果、実際の結果を入力できる。一般的な問い合わせでは不要。
既存の端末・OS欄と同様、ブラウザから不具合が起きた環境を推測しない。

`js/contact-form.js` が入力された項目だけを見出し付きで既存の本文へまとめる。
アプリ版は既存の `app_version` へ渡す。新しい保存先や削除対象は増やさない。
本文と追加項目・見出しを含めて4,000文字を検査し、超えた場合は送信せず内容を残す。
失敗時にも入力を残し、成功時だけフォームをリセットする。

## 確認

8件の回帰テスト：一般問い合わせ、日英の再現情報、合計文字数、任意欄、
429・ネットワーク失敗での保持、主本文の未記入。
Chromeでも日本語390px・英語1280pxで入力、テスト用の送信先への内容、成功時のリセットを確認。
390pxの画面を目視し、横方向へのはみ出しがないことを確認した。
本番へ試験問い合わせを投稿していない。

## 次に必要なこと

この経路から十分な再現情報が届いたとき、非公開側で個人情報を除いた再現ケースへ変換し、
実際の製品テストで再現を確かめる。問い合わせに書かれた操作をそのまま実行コードとして
扱わず、許可されたテスト操作と期待結果へ対応付ける。情報不足は不足のまま記録する。
本変更は材料の収集であり、自動テスト生成を完了したという主張には使わない。

Capture OS §13：保存の不具合を再現可能にし、Captureの信頼性を改善するための運営導線。
アプリ内の整理UI、保存先、Capture Object、修正情報の学習、Routing段階は変更しない。
ユーザーにAIを売り込む表示も加えない。
