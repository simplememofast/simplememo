# 連続出荷は、自分を直し続けても伸びていた — 出荷の内側にレーンを入れる

<!-- fact-check: internal -->

> 正は `scripts/autopilot-runs.mjs`。定義は `data/kpi-definitions.json` の
> `publishing_day_streak`。この文書は経緯。

---

## 0. 何が見えていなかったか

2026-09-03 時点の実測:

```
  連続稼働      17 日（2026-08-18〜09-03）
  連続出荷       3 日（2026-09-01〜09-03）
  連続公開       1 日（2026-09-03〜09-03）   ← 足したのはこれ
```

内訳を見ると理由は1行で済む:

```
  09-01  actions  lane F  PR #749   公開面の成果物なし（自己修復）
  09-02  actions  lane F  PR #774   公開面の成果物なし（自己修復）
  09-03  actions  lane A  PR #793   /obsidian/getting-started/
```

**連続出荷 3日のうち、公開面に何かが出たのは1日だけ。**残り2日は機械が自分を
直していた。連続出荷の定義（`shipped` の行がある日）は正しい —— 自己修復も出荷である。
だが**自分を直し続けても連続出荷は伸びる。**

これは 2026-09-02 に「連続稼働は失敗し続けても伸びる」として連続出荷を足したときと
**同じ形の穴**で、一段内側に残っていた。**穴を1つ塞いだ隣に、同じ形が残っていた。**

## 1. どこで切るか

Runbook §2 のレーン分類をそのまま使う。**新しい分類を作らない。**

```
  A  SEO（Refresh / New / 配線）        公開面
  B  AIO（回答ブロック）                 公開面
  C  Evidence Asset（一次情報）          公開面
  D  Paid relevance 例外（四半期1本）    公開面
  E  Coverage（まとめサイト化）          公開面
  F  自己修復                            ← 切る
  lane なし（§6 の保守のみ）             ← 切る
```

レーンFを外すのは Runbook 自身がそう書いているから ——
「**レーンFで1日使い切ってよい。その日の記事はゼロでよく**」。
あれは自分を直す日であって、公開面に何かが出た日ではない。

## 2. この指標は優先順位を決めない

**故障が続く日はレーンFが勝つのが正しい。**この指標はそれを責めるためのものではない。

言えるのは「**いま何が起きているか**」だけで、レーンFが勝ち続けるのが妥当な状況か、
カバレッジが飢えているのかは、**分けて数えて初めて判断できる。**
分けずに1本にしていると、どちらの状態も「連続出荷3日」に見える。

## 3. 手書きの欄が隣にあった（未解決・要判断）

status JSON には既に近い欄がある:

```json
"streak": { "consecutive_no_article_days": 0, "last_article_date_jst": "2026-09-03" }
```

これは日報メールにも `autopilot-health` にも出ている。**ところが台帳から導かれていない** ——
`--write-status` が書くのは `runs` ブロックだけで、`streak` は
`reason` / `verified` / `next` と同じ**セッションが手で書く散文の列**にある。

つまり**書いた本人以外は確かめられない数字**が、オーナーの読む面に出ている。
今日の値（最終記事 09-03・連続無記事 0）は**台帳と一致していた**ので、いま誤りは無い。
だが一致を確かめる仕組みは無い。

**この文書では直していない。**「記事（article）」と「公開面（レーンA〜E）」は
範囲が違う —— レーンCは記事ではなく引用可能な証拠を作る回なので、
**両者を等号で結ぶと、片方の定義がもう片方に化ける。**等号にするか、
別物として2本並べるかは決めていない。

やったのは、`runs` ブロックに導出値（`publishing_streaks` / `last_publishing`）を
**隣に置く**ところまで。突き合わせる側が現れたときの正はこちら。
