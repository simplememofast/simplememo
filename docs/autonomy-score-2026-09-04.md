## 1. 実装したもの（2026-09-04）

### A. 失敗の層（`failure_stage`）— 記録が同じ列に入っていた

**「22件の死は選択ミスか実行ミスか」は、調べれば分かる問いではなかった。**
Gateが寝た日・実行が落ちた日・枠が尽きた日が、すべて同じ「失敗」として運転台帳に並んでいたので、
**記録の側で原理的に答えられない問いだった。**

層を1フィールド足して数えたら、出荷しなかった 23 行はこう分かれた:

```
    適格性 eligibility   12 件   実行前の判定で止まった（L1）
    実行   execution      6 件   着手して実装の層で死んだ（L0）
    コスト cost           3 件   枠・予算で止まった
    経路不在 absent       2 件   経路そのものが無く、判定も実行も行われていない
```

**`absent` は設計ノートの3分類（適格性/実行/コスト）に無い。**足したのは、2026-08-16〜17 の2行が
どれにも入らなかったから。副系Routineが当時そもそも存在せず、判定も実行もされていない。
3つに押し込むと「実行の層で死んだ」と読めてしまい、**機械が居なかった日と、機械が失敗した日が同じ色になる。**

適格性の12件はさらに割れる:

```
    declined_by_design    8 件   秘密鍵が無い日に静かに寝た（理由が記録されている正しい棄却）
    declined_unrecorded   4 件   **寝た理由が台帳から読めない**
```

判定の結果はもう1つある —— **`declined_by_fault`**。鍵の失効・API 到達不能・判定器の例外は、
どれも outcome が `skipped_gate` になり層も `eligibility`（実行前に止まった）だが、
**静かに寝たのではなく壊れている。**混ぜると**鍵が切れた日が「設計どおり静かに寝た日」として台帳に残る。**
`escalation-rules.json` も `fail_credential` を4時間・`stop_automation: true` として
別物に扱っており、台帳だけが同じ色にしていた。検査は**両方向**を落とす ——
故障コードを設計どおりと書いても、正常な棄却を故障と書いても。

後者4件が 2026-08-27〜29 と 09-03 の沈黙で、**セッションが手で起こすまで4日目まで誰も気づいていない**
という既知の事故そのもの。`scripts/autopilot-runs.mjs --check` が、2026-09-04 以降の新しい行について
`gate_code` を要求する（過去分は遡って復元できないので免除する。**思い出せない行を埋めるために推測が入る**）。

### B. L1適格性ゲート（`scripts/autonomy-eligibility.mjs`）

**いちばん多いのは適格性の層で、そこには「秘密鍵が在るか」以外の判定が無かった。**

開いている候補を5基準で判定する。新しい概念は要らない —— 既存のチェックと同じ機構を実行**前**に置くだけ。

| 基準 | 見るもの | 2026-09-04 の実測（候補10件） |
|---|---|---|
| `reversibility` | 可逆性クラス R0/R1/R2。**R2 は例外なく止めて L4 へ** | pass 4 / fail 0 / unknown 6 |
| `boundedness` | 触るパスが、宣言された許可リストのどれかに収まるか | pass 2 / fail 5 / unknown 3 |
| `evidence_age` | 14日以内のデータ点を1つ以上引用しているか | pass 5 / fail 0 / unknown 5 |
| `budget` | 予測コストが1回上限以下か。**加えて予測を必ず記録する** | pass 2 / fail 0 / unknown 8 |
| `repeat_guard` | 7日以上開いたまま、実行主体も上げ先も無い候補 | pass 7 / fail 3 / unknown 0 |

### B-2. 「なぜ寝たか」を機械が言えるようにした

適格性12件のうち4件が `declined_unrecorded` なのは、**Gate が寝た理由を台帳が持っていない**から。
これを放っておくと、`--check` のラチェット（新しい行には `gate_code` が要る）は
**一度も噛まない** —— 全部が「記録が取れなかった」で通ってしまう。

停止理由5つのうち**3つはステップの実行結果から一意に決まる**ことが分かったので、
`interpretRun`（`scripts/autopilot-act.mjs`）が名前を付けて返すようにした:

```
    緊急停止が failure                    → emergency_stop
    振り分けまで走って Claude だけ skipped → skip_run_cap（1回あたりの上限）
    予算ゲートまで走って振り分けが skipped → skip_budget（月次上限）
    Gate で止まった（それ以外）           → **決まらない**
```

**残る1つ（秘密鍵未設定 / 当日重複）は、同じ形になるので決まらない。**
どちらも「Gate が run=false を出して以降が skipped」で、ステップ情報からは区別が付かない。
そこで `obsidian-autopilot.yml` に**何もしないステップを1つ**足した ——
`判定コード: ${{ steps.gate.outputs.code }}`。判定コードは `$GITHUB_OUTPUT` にも
`::notice` にも出ているが、**Actions API の run 一覧から読めるのはステップの name と
conclusion だけ**なので、名前に埋めれば日次アクチュエータが既に取っている情報の中に入る。

**判定そのもの（`autopilot-gate.mjs`）には1ミリも触っていない。**足したのは写しを出す口だけ。

**この写しが無い run（2026-09-04 より前の全部）では null を返し、台帳側が
`declined_unrecorded` と自己申告する。後から足した観測手段が、過去を「記録があった」ことにしない。**

**enforcement は `record_plus_r2_block`**（2026-09-04 オーナー判断）。
判定は全候補に行うが、**止めるのは R2 だけ。**閾値の初期値が外れていた場合に翌朝から出荷が止まるのを
避ける順序であって、「他は飾り」という意味ではない。1周まわして分布を見てから倒す。

**落ちた候補は運転台帳とは別のテーブル（`data/eligibility-log.json`）に書く。**
これが仕組みとしていちばん重要な一点で、混ぜた時点でAの分離が消える。
`validate()` が `outcome` / `failure_class` の混入を落とす。

## 2. 設計ノートから、意図して変えたところ

**3つある。どれも「そのまま実装すると、測っていることが見えなくなる」ため。**

### RA を「検知」と「復旧」に割った

設計ノートの定義は「悪い結果を**システム自身が検知し、人手なしで巻き戻した**割合」。
そのまま測ると **自動 revert が1回も起きていない現状で恒久的に 0** になり、
実際に動いている自動検知と自己修復（レーンF）が一切見えなくなる。

割った代わりに、**Phase 6 のハードゲートは点数ではなく `auto_revert_count >= 1` に紐づけた。**
点で代替すると、検知だけで満点に近づいて「巻き戻せる」ことになってしまう。

**RA の検知は 0/11 で入った。**窓内の故障11件のうち、機械が自分で気づいたものは1件も無い
（10件は検知されているが、すべて人が起こしたセッションが見つけている）。
**同じ機械が適格性の沈黙は3件自分で拾っている** —— 拾えていないのは故障のほう。
0% だけを出すと「何も検知していない」と読めるので、この文脈を必ず併記する。

### EP を「見逃し」と「精度」に割った

**片方しか測れないので、割らないと「測れない」が「満点」になる。**

- 見逃し … 規則の `within_hours` を超えた検知の率から出す。**下界しか測れない** ——
  規則が定める区間は「検知から人へ届くまで」だが、届いた時刻を台帳が持っていない。
  持っているのは `failed_at` → `detected_at` で、**検知だけで既に超えていれば配達も超えている。**
  片側検定として成立するので、そう書いたうえで使う。
- 精度 … 上げたうち本当に必要だった割合。**いまは測れない。**アクション台帳に「人が要ったか」の欄が無い。
  `owner_needed` を足したので、以後オーナー送りのアクションを閉じるときに埋まる。埋まるまでこの半分は0点。

### `absent` を4つ目の層として足した

上の §1-A のとおり。**測り方が狭いと、直し方まで間違える。**

## 3. アンチゲーミング（省略不可）

どの成分も**チェックを緩めれば上がる。**だから:

- **検査被覆率の非退行制約**を全成分に掛ける。被覆率が下がった窓はスコアを**据え置く**（上げない）。
  0点にはしない —— 0点にすると正当な統廃合まで止まる
- **R0 の寄与に上限**（窓の総重みの60%）。些末で可逆なコンテンツ更新を量産すれば点が伸びる抜け道を塞ぐ
- **変更失敗率（30.0%）はスコアに入れない。**死亡率を最適化対象にした瞬間、チェックを緩める圧力が生まれる
- **スコアを ranker に見せない。**`--check` が、日次runのプロンプト経路（`obsidian-autopilot.yml` /
  `AUTOPILOT_RUNBOOK.md`）がこのスコアを参照していないことを実際にファイルを読んで確かめる。
  **読めなかったファイルを「参照が無い」と読まない**（これも検査で固定してある）

## 4. 次にやること（順序が本体）

**反証器を作ってから権限を上げる。逆順は事故になる。**
各段の出口条件が、次に進んでよいかの入口条件になっている。

| 段 | やること | 出口条件 | いま |
|---|---|---|---|
| 1 | L1適格性ゲート＋失敗タクソノミー分離 | 死んだ run の100%がいずれかの層に帰属 | **済**（23/23） |
| 2 | L2 価値契約＋決済ジョブ | 出荷の80%以上が決済済みの契約を持つ | 未着手。**指標の許可リストと null model を人間側で確定させるのが先** |
| 3 | 較正の ranker へのフィードバック | 方向的中率が null model を有意に上回る | 未着手 |
| 4 | L3 成熟ゲート・スタック検出・強制探索 | `futile` が1回発火し、探索が枠外データを生む | 未着手 |
| 5 | 復旧自律性（自動 revert） | **人手を介さない revert が1回成功する** | 未着手 |
| 6 | 権限の拡大（R1 の無検査マージ・cadence） | UMR の R1 加重分がプラスに転じ、RA と EP が退行していない | **段5の出口まで進んではいけない** |

**段2に着手する前に決めることが2つある。どちらもオーナーの判断で、機械は代われない。**

1. **指標の許可リスト** —— picker が指標を選べる以上、放っておいても動く指標を名指しすれば較正は完璧に見える。
   指標を新設する権限を picker に与えないことで、ゲーミングの自由度そのものを奪う
2. **各指標の null model** —— ゼロではなく「何もしなかった場合」に対して採点する。
   これが無いと、勝手に動く指標を選んだときの上乗せをゼロにできない

### 起案した（`data/value-metrics.json`・2026-09-04）— **承認欄は空のまま**

オーナーの指示で候補を起案した。**起案（`drafted_by: ai`）と承認（`approved_by`）は別の欄**で、
埋めるのは人。承認は指標1件ずつで、まとめて承認する欄は作っていない。
**いまは 0/12。**

**起案する前に、実際に何が読めるかを測った。そこで骨格が決まった。**

```
    運転台帳（出荷・失敗・介入・実費）  25日・日次      ← **null model を作れるのはこれだけ**
    ASC ダウンロード数                   9日（08-24〜09-02・08-29 欠落）
    収入                                 covered_days 4
    BigQuery（GSC export）              22日蓄積だが**主系から読む経路が無い**
    GSC の手動スナップショット           4本。**日次系列ではない**
    GA4                                  README のみ。データ無し
```

**事業の指標は、どれも日次系列が足りず null model を作れない。**
したがって第1版の許可リストは**運営の指標しか持てない** ——
「事業の数字で価値を較正する」は、系列が貯まるまで**できない**。
**設計ノートのリスク①（統計的検出力が足りない）が、着手前に実測で出た形。**

| tier | 件数 | 意味 |
|---|---:|---|
| A | 6 | いま契約に使ってよい（日次系列があり null model が作れる） |
| B | 3 | 系列が貯まれば A へ。**いつ・何件で移るかを条件に書く**（推測で早めない） |
| C | 3 | 使わない。理由を書く |

**tier C がいちばん重要。**変更失敗率・自律スコア自身・総合自動化率の3つで、
どれも「契約の指標にすると別の仕組みの意味が消える」もの:

- **変更失敗率** —— 自律スコアが意図して除外している。契約に入れれば除外の意味が裏口から消える
- **自律スコア自身** —— 契約の指標にした時点で ranker に見せている
- **総合自動化率** —— 分母が棚卸しで動く（2026-08-25 に13件足して 61.3% → 58.6%）。
  契約の指標にすると**「棚卸しをしない」が最適戦略になり、台帳の正確さと利益相反する**

`scripts/autonomy-score.mjs --check` が、この裏口2つを実データで落とす
（`change_failure_rate` を tier C から A へ移すと exit 1 になることを実測した）。

**null model の作り方は、系列が短いので分解を使わない。**
トレンド＋季節性の分解には最低3〜4週が要る。曜日効果の有無だけで2つに分けた ——
`same_weekday_median`（同じ曜日の直近 k 回の中央値）と `trailing_median`（直近 n 日の中央値）、
それに `zero`（0/非0 でしか読めない指標）。

**採点規則の落とし穴も先に書いておく。** Brier score は proper scoring rule なので正直な確率申告が最適戦略になるが、
**skill score（基準比の正規化）は proper ではない。**基準スコアで割った瞬間、確率を歪めて申告するほうが得になる。
したがって **学習・報酬信号には生の Brier を使い、null model 比の skill score は人間向けの表示にだけ使う。**

## 5. この仕組みが失敗する条件

**空欄にして「考えていない」と読ませないために書く。**

- **統計的検出力が足りない。**1日1出荷、小規模アプリでは効果量の有意判定は年単位になる。
  緩和策は効果量ではなく較正（方向的中）で回すことだが、Wilks (2010) の `n > 1000` は依然として重い。
  **L2 は「価値の測定器」ではなく「価値についての嘘を検出しにくくする装置」**だと期待値を下げておく
- **反事実は基本的に仮説のまま残る。**N回に1回2位候補を実走させても、統計的にはほぼ何も言えない。
  「たまに答え合わせができる」以上を期待しない
- **スコア自体が Goodhart の対象になる。**アンチゲーミング項を入れてもいたちごっこ。
  だから ranker に見せない —— 見せた時点で最適化対象になり、指標としての寿命が終わる
- **フレーム問題は内側から解けない公算が高い。**強制探索はデータを買うだけで、正しいフレームを保証しない。
  L4 が恒久的に人間である可能性は十分にあり、その場合「完全なゼロプレナー」は L0〜L3 に限定して使うべき語になる
- **n = 1。**アプリ1本・市場1つ。ここで得た知見のすべてがこのアプリ固有である可能性を排除できない

## 6. まだ本番で1回も動いていない

**この文書に書いた仕組みは、すべて 2026-09-04 に作ったもの。**
L1ゲートの `--write` も、スコアの `--snapshot` も、日次アクチュエータ（09:00 JST）が
初めて回すのは翌日以降になる。

**門を作った日ではなく、門を通って何かが動いた日に「動いた」と書く**（`autonomy-95-gap.md` の規律）。
現時点で言えるのは:

- **判定は実データに対して回した。**候補10件が5基準で分岐し、`ineligible_recorded` 6件・`eligible` 4件・停止0件
- **スコアは実データから出した。**35.5/100、履歴に1点
- **検査は壊して落ちることを観測した。**スコア側5通り・ゲート側10通り・公開ページ側3通り
- **本番の日次で回った実績は、まだ無い**
- **判定コードの写し（ワークフローのステップ名）も、まだ1回も出ていない。**
  読む側は合成したステップ一覧で当ててあるが、**書く側が実際に出すのは次の主系 run から。**
  確かめるには翌朝の `data/autopilot-runs.json` に `gate_code` が入るかを見る
