Copilot：即使選擇模型，附加功能的路徑也會另外留下

固定版的指南分為hosted・Cloud BYOK・Local BYOK・opencode・Claude・Codex的處理物件。 例如，Local BYOK的模型是local endpoint的解釋，根據使用的Skill和project context，也有涉及其他服務的情況。 Q03

將筆記的參考和Miyo的索引分開

資料中有說明，agent閱讀筆記，將必要的部分放入選擇模型的prompt中。“ 僅僅開啟Agent Chat就上傳了整個Vault”的行為沒有說明。 Miyo有local連線和remote server連線，分別選擇索引和搜尋目的地。 透過搜尋找到的摘錄也進入了模型的語境。 僅僅使用local的索引，不能說摘錄不會傳到模型provider。 Q03 / Q05

檔案處理也不是統一的。 資料上，Agent Chat的Miyo處理使用local CLI，Quick Chat使用連線的Miyo service，remote的話使用那個server處理。 使用Web・YouTube・binary file的saved project context有使用hosted project service的情況，與Miyo的選擇是不同的路徑。 Q03

不保證Self-Host Mode會切斷通訊

指南明確指出，即使是Self-Host Mode，cloud也不會失效。 傳送到選定的Claude、Codex、cloud model和搜尋provider等的路徑仍然存在。 這是為了確認每個功能是否與想要使用的功能和允許的處理物件一致的設定。 Q04

關鍵的getter、初期定數、診斷的方針，根據各自的依據來閱讀

確認的KeychainService的範圍是，確認有沒有app.secretStorage，如果沒有就會出錯的getter。 不是實際儲存金鑰的結果，也不是驗證OS加密的記錄。 enableMiyo=false、enableMiyoSearchSkill=false、activeBackend=opencode、debugFullFrames=true是源內的初始值，不顯示已轉移的設定或讀者GUI的值。 Q07 / Q08 / Q09

README說明了hosted request的隨機UUID和讀者選擇upload的診斷ZIP。 ZIP的60天后刪除，hosted request的臨時處理、非保留、非學習是提供者說明的方針。 並不是在這裡稽核backend的運用。 不能判斷只從debugFullFrames=true開始自動傳送診斷ZIP。 Q02

Smart Connections：local embedding的說明和，全部通訊的有無分開

README稱，內建本地模型會為Vault建立索引，無需API金鑰。這可作為查詢相關筆記機制的說明，但在本次比較中，我們沒有執行模型，也沒有觀察實際索引過程或網路通訊。README關於“private”“offline”和移動端的說明也僅作為提供方的宣告。Q10 / Q11

另一方面，自己的src/main.js有從initialize後的更新確認到GitHub latest-release的GET預約程式碼。 首次使用者的StoryModal會傳遞smartconnections.app的URL。 這是與通訊相關的程式碼路徑的確認。 StoryModal的實現在依賴方，實際讀取URL，以及傳遞什麼樣的payload尚未確認。 Q12 / Q13

model・settings・HTTP等部分參考了Smart Environment/jsbrains相關的外部package。 僅憑這個範圍，不能斷定“所有功能都在終端內”“沒有telemetry”“筆記本一定會被髮送”。 將本地索引的說明、更新確認的程式碼、未確認的依賴、實際通訊分開的話，可以知道追加調查的物件。 Q14

Text Generator：確認上下文的候選人和金鑰儲存的分支

可以獲取剪貼簿的設定和實際prompt是不同的

固定版的初始設定有includeClipboard=true，context builder如果其值為true，則具有可以獲取clipboard的分支。 另一方面，引用的初期template是title、starredBlocks、tg_selection，不是clipboard placeholder。 Q15 / Q17

根據template、frontmatter、context options、選擇範圍，解決的值會發生變化。 請不要將可用的值一覽表和實際請求中的值視為相同的。 這個程式碼確認不是“clipboard一定會被髮送”“Vault全部會一直被髮送”的結果。 Q17 / Q18

plain key欄的空文字不能成為加密的證據

初始值是encrypt_keys=false。 有儲存時將plain key欄清空的處理和準備其他secret相關欄位的處理。 getEncryptedKey在加密不可用或encrypt_keys無效時，返回連線固定prefix和輸入key的值。 即使欄位名稱中包含encrypted/hashed，也不能僅憑這一點判斷為加密的bytes。 Q15 / Q19 / Q20 / Q21 / Q22

鍵，所以實際儲存的內容和這個終端的safeStorage動作尚未確認。 在共享包含金鑰的配置檔案和診斷記錄之前，不僅需要關注plain欄，還需要關注儲存的其他值。

將初期provider和local對應分開選擇

源的初始provider是OpenAI Chat (Langchain)，endpoint是https://api.openai.com/v1。 Ollama provider有接收設定的basePath的實現。 僅憑有local對應provider的事實，並不能證明其他功能的處理目的地和全通訊都沒有。 Q15 / Q23 / Q24

附加request、automatic suggestions、slash suggestions、JavaScript執行在引用的初始值中是OFF。 這些也不是現行GUI的實際測量值。 請在自己的環境中確認使用的template和已儲存的設定。 Q15 / Q16

常見問題

選擇本地模型的話，外掛完全不通訊嗎？
模型的處理目的地和索引、Web搜尋、檔案轉換、更新確認是不同的路徑。 Copilot的資料區分了附加功能的路徑，Smart Connections的自前程式碼有GitHub更新確認GET。 在這次資料確認中，沒有確認所有功能沒有通訊和實際傳送內容。
Smart Connections會把筆記本傳送到外部嗎？
固定版README說明了透過內建的本地模型製作embedding和索引。 這是提供者的說明。 自己的來源有更新確認和首次介紹的URL，模型、設定等有一部分是外部依賴。 這個比較沒有測量實際的筆記傳送和全部通訊的有無。
Text Generator的includeClipboard=true，是一定要傳送剪貼簿的意思嗎？
在原始碼中，當該設定為true時，context builder可以獲取剪貼簿的分支。 另一方面，刊登的初期模板使用title、starredBlocks、tg_selection，沒有指定clipboard。 可用的值和實際組裝的請求內容是不同的。 實際payload未測量。
如果儲存資料的api_key是空的，金鑰已經加密了嗎？
僅憑空鍵欄無法判斷。 在Text Generator 0.8.7中，有清空plain key欄的儲存處理和單獨的儲存欄位，如果無法使用加密或encrypt_keys無效時，有返回固定prefix和輸入鍵的分支。 沒有嘗試過實際的金鑰儲存和平臺的加密動作。
這篇報道是否比較了AI的回答質量和費用、iPhone的動作？
比較物件是固定的3版的官方資料和程式碼中顯示的資料路徑和設定。 外掛的安裝、設定畫面的實際操作、模型生成、收費、實際通訊、包括iPhone在內的終端動作、提供者的儲存、非學習方針的遵守沒有確認。
