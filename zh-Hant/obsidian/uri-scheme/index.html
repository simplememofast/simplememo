obsidian:// URI方案完整指南 — 全部動作和陷阱

obsidian://是從其他應用程式或啟動器開啟、製作、搜尋Obsidian筆記的URI。 首先選擇適合用途的動作，每個值進行URI編碼。 對現有正文的補充，可以從這次確認儲存的new+append=true的例子開始。

輸入正文複製URI時，也請參考將語法和固定Linux觀測分開的免費URI生成器。

這裡整理了官方正文的6動作一覽表中新增了Hook用的別節7節・38的動作引數專案，對應傳遞給Linux Obsidian1.13.7的58個記錄。 也刊登了無法獲得結果的輸入，以便將規格的描述和實際的儲存地址分開閱讀。

確認的範圍：作者用的本地Vault，官方Linux應用程式1.13.7，英語UI，隔離的Xorg畫面。 向執行檔案傳遞URI，確認了應用程式收到後的操作。 來自瀏覽器連結的OS關聯、物理iPhone、iOS快捷鍵、SimpleMemo、同步未驗證。 58件並不意味著全價、全組合、全終端的保證。

想要製作URL的話，請到現有的URI生成器。 iPhone無法啟動、快捷鍵停止的症狀請前往快捷鍵處理指南。 這個頁面是用來查詢標準URI的含義和輸入結果的參考。

正文的#和標題的#都編碼為值

官方正文說明空白為%20，斜槓為%2F。 在混合了日語、換行、# & ? + % / =的作者正文按值轉換的I:N1中，儲存Markdown與輸入一致。 URL整體轉換一次的話，分隔也會改變，所以vault、file、content的值單獨處理。

const vault = encodeURIComponent('練習Vault');
const file = encodeURIComponent('ノート/日本語 メモ');
const content = encodeURIComponent('本文 # & ? + % / =\n二行目');
const uri = `obsidian://new?vault=${vault}&file=${file}&content=${content}`;

上面是說明組裝方法的程式碼。 不包括儲存在終端上的筆記中的執行。 將練習Vault和儲存地址替換為自己的名字。

在留下生#的輸入中後半部分掉了

I:W1只留下了content途中的#。 儲存的只有開頭的句子，後半部分的正文沒有在檔案中。 這件事不是“Obsidian擅自刪除正文”的證據，而是URI的分隔和數值混合的輸入結果。

將新建、補充、覆蓋分開

new的name是新的筆記名，將儲存地址委託給Obsidian的“Default location for new notes”。 file是包含Vault路線的儲存目的地的值。 官方記載file優先於name，I:N2也儲存到file指定目的地。 S:N01中只有name，儲存在預先設定的預設資料夾中。

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Hello%20World

保留現有正文新增時，會傳遞append=true。 I:N3保留了現有的正文並追加了。 overwrite=true是替換現有正文的指定，I:N5有另外的原文/儲存後的記錄。 官方記載了“只有在沒有設定append的情況下才overwrite”，在S:N03的兩個指定中都追加了。 不需要在日常的正文新增中混合覆蓋指定。

obsidian://new?vault=Practice&file=Inbox%2FURI-test&content=Another%20line&append=true

silent=true的I:N4，在製作儲存檔案的同時保持了顯示中的筆記。 clipboard=true的S:C01/C02/C03將專用畫面的作者正文儲存在new/daily/unique中。 同時交出content的S:C04儲存了clipboard正文。 這組的優先結果，不能擴充套件到所有終端的所有形式。

## 対象の節

ブロック移動を確認する著者用本文です。 ^target-01

T:B1的長原Markdown全文下載

縮寫obsidian://vault/Vault名/ノート名和obsidian:///絶対パス是open的省略記法。 S:H01/H02分別顯示了作者筆記。 值的日語、空白、分隔符的處理和普通的引數一樣進行確認。

每日筆記、固有名筆記也確認外掛和儲存地址

官方記載了daily需要Daily notes，unique需要Unique note creator核心外掛。 首次I:D1/U1無法建立檔案，原封不動地留下了失敗記錄。 在之後的另一個計劃中，準備了真實存在的作者用儲存資料夾，觀測了從索引中建立日次檔案的I:D2，建立固有名檔案的I:U2。 並不是只斷定這個前提變更是失敗的原因。

obsidian://daily?vault=Practice&content=Daily%20entry
obsidian://unique?vault=Practice&content=Unique%20entry

固定的官方正文說明了daily接收與new相同的引數。 但是S:D01/D02/D03不能指定name、file、path，被新增到Daily notes設定的日次/2026-09-30.md中。 指定名稱的新筆記是new，日期筆記的輸入是daily，用實際檔案確認最終儲存地址，這是從這個觀測開始可以引導的範圍。

S:D04在silent保持索引顯示的同時儲存在日次上。 S:D05同時指定了append和overwrite並保留了原文，但是由於沒有標誌的daily也追加了，所以append單獨的貢獻和overwrite的動作尚未確認。

選擇顯示目的地paneType

針對 open/new/daily/unique，分別記錄了 paneType=tab、split 和 window 的 12 次輸入（S:P01〜P12）。官方說明 window 僅適用於桌面端。我們讀取了實際主標籤頁、標籤組和獨立彈出視窗，並保留了截圖。由於已關閉視窗的後設資料仍然存在，因此並未僅憑全域性 leaf 總數判斷成功與否。

x-success・x-error在退貨地址確認接收

官方解釋說，退回x-success包括name（無副檔名）、url（obsidian URI）、桌面的file（file URI）。 儲存成功和呼叫方收到退貨是分開的。 S:X01/X02/X03觀測到筆記的儲存，但作者擁有的localhost HTTP接收地址沒有接收。 準備好的BROWSER介面卡也沒有執行，連OS、呼叫源交接都無法確認。

Hook用hook-get-address有x-success的話會返回那裡，如果省略的話，官方記載了現在筆記本的Markdown連結複製到clipboard。 在S:K01中，作者clipboard的番兵值沒有變化，S:X04也沒有返回。 Hook本體沒有執行。 S:X05的不存在Vault顯示了實際的“Vault not found”對話方塊，但沒有接收x-error。 錯誤顯示不會用退貨成功或全部callback的產品故障代替。

常見問題

obsidian://和普通的Web URL有什麼不同？

obsidian://是Obsidian接收的獨自URI。 不是獲取網頁的URL。 終端端的關聯和Obsidian之後的筆記操作要分開確認。 這篇報道的實際測量是在收到Linux應用程式的URI之後。

日語、空白、#怎麼寫？

按值進行URI編碼。 空白是%20，#是%23，/是%2F。 標題、塊指定的#也在file值中編碼。 在本文留下原始#的作者例子中，#之後沒有儲存。

在現有筆記本上追加記的話使用open嗎？

正文補充的確認例子是給new傳遞file、content、append=true。 open節也有append/prepend的記載，但content沒有列舉在同一節中，在這個驗證的探索性輸入中，正文沒有改變。

給daily交file或name的話，可以更改儲存地址嗎？

固定的官方正文記載了daily接收與new相同的引數。 另一方面，在這次的Linux輸入中，沒有建立name、file、path的指定目的地，而是新增到了Daily notes設定的日期筆記中。 請用實際設定和檔案確認儲存地址。

指定x-success的話，已經確認退貨了嗎？

不。 new、daily、unique也有觀測儲存的輸入，但擁有的HTTP寄回地址沒有接收。 接收到應用程式的URI和CLI結束0不能成為返回給呼叫方的證據。 Hook、OS的交接、實際的呼叫源應用程式尚未確認。

iPhone也是同樣的結果嗎？

本文沒有執行物理iPhone、iOS快捷鍵、SimpleMemo。 這是Linux Obsidian1.13.7的作者用Vault的結果。 iPhone固有的症狀請參考現有的快捷鍵處理指南，在終端上確認。
