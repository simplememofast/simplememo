Obsidian的屬性活用
frontmatter一覽

將狀態、數值、檢查、日期、標籤儲存在筆記中，在Dataview中顯示符合條件的記錄。 這是使用虛構的三件的實GUI操作和確認儲存Markdown的入門。

屬性是處理筆記開頭的YAML的UI

在Properties中輸入的名稱和值會儲存在筆記開頭的frontmatter中。 例如，如果準備好status: 進行中，就可以在Dataview的WHERE條件下選擇“進行中”的筆記。 和本文中寫的普通文章的處理方式不同。

首先，決定要比較什麼，然後使用少數專案。 在這個例子中，狀態為status，優先度為priority，完成為done，期限為due，分類為tags。 作者製作的虛構記錄，不是使用者的資料。

用GUI輸入儲存YAML表・列表變更和結果練習用原件

按順序決定名稱、型別、值

  1. 開啟筆記，從Add property或官方的Ctrl/Cmd+;中新增專案。 在實機例子中，點選Add property新增了priority。
  2. 按專案名旁邊的型別圖示，開啟Property type選擇型別。 在實機上選擇Number，輸入3儲存。
  3. 現有的status選擇了Text，從“未著手”變更為“進行中”。 檢查、Date輸入、Tags輸入也透過實際的UI進行變更，確認會反映在儲存YAML中。
  4. Tags不只是輸入文字就結束了，而是透過聚焦的輸入按Enter進行確定。 這次的輔助操作也無法確定一次，再次透過Enter和焦點移動確認了儲存。
名字這個例子的型別和值在實機上做過的事情
狀態Text / 進行中Text選擇，未着手→進行中
優先順序編號/3新增專案，選擇Number，輸入3

到期日期/2026-10-0310月1日→10月3日
標籤Tags / 驗證、屬性新增屬性確定

在官方資料中，同名的型號在整個保管庫中是通用的。 在將相同的名稱用於其他含義的值之前，先確認型別和用途。 List和Date & time等，這裡沒有處理的型別不包含在這次的動作確認中。

確認儲存的frontmatter

下面是調查A的最後儲存全文，211 bytes。 在GUI中將done更改為true後的狀態，包括正文在內，內容與原Markdown相同。

檢視調查A的儲存Markdown全文
---
status: 進行中
tags:
  - 検証
  - プロパティ
done: true
due: 2026-10-03
priority: 3
---

# 調査A

著者が検証用に作成した架空の記録です。顧客データではありません。

在官方資料中，frontmatter用---包圍檔案開頭，以名前: 値的YAML格式進行描述。 屬性名稱不會在一個筆記中重複。 這個例子的數值3和檢查true分別儲存為數值和boolean。 Date是儲存這個值的確認，不是驗證所有日期格式和輸入的正確性的結果。

將相同的值作為TABLE和LIST的條件

在實機中，將官方Dataview穩定釋出的三個檔案事先複製到隔離的保管庫中，透過實際的信任確認啟用了外掛。 這不是驗證Browse/Install的畫面操作的記錄。 外掛為了執行第三方程式碼，確認分發來源和使用條件後進行選擇。

釋出名稱是0.5.70，分發manifest和實際畫面的顯示版是0.5.68。 需要的Obsidian最小版是manifest上的0.13.11，實際執行的Obsidian是1.13.7。 DataviewJS設定是false，將下一個DQL輸入到實際編輯器中，在Reading view中顯示。

資料夾名記録、專案名、狀態字串一致。 調查A/B正在進行中，C已完成。

# Properties接続検証

著者が作成した架空の3件だけを表示します。

## 進行中の表

```dataview
TABLE status AS "状態", priority AS "優先度", done AS "完了", due AS "期限"
FROM "記録"
WHERE status = "進行中"
SORT file.name ASC
```

## 未完了の一覧

```dataview
LIST
FROM "記録"
WHERE done = false
SORT file.name ASC
```

## 保留の該当なし

```dataview
LIST
FROM "記録"
WHERE status = "保留"
SORT file.name ASC
```

TABLE將正在進行的兩件列為表，LIST將done將false的筆記列為列表。 最後的LIST選擇了保留的筆記，也確認了沒有物件的情況下的實際顯示。 DQL的全部功能、內聯欄位、DataviewJS沒有在這裡嘗試。

更改完成檢查後，未完成列表從2件到1件

條件調查A的done=false在GUI中更改為done=true後
status = 進行中的TABLE調查A・B / 2件調查A・B / 2件。 顯示A的完成值true
done = false的LIST調查A・C / 2件調查C / 1件
status = 保留的LIST不適用不適用

變更前的TABLE兩件用實際Reading DOM確認了，當時的PNG從表向下滾動。 上面的變更後，在PNG中可以看到表兩件和未完成一覽一件。 沒有重新制作並替換顯示位置和影象。

從檔案一覽表中再次開啟調查A和一覽表筆記，也確認了儲存Markdown的bytes和SHA256相同。 同一應用程式啟動中重新顯示，不是整個應用程式的重啟或確認其他終端。 在這次的條件下，數值反映在顯示上，沒有測量工作速度和生產力提高的因果關係。

是將實機儲存的原Markdown的bytes原樣複製的檔案。 調查A的done是true。 在以下配置中，查詢的FROM和資料夾名是一致的。 讀者在保管庫的匯入尚未驗證。

常見問題

Obsidian的屬性和frontmatter是不同的資料嗎？
屬性是操作筆記結構化值的UI，值作為檔案開頭的YAML frontmatter儲存。 在這次的實機中，用GUI操作了status、tags、done、due、priority，與儲存的Markdown的值進行了核對。
屬性的型別是按筆記設定的嗎？
在官方資料中，同一屬性名稱在整個保管庫中使用相同的型別。 從名字旁邊的型別圖示開啟Property type，選擇型別。 在這次的實機中，在priority中選擇了Number，儲存了3。 並不是所有的型別和日期輸入都進行了驗證。
在Dataview中列出屬性的基本形式是什麼？
在dataview程式碼塊上寫TABLE或LIST、FROM和WHERE。 在這次的三件中，以FROM "記録"為物件的資料夾，status = "進行中"的TABLE是2件，done = false的LIST是完成檢查變更前兩件，變更後一件。
下載的例子是什麼狀態？
這是在GUI中將調查A的done更改為true後的儲存原件。 記録 資料夾內調查A・B・C，顯示了將一覧.md放在同一保管庫正下方的構成。 這次的實機結果是TABLE兩件，未完成LIST是調查C一件，保留不適用。 讀者匯入保管庫和其他環境的動作尚未驗證。

官方資料和這個實機確認的範圍

GUI確認的UTC日是2026年9月30日，日本時間是2026年10月1日。 實際畫面、儲存原件、固定來源、輔助的更正、結束記錄的不足總結為驗證記錄。 雖然傳送了結束Close，但根據記錄器的結束順序，Obsidian的結束程式碼未記錄。

  • 已確認：Linux Obsidian 1.13.7，五種型別的有限GUI操作，儲存YAML，DQL三條件的實Reading顯示，值變更和重新顯示，同一啟動中的儲存一致。
  • 官方說明：Properties的儲存形式、型別的共享，用固定資料確認Dataview的frontmatter/QUERY/TABLE/LIST/WHERE。
  • 未確認：全型・全輸入驗證，外掛的安全稽核，全DQL/JS，應用程式重啟，iOS，同步，SimpleMemo配合，大保管庫·速度·生產力。
