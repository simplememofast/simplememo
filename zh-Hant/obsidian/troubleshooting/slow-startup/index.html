Obsidian重、啟動慢時的
分割步驟

首先保管原來的保管庫，在複製的保管庫中分離外掛和設定。 刊登在作者的小驗證保管庫中測量的9次結果，作為在相同條件下進行比較的例子。

寫作: SimpleMemo Developer · 測量: 2026年9月30日 · Linux版Obsidian 1.13.7

在更改設定之前，保管原來的保管庫

確保筆記、附件、設定的備份，用驗證用副本而不是原來的保管庫進行測試。 將社群外掛統一禁用，比較顯示相同筆記的時間，如果有差異，逐一返回確認。

先備份。 關閉Obsidian，將自己的保管庫複製到其他地方。 隱藏資料夾的 .obsidian 也作為設定包含。 請確認副本存在，可以讀取已知的筆記後，請更改設定。 不是刪除原來的筆記和外掛檔案的步驟。

從這裡開始的分割是面向讀者的提案。 不是診斷讀者終端原因的結果。 後半部分的實測只處理作者準備的1筆記本的固定條件。

  1. 保管原來的筆記本・附加・設定
  2. 分症狀啟動・正文顯示・編輯中
  3. 用複製比較相同的筆記・相同的標準
  4. 一個一個恢復記錄版本和變更
安全切割9次的實際測量值測量方法和極限原CSV・畫面常見問題

將“重”分開，用驗證用副本確認

  1. 記下哪個階段比較慢。 在啟動
    應用程式之前，在開啟保管庫看到正文之前，搜尋、連結、編輯的過程中，都是不同的症狀。 記錄OS、Obsidian的版本、保管庫的大致規模、之前更改的設定和有效的外掛。
  2. 確認備份，將驗證的副本分開。
    應用程式關閉並製作副本，原件保持儲存狀態。 確認放置位置，以免將驗證用副本與自動同步物件混淆，在兩個同時開啟的情況下不要更改設定。 不需要使用陌生人的保管庫或未確認的外掛。
  3. 透過複製禁用社群外掛進行比較。
    在記錄有效的列表和設定後，從社群外掛的設定中使用無效化和Restricted mode（限制模式），在重啟後看到相同的已知筆記之前進行比較。 選單的顯示請用版本、語言確認。 外掛停止時，該外掛所承擔的功能將無法使用。
  4. 如果看到差異，一個一個地恢復有效。
    保持相同的副本、筆記、核心功能、測量標準，記錄外掛的名稱、版本、啟用的順序。 多次測量相同的條件，避免僅根據第一次的時間或一次的快速值得出結論。
  5. 如果看不到差異，就分開比較保管庫和環境。
    在自己準備的小筆記本的單獨保管庫中，確認同一階段是否慢。 同時記錄執行的應用程式和OS負荷、同步、儲存狀態等。 如果在這裡一次性更改設定和檔案，就無法知道與哪個更改有關。

備份的製作、切換到限制模式、讀者的外掛的回放、同步・儲存的診斷，不是這個9次的測量中演示的操作。 實測使用事先準備好的啟用列表，沒有進行啟動中的操作和筆記改寫。

在固定的小保管庫中，0・1・2個各3次測量

使用相同的Linux環境和作者製作筆記，比較了實際匯入的社群外掛是0個、只有Templater的1個、Templater+QuickAdd的2個的條件。 本文顯示的中位數分別約為0.92秒・0.95秒・1.02秒。

0個也有2種的分發檔案。 更改的是社群外掛的啟用一覽表。 不僅計算已安裝的manifest，還讀取了執行時的有效列表和實際外掛例項的ID・版本，確認了0・1・2個。 核心功能在所有條件下都是相同的5種。

這個順序的中值，不能作為外掛數的因果關係和一般的“越多越慢”定律。 外掛的種類隨著數量的變化而變化，每個3次很少，共享CPU和快取也不固定。 請不要將這種差異直接應用到讀者的大型保管庫和終端上。

測量了啟動的“到什麼程度”

連線的準備和正文的顯示分開

用單調增加的時鐘，測量了從啟動Obsidian程序之前開始的經過時間。 顯示環境的準備在開始前就已經做好了。 CDP ready是測量用的連線點響應，獲得連線點資訊的時間點。 僅憑這一點，不能說螢幕上顯示了筆記。

GUI text ready是使用該連線確認真實畫面，起動確認.md的標題“起動確認”和已知的確認標記顯示的時間點。 包括從啟動到連線、讀取處理。 與最初的繪製、所有外掛的初始化完成、可以編輯的時間點是不同的指標。 讀取件數的狀態確認，在本文顯示的觀測後另行記錄。

使用相同的輸入和順序

  • 官方Obsidian 1.13.7。 在實際的General畫面中確認了應用程式和installer的版本。
  • Templater 2.25.1、QuickAdd 2.29.0的相同官方分發檔案複製到全部條件。 這次沒有新的獲取、依賴的安裝。
  • 輸入是作者直接準備的148位元組的Markdown 1件。 使用相同的保管庫設定、核心功能5種、兩個外掛的分發檔案，在啟動前核對了啟用列表以外的保管庫檔案。 啟動後正文的bytes/hash也沒有改變。
  • 核心功能是file-explorer、backlink、outline、properties、bookmarks。 沒有執行Templer的啟動template和QuickAdd的choice・macro・AI設定等。
  • 事先確定0・1・2個3條件和各3次，按照0,1,2 / 1,2,0 / 2,0,1的順序進行測量。 預定的9次全部刊登，沒有隻篩選快速值和刪除偏離值。
  • 測量中點選GUI，開啟・寫筆記API，不執行外掛命令，透過讀取確認狀態。 每次都儲存了實畫面，只讓測量時使用的應用程式正常結束。

快取、負載、配置檔案的極限

首先在未測量的準備用配置檔案中，進行實際的信任確認和General的版本確認，將準備好的設定複製到每次。 每次製作新的配置檔案、快取用目錄，OS的頁面、磁碟快取透過準備和重複來升溫。 沒有重啟或清除OS快取，不是物理冷啟動或第一次未使用設定。

關於每次的整個全域性配置檔案，沒有記錄啟動前的完整hash一覽表。 雖然保留了共同的準備原始設定和複製方法，各保管庫的啟動前檔案核對，但並不主張所有配置檔案的所有bytes是相同的。

在共享環境中，CPU使用率的觀測值約為35–44%，其他應用程式也在執行。 可見的邏輯CPU是5，CPU分配相當於4 CPU，記憶體上限是16 GiB。 CPU的觀測區間包括測量、狀態獲取、影象儲存，不是個別外掛的CPU使用率。 準備前還確認了其他構建工作，但並不是在所有9次中執行相同的構建的記錄。

關於測量前的停止和記錄的更正

在未測量的準備階段，檢查正常結束的應用程式的連線目的地是否被釋放的檢查，將TCP的TIME_WAIT與待接中的連線混淆而停止。 保管失敗記錄，確認無待接、拒絕連線，更正檢查後，測量了預定未實施的9次。 準備階段的時間沒有放在測量樣本中。

在原影象的一覽確認中，將準備用的信任確認畫面計算掉的11件的預期值更正為12件。 影象、GUI、時間不重新生成，保留現有的CSV等bytes，更正記錄的件數。

確認原來的CSV、筆記、實畫面

CSV是包含未四捨五入的9次的時間、執行時的讀取件數和版本、共享負載、結束結果的原始檔案。 除了表中的整數以外，可以確認原來的值。 Markdown是作者事先直接準備的輸入，不是透過應用程式儲存正文的成果。

常見問題

啟動慢的原因，是由外掛的數量決定的嗎？
僅憑數量無法判斷。 在這個固定的小保管庫中，0・1・2個各測量了3次，隨著個數外掛的種類也發生了變化，共享環境的負荷和快取也會受到影響。 不是確定讀者保管庫的原因或個數的因果關係的結果。
在停止外掛之前，要備份什麼？
工作前關閉Obsidian，將包含自己保管庫的筆記和附件、隱藏資料夾.obsidian的設定複製到其他地方。 確認副本存在，可以讀取已知的筆記後，在保管原來的保管庫時，用驗證用副本進行切割。 這是面向讀者的程式提案，並不是實際確認讀者的備份。
0個的條件是沒有安裝外掛的條件嗎？
不。 將Templar和QuickAdd的相同官方分發檔案置於全部條件，只更改了啟用的列表。 0個是社群外掛無效，執行時讀取的例項是0個的條件。 核心功能是相同的5種。
表的CDP準備時間和正文顯示時間是一樣的嗎？
不一樣。 CDP準備是測量用連線物件響應的時間點。 正文顯示是，之後連線，讀取已知的Markdown的標題和確認標記出現在實際畫面上的時間點。 兩者都是從程序啟動前開始測量的，正文顯示也包括連線和確認處理的時間。 不是測量最初的繪製和所有外掛的初始化完成。
這篇報道的秒數，也可以用於其他終端或大型保管庫嗎？
無法使用。 Linux版Obsidian 1.13.7，只有小作者製作筆記、固定設定、準備好的配置檔案副本9次。 OS快取正在升溫，共享CPU負載約為35–44%。 Windows，macOS，iOS，大型實用儲存庫，物理冷啟動，SimpleMemo的速度沒有測量。
